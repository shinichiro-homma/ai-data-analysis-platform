# タスク詳細: 3.1 環境別ボリューム対応（docker-compose + スクリプト基盤）

## 概要

PostgreSQL データボリュームを環境ごとに分離（`postgres_data_sample` / `postgres_data_production`）し、環境切り替え時のデータ再ロードを不要にする基盤を構築する。

現状では `postgres_data` という単一ボリュームを使い、`switch-env.sh` 実行時に毎回ボリューム削除 → フルロード（production で数十分）を行っている。環境別ボリュームにすることで、両環境のデータを同時に保持し、切り替えはボリュームの参照先変更のみで完了するようになる。

タスク 3.2（switch-env.sh のスキップ判定 + ユーザー確認フロー）の前提基盤。

### 変更するファイル

| ファイル | 変更内容 |
|----------|------|
| `docker-compose.yml` | ボリューム名を `postgres_data_${DATA_ENV:-sample}` に動的化、トップレベルから `postgres_data:` を削除 |
| `scripts/lib/common.sh` | `remove_postgres_volume()` に環境引数を追加、`get_postgres_volume_name()` / `postgres_volume_exists()` ヘルパー追加 |

| `scripts/rebuild.sh` | `remove_postgres_volume` 呼び出しに環境引数を渡す、`--reset` 時のボリューム削除を環境別に変更 |

### 実装手順

#### ステップ 1: docker-compose.yml のボリューム名動的化

```yaml
# Before
services:
  postgres:
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
  jupyter_work:

# After
services:
  postgres:
    volumes:
      - postgres_data_${DATA_ENV:-sample}:/var/lib/postgresql/data

volumes:
  jupyter_work:
  # postgres_data を削除（スクリプトで明示管理するため）
```

**設計判断**: トップレベル `volumes:` から postgres ボリュームを削除する。
- Docker Compose はトップレベルに未定義でも名前付きボリュームを自動作成する
- トップレベルに `postgres_data_sample:` と `postgres_data_production:` を定義すると `docker compose down -v` で両方削除されるリスクがある
- postgres ボリュームのライフサイクルはスクリプトで明示管理する

#### ステップ 2: common.sh にヘルパー関数を追加

```bash
# Docker Compose プロジェクト名を取得
get_compose_project_name() {
  docker compose config --format json 2>/dev/null \
    | python3 -c "import sys,json; print(json.load(sys.stdin).get('name',''))" 2>/dev/null \
    || basename "$(pwd)" | tr '[:upper:]' '[:lower:]' | sed 's/[^a-z0-9]//g'
}

# 環境別ボリューム名を取得
get_postgres_volume_name() {
  local env="${1:-sample}"
  local project_name
  project_name=$(get_compose_project_name)
  echo "${project_name}_postgres_data_${env}"
}

# ボリュームが存在するか確認
postgres_volume_exists() {
  local env="${1:-sample}"
  local vol_name
  vol_name=$(get_postgres_volume_name "$env")
  docker volume inspect "$vol_name" >/dev/null 2>&1
}

# 既存の remove_postgres_volume を環境引数対応に変更
remove_postgres_volume() {
  local env="${1:-sample}"
  local vol_name
  vol_name=$(get_postgres_volume_name "$env")
  if docker volume inspect "$vol_name" >/dev/null 2>&1; then
    echo "  Removing volume: $vol_name"
    docker volume rm "$vol_name"
  fi
}
```

**設計判断**: Docker Compose のプロジェクト名プレフィックスを考慮する。
- Docker Compose は `{project_name}_{volume_name}` の形式でボリュームを作成する
- プロジェクト名は `docker compose config` から取得し、フォールバックはディレクトリ名

#### ステップ 3: switch-env.sh の修正

`remove_postgres_volume` の呼び出しに切り替え**先**の環境引数を渡す。

```bash
# Before
remove_postgres_volume

# After
remove_postgres_volume "$ENV"  # 切り替え先の環境ボリュームを削除（3.2でスキップ判定追加予定）
```

**動作フロー**（sample → production への切り替え例）:
1. `.env` の `DATA_ENV` を `production` に書き換え
2. `docker compose rm -fs postgres document-server jupyter-server`
3. `remove_postgres_volume "production"` — production ボリュームを削除（3.2 でスキップ可能に）
4. `docker compose up -d postgres` — `postgres_data_production` ボリュームが新規作成
5. `run_load_data "production"` でデータロード
6. sample ボリュームは保持される

**注意**: タスク 3.1 では「常に削除 → 再ロード」の現在の動作を維持する。スキップ判定はタスク 3.2 のスコープ。

#### ステップ 4: rebuild.sh の修正

```bash
# reinitialize_postgres() 内
remove_postgres_volume "$DATA_ENV"

# --reset 時: docker compose down -v を個別削除に変更
docker compose down --remove-orphans
remove_postgres_volume "$DATA_ENV"
```

#### ステップ 5: clean-rebuild.sh の修正

```bash
# --keep-volumes なし時
# Before: docker compose down -v
# After:
docker compose down --remove-orphans
remove_postgres_volume "$TARGET_ENV"

# メッセージ更新
echo "  - ボリューム (postgres_data_${TARGET_ENV}, jupyter_work) を削除"
```

旧 `postgres_data` ボリュームのクリーンアップも追加:

```bash
remove_legacy_postgres_volume() {
  local project_name
  project_name=$(get_compose_project_name)
  local legacy_vol="${project_name}_postgres_data"
  if docker volume inspect "$legacy_vol" >/dev/null 2>&1; then
    echo "  Removing legacy volume: $legacy_vol"
    docker volume rm "$legacy_vol" 2>/dev/null || true
  fi
}
```

### 技術的な考慮事項

- **docker-compose.yml のボリューム名変数展開**: Docker Compose は `.env` ファイルの変数を自動展開する。`DATA_ENV=sample` → `postgres_data_sample`
- **`docker compose down -v` の影響範囲変更**: トップレベルに postgres ボリュームがないため、`down -v` は `jupyter_work` のみ削除。postgres ボリュームの削除は明示的なスクリプト操作が必要になる
- **既存 `postgres_data` ボリュームの移行**: 初回 clean-rebuild 時に旧ボリュームも削除する処理を追加
- **ディスク使用量**: 2環境分のデータが保持されるため最大2倍。ただし Parquet → DB ロード後のサイズなので許容範囲
- **check-freshness.sh は変更不要**: postgres 鮮度チェックはファイルパスとコンテナ作成時刻の比較であり、ボリューム名に依存しない
