# タスク詳細: 1.6 ワークスペースメタデータ拡張・更新

## 概要

ワークスペースに `summary`（作業内容の概要）と `status`（ステータス）のメタデータを追加し、作成・一覧・更新の全操作で利用可能にする。

- `workspace_create` に `summary` / `status` パラメータを追加
- `workspace_list` のレスポンスに `summary` / `status` を含める
- 新ツール `workspace_update` で既存ワークスペースの `summary` / `status` を更新
- jupyter-server に `PUT /api/workspaces/{workspace_id}` API を追加

AIが分析の進行状況をワークスペースに記録・参照できるようにすることで、マルチワークスペース運用時の状態管理を実現する。

### 実装手順

#### ステップ 1: jupyter-server — metadata.json の summary/status 対応

`workspace_handlers.py` を修正：

1. `WorkspacesHandler.post`（POST /api/workspaces）でリクエストから `summary`（string, 最大200文字, デフォルト空文字）と `status`（enum, デフォルト `not_started`）を受け取り、`metadata.json` に保存
2. `_read_workspace` / `_format_workspace_info` で `summary` と `status` を読み出してレスポンスに含める（既存ワークスペースに `summary`/`status` がない場合はデフォルト値を使用）
3. `WorkspacesHandler.get`（GET /api/workspaces）は `_format_workspace_info` 経由で自動的に対応

#### ステップ 2: jupyter-server — PUT /api/workspaces/{workspace_id}

1. `workspace_handlers.py` に `WorkspaceHandler` クラスを新規追加（単一ワークスペース操作用）
2. `put` メソッドで `summary` と `status` のみ更新可能。`metadata.json` を読み出し → 更新 → 書き戻し
3. `workspace_id` のバリデーション（`validate_workspace_id` 使用）
4. 存在しない workspace_id は 404 エラー
5. `status` は `not_started` / `in_progress` / `completed` / `blocked` のいずれかのみ許可（それ以外は 400）
6. `summary` は最大200文字（超過時は 400）
7. `handlers.py` に `(f"{base_url}/api/workspaces/([^/]+)", WorkspaceHandler)` ルートを追加（`WorkspacesHandler` の後に配置）

#### ステップ 3: jupyter-mcp — 型定義の更新

`types.ts` を修正：

1. `WorkspaceInfo` に `summary: string` と `status: string` を追加
2. `CreateWorkspaceRequest` に `summary?: string` と `status?: string` を追加
3. `UpdateWorkspaceRequest` インターフェースを新規追加（`workspace_id`, `summary?`, `status?`）

#### ステップ 4: jupyter-mcp — クライアントメソッド

`client.ts` を修正：

1. `createWorkspace(name, summary?, status?)` の引数を拡張
2. `updateWorkspace(workspaceId, params)` メソッドを新規追加（PUT /api/workspaces/{workspace_id} を呼び出し）

#### ステップ 5: jupyter-mcp — ツール実装

1. `workspace-create.ts`: `summary` / `status` パラメータを受け取り、`jupyterClient.createWorkspace()` に渡す
2. `workspace-list.ts`: レスポンスに `summary` / `status` を含める（サーバーから返却されるので、そのままマッピング）
3. `workspace-update.ts`: 新規作成。`workspace_id`（必須）+ `summary` / `status`（任意）を受け取り、`jupyterClient.updateWorkspace()` を呼び出す
4. `tools/index.ts`: `workspace_create` のスキーマに `summary` / `status` プロパティを追加、`workspace_update` ツール定義を追加、`handleToolCall` の switch 文にルーティング追加

#### ステップ 6: テスト作成

1. `workspace-update.test.ts`: 正常系（summary のみ、status のみ、両方）、バリデーションエラー（workspace_id 未指定、不正 status 値）、API エラー（404、接続エラー）
2. `workspace-create.test.ts`: summary/status 指定時のテスト追加

### 技術的な考慮事項

- **後方互換性**: 既存ワークスペースの `metadata.json` には `summary` / `status` が存在しない。読み出し時にデフォルト値（`summary: ""`, `status: "not_started"`）を適用することで後方互換を維持する
- **`status` のバリデーション**: サーバー側（jupyter-server）とクライアント側（jupyter-mcp）の両方でバリデーションを行う。サーバー側が最終防壁
- **部分更新**: PUT は指定されたフィールドのみ更新（未指定フィールドは既存値を保持）。`summary` と `status` の両方が未指定の場合は 400 エラー
- **ルート順序**: Tornado のルートマッチは先勝ち。`/api/workspaces` と `/api/workspaces/([^/]+)` は正規表現の違いで正しくマッチするが、`/api/workspaces/([^/]+)` を `WorkspacesHandler` の後に配置する
