# タスク詳細: 1.2 既存ツールのワークスペーススコープ対応

## 概要

1.1 で作成したワークスペースを、既存の MCP ツール（`session_create`, `file_list`, `notebook_create`）から利用可能にする。具体的には以下を実現する:

- `session_create(workspace_id=...)` でカーネルの作業ディレクトリ（cwd）がワークスペースに設定される
- `file_list(workspace_id=...)` でワークスペース内のファイルのみ表示される
- `notebook_create(workspace_id=...)` でワークスペース内にノートブックが作成される

このタスクにより、チャットごとに独立した作業空間でデータ分析が行えるようになる。

### 実装手順

#### ステップ1: jupyter-server カスタムセッション作成 API

`jupyter-server/extensions/custom_api/session_handlers.py` を作成する。

**POST /api/custom/sessions（ワークスペース内セッション作成）:**

```python
class CustomSessionsHandler(BaseCustomHandler):
    """POST /api/custom/sessions"""

    async def post(self):
        # 1. リクエストから workspace_id（必須）, notebook_path, kernel_name を取得
        # 2. workspace_id のバリデーション（形式チェック、ディレクトリ存在確認）
        # 3. ワークスペースの絶対パスを取得: {WORKSPACE_ROOT_DIR}/{workspace_id}/
        # 4. カーネル起動（cwd=workspace_dir）:
        #    kernel_id = await self.kernel_manager.start_kernel(
        #        kernel_name=kernel_name, cwd=str(workspace_dir)
        #    )
        # 5. notebook_path がある場合:
        #    - フルパス構築: workspaces/{workspace_id}/{notebook_path}
        #    - 標準 /api/sessions で session 作成（kernel_id 指定）
        # 6. レスポンス返却
```

**なぜカスタムエンドポイントが必要か:**
- Jupyter 標準の `POST /api/kernels` は `cwd` パラメータをサポートしない（REST レベルで）
- `MappingKernelManager.start_kernel(cwd=...)` を直接呼ぶ必要がある
- ワークスペース存在確認も server 側で行うのが自然

**レスポンス:**
```json
{
  "data": {
    "session_id": "abc123",
    "kernel_id": "kernel-xyz",
    "workspace_id": "ws-abc123",
    "notebook_path": "workspaces/ws-abc123/analysis.ipynb",
    "status": "starting",
    "created_at": "2024-01-15T10:00:00Z"
  }
}
```

`notebook_path` がない場合は `kernel_id` のみ（session_id は kernel_id と同一）。

**ハンドラー登録:** `handlers.py` の `get_handlers()` に `/api/custom/sessions` ルートを追加。

#### ステップ3: jupyter-mcp クライアントメソッド追加

`jupyter-mcp/src/jupyter-client/client.ts` に以下のメソッドを追加:

```typescript
async createSessionInWorkspace(
  workspaceId: string,
  notebookPath?: string,
  kernelName?: string
): Promise<WorkspaceSessionInfo> {
  const body: CreateWorkspaceSessionRequest = {
    workspace_id: workspaceId,
    ...(notebookPath ? { notebook_path: notebookPath } : {}),
    ...(kernelName ? { kernel_name: kernelName } : {}),
  };
  const response = await this.request<ApiResponse<WorkspaceSessionInfo>>(
    'POST',
    '/api/custom/sessions',
    body
  );
  return response.data;
}
```

### 技術的な考慮事項

#### カーネル cwd の設定方法

Jupyter の `MappingKernelManager.start_kernel()` は `cwd` キーワード引数をサポートしている。カスタムエンドポイントからこのパラメータを直接渡すことで、カーネルの作業ディレクトリをワークスペースに設定する。

代替案として「カーネル作成後に `os.chdir()` を実行する」方法があるが、以下の理由でカスタムエンドポイント方式を採用:
- カーネル起動時から正しい cwd が設定される（追加の API 呼び出し不要）
- ワークスペース存在確認がサーバー側でアトミックに行われる
- 失敗時の状態が明確（カーネルが作られない or ワークスペース cwd で作られる）

#### notebook_path とセッションの関係

`session_create(workspace_id, notebook_path)` で `notebook_path` が指定された場合:
- Jupyter 標準の session にフルパス `workspaces/{workspace_id}/{notebook_path}` で登録される
- ユーザーが JupyterLab でそのノートブックを開くと同じカーネルが共有される
- `notebook_add_cell` 等の後続ツールは session 経由でフルパスを解決するため、変更不要

#### ワークスペースパスの一貫性

ワークスペースの Jupyter root からの相対パスは `workspaces/{workspace_id}/` で統一する:
- `workspace_create` のレスポンス `path` フィールドと一致
- `file_list` は内部でこのプレフィックスを付加し、レスポンスでは除去して返す
- `notebook_create` は内部でプレフィックスを付加してフルパスで作成する

#### 後続ツールへの影響

以下のツールは、セッションに紐づくパス情報を通じてワークスペースを間接的に利用するため、本タスクでの変更は不要:
- `execute_code`: kernel_id を使ってコード実行。カーネル cwd がワークスペースなので相対パスが正しく解決される
- `notebook_add_cell`: session の notebook_path（フルパス）を使ってセルを追加
- `ai_edit_start` / `ai_edit_end`: session の notebook_path を使用

1.3 の結合テストで、これらのツールがワークスペースコンテキストで正しく動作することを確認する。

#### workspace_id のバリデーション

jupyter-mcp 側:
- 必須パラメータとして検証（空文字・未指定はエラー）
- 文字列長チェック（最大 50 文字）
- パストラバーサル防止（".." 禁止）

jupyter-server 側:
- ワークスペースディレクトリの存在確認
- metadata.json の存在確認
- ディレクトリがワークスペースルート配下にあることを検証
