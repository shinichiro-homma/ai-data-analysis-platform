# タスク詳細: 6.1 check-freshness.sh のバグ修正

## 概要

`check-freshness.sh` が Docker コンテナの鮮度を正しく検出できず、SKIP になるバグを修正する。

### 根本原因: `grep -q` + `set -o pipefail` による SIGPIPE

スクリプトは `set -euo pipefail` で動作している。`docker compose ps --status running 2>/dev/null | grep -q "service"` というパターンが多用されているが、`grep -q` はマッチを見つけるとすぐに stdin を閉じるため、`docker compose` がまだ出力中の場合 SIGPIPE シグナルが発生し exit 255 となる。`pipefail` によりパイプライン全体の終了コードが 255 になり、`if ! ...` の条件が常に true（= コンテナ未起動と誤判定）になる。

#### 再現メカニズム

`docker compose ps --status running` の出力順:
```
analysis-db       postgres:16       ...  postgres        ...
document-server   ai-data-...       ...  document-server ...
jupyter-server    ai-data-...       ...  jupyter-server  ...
```

- `grep -q "postgres"`: 1行目でマッチ → すぐに stdin を閉じる → `docker compose` が 2,3行目を書こうとして SIGPIPE → **常に SKIP**
- `grep -q "document-server"`: 2行目でマッチ → `docker compose` が3行目書き込みで SIGPIPE → **SKIP になることがある（race condition）**
- `grep -q "jupyter-server"`: 最終行でマッチ → `docker compose` は既に書き込み完了 → **正常動作**

#### 実機での確認結果

```bash
$ bash -c 'docker compose ps --status running 2>/dev/null | grep -q "postgres"; echo "PIPESTATUS: ${PIPESTATUS[@]}"'
PIPESTATUS: 255 0
# → docker compose が SIGPIPE で exit 255、grep は 0
```

### 修正方針

`docker compose ps --status running | grep -q` パターンを廃止し、`docker compose ps -q {service}` でコンテナ ID を直接取得する方式に統一する。パイプを使わないため SIGPIPE が発生しない。

これは Infrastructure Phase 6 全体の基盤となるタスクであり、最初に実施する。

## 実装計画

### 修正するファイル

| ファイル | 修正内容 |
|----------|----------|
| `scripts/check-freshness.sh` | 全4箇所の `docker compose ps --status running \| grep -q` を `docker compose ps -q` に置換。`check_docker_service` と `container_epoch` もコンテナ ID ベースに変更 |

### 実装手順

1. **ヘルパー関数 `is_service_running` を追加**
   ```bash
   is_service_running() {
     local service="$1"
     local container_id
     container_id=$(docker compose ps -q "$service" 2>/dev/null) || true
     [[ -n "$container_id" ]] && docker inspect --format='{{.State.Running}}' "$container_id" 2>/dev/null | grep -q "true"
   }
   ```

2. **メイン処理（L274-284）の起動中チェックを修正**
   - `docker compose ps --status running 2>/dev/null | grep -q "jupyter-server"` → `is_service_running "jupyter-server"`
   - `docker compose ps --status running 2>/dev/null | grep -q "document-server"` → `is_service_running "document-server"`

3. **`check_docker_service` 関数（L51-95）を修正**
   - `docker inspect "$service"` → `docker compose ps -q "$service"` でコンテナ ID 取得 → `docker inspect "$container_id"`
   - 起動中チェックはメイン処理で済んでいるため、ここではコンテナ ID 取得のみ

4. **`container_epoch` 関数（L167-183）を修正**
   - 引数をサービス名に変更（`analysis-db` → `postgres`）
   - `docker compose ps -q "$service"` でコンテナ ID 取得 → `docker inspect "$container_id"`

5. **`check_postgres` 関数（L222）の起動中チェックを修正**
   - `docker compose ps --status running 2>/dev/null | grep -q "postgres"` → `is_service_running "postgres"`
   - `container_epoch "analysis-db"` → `container_epoch "postgres"`

### 技術的な考慮事項

- **SIGPIPE の根本回避**: `docker compose ps -q` は1サービスにつき1行（コンテナ ID のみ）を返すため、パイプ不要で SIGPIPE が発生しない
- **`docker compose ps -q` の挙動**: 停止中コンテナでも ID を返す。`docker inspect --format='{{.State.Running}}'` で起動状態を確認する
- **`docker compose ps -q` が複数 ID を返す場合**（スケーリング時）: `head -1` で先頭を取得
- **`container_epoch` の引数変更**: `container_name`（`analysis-db`）ではなく `service`（`postgres`）を渡す方式に統一。`docker compose ps -q` はサービス名で検索するため

# 2. 3回連続実行して結果が安定することを確認（race condition がないこと）
