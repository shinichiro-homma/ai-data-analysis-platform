# タスク詳細: 7.6 production 環境の大容量データロード対応

## 概要

production 環境の大容量テーブル（`dm_purchase_history` 56M行等）をロードする際、`load-data.py` が Parquet ファイル全体をメモリに読み込み → CSV に変換 → `COPY FROM STDIN` で流し込む方式のため、メモリ不足で失敗する。

チャンク分割ロードを実装し、メモリ消費を一定量に抑えつつ大容量テーブルをロードできるようにする。

### メモリ不足の原因（現在の実装）

`load_table` 関数で 3 段階のメモリ消費が発生:

1. `pq.read_table()` — Parquet 全量をメモリに展開（圧縮解除後のサイズ）
2. `pa_csv.write_csv(tbl, buf)` — CSV テキストとしてメモリ上にさらにコピー
3. ピーク時に PyArrow Table + CSV BytesIO が同時に存在（テーブルサイズの 2-3 倍）

### 実装手順

#### Step 1: `generate_init.py` の `load_table` テンプレートをチャンク分割に書き換え

現在の方式:
```python
tbl = pq.read_table(parquet_path, columns=[...])  # 全量読み込み
buf = io.BytesIO()
pa_csv.write_csv(tbl, buf)  # 全量 CSV 変換
cur.copy_expert(copy_sql, buf)  # 全量 COPY
```

新しい方式:
```python
pf = pq.ParquetFile(parquet_path)
first_chunk = True
for batch in pf.iter_batches(batch_size=CHUNK_SIZE, columns=[...]):
    buf = io.BytesIO()
    # ヘッダーは最初のチャンクのみ
    options = pa_csv.WriteOptions(include_header=first_chunk)
    pa_csv.write_csv(pa.Table.from_batches([batch]), buf, write_options=options)
    buf.seek(0)
    if first_chunk:
        cur.copy_expert(f'COPY ... FROM STDIN CSV HEADER', buf)
        first_chunk = False
    else:
        cur.copy_expert(f'COPY ... FROM STDIN CSV', buf)
    total_rows += batch.num_rows
```

**ポイント:**
- `ParquetFile.iter_batches(batch_size=N)` で N 行ずつ読み込み
- 各チャンクを CSV 変換 → COPY → バッファ解放のサイクルで処理
- メモリ消費は `CHUNK_SIZE` 行分に固定される
- `CHUNK_SIZE` のデフォルトは `100_000`（10万行）とする。56M 行で約 560 回のイテレーション
- テーブルごとに commit 済み（27.5 で対応済み）なので、チャンク間での commit は不要（テーブル単位の commit で十分）

### 技術的な考慮事項

- **CHUNK_SIZE の選択**: 100,000 行。1行あたり平均 500 バイト（CSV）と仮定すると、チャンクあたり約 50MB。ピーク（PyArrow batch + CSV buffer）で約 100-150MB。十分安全な範囲
- **`copy_expert` の HEADER 制御**: 最初のチャンクは `CSV HEADER` で送信し、2 回目以降は `CSV`（ヘッダーなし）で送信する必要がある。`pa_csv.WriteOptions(include_header=False)` で制御可能
- **パフォーマンス**: チャンク分割によるオーバーヘッドは軽微。`COPY FROM STDIN` は PostgreSQL 側でバッチ処理されるため、チャンクサイズが数万行以上あれば性能劣化はほぼない
- **既存の sample 環境への影響**: sample は小規模テーブル（数千行）なのでチャンク分割でも 1 イテレーションで完了する。既存動作に影響なし
- **進捗表示**: 大容量テーブルではロードに時間がかかるため、チャンクごとの進捗表示（ロード済み行数）を追加する
