# タスク詳細: 11.2 ruff ASYNC ルールの有効化

## 概要

不変条件 I3（async コンテキストでブロッキング I/O をしない）を ruff の `ASYNC` ルールで機械検知できるようにする。Python の 3 コンポーネント（jupyter-server / document-server / scripts）の `pyproject.toml` の `select` に `"ASYNC"` を追加し、既存違反 5 件を解消する（ASYNC240 の 2 件は実装修正、ASYNC109 の 3 件は API 契約上意図的なため `per-file-ignores` で 2 ファイルに限定して抑制する。コンポーネント全体の `ignore` にはしない）。

CI 設定（`.github/workflows/ci.yml`）の変更は不要。既存の `python-lint-and-test` ジョブが `scripts/lint.sh` 経由で `ruff check` を実行しており、`select` の変更だけでゲートが有効になる。

## 関連ドキュメント

- 不変条件: `docs/design/invariants.md` の「I3: async コンテキストでブロッキング I/O をしない」
- タスク設計: `.claude/rules/task-design.md` の「横断的な性質もタスクにする」（本タスクは機能ではなく構造の健全性を守る横断タスク）
- lint 運用: `.claude/rules/lint.md`（`--fix` 等の自動修正モードは使わない）

## 背景: 3ゲートの実測（Phase 11.2〜11.4 の分割根拠）

計画時に実際にツールを走らせて得た数値。推測ではない。

### ASYNC240 の検知範囲（実測で確認した限界）

`Path(x) / y` の join を挟むと ruff の型推論が切れ、以降のメソッド呼び出しは検知されない。プローブファイルで確認した挙動:

| 書き方 | 検知 |
|--------|------|
| `Path(p).mkdir()` | される |
| `d = Path(p)` → `d.mkdir()` | される |
| `d = Path(ROOT) / p` → `d.mkdir()` | **されない** |
| `async def f(d: Path)` → `d.mkdir()` | される |

このため `cell_handlers.py:102-103`（`output_dir = workspace_dir / "output"` → `.mkdir()`）や `preview_handlers.py:152-154`（`abs_path = Path(JUPYTER_ROOT_DIR) / path` → `.exists()`）は検知されない。本ゲートは I3 の**完全な保証ではなく部分的な網**である。この限界を承知の上で、コストがほぼゼロなので回帰防止ネットとして導入する。

なお `sql_handlers.py:697` の `df.to_csv()`（最大 100 万行を event loop 上で書き出す）は ruff では原理的に検知できない実質的な I3 違反だが、振る舞い変更を伴うため本タスクのスコープ外とし、別タスクとして起票する（「リスクと検知方法」参照）。

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | ブロック 3 のパス解決を `_resolve_workspace_id_from_cwd_sync()` に切り出し、`run_in_executor` でオフロード | `workspace_handlers.py` / `preview_handlers.py` / `sql_handlers.py` と同じ `_*_sync` + executor の既存イディオムに揃う。I3 を実際に満たす。切り出した純粋関数を単体テストできる | executor へのホップ分のオーバーヘッドが増える（`.resolve()` 自体は数マイクロ秒のシステムコール） |
| B | `# noqa: ASYNC240` に理由コメントを添えて抑制 | 変更が 2 行で済む。実行時コストが増えない | ゲート導入初日に例外を作ることになり、以後 `noqa` が前例として増殖しやすい。I3 違反自体は残る |
| C | `os.path.realpath()` に置き換える | ruff が検知しなくなる（pathlib メソッドではないため） | ブロッキング I/O は残ったままで、ルールの検知を回避しているだけ。最も筋が悪い |

採用理由: A は本リポジトリに確立済みのオフロードパターン（後述の通り既存 8 個）の **9 個目**にあたり、実装イディオムとして完全に定着している。B は「2 行のために executor は過剰では」という妥当な反論があるが、ゲートを入れる初日に抑制コメントを置くと、後続タスクで `noqa` を足す心理的ハードルが下がる。C はルールを回避するだけで I3 を満たさないため却下。

### ASYNC109 の抑制範囲（案 B 却下の論理との整合）

案 B を「初日に例外を作らない」という理由で却下した以上、ASYNC109 をコンポーネント全体の `ignore` に入れるのは矛盾する（`ignore` は `noqa` より作用範囲が広く、かつ違反箇所に痕跡が残らない）。そこで **`per-file-ignores` で既存 2 ファイルに限定**する。

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A2（採用） | `[tool.ruff.lint.per-file-ignores]` で `kernel_executor.py` と `sql_handlers.py` に限定 | 新規ファイルでは ASYNC109 が生きる。抑制の対象と理由が設定ファイル上で可視 | 設定の行数が増える |
| B2 | `ignore = [..., "ASYNC109"]` でコンポーネント全体を抑制 | 設定が 1 語で済む | jupyter-server 全体で恒久的に無効化され、将来の新規 async 関数も検知されない。案 B を却下した論理と矛盾する |

`timeout` 引数自体は REST API の契約（`docs/design/api-contracts.md` の `timeout` パラメータ）であり、`kernel_executor.py:101-113` と `sql_handlers.py:677-680, 727-730` はロック取得後に deadline を計算したり `asyncio.wait_for(..., timeout + 5)` で内側の SQL タイムアウトと二段構えにしたりしている。外側の `asyncio.timeout` に置き換えるとロック待機時間を含む別の意味になるため、抑制は妥当。ただし**この 2 ファイルに限る**。

ADR 要否: 不要。状態の所有権・コンポーネント間契約・方式選定のいずれも変えない。既存の不変条件 I3 を機械検知するだけで、新しい設計判断を含まない。

## 参考にする既存実装

- コピー元: `jupyter-server/extensions/custom_api/preview_handlers.py:158-160`（`run_in_executor` によるオフロード）
- **同種の実装は現在 8 個あり、本タスクで追加するのは 9 個目**（`grep -rn "^def _.*_sync" jupyter-server/extensions/` で確認）:
  `_create_workspace_sync` / `_list_workspaces_sync` / `_update_metadata_sync` / `_read_templates_sync`（`workspace_handlers.py:93,120,140,174`）、`_preview_file_sync`（`preview_handlers.py:72`）、`_export_sql_sync` / `_execute_sql_sync` / `_execute_non_select_sync`（`sql_handlers.py:447,510,548`）
- **I8（rule of three）に対する判断 — 共通化しない**: 9 個目にもかかわらず共通ヘルパーを作らない。理由は、共通部分が `loop = asyncio.get_running_loop()` + `await loop.run_in_executor(None, fn, *args)` の 2 行しかなく、**可変なのは関数・引数個数・戻り値型の 3 つすべて**だからである。ラッパーを被せると引数を `*args` で受けて戻り値を `Any` に潰すことになり、既存 8 箇所が持っている型情報を失う。標準ライブラリの呼び出し規約をそのまま使うことが最も明快であり、共通化は可読性・型安全性の両方を悪化させる。この判断は `docs/design/invariants.md` I8 の「同種の実装の3回目のコピーは共通化する」に対する意図的な例外であり、将来「オフロード + タイムアウト + エラー変換」のように共通部分が育った時点で再検討する

## 異常系・不変条件

- **該当する異常系（不正入力）**: カーネルの cwd がワークスペースルート配下にない場合、`Path.relative_to()` が `ValueError` を送出する。`run_in_executor` はワーカースレッドの例外を await 側で再送出するため、既存の `except Exception as exc:`（`cell_handlers.py:91-95`）がこれまで通り捕捉し info ログに落とす。**この例外伝播の維持を新規テストで検証する**（完了条件「異常系: cwd 解決」）
- **該当する異常系（ゲート自体の機能）**: async 関数内にブロッキング I/O を新規に書いた場合に `ruff check` が exit 1 になること。ゲートが実際に検知することを完了条件「異常系: ゲート回帰」で検証する
- **関係する不変条件**: I3（async でブロッキング I/O しない）— 本タスクはこの不変条件の機械検知を導入するもの。ただし上記「ASYNC240 の検知範囲」の通り部分的な網であり、I3 の完全な保証にはならない点を計画上の既知の限界として明記する

### 実装手順

1. **`jupyter-server/extensions/custom_api/cell_handlers.py` に同期ヘルパーを新設する。** モジュール先頭に `import asyncio` を追加し、`resolve_workspace_for_kernel` の直前に以下を定義する:

   ```python
   def _resolve_workspace_id_from_cwd_sync(cwd: str) -> str | None:
       """カーネルの cwd からワークスペース ID を推定する（同期のパス解決を含む）。

       cwd がワークスペースルート配下にない場合、relative_to が ValueError を送出する。
       呼び出し側の except で捕捉される想定。
       """
       workspace_root = Path(WORKSPACE_ROOT_DIR).resolve()
       rel = Path(cwd).resolve().relative_to(workspace_root)
       return str(rel.parts[0]) if rel.parts else None
   ```

   検証: `uv run ruff format --check jupyter-server/extensions/` が exit 0（整形済み）。

2. **ブロック 3（`cell_handlers.py:86-90`）を executor 呼び出しに置き換える。** `if cwd:` の中身を以下にする（`try` / `except` の構造は変更しない）:

   ```python
   if cwd:
       loop = asyncio.get_running_loop()
       workspace_id = await loop.run_in_executor(None, _resolve_workspace_id_from_cwd_sync, cwd)
   ```

   検証: `uv run ruff check --extend-select ASYNC jupyter-server/extensions/custom_api/cell_handlers.py` の出力に `ASYNC240` が含まれないこと（`ASYNC109` は他ファイルのため本ファイルには出ない）。

3. **`jupyter-server/pyproject.toml` の ruff 設定を更新する。** ASYNC109 は `ignore` ではなく `per-file-ignores` で既存 2 ファイルに限定する（「ASYNC109 の抑制範囲」の案 A2）。

   ```toml
   [tool.ruff.lint]
   select = ["E", "F", "W", "I", "UP", "B", "SIM", "ASYNC"]
   ignore = ["E501"]

   # ASYNC109: REST API が timeout パラメータを公開する契約のため、async 関数が
   # timeout 引数を取るのは意図的。内部でロック取得後の deadline 計算や
   # asyncio.wait_for(..., timeout + 5) の二段構えを行っており、呼び出し側の
   # asyncio.timeout では代替できない。新規ファイルでは検知させたいため全体 ignore にはしない
   [tool.ruff.lint.per-file-ignores]
   "extensions/custom_api/kernel_executor.py" = ["ASYNC109"]
   "extensions/custom_api/sql_handlers.py" = ["ASYNC109"]
   ```

   検証: `uv run ruff check jupyter-server/extensions/ jupyter-server/tests/` が exit 0。加えて ASYNC109 の 3 件が抑制されていることを確認するため、`uv run ruff check --select ASYNC109 jupyter-server/extensions/` が exit 0 であること（CLI の `--select` 上書き下でも `per-file-ignores` は有効。計画時にサンドボックスで実測確認済み）。なおこの検証は「抑制が効いていること」しか示さず、パターンを広く書きすぎた場合も同じく exit 0 になるため、**抑制範囲の限定は完了条件「抑制の限定」の目視確認で担保する**。

4. **`document-server/pyproject.toml` と `scripts/pyproject.toml` の `select` に `"ASYNC"` を追加する。** `ignore` は変更しない（ASYNC109 の該当箇所がないため、将来書かれたら検知されるべき）。

   検証: `uv run ruff check document-server/src/ document-server/tests/ scripts/*.py scripts/lib/*.py` が exit 0。

5. **新規テスト `jupyter-server/tests/test_workspace_cwd_resolution.py` を作成する（全 6 ケース）。** モジュールロードの模倣元は **`test_cell_execute_batch.py:19-130`**（`test_cell_clear_outputs.py` ではない）。理由は「テスト参照ポインタ」の注意点を参照 — `resolve_workspace_for_kernel` は `cell_handlers.py:51` で `from .session_handlers import get_kernel_workspace` を関数内 import するため、`custom_api.session_handlers` のモック登録が必須で、`test_cell_clear_outputs.py` にはそれがない。

   ゲート自体の回帰テスト（ケース 6）は ruff の stdin モードを使い、ソースツリーにプローブファイルを作らない。`--stdin-filename` に jupyter-server 配下のパスを渡すと実際の `jupyter-server/pyproject.toml` が解決される（計画時に検証済み。`select` に `SIM` を持つのは jupyter-server だけなので、`SIM115` が併せて報告されることが設定解決の証拠になる）:

       ["uv", "run", "ruff", "check", "--stdin-filename",
        "jupyter-server/extensions/custom_api/_probe.py", "--output-format", "concise", "-"],

### 技術的な考慮事項

- `run_in_executor` はワーカースレッドで発生した例外を await 側で再送出する（計画時にスクラッチで実行確認済み）。したがって `relative_to` の `ValueError` は既存の `except Exception as exc:` に届き、`isinstance(exc, ValueError)` の分岐（info ログ）もこれまで通り機能する。この挙動は新規テストのケース 2・5 で固定する
- `WORKSPACE_ROOT_DIR` は `base.py` からの import で、モジュールロード時点の値が使われる。ヘルパー内で毎回 `.resolve()` するのは既存挙動の踏襲であり、本タスクでは最適化しない（挙動を変えない）
- `scripts/lint.sh:51-58` の `ruff_targets()` は jupyter-server について `extensions/` と `tests/` を対象にしているため、新規テストファイルも自動的に ruff の対象になる。`lint.sh` の変更は不要
- ruff のバージョンはルート `pyproject.toml` の dev 依存で `"ruff"`（バージョン未固定）。ASYNC ルールの検知範囲は将来の ruff 更新で広がりうる。広がった結果として新たな違反が出た場合は、その時点で個別に判断する（本タスクでバージョンを固定しに行くと `docs/design/invariants.md` I7 の議論に踏み込むためスコープ外）

## リスクと検知方法

- **`resolve_workspace_for_kernel` の呼び出し元 3 箇所（`handlers.py:245`, `cell_handlers.py:551`, `cell_handlers.py:752`）で挙動が変わる**: いずれも `await` して `(output_dir, workspace_rel_path)` を受けるだけで、シグネチャも戻り値も変えないため影響はない。**ただし既存テストはこの関数を一度も実行していない**（`grep -rn "resolve_workspace_for_kernel" jupyter-server/tests/` がヒット 0。`test_cell_execute_batch.py` の各テストはハンドラクラスの存在確認と `validate_path` の検証のみで、`post()` を呼ばない）。したがって**回帰検知は既存テストではなく本タスクで新設するケース 5（end-to-end 異常系）が唯一の網**である
- **executor 内の例外伝播が壊れると、ワークスペース解決の失敗が握りつぶされる**: 新規テストのケース 2（同期ヘルパーの `ValueError`）とケース 5（`resolve_workspace_for_kernel` 経由で `(None, None)`）で固定する
- **オフロードしたつもりで実際は event loop 上で実行される実装ミス**: ケース 4 で `loop.run_in_executor` が実際に呼ばれることを spy して検証する（`inspect.iscoroutinefunction` だけでは、ヘルパーを直接呼ぶ実装ミスを検知できない）
- **ruff 更新で ASYNC の検知範囲が広がり、無関係な PR が赤くなる**: `.claude/rules/test-failure-workflow.md` の「自タスク無関係」に該当するため、別 fix ブランチで対応する
- **本タスクのスコープ外に残る I3 違反**: `sql_handlers.py:697` の `df.to_csv()`（最大 100 万行を event loop 上で実行）は ruff で検知できない。**本タスクの PR 作成時に別タスクとして `docs/plan/01-jupyter.md` に起票する**こと。ゲートがグリーンでも I3 が完全に守られているわけではない

### 新規テスト

`jupyter-server/tests/test_workspace_cwd_resolution.py` に 6 ケース（対応する完了条件を併記）:

1. `test_returns_workspace_id_for_cwd_under_root` — cwd が `{WORKSPACE_ROOT_DIR}/ws-a/sub` のとき `"ws-a"` を返す（完了条件「異常系: cwd 解決」の正常系側）

3. `test_returns_none_when_cwd_is_root_itself` — cwd がルート自身のとき `rel.parts` が空で `None` を返す（境界値）
4. `test_offloads_via_run_in_executor` — `loop.run_in_executor` を spy し、実際にオフロード経由で呼ばれることを検証する（ヘルパーを直接呼ぶ実装ミスの検知）。あわせて `resolve_workspace_for_kernel` が coroutine function のままであることも確認する。**spy の方法**: `asyncio.get_running_loop` をグローバルに patch すると他テストに波及するため、async テスト内で `loop = asyncio.get_running_loop()` を取得し `monkeypatch.setattr(loop, "run_in_executor", wrapper)` でインスタンス属性を差し替える（実装コードも同じ loop インスタンスを取得するため確実に捕捉できる）
5. `test_resolve_returns_none_tuple_for_cwd_outside_root` — **end-to-end 異常系**（完了条件「異常系: cwd 解決」の後半）。`@pytest.mark.asyncio` 下で、`session_manager` なし・`get_kernel_workspace` が `None` 返し・`handler.kernel_manager.get_kernel()` がワークスペース外の cwd（例 `/etc`）を持つカーネルを返すモックを渡し、`await resolve_workspace_for_kernel(handler, "k1")` が `(None, None)` を返すことを検証する。executor 越しの `ValueError` が既存の `except Exception` に届き握りつぶされないことを固定する
6. `test_ruff_async_gate_detects_blocking_io` — **ゲート自体の回帰テスト**。`async def` 内の `Path(p).resolve()` を ruff の stdin モードに流し、exit 1 と `ASYNC240` を確認する（**異常系**・完了条件「異常系: ゲート回帰」）。**skip 条件は `FileNotFoundError`（ruff/uv 未インストール）に限定する。** `returncode` が 0 や 2 以上の場合は skip せず fail させること（無言 skip でこの完了条件が空洞化するのを防ぐ）
