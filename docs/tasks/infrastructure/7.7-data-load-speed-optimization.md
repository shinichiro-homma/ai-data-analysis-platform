# タスク詳細: 7.7 データロード速度の最適化

## 概要

Infrastructure Phase 7.6 で実装したチャンク分割ロードはメモリ消費を抑える設計だが、ロード速度自体は最適化されていない。ストレージ（メモリ・ディスク）を圧迫せずにロード速度を改善する。

### 改善項目

#### ~~1. UNLOGGED テーブルでのロード~~ （撤回）

~~初期ロード中は WAL を書かない UNLOGGED テーブルとしてデータを投入し、ロード完了後に LOGGED に変更する。~~

**撤回理由:** `ALTER TABLE ... SET LOGGED` はテーブル全体を WAL に書き直すため、COPY 中に節約した WAL が一括で書き込まれストレージを圧迫する。production 環境（2億行超）では Docker ボリュームのディスク容量を超過し、PostgreSQL がクラッシュした。

#### 2. インデックス遅延作成（将来対応）

現時点の `generate_create_tables()` はインデックスを生成していないため、将来インデックスを追加する場合に備えた設計とする。現在は変更不要。

#### 3. PostgreSQL チューニング（ロード時のみ）

`load-data.py` の冒頭で一時的にパフォーマンス設定を変更し、終了時に戻す。

```python
# ロード前
cur.execute("SET maintenance_work_mem = '256MB'")
cur.execute("SET synchronous_commit = OFF")

# ロード後
cur.execute("SET maintenance_work_mem = DEFAULT")
cur.execute("SET synchronous_commit = ON")
```

#### 4. 文字列クリーニングの最適化

現在のテンプレートでは全カラムをループして文字列型を判定している。事前に文字列カラムのインデックスリストを作成し、非文字列カラムのループをスキップする。

```python
# 現在: 全カラムループ
for i, field in enumerate(batch.schema):
    if pa.types.is_string(field.type) or pa.types.is_large_string(field.type):
        ...

# 改善: 事前にインデックスリストを作成（ループ外）
string_col_indices = [i for i, f in enumerate(schema) if pa.types.is_string(f.type) or ...]
# ループ内では string_col_indices のみ処理
```

#### 5. CHUNK_SIZE / COMMIT_INTERVAL の調整

- `CHUNK_SIZE`: 100,000 → 300,000 に変更（COPY 呼び出し回数を 1/3 に削減。300,000 行 × 500 バイト ≈ 150MB/チャンクで安全範囲内）
- `COMMIT_INTERVAL`: 10 → テーブル単位コミットに変更（チャンク間コミットを廃止）

テーブル単位コミットにすることで、コミットのオーバーヘッドを最小化する。チャンク分割はメモリ制御のためであり、トランザクション分割の必要はない。

**スコープ外:** `docker-compose.yml` での PostgreSQL サーバーレベルチューニング（`shared_buffers` 等）は、ロード後のクエリ性能に効くものであり、初期ロード速度の改善には寄与しないため対象外とする。

### 実装手順

1. `generate_load_data()` テンプレートに以下を追加:
   - ロード前: PostgreSQL チューニング設定（`maintenance_work_mem`, `synchronous_commit`）
   - 文字列カラムの事前フィルタリング（`string_col_indices`）
   - CHUNK_SIZE を 100,000 → 300,000 に拡大
   - COMMIT_INTERVAL 廃止（テーブル単位コミット）
   - ロード後: チューニング設定を戻す
3. init スクリプト再生成（sample / production）
4. sample 環境でクリーンリビルド + スモークテスト
5. production 環境で切り替え + スモークテスト

### 技術的な考慮事項

- **ストレージ安全性**: すべての改善はメモリ・ディスク使用量を増やさない
- **synchronous_commit = OFF**: クラッシュ時に直近の数トランザクションが失われる可能性があるが、初期ロードでは問題ない
- **テーブル並列化は採用しない**: 複数テーブルの同時ロードはメモリ使用量が倍増するため、ストレージ圧迫の制約に反する
- **UNLOGGED テーブルは不採用**: `ALTER TABLE SET LOGGED` がテーブル全体を WAL に書き直すため、production 規模（2億行超）ではストレージ不足でクラッシュする
