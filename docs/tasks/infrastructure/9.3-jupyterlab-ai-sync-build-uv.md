# タスク詳細: 9.3 jupyterlab-ai-sync ビルドのルート venv 統合

## 概要

`jupyterlab-ai-sync` の `npm run build`（内部で `tsc && jupyter labextension build .` を呼ぶ）が必要とする `jupyter` / `jupyterlab` / `jupyter_packaging` をルート venv に集約し、ローカル開発者が別途 `pip install jupyterlab` を実行しなくてもビルドできるようにする。

あわせて、これまで `scripts/lint.sh` / `scripts/test.sh` / `scripts/check-freshness.sh` のコンポーネント/鮮度チェック対象から抜け落ちていた `jupyterlab-ai-sync` をローカル検証経路に組み込む（Phase 9 のテーマ「ローカル環境の uv 統一」と整合）。

- `scripts/lint.sh` / `scripts/test.sh`: `jupyterlab-ai-sync` をコンポーネント一覧に追加し、ルート venv 経由の `npm run build` をローカル回帰検知に乗せる
- `scripts/check-freshness.sh`: `jupyter-server` Docker image の鮮度判定に `jupyterlab-ai-sync/` のソース変更を加味し、`jupyterlab-ai-sync/src/*.ts` を編集した場合に `jupyter-server` が STALE と判定されて `--rebuild` で `docker compose build jupyter-server` が再実行されるようにする（Docker のレイヤーキャッシュ無効化により、内部の `COPY jupyterlab-ai-sync` 以降のレイヤーが再ビルドされ、拡張も同時に再ビルドされる）

`jupyterlab-ai-sync/pyproject.toml` の `[build-system]`（`jupyter_packaging~=0.12` による build backend）、`jupyter-server/Dockerfile` の拡張ビルド経路、`.github/workflows/ci.yml` の `jupyterlab-ai-sync-build` ジョブ、`scripts/rebuild.sh` / `scripts/rebuild-mcp.sh` / `scripts/clean-rebuild.sh` には一切手を加えない（下記「変更対象外」参照）。

### 変更対象外

- `jupyterlab-ai-sync/pyproject.toml` — build backend の `[build-system]` を維持。uv workspace member にはしない（フラット配置方針）
- `jupyterlab-ai-sync/package.json` — `build` スクリプトは `tsc && jupyter labextension build .` のまま。`jupyter` の解決は `uv run` 環境の PATH に委ねる（`devDependencies` も変更しない）
- `jupyter-server/Dockerfile` — L28-34 の `COPY jupyterlab-ai-sync /tmp/jupyterlab-ai-sync && cd /tmp/... && npm install && npm run build && pip install .` をそのまま維持
- `.github/workflows/ci.yml` — `jupyterlab-ai-sync-build` ジョブは Phase 9 対象外
- `jupyter-server/requirements.txt` — 不変（Docker 用）
- `scripts/rebuild.sh` — Docker サービス（jupyter-server / document-server / postgres）単位のリビルドを行う。`jupyter-server` リビルド時は `docker compose build jupyter-server` が走り、Docker のレイヤーキャッシュが `COPY jupyterlab-ai-sync` の content hash を見て自動的に拡張ビルドを再実行する。したがって `rebuild.sh` 自体の変更は不要（jupyterlab-ai-sync の鮮度は `check-freshness.sh` の拡張で検知する）
- `scripts/rebuild-mcp.sh` — `MCP_SERVERS=(jupyter-mcp document-mcp)` のみ対象。jupyterlab-ai-sync は MCP サーバーではなく JupyterLab 拡張であり、意味的にミスマッチのため追加しない
- `scripts/clean-rebuild.sh` — Step 4 で `docker compose build --no-cache` を実行するため、jupyter-server Docker image 内の jupyterlab-ai-sync も常にフルビルドされる。追加作業は不要

### test.sh 拡張仕様

`scripts/test.sh` のテストループ冒頭に jupyterlab-ai-sync 専用分岐を追加する。既存の generic 分岐は変更しない。

```bash
# 擬似コード（実装時に精査）
for component in "${TARGETS[@]}"; do
  echo "--- $component ---"

  if [[ "$component" == "jupyterlab-ai-sync" ]]; then
    if [[ ! -d "$component" ]]; then
      echo "  SKIP: directory not found"
      FAILED+=("$component:skip"); continue
    fi
    # jupyterlab-ai-sync は npm workspaces 非参加のため node_modules を個別管理する
    if [[ ! -d "$component/node_modules" ]]; then
      echo "  Installing npm dependencies..."
      (cd "$component" && npm install) \
        || { FAILED+=("$component:install"); echo "  FAILED: npm install"; continue; }
    fi
    if $TYPECHECK; then
      echo "  Type checking..."
      (cd "$component" && npx tsc --noEmit) \
        || { FAILED+=("$component:typecheck"); echo "  FAILED: typecheck"; continue; }
      echo "  Typecheck OK"
    fi
    if $TEST; then
      if $INTEGRATION; then
        echo "  SKIP: integration tests not supported for jupyterlab-ai-sync"
      else
        echo "  Building labextension (uv run)..."
        (cd "$component" && uv run --project "$REPO_ROOT" npm run build) \
          || { FAILED+=("$component:test"); echo "  FAILED: build"; continue; }
        echo "  Build OK"
      fi
    fi
    echo ""
    continue
  fi

  # ... 既存の generic 分岐はそのまま ...
done
```

要点:

- **workspaces 非参加**: ルート `package.json` の `workspaces` は `packages/mcp-shared`, `jupyter-mcp`, `document-mcp`, `tests/e2e` のみ。`jupyterlab-ai-sync` は独立管理のため `npm install` を個別に呼ぶ
- **typecheck = `npx tsc --noEmit`**: package.json に `typecheck` スクリプトを追加せず、test.sh 側で直接呼び出す。`npm run build:lib`（= `tsc`）は lib/ に出力してしまうため型チェック用途には使わない
- **test = `uv run --project "$REPO_ROOT" npm run build`**: ルート venv の PATH を `npm run build` の子プロセスに継承させるため、`uv run` 経由で npm を起動する。`--project "$REPO_ROOT"` によりサブディレクトリの `pyproject.toml`（build backend）を拾わないようにする
- **`--integration` モードはスキップ**: jupyterlab-ai-sync に integration テストは存在しない
- **`--rebuild` は no-op**: `classify_rebuild_targets` の case 文は `jupyterlab-ai-sync` に対してマッチしないため、MCP/Docker どちらのリビルドにも含まれない（意図通り）

### check-freshness.sh 拡張仕様

現行の `check_docker_service` は単一ソースディレクトリのみ受け取る:

```bash
check_docker_service() {
  local service="$1"
  local source_dir="$2"
  ...
  source_epoch=$(newest_file_epoch "$source_dir" "*.ts" "*.py" "*.json" "Dockerfile")
  ...
}
```

これを複数ディレクトリ対応に拡張する。実装方針は以下のいずれかを実装時に選定:

**案 A（推奨）**: 可変長引数化して複数ソースディレクトリを受け取る:

```bash
# 呼び出し側
check_docker_service "jupyter-server" "jupyter-server" "jupyterlab-ai-sync"
check_docker_service "document-server" "document-server"

# 実装
check_docker_service() {
  local service="$1"
  shift
  local source_dirs=("$@")
  ...
  local max_source_epoch=0
  for dir in "${source_dirs[@]}"; do
    local epoch
    epoch=$(newest_file_epoch "$dir" "*.ts" "*.py" "*.json" "*.css" "Dockerfile")
    if [[ -n "$epoch" ]] && [[ "$epoch" -gt "$max_source_epoch" ]]; then
      max_source_epoch="$epoch"
    fi
  done
  ...
}
```

**案 B**: jupyter-server 専用関数を追加する（`check_jupyter_server_freshness`）

案 A を推奨。理由: 既存 `check_docker_service` の呼び出し箇所（2 箇所）への影響が最小限で、将来的に document-server にも同様の拡張が必要になった場合に再利用しやすい。

対象拡張子を現行の `*.ts *.py *.json Dockerfile` に `*.css` を追加する（jupyterlab-ai-sync の `style/` 配下で使われる）。

`--rebuild` 分岐は既存の `jupyter-server` ケースがそのまま機能する:

```bash
jupyter-server|document-server)
  echo "  Rebuilding Docker service: $component"
  if ! docker compose build "$component" || ! docker compose up -d "$component"; then
    ...
  fi
  ;;
```

`docker compose build jupyter-server` が `COPY jupyterlab-ai-sync` の content hash を見て自動的にレイヤーキャッシュを無効化するため、追加ロジックは不要。

usage 文の「チェック対象」一覧を以下のように更新:

```
  - jupyter-server:       Docker イメージ vs jupyter-server/ + jupyterlab-ai-sync/ ソース
```

### 技術的な考慮事項

- **`uv run` の project 解決**: `jupyterlab-ai-sync/` 内で `uv run` を実行すると、uv はディレクトリ直下の `pyproject.toml`（build backend 定義）を拾ってしまう。ルート venv を使わせるには `--project "$REPO_ROOT"` を明示する必要がある
- **`jupyter_packaging` のバージョン互換**: `jupyterlab-ai-sync/pyproject.toml` の `build-system.requires` は `jupyter_packaging~=0.12` を要求する。`~=0.12` は `>=0.12, <1.0` と等価なので、ルート dev group の `jupyter-packaging>=0.12,<1` と互換
- **`jupyterlab` メジャーバージョン**: `build-system.requires` は `jupyterlab~=4.0`。ルート dev group を `jupyterlab>=4.0.0,<5` に揃えることで、拡張ビルド時に使う `@jupyterlab/builder` と整合する
- **PATH 解決**: `uv run -- npm run build` 形式で npm を起動すると、子プロセス（`tsc`, `jupyter labextension build .`）にも venv の PATH が伝播する。ホスト側のシステム Python に `jupyterlab` をインストールする必要はない
- **`npx tsc --noEmit` の動作**: `jupyterlab-ai-sync/devDependencies` に `typescript: ^5.3.0` があるため、`node_modules/` 展開後は `npx tsc` で組み込み TypeScript が解決される。typecheck のみならビルド成果物を出力しない
- **`node_modules/` の管理**: `jupyterlab-ai-sync` は ルート `package.json` の workspaces 対象外のため、`npm ci` 時に自動展開されない。test.sh では初回 `node_modules/` 不在時のみ `npm install` を自動実行する
- **CI との独立性**: 本タスクはローカル統一のみ。CI の `jupyterlab-ai-sync-build` ジョブは従来通り `pip install jupyterlab>=4.0.0 && npm install && npm run build` で動く
- **Docker との独立性**: `jupyter-server/Dockerfile` は JupyterLab 本体を Docker イメージ内に `pip install` し、`COPY jupyterlab-ai-sync /tmp/jupyterlab-ai-sync && cd /tmp/jupyterlab-ai-sync && npm install && npm run build && pip install .` でコンテナ内部で extension をビルドしている。ホスト側のルート `.venv/` とは完全に独立しているため、本タスクの変更は Docker 経路に影響しない
- **`--integration` モード**: 本タスクの対象外。jupyterlab-ai-sync 自体に integration テストは無く、`test.sh --integration` が指定されても build はスキップする
- **`jupyterlab-ai-sync/pyproject.toml` の非 workspace 化**: フラット配置方針を踏襲し、`[tool.uv.workspace]` には追加しない。ビルド時にルート venv の `jupyter_packaging` が PATH 経由で解決される
