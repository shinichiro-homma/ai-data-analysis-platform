# タスク詳細: 2.2 E2Eテストシナリオ作成・実行

## 概要

docker-compose で起動した全サービス（PostgreSQL、jupyter-server、document-server）に対して、「カタログ参照→分析実行」の完全フローを検証する E2E テストを作成する。

Document Phase 1.8 の結合テストとの違い:
- **Document Phase 1.8**: document-mcp のツール単体テスト + 簡易 E2E（テスト用 DataFrame で検証）
- **2.2**: 全サービス統合環境で **実際の PostgreSQL データ** を使った完全フロー検証

## 実装計画

### 作成するファイル

| ファイル | 内容 |
|----------|------|
| `tests/e2e/package.json` | E2E テスト用パッケージ定義（vitest, typescript, dotenv） |

### 設計方針

#### テストの配置場所

プロジェクトルート `tests/e2e/` に配置する。理由:
- Infrastructure Phase 2「全体統合」のテストであり、特定コンポーネントに属さない
- document-server と jupyter-server の両方を横断してテストする
- Document Phase 1.8 の component-level テストと明確に区別できる

#### API 呼び出し方式

REST API を直接呼び出す（MCP の `handleToolCall` をインポートしない）。理由:
- クロスパッケージの import 依存を回避
- docker-compose で起動した実際のサービスに対してテストする
- MCP ツール層の単体テストは各コンポーネントで実施済み
- E2E テストの目的はシステム全体の統合検証

#### ヘルパー設計

`api-client.ts` に document-server / jupyter-server の API ラッパーを集約する。Document Phase 1.8 の `jupyter-helper.ts` を参考にしつつ、document-server API も同一ファイルに含める。

```typescript
// document-server API
export async function getTableIndex(): Promise<TableIndex>
export async function getTableDetail(tableNames: string[]): Promise<TableDetail>
export async function getTermIndex(): Promise<TermIndex>
export async function getTermDetail(termNames: string[]): Promise<TermDetail>
export async function getLogicIndex(): Promise<LogicIndex>
export async function getLogicDetail(logicNames: string[]): Promise<LogicDetail>
export async function getLogicCode(logicName: string): Promise<LogicCode>

// jupyter-server API
export async function createWorkspace(name: string): Promise<Workspace>
export async function createSession(workspaceId: string): Promise<Session>
export async function executeCode(kernelId: string, code: string, timeout?: number): Promise<ExecResult>
export async function deleteSession(sessionId: string): Promise<void>
export async function deleteWorkspace(workspaceId: string): Promise<void>
export async function checkServices(): Promise<{ document: boolean; jupyter: boolean }>
```

### 実装手順

#### ステップ 1: テスト基盤の構築

1. `tests/e2e/package.json` を作成（vitest, typescript, dotenv）
2. `tests/e2e/tsconfig.json` を作成
3. `tests/e2e/vitest.config.ts` を作成（testTimeout: 60000, sequential, dotenv 読み込み）
4. `npm install` で依存関係をインストール

#### ステップ 2: API クライアントヘルパーの実装

1. `tests/e2e/helpers/api-client.ts` を作成
2. document-server REST API ラッパーを実装（GET /catalog/index, POST /catalog/tables 等）
3. jupyter-server REST API ラッパーを実装（Document Phase 1.8 の jupyter-helper.ts を参考）
4. `checkServices()` でサービス起動確認関数を実装

#### ステップ 3: E2E テストシナリオの実装

`tests/e2e/e2e-workflow.test.ts` に以下の 5 シナリオを実装する。

### テストシナリオ詳細

#### シナリオ 1: カタログ駆動の SQL 分析

テーブルカタログ情報を参照し、実際の PostgreSQL テーブルに対して SQL を実行する。

```
1. GET /catalog/index → テーブル一覧を取得
2. POST /catalog/tables → 特定テーブル（例: id_pos_transactions）の詳細を取得
3. カラム情報を使って SELECT 文を構築
4. workspace_create → session_create
5. execute_code で SQL を Jupyter 経由で実行（psycopg2 or sqlalchemy）
6. 結果の DataFrame が期待するカラムを含むことを検証
7. クリーンアップ（session_delete, workspace_delete）
```

検証ポイント:
- カタログの `columns` 情報が実テーブルのスキーマと一致する
- SQL 実行結果が 0 行以上返る
- DataFrame のカラム名がカタログ定義と一致する

#### シナリオ 2: 用語解決→テーブル特定→分析

業務用語から関連テーブルを特定し、分析を実行する。

```
1. GET /glossary/index → 用語一覧を取得
2. POST /glossary/terms → 特定用語（例: ロイヤルティランク）の詳細を取得
3. 用語の定義から関連テーブルを推定
4. POST /catalog/tables → 関連テーブルの詳細を取得
5. 用語定義 + テーブル情報から分析コードを構築
6. Jupyter で実行し結果を検証
```

検証ポイント:
- 用語詳細に `definition` が含まれる
- 用語に関連する `values`（値の体系）が取得できる
- 分析コードが正常に実行される

#### シナリオ 3: ロジック再利用→実行

既存ロジックのコードを取得し、Jupyter 上で実行する。

```
1. GET /logic/index → ロジック一覧を取得
2. POST /logic/meta → 特定ロジックのメタ情報を取得（input_tables, language 等）
3. GET /logic/code/{name} → コードを取得
4. input_tables の情報を catalog API で取得
5. テスト用 DataFrame を作成し、取得したコードと組み合わせて実行
6. 結果を検証
```

検証ポイント:
- ロジックの `language` が "python" であること
- コードが構文的に正しく、実行可能であること
- 出力が期待する形式であること

#### シナリオ 4: 完全統合フロー（メイン E2E）

要件定義の「具体例シナリオ」に沿った 4 フェーズの完全フロー。

```
Phase 1: 用語解決
  - get_term_index → 全用語を把握
  - get_term_detail(["ロイヤルティランク"]) → 用語の定義・値体系を取得

Phase 2: テーブル特定
  - get_table_index → 全テーブルを把握
  - get_table_detail(["id_pos_transactions", "customer_master"]) → カラム・統計情報を取得

Phase 3: ロジック参照
  - get_logic_index → 使えるロジックを確認
  - get_logic_detail → メタ情報を確認
  - get_logic_code → コードを取得

Phase 4: Jupyter 実行
  - workspace_create → session_create
  - execute_code（テスト用 DataFrame + ロジックコード）
  - get_variables / get_dataframe_info で結果検証
  - クリーンアップ
```

検証ポイント:
- 全 4 フェーズが正常に完了する
- 各 API レスポンスのスキーマが要件定義と一致する
- 分析結果が期待する構造を持つ

#### シナリオ 5: エラーハンドリング

異常系のテスト。

```
1. 存在しないテーブル名の指定 → 明確なエラーメッセージ
2. 存在しない用語名の指定 → 明確なエラーメッセージ
3. 存在しないロジック名の指定 → 明確なエラーメッセージ
4. 存在するものと存在しないものの混在指定 → 部分成功レスポンス
5. 不正な Python コードの実行 → エラー情報の返却
```

検証ポイント:
- エラーレスポンスに `not_found` フィールドが含まれる
- 部分成功時に成功分と不明分の両方が返る
- Python エラー時に stderr やトレースバックが返る

### 技術的な考慮事項

#### PostgreSQL データの利用

- docker-compose の init スクリプトで投入済みの実データを使用
- テスト実行時に PostgreSQL が healthy であることを前提とする
- テストがデータを変更しないこと（SELECT のみ）

#### テスト間の独立性

- 各シナリオで `afterEach` によるクリーンアップ（ワークスペース/セッション削除）
- テスト間で共有状態を持たない
- ワークスペース名にタイムスタンプを付与して衝突を回避

#### サービス起動確認

- `beforeAll` で document-server と jupyter-server の起動を確認
- いずれかが未起動の場合は全テストをスキップ（`console.warn` + `return`）
- エラーではなくスキップとすることで、CI での柔軟な実行を可能にする

#### タイムアウト設定

- vitest 全体: `testTimeout: 60000`（60 秒）
- 完全統合フロー（シナリオ 4）: 個別に `120000`（120 秒）を指定
- カーネル初回起動に時間がかかるため、余裕を持った設定にする

#### Document Phase 1.8 テストとの棲み分け

| 観点 | Document Phase 1.8（component-level） | 2.2（system-level） |
|------|------------------------|---------------------|
| 配置 | `document-mcp/tests/integration/` | `tests/e2e/` |
| 呼び出し方式 | `handleToolCall` 直接 | REST API |
| データ | テスト用 DataFrame | 実 PostgreSQL データ |
| 対象 | document-mcp ツール + 簡易 Jupyter | 全サービス統合 |
| 目的 | MCP ツールの動作検証 | システム全体の統合検証 |
