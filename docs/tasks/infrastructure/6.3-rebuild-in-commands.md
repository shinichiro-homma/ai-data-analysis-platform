# タスク詳細: 6.3 カスタムコマンドへのリビルド強制組み込み

## 概要

`custom-start-task`、`custom-start-fix`、`custom-refactor`、`custom-complete-task` の 4 つのカスタムコマンドに、テスト実行前のリビルドステップを追加する。

現状、これらのコマンドは `scripts/test.sh {component}` を直接呼び出しており、ソースコード変更後にリビルドが行われないまま古いビルド成果物に対してテストが実行される場合がある。`rebuild-before-test.md` ルールが存在するが、カスタムコマンド側で強制されていないため、ルール違反が起きやすい。

## 関連ドキュメント

- ルール: `.claude/rules/rebuild-before-test.md` — リビルド必須ルール
- ルール: `.claude/rules/scripts.md` — スクリプト一覧
- ルール: `.claude/rules/freshness-check.md` — 鮮度チェックルール

### 実装手順

#### 1. custom-start-task.md

現在の構成:
- ステップ 1〜5: 準備（git status、計画確認、PLAN.md 確認、ステータス更新、Skill 確認）
- ステップ 6: 実装開始
- ステップ 7: 開始報告

変更: ステップ 6 と 7 の間に「リビルド＋テスト」ステップを挿入する。

追加するステップの内容:
```markdown
## 7. リビルド＋テスト（必須）

実装が完了したら、**テスト実行前に必ずリビルドを行ってください。**

### 7.1 対象コンポーネントの種別を判定

| 変更対象 | リビルドコマンド |
|---------|----------------|
| MCP サーバー（jupyter-mcp, document-mcp） | `scripts/rebuild-mcp.sh {server}` |
| Docker コンテナ（jupyter-server, document-server） | `scripts/rebuild.sh {service}` |
| MCP + Docker 両方 | `scripts/rebuild-mcp.sh && scripts/rebuild.sh` |

### 7.2 リビルド実行

対象コンポーネントに応じたリビルドコマンドを実行してください。

### 7.3 テスト実行

```bash
scripts/test.sh {対象コンポーネント名}
```

テストが失敗した場合は修正してリビルド→テストを繰り返してください。
```

旧ステップ 7（開始報告）はステップ 8 に繰り下げる。

#### 2. custom-start-fix.md

現在のステップ 6 はテスト実行のみ:
```bash
scripts/test.sh {対象コンポーネント名}
```

変更: テスト前にリビルドステップを追加する。

```markdown
## 6. リビルド＋テストの実行

### 6.1 リビルド（必須）

実装した修正をビルド成果物に反映させます。修正対象に応じて適切なリビルドコマンドを実行してください：

| 変更対象 | リビルドコマンド |
|---------|----------------|
| MCP サーバー（jupyter-mcp, document-mcp） | `scripts/rebuild-mcp.sh {server}` |
| Docker コンテナ（jupyter-server, document-server） | `scripts/rebuild.sh {service}` |
| MCP + Docker 両方 | `scripts/rebuild-mcp.sh && scripts/rebuild.sh` |

### 6.2 テスト実行

型チェックとユニットテストは `scripts/test.sh` で実行してください：

```bash
scripts/test.sh {対象コンポーネント名}
```
```

#### 3. custom-refactor.md

現在のステップ 4（動作確認）のステップ 4.2 が直接 `scripts/test.sh` を呼んでいる。

変更: ステップ 4.2 の前にリビルドサブステップ（4.1.5 相当）を追加、またはステップ 4.2 のタイトルを変更してリビルドを含める。

### 4.2 リビルド（必須）

テスト実行前に、リファクタリングしたコードをビルド成果物に反映させます。

#### 4. custom-complete-task.md

現在のステップ 3 は完了検証で、「テストは実装中（start-task）で実行済みのため、ここでは実行しない。」と明記されている。

変更: テスト再実行ステップを追加する。理由: start-task 以降にドキュメント修正等の追加変更が入る可能性があり、最終確認としてテストを再実行すべき。

ステップ 3 の注意書きを削除し、新しいステップ「3. テスト再実行」を追加:

```markdown
## 3. テスト再実行

タスク完了前の最終確認として、リビルド＋テストを実行してください。

### 3.1 対象コンポーネントの種別を判定

| 変更対象 | リビルドコマンド |
|---------|----------------|
| MCP サーバー（jupyter-mcp, document-mcp） | `scripts/rebuild-mcp.sh {server}` |
| Docker コンテナ（jupyter-server, document-server） | `scripts/rebuild.sh {service}` |
| MCP + Docker 両方 | `scripts/rebuild-mcp.sh && scripts/rebuild.sh` |

### 3.2 リビルド実行

対象コンポーネントに応じたリビルドコマンドを実行してください。

### 3.3 テスト実行

```bash
scripts/test.sh {対象コンポーネント名}
```

テストが失敗した場合は修正してリビルド→テストを繰り返してください。
```

旧ステップ 3（完了検証）→ ステップ 4、旧 4 → 5、旧 5 → 6、旧 6 → 7、旧 7 → 8、旧 8 → 9 に繰り下げ。

### 技術的な考慮事項

- **リビルドコマンドの判定**: コンポーネントの種別（MCP / Docker）に応じて適切なリビルドコマンドを選択する必要がある。判定表を各コマンドに統一的に記載する。
- **タスク 6.4 との関係**: 6.4 で `scripts/test.sh --rebuild` が通常テストでも有効になれば、リビルド＋テストを 1 コマンドに統合できる。ただし 6.3 は 6.4 に依存せず、明示的なリビルドコマンドで実装する。
- **complete-task のテスト追加**: 既存の注意書き「テストは実装中で実行済み」を削除し、最終確認としてのテスト再実行を追加する。start-task 後にドキュメント修正等の追加変更が入るケースがあるため。
