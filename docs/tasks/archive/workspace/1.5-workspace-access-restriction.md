# タスク詳細: 1.5 ワークスペース間アクセス制限

## 概要

カーネル起動時に Python スタートアップスクリプトを注入し、カーネル内の Python コードがワークスペースディレクトリ外のファイルにアクセスすることを防ぐ「ソフトな制限」を実装する。

現状、`session_create` で `cwd=workspace_dir` を設定しているが、Python コードから `os.chdir()` で別ディレクトリに移動したり、絶対パスで他のワークスペースにアクセスすることは制限されていない。本タスクでこれを対処する。

## 実装計画

### 実装アプローチ

**方法: カーネル起動後にコード実行でスタートアップスクリプトを注入**

`session_handlers.py` の `start_kernel()` 直後に `KernelExecutor.execute()` で Python サンドボックスコードを実行する。

この方法を選択する理由:
- ワークスペースごとに異なる制限パス（ワークスペースディレクトリ）を動的に設定できる
- IPython startup ディレクトリにファイルを配置する方法と比べ、環境変数やファイルシステムの前準備が不要
- 既存の `KernelExecutor.execute()` を再利用でき、追加の依存が少ない

制限対象（要件 F6.3 より）:
1. **ファイルアクセス**: `builtins.open()` をラップし、ワークスペース外パスへのアクセスを拒否
2. **`os.chdir()`**: ワークスペース外への作業ディレクトリ変更を拒否

### 作成・変更するファイル

| ファイル | 変更種別 | 内容 |
|----------|----------|------|
| `jupyter-server/extensions/custom_api/workspace_sandbox.py` | 新規 | サンドボックススクリプト生成モジュール。ワークスペースパスを受け取り、注入用 Python コード文字列を返す |
| `jupyter-server/extensions/custom_api/session_handlers.py` | 変更 | `start_kernel()` 直後にサンドボックススクリプトをカーネルに注入する処理を追加 |
| `jupyter-mcp/tests/integration/workspace-access-restriction.test.ts` | 新規 | ワークスペース間アクセス制限の結合テスト |

### 実装手順

#### Step 1: サンドボックススクリプトモジュール作成

`jupyter-server/extensions/custom_api/workspace_sandbox.py` を新規作成する。

主な機能:
- `generate_sandbox_code(workspace_dir: str) -> str` 関数を実装
- 返り値は、カーネルで実行されるとサンドボックスを設定する Python コード文字列
- サンドボックスコードの内容:
  - `builtins.open` をラップし、引数のパスを `os.path.realpath()` で解決してワークスペースディレクトリ配下かチェック
  - `os.chdir` をラップし、同様にワークスペースディレクトリ配下かチェック
  - 制限に違反した場合は `PermissionError` を送出（メッセージ例: "Access denied: path is outside workspace directory"）
  - ワークスペースディレクトリ自体と、`/tmp` 等のシステム一時ディレクトリはホワイトリストとして許可
  - Python 標準ライブラリのインポートは制限しない（ソフトな制限のため）

#### Step 2: セッションハンドラーへの注入処理追加

`session_handlers.py` の `CustomSessionsHandler.post()` を変更する。

- `start_kernel(cwd=workspace_dir)` の直後に、`KernelExecutor` を使ってサンドボックスコードを実行
- サンドボックス注入が失敗した場合はカーネルを停止し、エラーを返す
- カーネル起動→サンドボックス注入の流れを確実にするため、注入完了を待ってからレスポンスを返す

#### Step 3: 結合テスト作成

`jupyter-mcp/tests/integration/workspace-access-restriction.test.ts` を新規作成する。

テストケース:
1. ワークスペースA のセッションから `open('/path/to/workspaceB/file')` を実行 → `PermissionError`
2. ワークスペースA のセッションから `os.chdir('/path/to/workspaceB')` を実行 → `PermissionError`
3. ワークスペースA のセッションから自ワークスペース内のファイルに `open()` で読み書き → 成功
4. ワークスペースA のセッションから `os.chdir()` で自ワークスペース内のサブディレクトリに移動 → 成功
5. `/tmp` へのファイル書き込み → 成功（ホワイトリスト）
6. `pathlib.Path` を使った相対パスでのワークスペース外アクセス（`../../`）→ `PermissionError`

### 技術的な考慮事項

- **ソフトな制限**: 要件にある通り、これは完全なセキュリティサンドボックスではなく「ソフトな制限」。`ctypes` や `importlib` を使った回避は想定しない。一般的な Python ファイル操作（`open`, `os.chdir`, `pathlib.Path`）を制限する
- **symlink 対策**: `os.path.realpath()` でシンボリックリンクを解決してからパスチェックを行うことで、symlink を使ったバイパスを防ぐ
- **`/tmp` の許可**: データ処理の一時ファイルに `/tmp` が使われることが多いため、ホワイトリストに含める。ただし `/tmp` 経由で他ワークスペースのデータにアクセスすることは本質的に防がれる（他ワークスペースのデータは `/tmp` にない）
- **パフォーマンス**: モンキーパッチはカーネル起動時に1回のみ実行。ファイルアクセスごとのオーバーヘッドは `os.path.realpath()` のコスト程度で、分析処理への影響は無視できるレベル
- **カーネル再起動**: カーネルが再起動した場合、スタートアップスクリプトは再度注入が必要。ただし現在のアーキテクチャではカーネル再起動は新セッション作成で対応するため、この問題は発生しない
