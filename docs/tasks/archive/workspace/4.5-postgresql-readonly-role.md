# タスク詳細: 4.5 PostgreSQL read-only ロール（SQL防御）

## 概要

PostgreSQL に read-only ロール（`jupyter_readonly`）を作成し、`jupyter-server` の `DATABASE_URL` をこのロールで接続するよう変更する。これにより `execute_sql` ツール経由の書き込み操作（DELETE, INSERT, UPDATE, ALTER 等）が PostgreSQL 側で拒否されるようになり、アプリケーション側のブラックリスト（`BLOCKED_COMMANDS`）と合わせた二重防御を実現する。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-server.md`
  - F7.1: `DATABASE_URL` 環境変数で指定されたデータベースに **read-only ロール**（`jupyter_readonly`）で接続
  - NF2.2: SQL 実行のインフラレベル防御（read-only ロールで全書き込み操作を DB レベルで拒否）
  - AC8: `COPY ... TO PROGRAM` を送信すると PostgreSQL がエラーを返す（read-only ロール）
  - AC7: SELECT は正常動作、DELETE 等はエラー
- 防御レイヤー: NF2.1 レイヤー5（インフラ境界）の一部

## 背景

現在の実装では以下の防御が存在する:

1. **アプリ側ブラックリスト**: `sql_handlers.py` の `BLOCKED_COMMANDS` で DELETE, ALTER, GRANT 等を拒否
2. **セッション READ_ONLY**: `_execute_sql_sync` 内で `SET default_transaction_read_only = ON` を設定

しかし以下の問題がある:

- `_execute_non_select_sync` では `default_transaction_read_only` を設定していない（INSERT, UPDATE, CREATE TEMP TABLE 等を許可するため）
- ブラックリストをすり抜ける SQL（例: `COPY ... TO PROGRAM`）が実行可能
- DB レベルのロール権限による防御が未実装

### 実装手順

#### Step 1: `00-create-roles.sql` を作成

`postgres/init/00-create-roles.sql` を作成する。Docker の `/docker-entrypoint-initdb.d/` はファイル名のアルファベット順で実行されるため、`01-init-db.sh` より前に実行される。

```sql
-- jupyter_readonly ロール作成
-- DATA_ENV に関係なく、DB 初期化時に1回だけ実行される

DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'jupyter_readonly') THEN
        CREATE ROLE jupyter_readonly WITH LOGIN PASSWORD :'POSTGRES_READONLY_PASSWORD';
    END IF;
END
$$;

-- 基本権限
GRANT CONNECT ON DATABASE analysis_db TO jupyter_readonly;

-- デフォルト権限（将来作成されるテーブルにも SELECT を自動付与）
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO jupyter_readonly;

-- TEMP TABLE 作成を許可（分析用の一時テーブル）
GRANT TEMPORARY ON DATABASE analysis_db TO jupyter_readonly;
```

**ロール権限の設計:**

| 操作 | 許可/拒否 | 理由 |
|------|----------|------|
| `SELECT` | 許可 | データ参照（主用途） |
| `CREATE TEMP TABLE` | 許可 | 分析用の一時テーブル |
| `INSERT`, `UPDATE`, `DELETE` | 拒否 | 書き込み操作は不要 |
| `CREATE TABLE`（永続） | 拒否 | スキーマ変更は不要 |
| `ALTER`, `DROP` | 拒否 | スキーマ変更は不要 |
| `GRANT`, `REVOKE` | 拒否 | 権限操作は不要 |
| `COPY ... TO PROGRAM` | 拒否 | スーパーユーザーのみ実行可能 |
| `CREATE FUNCTION` | 拒否 | 関数作成は不要（ブラックリストでは許可しているが、ロール権限で拒否） |

> **注意:** `CREATE OR REPLACE FUNCTION` と `DROP TABLE/FUNCTION` はアプリ側ブラックリストでは許可しているが、`jupyter_readonly` ロールには `CREATE` / `DROP` 権限を付与しないため、DB レベルで拒否される。要件定義の F7.1 ではこれらを「許可」としているが、read-only ロール導入後は実質的に DB が拒否する形となる。アプリ側のブラックリスト分類（`_classify_create`, `_classify_drop`）はそのまま維持し、ユーザーへのエラーメッセージの明確化のために残す。

#### Step 2: `01-init-db.sh` を更新

ロール作成スクリプト（`00-create-roles.sql`）は Docker が自動実行するため、`01-init-db.sh` での変更は最小限:

- テーブル作成後に `GRANT SELECT ON ALL TABLES IN SCHEMA public TO jupyter_readonly;` を実行

```bash
# テーブル作成後に権限付与
echo "--- Granting SELECT to jupyter_readonly ---"
psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" \
  -c "GRANT SELECT ON ALL TABLES IN SCHEMA public TO jupyter_readonly;"
```

#### Step 3: `docker-compose.yml` を更新

```yaml
postgres:
  environment:
    - POSTGRES_READONLY_PASSWORD=${POSTGRES_READONLY_PASSWORD}

jupyter-server:
  environment:
    - DATABASE_URL=postgresql://jupyter_readonly:${POSTGRES_READONLY_PASSWORD}@postgres:5432/${POSTGRES_DB:-analysis_db}
```

**ポイント:**
- `POSTGRES_USER`（`jupyter`）はデータロード用にスーパーユーザーとして維持
- `jupyter-server` の `DATABASE_URL` のみ `jupyter_readonly` に変更
- `POSTGRES_READONLY_PASSWORD` を新規環境変数として追加

#### Step 4: `.env.example` を更新

```
POSTGRES_READONLY_PASSWORD=your-readonly-password-here
```

#### Step 5: `00-create-roles.sql` のパスワード注入

Docker の `docker-entrypoint-initdb.d/` で実行される SQL にはシェル変数を直接埋め込めないため、`01-init-db.sh` でロール作成を行う方式に変更する可能性がある。

**代替案:** `00-create-roles.sql` を `.sh` スクリプトに変更し、`psql` コマンドで SQL を実行する:

```bash
#!/bin/bash
# 00-create-roles.sh
set -euo pipefail

READONLY_PASSWORD="${POSTGRES_READONLY_PASSWORD:-readonly_password}"

psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" <<EOSQL
DO \$\$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'jupyter_readonly') THEN
        CREATE ROLE jupyter_readonly WITH LOGIN PASSWORD '${READONLY_PASSWORD}';
    END IF;
END
\$\$;

GRANT CONNECT ON DATABASE ${POSTGRES_DB} TO jupyter_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO jupyter_readonly;
GRANT TEMPORARY ON DATABASE ${POSTGRES_DB} TO jupyter_readonly;
EOSQL
```

> **決定:** `00-create-roles.sh`（シェルスクリプト）方式を採用する。SQL ファイルではパスワードの動的注入ができないため。

#### Step 6: `generate_init.py` を更新

`create-tables.sql` の末尾に権限付与文を追加する:

```sql
-- Grant SELECT on all tables to jupyter_readonly
GRANT SELECT ON ALL TABLES IN SCHEMA public TO jupyter_readonly;
```

これにより、`scripts/generate-init-scripts.sh` で再生成した場合も権限付与が含まれるようになる。

#### Step 7: `sql_handlers.py` のコメント更新

`_execute_non_select_sync` の `※ read_only は設定しない` コメントを更新し、DB ロールによる防御を明記する:

```python
# ※ セッションレベルの read_only は設定しない。
# jupyter_readonly ロール（NF2.2）により、INSERT/UPDATE/DELETE 等は
```

`jupyter-server/tests/test_readonly_role.py`:

   - `00-create-roles.sh` に `jupyter_readonly` ロール作成が含まれることを検証

### 技術的な考慮事項

- **init スクリプトの実行順序:** Docker の `/docker-entrypoint-initdb.d/` はファイル名の辞書順で実行される。`00-create-roles.sh` → `01-init-db.sh` の順で実行されることが保証される。
- **既存 volume との互換性:** 既に `postgres_data` volume が存在する場合、`docker-entrypoint-initdb.d/` は実行されない（PostgreSQL の仕様）。read-only ロールを有効にするには `scripts/clean-rebuild.sh` で volume を削除してから再構築する必要がある。これは完了条件のテスト手順に含める。
- **`CREATE TEMP TABLE` の挙動:** `GRANT TEMPORARY ON DATABASE` で一時テーブルの作成を許可する。read-only ロールでも `CREATE TEMP TABLE` は動作する。
- **`_execute_non_select_sync` への影響:** 現在 INSERT, UPDATE, BEGIN/COMMIT/ROLLBACK を許可しているが、`jupyter_readonly` ロールでは INSERT/UPDATE が DB レベルで拒否される。ブラックリストは通過するが DB でエラーになる。これは意図した動作であり、エラーメッセージは `SQL_EXECUTION_ERROR` として返される。
- **healthcheck への影響:** `pg_isready -U jupyter` はスーパーユーザーで接続するため影響なし。
- **load-data.py への影響:** データロードは `POSTGRES_USER`（`jupyter`）で実行されるため影響なし。
