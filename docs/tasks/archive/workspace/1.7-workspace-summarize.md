# タスク詳細: 1.7 ワークスペースサマリ生成

## 概要

ワークスペースの作業内容に基づいて検証レポートを生成するためのテンプレートと検証観点を提供する機能を実装する。

- `POST /api/workspaces/{workspace_id}/summarize` API でテンプレート・検証観点・指示文を返却
- `workspace_summarize` MCP ツールで上記 API を呼び出し、AI にレポート生成に必要な情報を提供
- テンプレートと検証観点はサーバー側のファイルに格納し、ツール定義（description）には含めない
- AI はレスポンスに含まれるテンプレートに従ってレポートを生成し、SUMMARY.md としてワークスペースに保存する
- 難易度評価観点はシナリオの事前属性であり、SUMMARY.md には含めない。横断サマリー時に別途提供する

### 実装手順

#### ステップ 1: テンプレートファイルの作成

`jupyter-server/templates/` ディレクトリを新設し、2つのテンプレートファイルを作成する。

1. `summary_template.md` — SUMMARY.md のマークダウンテンプレート。AI がこのテンプレートに従ってレポートを生成する
2. `verification_criteria.md` — 検証観点 A-F の定義。分析結果の品質を評価する基準

テンプレートの具体的な内容は以下の通り（20260121/20260204 定例資料に基づく）。

##### summary_template.md の内容

検証結果のサマリーテンプレート。ナラティブ（経過・所見・考察）と構造化データ（成功条件判定・検証観点評価）の2層構造とする。
難易度評価観点はタスクの事前属性であり、検証結果から逆算して記入すると情報リークとなるため、SUMMARY.md には含めない。横断サマリー時に別途提供する。

##### verification_criteria.md の内容

検証観点 A-F の定義（22項目）。各項目に説明と検証項目を含む。

```markdown
# 検証観点 A-F

検証観点は大きく6カテゴリで分類。各カテゴリごとの具体的な検証観点を以下に定義する。

## A. データ理解・処理能力

AIエージェントがデータカタログを活用してデータ構造を理解し、適切にデータを抽出・加工・結合する能力を検証する。
データ分析の基礎となる部分。ここが不十分だと後続の分析が全て誤った結果になる可能性がある。

### A1. データカタログの活用・理解

データカタログから必要な情報を適切に検索・取得し、テーブル構造やカラムの意味を正しく理解できる。

検証項目:
- データカタログの検索キーワードが適切か
- 必要なテーブルを正しく特定できるか
- カラムの意味や型を正しく理解しているか
- テーブル間の関係性（リレーション）を把握できるか

### A2. データ抽出・結合

複数テーブルからデータを抽出し、適切なキーで結合できる。

検証項目:
- 必要なテーブルを過不足なく選択できるか
- 適切な結合キーを選択できるか（会員番号、店舗コード等）
- 結合方法（inner/left/outer）を正しく選択できるか
- 結合後のデータ件数の妥当性を確認できるか

### A3. データクレンジング・前処理

欠損値、異常値、重複データなどを適切に処理し、分析可能な状態にデータを整形できる。

検証項目:
- 欠損値を検出し、適切に処理（除外/補完）できるか
- 異常値・外れ値を検出し、対処できるか
- 重複レコードを検出・処理できるか
- データ型の変換（文字列→日付、カテゴリ化等）が適切か

### A4. 特徴量エンジニアリング

分析目的に応じた新しい変数や集計値を作成できる。

検証項目:
- 日付から期間（年月、曜日等）を抽出できるか
- 顧客セグメント、購買区分などのカテゴリ変数を作成できるか
- 集計指標（合計、平均、構成比等）を正しく計算できるか
- 複数条件での絞り込み・フラグ作成が適切か

## B. ドメイン知識の理解

森ビル特有の情報（業務用語、ビジネス背景など）をAIエージェントが正しく理解し、適用する能力を検証する。
汎用的なデータ分析能力だけでなく、森ビルのビジネス特性を理解したデータ分析が求められる。

### B1. 森ビル特有用語の理解

スターランク、OTAC、会期、稼働率など森ビル特有の用語を正しく理解し使用できる。

検証項目:
- 森ビル特有の用語を正しく解釈できるか
- 用語に対応するデータ項目を正しく特定できるか
- 用語の定義に基づいた計算・集計ができるか
- 類似用語（ランク/ステージ等）を混同していないか

### B2. 業務ルール・計算ロジックの理解

OTAC洗い替え、稼働率計算、会期設定など森ビル特有の業務ルールを正しく適用できる。

検証項目:
- OTAC洗い替え処理を正しく実装できるか
- 稼働率の定義に基づいて正確に計算できるか
- 会期の考え方（開始日・終了日、ズレ等）を理解しているか
- 館ごとの特性や違いを考慮できるか

### B3. ビジネス文脈の理解

施策の目的、顧客行動の背景など、ビジネス文脈を理解した上で分析できる。

検証項目:
- 施策の目的や期待効果を理解しているか
- 顧客の購買行動パターンの意味を理解しているか
- 館回遊、買い控えなどの概念を適切に扱えるか
- 季節性、イベント、外部要因の影響を考慮できるか

## C. コード生成・実行能力

Pythonコードを正確に記述・実行し、実行結果を適切に取得する能力を検証する。
AIエージェントのデータ分析実行におけるエンジン部分。コードが動かなければデータ分析ができない。

### C1. Pythonコードの正確性

文法的に正しく、意図通りに動作するPythonコードを生成できる。

検証項目:
- 構文エラーがないか
- ライブラリのインポートが適切か
- 変数名・関数名が適切で可読性が高いか
- インデント、コメントなどコードの品質が高いか

### C2. Pandas/NumPyの適切な利用

データ操作に必要なPandas/NumPyの機能を正しく使用できる。

検証項目:
- DataFrameの操作（filter, groupby, merge等）が適切か
- ベクトル化演算を活用し、効率的に処理できるか
- 日付・時系列データの処理が正確か
- 欠損値処理（isna, fillna, dropna等）が適切か

### C3. データ可視化の実装

matplotlib/seaborn等を用いて適切なグラフを生成できる。

検証項目:
- データの性質に応じた適切なグラフ種別を選択できるか
- 軸ラベル、タイトル、凡例が適切に設定されているか
- 複数グラフの配置（subplot）が適切か
- グラフが見やすく、解釈しやすいか

## D. 分析設計能力

ユーザーの要求から論点を整理し、適切な分析手法を選択・設計し、段階的に実行する能力を検証する。
「何をするべきか」を決める部分。設計が悪いと意味のない結果しか得られない。

### D1. 要件から分析観点への変換

ユーザーの曖昧な要求から、具体的な分析観点・論点を整理できる。

検証項目:
- 要求の背景や目的を理解しているか
- 分析すべき論点を適切に構造化できるか
- 必要な比較軸・切り口を特定できるか
- 分析の優先順位を判断できるか

### D2. 適切な分析手法の選択

分析目的に応じて、基礎集計、比較分析、統計検定、予測モデル等の適切な手法を選択できる。

検証項目:
- 目的（記述/比較/検証/予測）に応じた手法を選択できるか
- 集計レベル（全体/セグメント別等）が適切か
- 比較対象（ベースライン）の設定が妥当か
- 統計手法の前提条件を理解し、適用可否を判断できるか

### D3. 仮説設定と検証設計

データ分析の前に検証すべき仮説を設定し、検証方法を設計できる。

検証項目:
- 検証可能な仮説を設定できるか
- 仮説を検証するために必要なデータを特定できるか
- 対照群の設定など、検証設計が適切か
- 交絡因子や外部要因を考慮できるか

### D4. 段階的な分析の実行

全体→詳細、単純→複雑というように、段階的に分析を深掘りできる。

検証項目:
- まず全体像を把握してから詳細に入るアプローチをとれるか
- 異常値や特徴的な点を発見し、深掘り分析できるか
- 分析の途中結果を確認しながら進められるか
- 分析の方向性を柔軟に修正できるか

## E. 結果解釈・示唆出し

分析結果を正確に解釈し、そこからパターンなどの傾向を見出し、ビジネス上の示唆を導出する能力を検証する。
結果を読み解く部分。結果が出てもその意味が分からなければ価値がない。

### E1. 統計指標の正確な解釈

平均値、中央値、標準偏差、相関係数などの統計指標を正しく解釈できる。

検証項目:
- 基本統計量（平均、中央値、分散等）の意味を理解しているか
- 構成比、前年比、増減率などの計算が正確か
- 統計的有意性を適切に評価できるか
- 相関と因果の違いを理解しているか

### E2. データパターンの発見

データから傾向、パターン、異常値を発見し、意味づけができる。

検証項目:
- 時系列トレンドや季節性を発見できるか
- セグメント間の差異を発見できるか
- 異常値や外れ値を発見し、その意味を考察できるか
- 複数指標の関係性を発見できるか

### E3. ビジネス示唆の導出

分析結果からビジネス上の示唆やactionableな提言を導出できる。

検証項目:
- 分析結果をビジネス文脈で解釈できるか
- 「なぜそうなったのか」の要因を考察できるか
- 「今後どうすべきか」の示唆を提示できるか
- 提言が具体的で実行可能か

### E4. 結果の妥当性確認

分析結果の妥当性を多角的に検証し、誤りや偏りを検出できる。

検証項目:
- 計算結果の桁数やオーダーが妥当か確認しているか
- 合計値の整合性を確認しているか
- サンプルサイズが十分か確認しているか
- 結果が常識的に妥当か（センスチェック）を行っているか

## F. 対話・要件整理

ユーザーとの対話を通じて要件を明確化し、分析スコープを調整し、修正に柔軟に対応する能力を検証する。
ユーザーとAIエージェントの協働部分。一方通行的な分析過程ではなく、対話を通じて最適な結果に導くために必要な能力。

### F1. 不明点の確認・逆質問

要件が不明確な場合、適切な質問でユーザーから必要な情報を引き出せる。

検証項目:
- 要件の曖昧さを検出できるか
- 必要な情報を特定し、質問できるか
- 質問が具体的で答えやすいか
- 質問のタイミングが適切か（早すぎず遅すぎず）

### F2. 分析スコープの調整

ユーザーと対話しながら、分析の範囲や優先度を調整できる。

検証項目:
- 分析の範囲（対象期間、顧客セグメント等）を明確にできるか
- 時間・リソースの制約を考慮し、優先順位をつけられるか
- クイックな概算と詳細分析を使い分けられるか
- 段階的な分析計画を提示できるか

### F3. 分析プロセスの説明

分析の進め方や途中経過をユーザーに分かりやすく説明できる。

検証項目:
- 分析の全体像や手順を説明できるか
- 途中経過や中間結果を適切に共有できるか
- 専門用語を使いすぎず、平易に説明できるか
- 分析の限界や前提条件を明示できるか

### F4. 修正・再実行への対応

ユーザーからのフィードバックに基づき、柔軟に分析を修正・再実行できる。

検証項目:
- フィードバックの意図を正しく理解できるか
- 過去の分析結果を活用し、効率的に修正できるか
- 複数回の試行錯誤に耐えられるか
- 前回との差分を明確に説明できるか
```

#### ステップ 2: jupyter-server — POST /api/workspaces/{workspace_id}/summarize

`workspace_handlers.py` に `WorkspaceSummarizeHandler` クラスを追加：

1. `post(self, workspace_id)` メソッドを実装
2. `validate_workspace_id(workspace_id)` でバリデーション
3. `resolve_workspace_dir(workspace_id)` でワークスペースの存在確認（metadata.json の存在チェック）
4. 存在しない場合は 404 エラー
5. `templates/` ディレクトリからテンプレートファイルを読み込む
6. レスポンス: `{ workspace_id, template, verification_criteria, instructions }`
7. テンプレートファイルが見つからない場合は 500 エラー（INTERNAL_ERROR）

`handlers.py` にルート登録：
- `(f"{base_url}/api/workspaces/([^/]+)/summarize", WorkspaceSummarizeHandler)` を `WorkspaceHandler` の前に配置（`/summarize` が `([^/]+)` にマッチしないよう、より具体的なパスを先に登録）

### 技術的な考慮事項

- **テンプレートファイルの配置**: `jupyter-server/templates/` に配置し、Docker ビルド時にコンテナ内にコピーする。Dockerfile の COPY 対象に `templates/` を追加する必要がある
- **テンプレートファイルの読み込み**: サーバー起動時に1回読み込んでキャッシュするか、リクエスト毎に読み込むか。テンプレートは頻繁に変わらないため、起動時キャッシュが効率的だが、実装の単純さを優先してリクエスト毎の読み込みとする（ファイルサイズは小さいため性能影響は無視できる）
- **ルート順序**: Tornado のルートは先勝ちのため、`/api/workspaces/([^/]+)/summarize` を `/api/workspaces/([^/]+)` より前に配置する必要がある
- **リクエストボディ**: API 仕様ではリクエストボディなし（POST だがパラメータ不要）。workspace_id はパスパラメータのみ
- **テンプレートの内容**: 20260121/20260204 定例資料に基づく検証フロー・検証観点・難易度評価観点を反映した内容。ファイルベースで管理し、ユーザーが更新可能
- **instructions フィールド**: API レスポンスの `instructions` には検証レポート作成手順の指示文を記載する。具体的な文言はサーバー側テンプレートで管理する
