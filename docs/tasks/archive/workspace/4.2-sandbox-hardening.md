# タスク詳細: 4.2 sandbox 強化（二重防御）

## 概要

`workspace_sandbox.py` の `generate_sandbox_code()` に monkey patch を追加し、カーネル内でのシェルコマンド実行（`os.system`, `subprocess.run` 等）を実行時にブロックする。これはタスク 4.1（AST 解析 + ホワイトリスト検査）の「保険」として機能するレイヤー3の防御であり、AST 検査をすり抜けた場合でもカーネル内で実行時エラーとなる。

- 要件定義: `docs/requirements/jupyter-server.md` の「NF2.1: シェルコマンド実行の阻止」セクション（レイヤー3: sandbox 強化）
- 要件定義: `docs/requirements/jupyter-server.md` の「AC8: シェルコマンド実行阻止」（AC8 の sandbox monkey patch 関連項目）
- API仕様: `docs/design/api-contracts.md` の「POST /api/kernels/{kernel_id}/execute」セクション（コード実行 API）

### 実装手順

#### Step 1: `workspace_sandbox.py` に monkey patch を追加

`generate_sandbox_code()` が生成する Python コード（`_setup_workspace_sandbox()` 関数内）に、以下の monkey patch を追加する。既存のファイルアクセス制限（`builtins.open`, `os.chdir`, `pathlib.Path.*`）の後に追記する。

**1.1 os モジュールの危険関数をブロック**

`os.system`, `os.popen`, `os.exec*`, `os.spawn*`, `os.posix_spawn*` を monkey patch でブロックする。

**1.2 subprocess モジュールをブロック**

`subprocess.Popen`, `subprocess.run`, `subprocess.call`, `subprocess.check_output`, `subprocess.check_call` をブロックする。

**1.3 asyncio のサブプロセス関数をブロック**

`asyncio.create_subprocess_exec`, `asyncio.create_subprocess_shell` をブロックする。

詳細な実装は `workspace_sandbox.py` の `_setup_workspace_sandbox()` を参照。

**設計判断:**
- `_blocked()` は `PermissionError` を送出する。既存のファイルアクセス制限と同じ例外クラスを使うことで、エラーハンドリングの一貫性を保つ。
- `setattr` + ループで `os.exec*`, `os.spawn*` をまとめて処理する。個々の関数名を列挙するのは冗長だが、monkey patch 対象を明示的にするため列挙方式を採用する。
- `subprocess` と `asyncio` は `import` で明示的にロードする。カーネル起動時点ではこれらのモジュールが未ロードの可能性があるが、monkey patch 時に import しておくことで、後から `import subprocess` した際にも既にパッチ済みのモジュールオブジェクトが `sys.modules` から返される。

#### Step 2: 安全な os 関数が引き続き使えることを確認

monkey patch は `os.system`, `os.popen`, `os.exec*`, `os.spawn*`, `os.posix_spawn*` のみを対象とし、以下の安全な関数には影響を与えないことを確認する:
- `os.path.join()`, `os.path.exists()`, `os.path.dirname()` 等
- `os.getcwd()`, `os.listdir()`, `os.makedirs()`, `os.stat()`
- `os.environ`（環境変数の読み取り）

#### Step 3: テスト作成（`test_workspace_sandbox.py`）

`test_sql_handlers.py` のモジュール直接ロード方式に倣い、重い依存（tornado 等）をモックして `workspace_sandbox.py` を直接テストする。

テストでは `generate_sandbox_code()` が返すコードを `exec()` で実行し、monkey patch が正しく設定されていることを検証する。

### 技術的な考慮事項

- **monkey patch のタイミング**: sandbox コードはカーネル起動直後に `KernelExecutor.execute()` で注入される（`session_handlers.py` L124-125）。カーネルの `user_ns` で実行されるため、`import os` で得られるモジュールオブジェクトは monkey patch 済みのものとなる。
- **`sys.modules` 経由の迂回防止**: `import subprocess` は `sys.modules` を参照するため、sandbox コード内で先に `import subprocess` してパッチすれば、後続の `import subprocess` でもパッチ済みオブジェクトが返る。ただし `importlib.reload(subprocess)` で再ロードされた場合はパッチが消える。これは AST 検査（レイヤー1）で `importlib` をブロックすることでカバーする。
- **`os` モジュールの参照**: sandbox コードは `import os as _os` で `os` モジュールを取得し、その属性を上書きする。カーネル内で `import os` した場合も同じモジュールオブジェクトを参照するため、パッチが有効。
- **既存のファイルアクセス制限との共存**: 既存の `builtins.open`, `os.chdir`, `pathlib.Path.*` の monkey patch と干渉しない。同じ `_setup_workspace_sandbox()` 関数内に追記するため、スコープも同一。
- **`_blocked()` のエラーメッセージ**: 関数名を含めたメッセージ（例: `os.system() is blocked for security reasons`）を返す。デバッグ時にどの関数がブロックされたか特定しやすい。
- **パフォーマンス**: monkey patch は関数参照の上書きのみであり、カーネル起動時に1回実行されるだけ。通常のデータ分析コードへの影響はない。

## テスト計画

### 単体テスト（`test_workspace_sandbox.py`）

`test_sql_handlers.py` と同じモジュール直接ロード方式を使用。`generate_sandbox_code()` の戻り値を `exec()` で実行し、monkey patch の動作を検証する。

**ブロックされるケース（PermissionError が送出される）:**
- `os.system("ls")`
- `os.popen("ls")`
- `os.execvp("ls", ["ls"])`（exec* 系の代表）
- `os.spawnlp(os.P_WAIT, "ls", "ls")`（spawn* 系の代表）
- `subprocess.run(["ls"])`
- `subprocess.Popen(["ls"])`
- `subprocess.call(["ls"])`
- `subprocess.check_output(["ls"])`
- `subprocess.check_call(["ls"])`
- `asyncio.create_subprocess_exec("ls")`
- `asyncio.create_subprocess_shell("ls")`

**許可されるケース（正常に動作する）:**
- `os.path.join("a", "b")` -> `"a/b"`
- `os.path.exists("/tmp")`
- `os.getcwd()`
- `os.environ.get("HOME")`
- `os.listdir(".")`

**既存機能の回帰テスト:**
- ワークスペース外へのファイルアクセスが引き続き `PermissionError` になる
- ワークスペース内へのファイルアクセスが正常に動作する

Docker 環境で実際にカーネルを起動し、`POST /api/kernels/{id}/execute` で `os.system("ls")` を実行してブロックされることを確認する。
