# タスク詳細: 4.1 AST 解析 + ホワイトリスト検査（主防御）

## 概要

`POST /api/kernels/{id}/execute` に送信されたコードをカーネルに渡す前に、Python の `ast` モジュールで静的解析を行い、データ分析に不要な危険モジュール・関数の使用をブロックする。ホワイトリスト方式でインポートを制限し、危険パターン（`eval` に動的引数、`__import__()` 呼び出し等）を検出する。

これはシェルコマンド実行阻止の多層防御におけるレイヤー1（主防御）であり、MCP 経由・curl 直接アクセスの両方がこの検査を通る。

### 実装手順

#### Step 1: `code_validator.py` を新規作成

`workspace_sandbox.py` や `sql_handlers.py` の設計パターンに倣い、独立したモジュールとして実装する。

**1.1 ホワイトリスト定義**

データ分析に必要なモジュール（pandas, numpy, matplotlib 等）のみ許可するホワイトリストを定義する。`os` モジュールは `os.path` 等の安全な属性のみ許可する特別扱い。詳細は `code_validator.py` の `ALLOWED_MODULES` / `ALLOWED_OS_ATTRIBUTES` を参照。

**1.2 AST 解析ロジック**

`validate_code(code: str) -> CodeValidationResult` 関数を実装する。

- `ast.parse(code)` でパースし、パースエラー時は IPython マジック（`!command`）の可能性をチェック
- `ast.walk()` で全ノードを走査し、以下を検査:
  - **`ast.Import` / `ast.ImportFrom`**: モジュール名がホワイトリストに含まれるか
  - **`ast.Call`**: `eval()`, `exec()`, `__import__()`, `getattr()` に動的引数がないか
  - **`ast.Attribute`**: `__subclasses__`, `__bases__`, `__mro__`, `__globals__`, `__builtins__` 等の危険属性アクセスがないか
  - **`ast.Attribute`** (os 関連): `os.system`, `os.popen`, `os.exec*`, `os.spawn*` 等の呼び出しがないか
  - **`ast.Call`**: `gc.get_objects()`, `sys.modules` 操作の検出
  - **`ast.Call`**: `get_ipython().system()` 等の IPython API 呼び出しの検出

**1.3 戻り値の型**

```python
@dataclasses.dataclass
class CodeValidationResult:
    valid: bool
    error: str | None = None  # 拒否理由（人間が読めるメッセージ）
    blocked_item: str | None = None  # 拒否されたモジュール名/関数名
```

#### Step 2: `handlers.py` の `KernelExecuteHandler.post()` を変更

### 技術的な考慮事項

- **`ast.parse` の失敗ケース**: IPython マジック（`!ls`, `%%bash`）は有効な Python ではないため `ast.parse` で `SyntaxError` になる。これを検出して「IPython マジックコマンドは許可されていません」というエラーメッセージを返す。
- **`os` モジュールの特別扱い**: `import os` 自体は許可するが、`os.system()` 等の危険な属性アクセスは拒否する。`from os import path` は許可、`from os import system` は拒否。
- **動的引数の判定**: `eval("pandas")` のような文字列リテラル引数は安全だが、実装の簡潔さを優先し、`eval` / `exec` / `getattr` / `__import__` は引数の種類によらず一律拒否する。要件定義にも「eval/exec に動的引数」とあるが、静的引数でも `eval` の正当な用途はデータ分析において限定的であり、一律拒否が安全。
- **空文字列の扱い**: 空コードは既存の `KernelExecuteHandler` で許可されている（何もしないだけ）。AST 検査では空文字列を有効として扱う（`ast.parse("")` は成功する）。
- **エラーコード**: 新しいエラーコード `CODE_NOT_ALLOWED` を使用する。既存の `SQL_NOT_ALLOWED` と命名規則を揃える。
- **パフォーマンス**: `ast.parse` + `ast.walk` は O(n) で高速。1MB 上限のコードでも数ミリ秒で完了する見込み。

### 単体テスト（`test_code_validator.py`）

`test_sql_handlers.py` と同じモジュール直接ロード方式を使用。

**許可されるコード（正常系）:**

- `from matplotlib import pyplot as plt`
- `import os; os.path.join('a', 'b')`
- `from os.path import join`
- `import json, re, math`
- `df = pd.DataFrame({'a': [1,2,3]})`
- `print("hello")`（import なしのコード）
- 空文字列

**拒否されるコード（異常系 - インポート）:**
- `import subprocess`
- `import ctypes`
- `import cffi`
- `import pty`
- `import multiprocessing`
- `from subprocess import run`
- `import shutil`（ファイル操作）
- `import socket`（ネットワーク）
- `import http`（ネットワーク）

**拒否されるコード（異常系 - os 関連）:**
- `import os; os.system('ls')`
- `import os; os.popen('ls')`
- `from os import system`
- `from os import popen`

**拒否されるコード（異常系 - 危険パターン）:**
- `eval("something")`
- `exec("something")`
- `__import__('subprocess')`
- `getattr(os, 'system')('ls')`
- `x.__subclasses__()`
- `x.__bases__`
- `gc.get_objects()`
- `sys.modules['subprocess']`

**拒否されるコード（異常系 - IPython マジック）:**
- `!ls`（SyntaxError で検出）
- `get_ipython().system('ls')`（AST で検出）
