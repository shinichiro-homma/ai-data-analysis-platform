# タスク詳細: 4.3 IPython シェルマジック無効化（二重防御）

## 概要

カーネル起動時に IPython のシェルマジックおよび関連メソッドを無効化し、`!command` 構文や `%%bash` セルマジック経由でのシェルコマンド実行をブロックする。これはレイヤー1（AST 検査）の保険として機能するレイヤー4の防御であり、AST 検査をすり抜けた場合でもカーネル内で実行時エラーとなる。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-server.md` の「NF2.1: シェルコマンド実行の阻止」セクション（レイヤー4: IPython シェルマジック無効化）
- 要件定義: `docs/requirements/jupyter-server.md` の「AC8: シェルコマンド実行阻止」（`get_ipython().system('ls')` の項目）
- 既存実装: `jupyter-server/extensions/custom_api/workspace_sandbox.py`（レイヤー3 sandbox 強化、monkey patch パターンの参考）

## 無効化対象（NF2.1 レイヤー4 より）

シェルマジック（`!command`, `%%bash` 等）および `get_ipython().system()` 等のシェル実行メソッドを無効化する。詳細は `workspace_sandbox.py` を参照。

### 実装手順

#### Step 1: `workspace_sandbox.py` に IPython マジック無効化コードを追加

`generate_sandbox_code()` が生成する `_setup_workspace_sandbox()` 関数内に、既存のシェルコマンドブロック（レイヤー3）の後に以下のコードを追記する。

**1.1 InteractiveShell のシェル実行メソッドを上書き**

`get_ipython()` で取得した InteractiveShell インスタンスの `system`, `system_raw`, `system_piped`, `getoutput` を `PermissionError` を送出する関数に上書きする。加えて、`magics_manager.magics` 辞書からシェル関連のセルマジック・ラインマジックを削除する。詳細は `workspace_sandbox.py` を参照。

**1.2 設計判断:**

- `get_ipython()` はカーネルの `user_ns` で実行される場合にのみ利用可能。sandbox コードはセッション作成時に `KernelExecutor.execute()` で注入されるため（`session_handlers.py` L124-125）、`get_ipython()` が利用可能であることが保証される。
- `try/except NameError` で `get_ipython()` が存在しない環境（テスト環境等）でもエラーにならないようにする。
- マジックの削除は `magics_manager.magics` 辞書から直接削除する。`unregister_magic()` メソッドは IPython に存在しないため、辞書操作が正しいアプローチ。
- `%sx` は `%system` の別名（alias）であり、同様にシェルコマンドを実行するため削除対象に含める。
- `InteractiveShell.system` / `system_raw` / `system_piped` の上書きにより、`!command` 構文は実行時に `PermissionError` を送出する。`!command` は IPython が内部で `ip.system()` に変換するため、メソッドの上書きだけで無効化できる。

#### Step 2: テスト作成（`test_ipython_magic_disable.py`）

テストでは IPython の `InteractiveShell` を実際にインスタンス化し、sandbox コードを実行して無効化が正しく動作することを検証する。

ただし、テスト環境（pytest）では `get_ipython()` がカーネル内と同じ動作をしない可能性がある。以下の2つの戦略を組み合わせる:

**戦略A: コード文字列の内容検証**
`generate_sandbox_code()` の出力に必要なパッチコードが含まれていることを文字列検査で確認する。

**戦略B: IPython InteractiveShell を使った動作テスト**
`IPython.core.interactiveshell.InteractiveShell.instance()` を使ってシェルを作成し、sandbox コードを `run_cell()` で実行してから、マジックの無効化を検証する。

### 技術的な考慮事項

- **`get_ipython()` の可用性**: sandbox コードは `KernelExecutor.execute()` 経由でカーネル内で実行される。カーネルの `user_ns` には `get_ipython` が自動的に挿入されている。テスト環境では `IPython.core.interactiveshell.InteractiveShell` を手動でセットアップする必要がある。
- **マジック再登録の防止**: `%load_ext` で外部拡張をロードした場合にマジックが再登録される可能性がある。ただし AST 検査（レイヤー1）で `%load_ext` に相当する `get_ipython().run_line_magic('load_ext', ...)` はブロックされるため、実質的なリスクは低い。
- **既存の sandbox（レイヤー3）との共存**: レイヤー3（`os.system`, `subprocess` 等の monkey patch）とレイヤー4（IPython マジック無効化）は独立して機能する。`!command` は IPython が `ip.system()` → `os.system()` の順で呼び出すため、レイヤー4がブロックすればレイヤー3には到達しない。両方が有効な場合はレイヤー4が先にブロックする。
- **パフォーマンス**: マジック辞書からの削除と関数参照の上書きのみ。カーネル起動時に1回実行されるだけで、通常のコード実行には影響しない。
- **`%%!` セルマジック**: IPython には `%%!` という形式はないが、`!command` は行単位で処理されるため `ip.system()` の上書きでカバーされる。

## テスト計画

### 単体テスト（`test_ipython_magic_disable.py`）

**コード文字列の内容検証:**
- `generate_sandbox_code()` の出力に `system_raw` が含まれる
- `generate_sandbox_code()` の出力に `magics_manager` が含まれる
- `generate_sandbox_code()` の出力に `%%bash` 削除用の `"bash"` が含まれる

**IPython InteractiveShell を使った動作テスト（利用可能な場合）:**

ブロックされるケース（PermissionError が送出される）:
- `ip.system("echo hello")` - InteractiveShell.system
- `ip.system_raw("echo hello")` - system_raw
- `ip.system_piped("echo hello")` - system_piped
- `ip.getoutput("echo hello")` - getoutput
- `ip.run_cell("!echo hello")` - シェルマジック構文
- `ip.run_cell("%%bash\necho hello")` の実行がエラーになる（マジック未登録）

許可されるケース（正常に動作する）:
- `ip.run_cell("import pandas as pd")` - 通常の import
- `ip.run_cell("x = 1 + 1")` - 通常の計算
- `ip.run_cell("%who")` - 安全なマジックは引き続き使える

Docker 環境で実際にカーネルを起動し、`POST /api/kernels/{id}/execute` で `get_ipython().system('ls')` を実行してブロックされることを確認する（AC8 の該当項目）。
