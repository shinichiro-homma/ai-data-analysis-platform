# タスク詳細: 1.8 カタログ・用語集・ロジックの結合テスト

## 概要

Phase 1 で実装した全機能（1.1〜1.7: PostgreSQL環境構築、document-server API、document-mcp MCPツール）が連携して正しく動作することを結合テストで検証する。

テストは「AIエージェントが実際に行う分析フロー」を再現する:
1. **コンテキスト参照**: document-mcp のMCPツールで、テーブル構造・用語定義・既存ロジックを取得
2. **分析コード構築**: 取得したコンテキスト情報に基づいて分析用Pythonコードを構築
3. **Jupyter実行**: jupyter-mcp（jupyter-server REST API）でコードを実行し、結果を検証

これにより、3種類のコンテキスト情報（カタログ・用語集・ロジック）が正しくAIに提供され、分析実行まで一気通貫で動作することを保証する。

### 実装手順

#### ステップ 1: 結合テスト基盤の整備

`document-mcp/vitest.config.integration.ts` を作成する。jupyter-mcp の既存設定（`vitest.config.integration.ts`）をベースに以下を設定:
- `testTimeout: 30000`（30秒）
- `include: ['tests/integration/**/*.test.ts']`
- `singleFork: true`（テストの直列実行）
- `dotenv` 対応（環境変数読み込み）

`document-mcp/package.json` に `test:integration` スクリプトを追加:
```json
"test:integration": "vitest run --config vitest.config.integration.ts"
```

#### ステップ 2: Jupyter ヘルパーの作成

`document-mcp/tests/integration/helpers/jupyter-helper.ts` を作成する。
jupyter-server REST API を直接呼び出す軽量ヘルパー:
- `createWorkspace(name)`: `POST /api/workspaces` でワークスペース作成
- `createSession(workspaceId)`: `POST /api/sessions` でカーネルセッション作成
- `executeCode(kernelId, code, timeout?)`: `POST /api/kernels/{id}/execute` でコード実行
- `deleteSession(sessionId)`: `DELETE /api/sessions/{id}` でセッション削除
- `deleteWorkspace(workspaceId)`: ワークスペースのファイル削除
- `checkConnection()`: jupyter-server への接続確認

**設計判断**: jupyter-mcp の `handleToolCall` を直接インポートする代わりに、jupyter-server REST API を直接呼ぶ。理由:
- クロスパッケージインポートの複雑性を回避
- document-mcp の結合テストとして自己完結
- 実際の統合動作を検証（REST API レベル）

#### ステップ 3: テストケース実装

`document-mcp/tests/integration/catalog-integration.test.ts` に以下のテストケースを実装する。

### テストケース一覧

#### 1. カタログ参照フロー（get_table_index → get_table_detail）

```
get_table_index → テーブル一覧を取得（id_pos_transactions, customer_master）
→ get_table_detail(["id_pos_transactions"]) → カラム定義・データソース情報を取得
→ カラム名（customer_id, amount 等）が含まれることを検証
```

検証ポイント:
- インデックスに `total` と `tables` 配列が含まれる
- 詳細にカラム定義（name, type, description）が含まれる
- `key_type` による外部キー情報が含まれる

#### 2. 用語集参照フロー（get_term_index → get_term_detail）

```
get_term_index → 用語一覧を取得（ロイヤルティランク, 統合会員ID, 店舗）
→ get_term_detail(["ロイヤルティランク"]) → 用語の定義・エイリアス・関連用語を取得
→ related_terms に「統合会員ID」が含まれることを検証
→ get_term_detail(["統合会員ID"]) → 関連用語を再帰的に解決（参照フロー Phase 1）
```

検証ポイント:
- インデックスに `total` と `terms` 配列が含まれる
- 詳細に `definition`, `aliases`, `related_terms` が含まれる
- 関連用語の再帰的解決が可能（用語A → related_terms → 用語B を辿れる）

#### 3. ロジック参照フロー（get_logic_index → get_logic_detail → get_logic_code）

```
get_logic_index → ロジック一覧を取得（member_id_remapping, sales_basic_aggregation）
→ get_logic_detail(["sales_basic_aggregation"]) → メタ情報取得
→ input_tables に ["id_pos_transactions", "customer_master"] が含まれることを検証
→ get_logic_code("sales_basic_aggregation") → Pythonコード取得
→ コードに "def aggregate_sales" が含まれることを検証
```

検証ポイント:
- インデックスに `total` と `logic` 配列が含まれる
- メタ情報に `language`, `usage_type`, `input_tables`, `output_description` が含まれる
- コード取得で実際のPythonコードが返される

#### 4. 一括取得と部分エラー

```
get_table_detail(["id_pos_transactions", "存在しないテーブル"])
→ tables に id_pos_transactions の詳細が含まれる
→ not_found に "存在しないテーブル" が含まれる
```

同様のパターンを用語集・ロジックでも検証:
- `get_term_detail(["ロイヤルティランク", "存在しない用語"])`
- `get_logic_detail(["sales_basic_aggregation", "存在しないロジック"])`

#### 5. E2Eフロー: コンテキスト参照→コード構築→Jupyter実行

AIエージェントが行う分析フローを完全に再現する:

```
# Phase 1: コンテキスト収集
get_table_detail(["id_pos_transactions", "customer_master"])
→ テーブルのカラム情報を取得

get_term_detail(["ロイヤルティランク"])
→ ロイヤルティランクの定義を確認

get_logic_code("sales_basic_aggregation")
→ 既存の集計ロジック（Python）を取得

# Phase 2: 分析コード構築
→ 取得したカラム情報とロジックコードを組み合わせて、
   テスト用DataFrameを作成し集計を実行するPythonコードを構築

# Phase 3: Jupyter実行
→ workspace_create → session_create → execute_code
→ 集計結果（DataFrame）が正しく返ることを検証
→ session_delete（クリーンアップ）
```

具体的な実行コード（テスト内で構築）:
```python
import pandas as pd

# テスト用データ（カタログのカラム情報に基づいて構築）
df_transactions = pd.DataFrame({
    'customer_id': ['C001', 'C001', 'C002', 'C002'],
    'store_id': ['S01', 'S01', 'S01', 'S02'],
    'amount': [1000, 2000, 1500, 3000]
})
df_customers = pd.DataFrame({
    'customer_id': ['C001', 'C002'],
    'loyalty_rank': ['Gold', 'Silver']
})

# 既存ロジック（get_logic_code で取得したコード）を参考に集計
{取得したロジックコードの関数を定義}
result = aggregate_sales(df_transactions, df_customers)
print(result.to_json())
```

検証ポイント:
- execute_code の `success` が `true`
- stdout に集計結果（JSON）が含まれる
- 集計結果に `store_id`, `loyalty_rank`, `total_amount`, `customer_count` カラムが存在

### 技術的な考慮事項

- **テストの独立性**: 各テストケースは独立して実行可能。E2Eフローテストで作成するワークスペース/セッションは afterEach でクリーンアップ
- **クロスパッケージ依存の回避**: jupyter-mcp のコードは直接インポートせず、jupyter-server REST API を axios で呼び出す。これにより document-mcp テストの自己完結性を維持
- **テストデータの前提**: document-server の `data/` ディレクトリに配置されたサンプルYAML（タスク 1.1〜1.7 で作成済み）を使用。テスト専用データの作成は不要
- **PostgreSQL不要**: E2Eフローのコード実行では、テスト用の pandas DataFrame をコード内で作成する。実際のPostgreSQLへの接続は不要（PostgreSQL統合は Phase 12 で検証）
- **環境変数**: `.env` ファイルまたは環境変数で `DOCUMENT_SERVER_URL`（デフォルト: `http://localhost:3002`）と `JUPYTER_SERVER_URL`/`JUPYTER_TOKEN` を設定
- **タイムアウト**: E2Eフローテストはカーネル起動を含むため、個別タイムアウトを 60秒 に設定

## テスト計画

### テスト実行方法

```bash
# カタログ結合テストのみ
cd document-mcp
npm run test:integration

# 既存単体テストも含めた全テスト
npm test
```

### 前提条件

- `docker-compose up -d`（jupyter-server ディレクトリ）で jupyter-server と PostgreSQL が起動していること
- document-server が起動していること（`cd document-server && uvicorn src.main:app --port 3002`）
- 環境変数が設定されていること:
  - `DOCUMENT_SERVER_URL`（デフォルト: `http://localhost:3002`）
  - `JUPYTER_SERVER_URL`（デフォルト: `http://localhost:8888`）
  - `JUPYTER_TOKEN`

### テストフレームワーク

- Vitest（既存プロジェクトの統一フレームワーク）
- `vitest.config.integration.ts` を新規作成（testTimeout: 30000ms、singleFork: true）

### 期待されるテスト数

合計 **8〜10 テスト**:
- カタログ参照: 2テスト（インデックス取得、詳細取得）
- 用語集参照: 2テスト（インデックス取得、詳細取得＋関連用語）
- ロジック参照: 2テスト（インデックス＋メタ取得、コード取得）
- 部分エラー: 1〜2テスト（一括取得時のnot_found）
- E2Eフロー: 1テスト（コンテキスト参照→コード構築→Jupyter実行）
