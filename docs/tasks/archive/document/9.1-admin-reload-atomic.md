# タスク詳細: 9.1 /admin/reload の copy-on-write アトミック化

## 概要

`/admin/reload` は現在、稼働中の `CatalogStore` インスタンスの内部辞書を in-place で順次差し替えており、(1) reload 途中に別リクエストが新旧混在状態を観測しうる、(2) `load_tables` 成功後に `load_terms` が失敗すると「テーブルだけ新データ・残りは旧データ」の部分適用状態のままエラーが返る（ロールバックなし）、という問題がある（`tmp/refactor-notes.md` §3-1）。

本タスクでは reload を copy-on-write 化する: 新しい `CatalogStore` を構築して全リソースのロードに成功した場合のみ `app.state.catalog_store` の参照を差し替える。失敗時は旧ストアが無傷で残るため、ロールバックが不要になる。並行 reload はモジュールレベルの `threading.Lock` で直列化する。

## 関連ドキュメント

- 要件定義: `docs/requirements/document-server.md` の F1.2（API 経由リロード）/ F5.1 / AC5、NF3（運用性）
- API仕様: `docs/design/api-contracts.md` の document-server エンドポイント一覧（POST /admin/reload）。レスポンス形式は成功 `{"data": ...}` / エラー `{"error": {"code", "message"}}` の共通契約を維持する（入出力の変更なし）

## 調査したファイル

- `document-server/src/routers/admin.py`: `/admin/reload` 全体（1-44 行）。同期 `def`、`Depends(get_catalog_store)` で取得した稼働中ストアに `store.load_all(DATA_DIR)`（27 行）で in-place 更新。排他制御なし。失敗時 400/500 を `error_response` で返却
- `document-server/src/catalog_loader.py`: `CatalogStore.__init__`（237-245 行、全状態は 7 つの辞書 + `_data_dir`）、`load_all`（357-363 行、tables → terms → logic を順に実行）、`load_tables`（385-405 行、構築後に `self._indexes` / `self._details` へ属性代入）。ロック類は皆無
- `document-server/src/main.py`: lifespan（24-42 行）で起動時に新規 `CatalogStore` を構築し `app.state.catalog_store` に設定。`/health`（56-68 行）は `app.state.catalog_store` を 1 回取得してから件数を読む
- `document-server/src/dependencies.py`: `get_catalog_store` はリクエストごとに `request.app.state.catalog_store` を返す（8-10 行）。参照差し替え方式と相性が良い（長命なキャッシュなし）
- `document-server/tests/conftest.py`: `client` fixture（295-305 行）は `TestClient(app)` を with なしで生成し `app.state` を直接設定 → **lifespan は実行されない**。したがってロックを lifespan で `app.state` に置くとテストで存在しなくなる（モジュールレベルに置く根拠）
- `document-server/tests/test_tables_api.py`: `test_reload_catalog`（122-131 行、HTTP 経由 reload の正常系）
- `document-server/tests/test_terms_api.py`: `test_reload_includes_terms`（127-133 行）
- `document-server/Dockerfile`: uvicorn 起動は workers 指定なし（シングルプロセス・同期エンドポイントは threadpool で並行実行）

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | copy-on-write: 新規 `CatalogStore` を構築し、`load_all` 成功時のみ `app.state.catalog_store` を差し替え。reload はモジュールレベル `threading.Lock` で直列化 | 参照差し替えは単一の属性代入で、読み手は常に完全な新旧いずれかを見る。失敗時ロールバック不要（旧ストア無傷）。読み手側（各ルーター・/health）は変更不要 | reload 中は新旧 2 ストア分のメモリを一時使用（現規模では無視できる） |
| B | in-place 更新のまま読み書きロック（RWLock）導入 | メモリ増なし | 全読み取り経路（4 ルーター + /health）にロック取得が必要で侵襲大。部分適用問題は別途ロールバック実装が必要。Python 標準に RWLock がなく自作リスク |
| C | `CatalogStore.load_all` 内で全辞書を構築後に一括代入（build-then-assign） | 変更が catalog_loader に閉じる | 7 つの属性代入はアトミックでなく混在ウィンドウが残る。並行 reload の直列化も別途必要で、A に対する利点がない |

採用理由: A は「読み手が不完全な状態を観測しない」を単一の参照代入というアトミック操作に還元でき、読み手側の変更ゼロで invariants I6 を満たせる唯一の案。

ADR 要否: 不要。状態の所有者（`app.state.catalog_store`）・API 契約・レスポンス形式は不変で、実装内部のアトミック化のみのため。

## 異常系・不変条件

- 該当する異常系:
  - **不正入力（途中失敗）**: reload 先の YAML に構文エラーがある場合、400 を返し既存 API は旧カタログを返し続ける。特に「catalog は有効・glossary が不正」の部分失敗で旧データが維持されることをテストで検証（完了条件 2）
  - **並行**: 同時に来た reload はロックで直列化され、双方成功する。reload 中の読み取りリクエストは旧または新ストアの完全な状態のみを観測する（参照差し替えのアトミック性が根拠。invariants I6 の「安全である根拠」として本計画に明記）
- 関係する不変条件:
  - **I6**: 同一ストアへの並行アクセス — reload 同士はロックで直列化、reload と読み取りの並行は「読み手はリクエスト冒頭に取得した参照を使い続け、差し替えは単一属性代入」で安全
  - **I1**: 真実の情報源は YAML ファイルであり、ストアは派生キャッシュ。書き込み経路は増やさない（維持）
  - **I3**: 対象エンドポイントは同期 `def` のため FastAPI が threadpool で実行し、イベントループは塞がない（現状維持）

### 技術的な考慮事項

- **ロックの置き場所**: conftest の `client` fixture は lifespan を実行しないため、`app.state.reload_lock` 方式はテストで `AttributeError` になる。モジュールレベル `_reload_lock` とする（アプリはプロセスに 1 つなのでモジュールレベルで十分）
- **ロックは blocking 取得**: 同時 reload は後着が待ってから自分の reload を実行する（両方 200）。reload は管理操作で頻度が低く、409 を返す複雑さに見合わない
- **ロックの役割は reload 同士の直列化のみ**: 「読み手が部分ストアを観測しない」という I6 の中核は参照差し替えのアトミック性だけで満たされる。ロックは並行 reload による無駄な二重構築と差し替え順序の交錯を防ぐためのもの。`last_reload` の更新もロック内に置くが、`/health` はロックを取らずに読むため store と last_reload の瞬間的な不一致はありうる（表示用メタデータでありスコープ外と割り切る）
- **読み手の規約**: リクエスト処理中は冒頭で取得したストア参照を使い続け、`app.state.catalog_store` を途中で再取得しない。現行コード（`Depends(get_catalog_store)` / `/health` の 1 回取得）はすべて準拠済みで変更不要
- **正常系テストの前提**: HTTP reload は `src.routers.admin.DATA_DIR`（リポジトリの sample データ）から読むため、移設テストの `logic_loaded == 2` 等のアサーションはそのまま有効。異常系は monkeypatch で `DATA_DIR` を tmp_path の壊れたデータに差し替える

## リスクと検知方法

- reload 失敗時にレスポンス形式・ステータスコードが変わる: 移設した既存テスト + 新規 400 テストで検知
- `Depends(get_catalog_store)` 除去に伴う import 整理漏れ（未使用 import）: フルゲートの lint（ruff）で検知
- 差し替え方式への変更で古いストア参照を掴み続ける読み手が現れる: `grep -rn "app.state.catalog_store" document-server/src/` の結果が dependencies.py（都度取得）・main.py（lifespan 設定・/health の関数内取得）・admin.py（差し替え）のみであることを実装時に確認する
- conftest の fixture が `app.state.catalog_store` を直接差し替える方式との干渉: なし（テストも同じ「参照差し替え」であり、reload 後は fixture のストアが新ストアに置き換わるだけ。テスト間は fixture が毎回設定し直す）
