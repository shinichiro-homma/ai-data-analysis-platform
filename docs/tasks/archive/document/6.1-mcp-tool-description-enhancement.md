# タスク詳細: 6.1 MCPツールのdescription強化によるコンテキストエンジニアリング改善

## 概要

Claude Desktop から production 環境でデータ分析を行う際に、以下の問題が発生していた:

1. **既存ロジックが参照されない** — `get_logic_index` の description が「任意の確認用」という書き方のため、Claude が分析前にロジックを確認しない
2. **key_type が活用されない** — `get_table_detail` のレスポンスに `key_type`/`key_types`/`domain` が含まれるが、これらのフィールドが「JOIN キーの特定に使う」という意味が description に説明されていない
3. **ツール間のワークフローが伝わらない** — 各ツールの description が「そのツール単体の機能説明」に留まり、「分析フロー全体の中での役割」が記述されていない
4. **レスポンスフィールドの意味が不明** — `get_term_detail` の `aliases`/`related_terms` や `get_logic_detail` の `usage_type` など、フィールドの意味と使い方が description に説明されていない

### 改善のアプローチ

全 24 ツール（document-mcp 7 + jupyter-mcp 17）を精査し、以下の 2 つの観点で description を改善する:

1. **ワークフロー指示**: いつ呼ぶべきか、事前に何を確認すべきか、次に何をすべきか
2. **レスポンスフィールドの意味（JSON 形式）**: レスポンスの主要フィールドについて、フィールド名をキー・意味と使い方を値とした JSON 形式で記述。型情報は不要（Claude はレスポンスの実データから型を推測できる）。フィールドの「意味」と「どう使うべきか」に集中する

#### document-mcp

**1. get_table_index（ワークフロー: 次ステップ誘導）**

現在:
```
データカタログの全テーブルインデックスを取得します。テーブル名・表示名・概要・カテゴリの一覧を返します。どのテーブルを使うべきかの判断に使用してください。
```

改善案:
```
データカタログの全テーブルインデックスを取得します。テーブル名・表示名・概要・カテゴリの一覧を返します。分析対象のテーブルを特定する最初のステップとして使用してください。特定後は get_table_detail でカラム定義・結合キー情報を確認してください。
```

---

**2. get_table_detail（ワークフロー + JSON Schema: JOIN関連フィールド）**

現在:
```
指定テーブルの詳細情報を取得します。カラム定義（リレーション情報を含む）、基本統計量、注意点を返します。SQL作成前にテーブル構造を把握するために使用してください。複数テーブルを一度に取得できます。
```

改善案:
```
指定テーブルの詳細情報を取得します。SQL作成前に必ず呼び出してください。複数テーブルを一度に取得できます。

レスポンスの columns 各要素のJOIN関連フィールド:
{
  "key_type": "結合キーの種別名。同じkey_typeを持つ他テーブルのカラムとJOIN可能",
  "key_types": [{"value": "キー種別名", "condition": "この条件下でのみそのキーとして機能"}],
  "domain": {"master_table": "FK参照先テーブル", "master_column": "FK参照先カラム", "label_column": "名称取得用カラム"}
}

data_source.type が "external" の場合、DBにデータなし。upload_external_data でファイルを提供して使用。
```

**3. get_term_detail（ワークフロー + JSON Schema: 用語フィールド）**

現在:
```
指定した用語の詳細情報を取得します。aliases、definition、values等が含まれます。複数用語を一度に取得できます。用語インデックスで関連用語を特定した後に呼び出してください。
```

改善案:
```
指定した用語の詳細情報を取得します。複数用語を一度に取得できます。

レスポンスの主要フィールド:
{
  "aliases": "この用語の別名・略称の配列。ユーザーが略称で言及した場合にこの用語を特定できる",
  "definition": "用語の正式な定義",
  "related_terms": "関連用語名の配列。不明な用語があれば再帰的にget_term_detailで解決すること",
  "values": [{"label": "値のラベル", "description": "値の説明"}]
}
```

**4. get_logic_index（ワークフロー: 必須呼び出し + usage_type ガイド）**

現在:
```
既存ロジックの全インデックスを取得します。ロジック名、概要、カテゴリのリストを返します。分析に流用できる既存ロジックがあるか確認する際に呼び出してください。
```

改善案:
```
既存ロジックの全インデックスを取得します。【重要】データ分析やSQL作成を始める前に必ず呼び出してください。流用可能な既存ロジックがあれば、ゼロからSQLやコードを書くのではなくそのロジックを活用してください。get_logic_detail でメタ情報を確認し、usage_type が template ならパラメータを変えてそのまま使い、reference なら参考にして新たに書いてください。
```

**5. get_logic_detail（JSON Schema: メタフィールド）**

現在:
```
指定した既存ロジックのメタ情報を取得します。説明、言語、usage_type、入力テーブル、注意事項等が含まれます。複数ロジックを一度に取得できます。コードの中身は含まれません（get_logic_codeで別途取得してください）。
```

改善案:
```
指定した既存ロジックのメタ情報を取得します。複数ロジックを一度に取得できます。コードの中身は get_logic_code で別途取得してください。

レスポンスの主要フィールド:
{
  "usage_type": "template=パラメータを変えてそのまま流用可能 / reference=参考にして新規作成",
  "input_tables": "このロジックが使用するテーブル名の配列",
  "usage_context": "どのような分析場面で使うかの説明",
  "related_logic": "関連ロジック名の配列。組み合わせて使うロジックの参照に"
}
```

### 技術的な考慮事項

- **変更はテキストのみ**: ロジック・型・API は一切変更しない。description 文字列の書き換えのみ
- **複数行 description の実装**: 現在の description はすべてダブルクォートの単一行文字列。改善案の `get_table_detail`、`get_term_detail`、`get_logic_detail`、`execute_sql` は JSON ブロックを含む複数行のため、**テンプレートリテラル（バッククォート）** に変更する。単一行のまま変更する `get_table_index`、`get_logic_index`、`execute_code`、`get_dataframe_info` はダブルクォートのままでよい
- **テストへの影響なし**: 既存テストは description の存在チェック（`description.length > 0`）のみで、文言を検証していない（`jupyter-mcp/tests/unit/tools/index.test.ts:91-98`）
- **要件定義との関係**: 要件定義にはすでにワークフローガイドラインが存在する（document-mcp 572-676行、jupyter-mcp 1128-1243行）。description にこれらを反映する作業であり、要件の変更ではない。ただし、要件定義内の description 定義テキスト（document-mcp 108-445行）は実装後に同期が必要 → 別途 `/custom-change-requirement` で対応
- **JSON 形式によるフィールド説明の利点**: 散文よりも構造化された形式で、フィールド名と意味の対応が一目で分かる。description が「ワークフロー指示」と「フィールド説明」に明確に分離され、可読性が向上する。型情報は含めない（Claude はレスポンスの実データから推測可能）
- **フィールド説明を記載するツールの基準**: レスポンスに「フィールド名からは意味が推測しにくいフィールド」を持つツールにのみ記載。`name`/`type`/`size` のような自明なフィールドは対象外
