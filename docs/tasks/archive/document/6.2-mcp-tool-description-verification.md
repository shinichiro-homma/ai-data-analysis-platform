## 検証シナリオ

### シナリオ 1: ロジック参照の自発的呼び出し

**環境**: production
**プロンプト**: 「OTAC会員番号を最新化して、顧客別の売上を集計してください」

> production には `otac_id_washing`（usage_type: template）が存在する。このロジックは OTAC会員番号・商業顧客ID の洗い替え SQL テンプレートである。

**期待動作**:
1. `get_logic_index` が **execute_sql より前に**呼ばれる
2. `otac_id_washing` を発見し、`get_logic_detail` で usage_type=template を確認
3. `get_logic_code` で SQL テンプレートを取得
4. テンプレートを活用して execute_sql を実行（ゼロから SQL を書かない）

**確認ポイント**:
- `get_logic_index` の「【重要】データ分析やSQL作成を始める前に必ず呼び出してください」が機能しているか
- usage_type=template のロジックをそのまま流用しているか（reference なら参考に新規作成）

**判定基準**:
- OK: get_logic_index → get_logic_detail → get_logic_code → execute_sql の順で呼ばれ、テンプレートが活用されている
- NG: get_logic_index が呼ばれない、または execute_sql の後に呼ばれる

---

### シナリオ 2: JOIN キーの正しい特定

**環境**: production
**プロンプト**: 「顧客情報（dwh_sdt_customer_inf）と会員カード情報（dwh_sdt_member_card_inf）を結合して、カード種別ごとの顧客属性を分析してください」

> 両テーブルは key_type: "商業顧客ID" の `commercial_customer_id` カラムを共有している。

**期待動作**:
1. `get_table_detail(table_names: ["dwh_sdt_customer_inf", "dwh_sdt_member_card_inf"])` を呼ぶ
2. レスポンスから `commercial_customer_id` の key_type="商業顧客ID" を読み取る
3. `JOIN ON a.commercial_customer_id = b.commercial_customer_id` で結合する SQL を生成

**確認ポイント**:
- description の JSON フィールド説明 `"key_type": "結合キーの種別名。同じkey_typeを持つ他テーブルのカラムとJOIN可能"` が活用されているか
- 同じ key_type を持つカラム同士で JOIN しているか
- domain.values（gender: 0=不明/1=男性/2=女性 等）が正しく解釈されているか

**判定基準**:
- OK: key_type="商業顧客ID" のカラム同士で JOIN し、domain 値も正しく解釈
- NG: カラム名の推測で JOIN する、domain 値をラベルではなくコード値のまま使う

---

### シナリオ 3: 分析フロー全体の順序

**環境**: production
**プロンプト**: 「ビル別の月次売上推移をグラフにしてください」

> dwh_rs_sales_table_all_prepost（売上テーブル）と dwh_rs_building_master（ビルマスタ）を使う分析。get_logic_index で otac_id_washing が見つかるが、この分析には不要と判断すべき。

**期待動作**:
1. `get_table_index` — 全テーブル概要を確認（分析対象テーブルの特定）
2. `get_table_detail` — 売上テーブル・ビルマスタのカラム定義を確認（SQL 作成の前提）
3. `get_logic_index` — 既存ロジックを確認（流用可能なものがあるか）
4. `execute_sql` — データ取得 SQL を実行
5. `execute_code` — pandas/matplotlib で可視化

**確認ポイント**:
- get_table_detail が execute_sql より前に呼ばれるか（description: 「SQL作成前に必ず呼び出してください」）
- get_logic_index が呼ばれるか（description: 「データ分析やSQL作成を始める前に必ず」）
- execute_sql のレスポンスの file_path を使って execute_code で `pd.read_csv('data/...')` しているか

**判定基準**:
- OK: get_table_index → get_table_detail → get_logic_index → execute_sql → execute_code の順
- 許容: get_logic_index の位置が多少前後する（get_table_detail の前でも可）
- NG: get_table_detail なしで execute_sql を実行、または get_logic_index が呼ばれない

---

### シナリオ 4: 用語の再帰的解決

**環境**: sample（production には related_terms を持つ用語が存在しないため）
**プロンプト**: 「プラチナランクの顧客の購買傾向を分析してください」

> sample 環境の用語「ロイヤルティランク」は related_terms: ["統合会員ID"] を持つ。「プラチナランク」→「ロイヤルティランク」→ related_terms → 「統合会員ID」の再帰的解決が期待される。

**期待動作**:
1. `get_term_index(query: "プラチナ")` または `get_term_index()` で用語を検索
2. `get_term_detail(term_names: ["ロイヤルティランク"])` で詳細取得
3. レスポンスの `related_terms: ["統合会員ID"]` を確認
4. `get_term_detail(term_names: ["統合会員ID"])` で関連用語を追加解決
5. 解決した用語の知識を分析に活用

**確認ポイント**:
- description の `"related_terms": "関連用語名の配列。不明な用語があれば再帰的にget_term_detailで解決すること"` が機能しているか
- related_terms の用語を追加で get_term_detail しているか（再帰的解決）
- ロイヤルティランクの values（レギュラー/シルバー/ゴールド/プラチナ）が分析に反映されているか

**判定基準**:
- OK: related_terms に含まれる「統合会員ID」を追加で get_term_detail している
- NG: related_terms を無視して先に進む

## NG 時の対応手順

検証で NG が出た場合、以下の手順で description を修正する。

### 1. 原因分析

NG の原因を以下の観点で分析する:
- description の文言が弱い（「推奨」→「必須」に変更すべき等）
- description の位置が悪い（JSON ブロック内に埋もれている等）
- description の情報が不足（ワークフロー指示が欠けている等）
- 他のツールの description との整合性の問題

### 2. description 修正

```bash
# 1. description を修正（document-mcp/src/tools/index.ts または jupyter-mcp/src/tools/index.ts）
# 2. リビルド + テスト
scripts/test.sh --rebuild document-mcp
scripts/test.sh --rebuild jupyter-mcp
# 3. Claude Desktop を再起動して MCP を再接続
# 4. 同じシナリオで再検証
```

### 3. 記録

修正内容を本ファイルの「検証結果」セクションに追記する。
