# タスク詳細: 7.3 REST API 認証の結合テスト

## 概要

7.1（document-server への Bearer トークン認証導入）と 7.2（document-mcp 側のトークン付与）の結合動作を、document-server と document-mcp を実際に起動した状態で検証する結合テストを追加する。

検証の軸は次の 2 点。

1. **正常系**: `DOCUMENT_SERVER_TOKEN` を一致させた状態で、document-mcp 経由（`handleToolCall`）から全 7 ツール（カタログ / 用語集 / ロジック）が 200 で応答する
2. **異常系**: トークンが不一致 / 未設定の場合、document-server から 401 が返り、`DocumentClientError('HTTP_401', ..., 401)` として MCP ツールの `success: false` レスポンスに反映される

Phase 7 の締めとして「実際の HTTP 通信を通る形で」認証フローが動作することを保証する。

### 実装手順

#### ステップ 1: テスト設計

本テストは「document-mcp の `handleToolCall` 経由で実際に document-server を叩く」形で動作させる。`catalog-integration.test.ts` と同じ構造（`handleToolCall` + `parseToolCallResult`）を踏襲する。

ポイント:

- テスト実行前に `DOCUMENT_SERVER_TOKEN` が環境から供給されていること（`scripts/test.sh --integration` で docker-compose から渡る想定）
- `DocumentServerClient` は起動時に環境変数を読む（7.2 実装）ため、トークン差し替えテストでは **クライアントを作り直す** 必要がある
- `src/document-client/index.ts` のシングルトン `getDocumentClient()` が 1 度生成したインスタンスをキャッシュする場合、テスト間でリセットできない可能性がある。その場合は `new DocumentServerClient()` を直接呼び出す形でテストを書く

#### ステップ 2: Red フェーズ — テストを書く

`document-mcp/tests/integration/auth-integration.test.ts` に以下のテストケースを実装する。

##### 正常系（`describe('認証成功時', ...)`)

- **テーブル**: `handleToolCall('get_table_index')` が `success: true` を返す
- **テーブル詳細**: `handleToolCall('get_table_detail', { table_names: [fixture の既知テーブル名] })` が `success: true` を返す
- **用語集**: `handleToolCall('get_term_index')` が `success: true` を返す
- **用語集詳細**: `handleToolCall('get_term_detail', { term_names: [...] })` が `success: true` を返す
- **ロジック**: `handleToolCall('get_logic_index')` が `success: true` を返す
- **ロジック詳細**: `handleToolCall('get_logic_detail', { logic_names: [...] })` が `success: true` を返す
- **ロジックコード**: `handleToolCall('get_logic_code', { logic_name: ... })` が `success: true` を返し、Python コード文字列が返る

##### 異常系（`describe('認証失敗時', ...)`)

`DocumentServerClient` を誤ったトークンで直接生成し、document-server に対して 401 が返ることを検証する。

- **誤ったトークン**: `process.env.DOCUMENT_SERVER_TOKEN = 'wrong-token'` の状態で `new DocumentServerClient()` を生成 → `client.getTableIndex()` が `DocumentClientError` を投げ、`statusCode === 401` になる
- **空トークン** (ガード確認): `process.env.DOCUMENT_SERVER_TOKEN = ''` で `new DocumentServerClient()` → コンストラクタで `Error` が投げられる（7.2 の挙動確認。HTTP 到達前のガード）
- **MCP ツール経由の 401**: 誤ったトークンで生成したクライアントに差し替えた状態で `handleToolCall('get_table_index')` を実行した場合、`success: false` かつエラー内容が 401 相当であること
  - ※ `handleToolCall` は `getDocumentClient()` シングルトン経由でクライアントを取得するため、トークン差し替えのためにシングルトンをリセットする仕組みが必要。既存コードにリセット関数がなければ、このテストは `DocumentServerClient` を直接叩く形に限定する（MCP ツール経由の 401 検証は direct client test で代替）

##### `/health` エンドポイントの除外確認（任意）

- `axios.get('{DOCUMENT_SERVER_URL}/health')` を **Authorization ヘッダーなし** で実行 → 200 が返る
- 理由: Docker healthcheck との互換性を担保（7.1 の設計要件）

#### ステップ 3: Green フェーズ — テスト実行

```bash
scripts/test.sh --integration --rebuild document-mcp
```

- `--integration` が docker-compose で document-server を起動し、環境変数（`DOCUMENT_SERVER_TOKEN`）を供給する
- `--rebuild` で 7.1 / 7.2 の実装を最新化してから実行する
- 既存の `catalog-integration.test.ts` / `performance.test.ts` が引き続きパスすることも確認

#### ステップ 4: Refactor フェーズ

- 異常系テストでの `process.env` 操作は `beforeEach` / `afterEach` でスナップショット&復元し、他テストに副作用を残さない
- 環境変数の保存・復元パターンが既存テストにあれば流用する

### 技術的な考慮事項

- **シングルトンの扱い**: `getDocumentClient()` がプロセス内で単一インスタンスを保持するため、正常系テストはシングルトン経由、異常系テストは `new DocumentServerClient()` 直接生成に分ける。シングルトンを強制リセットする API を追加する必要がある場合は最小限の変更にとどめる（理想的には 7.2 の実装で `resetDocumentClient()` が用意されていればそれを使う）。
- **環境変数復元**: `DOCUMENT_SERVER_TOKEN` を一時的に上書きするテストは `afterEach` で元の値に戻す。戻し忘れると後続テスト（catalog-integration.test.ts 等）が全滅する。
- **テスト実行環境**: `scripts/test.sh --integration` が docker-compose 起動 → 環境変数注入を担うため、このテスト単体で docker-compose を明示的に立ち上げる必要はない。
- **document-server 起動の前提**: document-server 側に `DOCUMENT_SERVER_TOKEN` が設定されていないと起動そのものが失敗する（7.1 実装）。docker-compose の `document-server` サービス環境変数を確認する。
- **`/health` の除外検証**: 認証除外は 7.1 の完了条件で担保済みだが、結合テストでも再確認することで Docker healthcheck 破綻のリグレッションを防ぐ。
- **fixture の再利用**: `tests/integration/fixtures/` の既知テーブル名 / 用語名 / ロジック名を流用し、テスト自身が fixture を重複定義しない。
- **タイムアウト**: 認証系テストは HTTP 1 往復のみでありカーネル起動を伴わないため、`vitest.config.integration.ts` のデフォルト（30 秒）で十分。

## テスト計画

### テスト実行方法

```bash
# 結合テスト（リビルド込み。docker-compose 起動と環境変数注入を自動化）
scripts/test.sh --integration --rebuild document-mcp

# 認証テストのみ実行したい場合（開発中）
cd document-mcp
DOCUMENT_SERVER_URL=http://localhost:3002 \
DOCUMENT_SERVER_TOKEN=dev-document-token \
  npx vitest run --config vitest.config.integration.ts tests/integration/auth-integration.test.ts
```

### 前提条件

- docker-compose で document-server が `DOCUMENT_SERVER_TOKEN=dev-document-token` 付きで起動していること（`.env.example` に設定済み）
- document-server/data/ にサンプル YAML（カタログ/用語集/ロジック）が配置済み

### 期待されるテスト数

合計 **9〜11 テスト**:

- 正常系: 7 テスト（ツール1つにつき1ケース）
- 異常系: 2〜3 テスト（誤トークン 401 / 空トークンガード / ※MCP 経由 401）
- `/health` 除外: 1 テスト
