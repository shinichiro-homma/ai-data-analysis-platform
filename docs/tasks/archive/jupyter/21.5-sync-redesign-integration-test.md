## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | MCP 統合テスト（vitest + 実サーバー）で同期プロトコルを網羅し、ブラウザ側は playwright-cli による動作確認（ロック表示 + revert 反映の 1 シナリオ）をタスク完了時に実施して結果を PR に記録する | プロトコル検証は高速・安定な vitest 層に置く。ブラウザ確認は既存ルール（testing.md）の運用そのままで新規基盤が不要 | ブラウザ確認は自動回帰テストにならない（実施記録のみ） |
| B | Playwright テストスイートを新規導入して全シナリオを自動化 | ユーザー視点の自動回帰 | Playwright のテスト基盤がリポジトリに存在せず（tests/e2e は vitest）、基盤導入は別 Phase「ai-sync の堅牢化」のスコープ。本 Phase で先取りすると過大 |

採用理由: 検証対象（ロック強制・通知・再同期）の大半はサーバー/プロトコル層で完結し、vitest 統合テストで回帰検知できる。ブラウザ表示の確認は testing.md が定める playwright-cli 運用に従う。

ADR 要否: 不要（テスト計画のみ）。

### 技術的な考慮事項

- 統合テストは実 Docker 環境が前提（`--integration`）。CI での実行可否は既存の統合テスト運用に従う
- ブラウザ確認は playwright-cli による対話的操作で行い、自動テスト基盤（Playwright スイート）は導入しない（フロントの自動テスト整備は別 Phase「ai-sync の堅牢化」のスコープ）。事前に `docker compose ps` で jupyter-server の起動を確認する
- シナリオ4 の「未オープン相当」は、ブラウザなし（WS クライアントのみ接続）で再現する（旧実装では clients>=1 で出力が消えた条件そのもの）

## リスクと検知方法

- 統合テストのタイミング依存（TTL・debounce 待ち）: 待ち時間はポーリング + タイムアウトで書き、固定 sleep を避ける
- ブラウザ確認が回帰テストにならない（実施記録のみ）: プロトコル層の統合テスト（シナリオ 1〜5）で回帰は検知し、表示層の自動化は別 Phase「ai-sync の堅牢化」で解消する
