# タスク詳細: 21.3 変更通知 + 再読込の完全同期

## 概要

差分同期を廃止し、ディスク上の .ipynb を唯一の真実とする（不変条件 I1）。jupyter-server が書き込み成功時に `notebook_changed`（単調増加 seq 付き）を配信し、ブラウザは該当ノートブックを `context.revert()` でディスクから再読込する。jupyter-mcp の差分イベント配信（12 種）を削除し、execute 系の出力は接続クライアント数に関わらず常にディスクへ書く（Issue #76 の根本修正）。実行中スピナー用の `cell_execute_start` / `cell_execute_end` は ephemeral 通知として残す。

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | `notebook_changed` は jupyter-server の `contents_manager.save` ラップ（21.2 で導入）から発行する。MCP は内容変更イベントを一切配信しない | 発行漏れが構造的に不可能（書き込み = 通知）。ブラウザ保存など MCP 以外の書き込みも通知される。MCP 側の配信コード 12 箇所を削除でき、シンプル | ブラウザ自身の保存にも revert が走る（seq 比較 + dirty ガードで空振りさせる） |
| B | MCP が書き込み後に `notebook_changed` を POST する（現行アーキテクチャの縮約） | サーバー変更が少ない | 「書き込んだが通知し忘れる」経路が残る（現行の構造問題の再生産）。ブラウザ保存が通知されない |
| C | 差分イベントを維持し seq とギャップ検出だけ追加 | UI 反映が最も細粒度 | ADR-0002 で不採用と決定済み（2つの真実が残る） |

採用理由: A は「書き込みと通知の不可分性」をチョークポイントで保証し、I1/I5 の充足が実装の正しさに依存しない。

ADR 要否: 不要（ADR-0002 で決定済み）。

## 異常系・不変条件

- 通知配信失敗: ファイルは既に正しく書かれており、ブラウザ表示のみ古くなる。21.4 の再同期（seq 照会）で回復する設計とし、本タスクでは「配信失敗してもファイル書き込みは成功する」ことをテストで保証
- ブラウザ未接続・対象ノートブック未オープン: 出力が常にディスクへ書かれる（Issue #76 異常系。完了条件で検証）
- ブラウザに未保存変更（dirty）がある場合: revert すると失われるため、「ロック中でなく dirty なら revert をスキップして警告ログ」のガードを入れる（ロック中は readOnly のため dirty にならない）
- 不変条件: I1 充足（本タスクの目的）。I4: `notebook_changed` 等の新イベントペイロードはブラウザ側で最低限の形式検証（type / notebook_path / seq の存在チェック）を行う

### 技術的な考慮事項

- ephemeral イベント（cell_execute_start/end）は回復パスを持たない。これは I5 の「失われてよい情報」（スピナー表示のみ）に該当し、実行完了後の revert が表示を最終的に正しくする
- revert の debounce はノートブックパス単位（連続編集で revert を間引く）。「1 操作 = 1 revert」は保証しない（ADR の帰結）
- 出力の逐次ストリーミング表示は本タスクで廃止される（ADR で受け入れ済みのトレードオフ）。実行完了時に revert で一括表示
- `notebook-cell-tracker.ts`（pendingCells）は execute_code の重複セル防止に使われ続けるため本タスクでは削除しない（21.5 後の縮小候補として備考に残す）
- ブラウザ自身の保存でも `notebook_changed` が発行され revert が走るが、保存直後の revert は同一内容のため実害なし（dirty ガードで未保存変更は保護される）

## リスクと検知方法

- 差分イベント削除の漏れ: `grep -rn "cell_added\|cell_edited\|cell_deleted\|cell_reordered\|cell_output\b\|cells_merged\|cell_split\|cell_type_changed\|cell_copied\|output_cleared\|all_outputs_cleared" jupyter-mcp/src jupyterlab-ai-sync/src` が 0 件であることで検知
- 大きいノートブックでの revert 負荷: debounce で緩和。統合テストでは 50 セルのノートブックで通知 → revert が完走することを確認（NF1 の 100ms は「通知受信から revert 開始まで」と再定義して要件改訂に含める）
- `updateCellOutputs` 無条件化による二重書き込み（ブラウザ側の書き戻しとの競合）: ブラウザの SharedModel 書き戻し自体を削除するため競合経路が消える（手順 5 で削除確認）
