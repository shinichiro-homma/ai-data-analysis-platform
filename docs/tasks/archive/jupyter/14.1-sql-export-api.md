# タスク詳細: 14.1 jupyter-server SQL エクスポート API 実装

## 概要

`POST /api/sql/export` エンドポイントを jupyter-server に実装する。SELECT クエリの結果をワークスペースの `data/` ディレクトリに Parquet/CSV ファイルとしてストリーミング書き出しする。チャンク処理（10,000行ずつ `fetchmany`）でメモリ使用量を一定に抑え、行数制限なしで大規模データのエクスポートを実現する。

### 実装手順

#### 1. `pyarrow` 依存追加

`jupyter-server/requirements.txt` に `pyarrow` を追加する。Parquet 形式での書き出しに必要。

```
pyarrow>=19.0
```

#### 2. ファイル名バリデーション関数の追加 — `_validate_export_filename()`

既存の `_validate_filename()` は `.csv` 拡張子を強制するため、export 用に新しいバリデーション関数を作成する。

```python
def _validate_export_filename(filename: str, format: str) -> str | None:
    """
    エクスポート用ファイル名のバリデーション。

    - パストラバーサル防止（.., /, \\ を含まない）
    - 絶対パス防止
    - NULLバイト防止
    - 長さチェック（255文字以下）
    - 拡張子チェック（format に一致する .parquet / .csv）
    """
```

**ポイント:**
- 既存の `_validate_filename()` と同様のセキュリティチェック
- 拡張子は `format` パラメータに基づき `.parquet` または `.csv` を許可

#### 3. SELECT 専用バリデーション

export は SELECT 文のみ対応する。既存の `_classify_sql()` を流用し、`is_select=False` の場合はエラーを返す。非 SELECT 文に対しては `SQL_NOT_ALLOWED` エラー（"Only SELECT statements are allowed for export"）を返却する。

#### 4. ストリーミングエクスポート関数の追加 — `_execute_export_sync()`

```python
EXPORT_CHUNK_SIZE = 10_000  # 1チャンクあたりの行数

def _execute_export_sync(
    database_url: str,
    sql: str,
    timeout: int,
    output_path: Path,
    format: str,  # "parquet" or "csv"
) -> dict:
    """
    SELECT 結果をチャンク単位でファイルに書き出す（同期関数）。

    Returns:
        dict: {"row_count": int, "file_size_bytes": int}
    """
```

**Parquet 書き出しフロー:**
1. SQLAlchemy でクエリ実行（read-only トランザクション + statement_timeout）
2. `result.keys()` でカラム名を取得
3. `fetchmany(EXPORT_CHUNK_SIZE)` でチャンク取得をループ
4. 各チャンクを `pyarrow.RecordBatch` に変換
5. 初回チャンクで `pyarrow.parquet.ParquetWriter` を開く（スキーマ自動推論）
6. `writer.write_batch()` で書き出し
7. ループ完了後 `writer.close()`
8. 合計行数とファイルサイズを返却

**CSV 書き出しフロー:**
1. 同様にチャンク取得
2. 初回チャンクで `csv.writer` + ヘッダー書き出し
3. 後続チャンクは行のみ書き出し
4. UTF-8 BOM 付き（既存の CSV 保存と一貫性を保つ）

**エラーハンドリング:**
- 書き出し途中のエラーは中間ファイルを削除してから例外を再送出
- エラーコードは既存の `_handle_sql_error()` メソッドを流用

#### 5. `SqlExportHandler` クラスの追加

```python
class SqlExportHandler(BaseCustomHandler):
    """POST /api/sql/export"""

    @web.authenticated
    async def post(self):
        body = self.get_json_body()

        # 1. リクエストパース
        sql = body.get("sql")
        workspace_id = body.get("workspace_id")
        file_path = body.get("file_path")
        format = body.get("format", "parquet")
        timeout = body.get("timeout", 300)

        # 2. バリデーション
        #    - sql: 必須、SELECT のみ（_classify_sql で判定）
        #    - workspace_id: 必須（validate_workspace_id）
        #    - file_path: 必須（_validate_export_filename）
        #    - format: "parquet" or "csv"
        #    - timeout: デフォルト300秒、最大600秒（validate_timeout(timeout, max_timeout=600)）

        # 3. ワークスペース存在確認（resolve_workspace_dir）

        # 4. SQL 実行 + ファイル書き出し
        #    asyncio.get_running_loop().run_in_executor() で同期関数を実行

        # 5. レスポンス
        #    {
        #        "success": true,
        #        "file_path": "workspaces/{ws_id}/data/{file_path}",
        #        "row_count": N,
        #        "file_size_bytes": N,
        #        "format": "parquet",
        #        "execution_time_ms": N
        #    }
```

**既存の `SqlExecuteHandler` との共通パターン:**
- `BaseCustomHandler` 継承
- `@web.authenticated` デコレータ
- `DATABASE_URL` 確認
- `validate_workspace_id()`, `resolve_workspace_dir()` によるワークスペース検証
- `asyncio.wait_for()` + `run_in_executor()` によるスレッドプール実行
- `_handle_sql_error()` によるエラーハンドリング（メソッドの再利用またはモジュールレベル関数への抽出）

**`SqlExecuteHandler` との違い:**
- SELECT 文のみ許可（非 SELECT は `SQL_NOT_ALLOWED`）
- `max_rows` なし（行数制限なし）
- タイムアウトのデフォルトが 300 秒、最大 600 秒
- チャンク処理で Parquet/CSV に直接書き出し
- レスポンスに `format` フィールドを含む
- `FILE_WRITE_ERROR` エラーコードの追加

#### 6. ルーティング登録

`handlers.py` の `get_handlers()` に追加:

```python
from .sql_handlers import SqlExecuteHandler, SqlExportHandler

# ...
(f"{base_url}/api/sql/export", SqlExportHandler),
```

#### 7. エラーハンドリングの共通化

`SqlExecuteHandler._handle_sql_error()` はインスタンスメソッドとして定義されている。`SqlExportHandler` でも同じエラーハンドリングが必要なため、以下のいずれかで対応:

- **案A（推奨）:** `SqlExportHandler` にも `_handle_sql_error()` を定義（コピー）。簡潔で変更範囲が小さい。
- **案B:** 共通の基底クラスまたはモジュールレベル関数に抽出。リファクタリングが大きくなるため、このタスクでは見送り。

### 技術的な考慮事項

- **メモリ効率:** `fetchmany(10_000)` + 即座のファイル書き出しにより、全行をメモリに載せない。Parquet は `ParquetWriter` のストリーミング書き出し、CSV は `csv.writer` の逐次書き出しで対応。
- **pyarrow の型推論:** 最初のチャンクからスキーマを推論する。空の結果セット（0行）の場合は空ファイルを作成し `row_count: 0` を返す。
- **中間ファイルのクリーンアップ:** エクスポート途中でエラーが発生した場合、不完全なファイルが残らないよう `finally` ブロックで削除する。
- **`read_only` トランザクション:** 既存の `_execute_sql_sync()` と同様に `SET default_transaction_read_only = ON` を設定する。
- **Parquet のデータ型:** SQLAlchemy の結果セットから Python ネイティブ型を経由して pyarrow 型に変換する。日付型・数値型は pyarrow が自動推論する。
- **validate_timeout の max_timeout パラメータ:** 既存の `validate_timeout()` は `max_timeout` パラメータを受け取るため、`validate_timeout(timeout, max_timeout=600)` で 600 秒上限に対応できる。

## テスト計画

### ユニットテスト（`test_sql_handlers.py` に追加）

既存の `_classify_sql` / `_validate_filename` テストと同じパターンで、純粋関数のテストを追加。

**`_validate_export_filename` テスト:**
- 正常系: `"data.parquet"` (format="parquet") → None
- 正常系: `"data.csv"` (format="csv") → None
- 異常系: パストラバーサル (`"../data.parquet"`) → エラー
- 異常系: 拡張子不一致 (`"data.csv"` with format="parquet") → エラー
- 異常系: 空文字列 → エラー

**SELECT 専用バリデーションテスト:**
- 正常系: SELECT 文 → 通過
- 異常系: INSERT 文 → `SQL_NOT_ALLOWED`
- 異常系: DELETE 文 → `SQL_NOT_ALLOWED`

統合テストはタスク 14.2（jupyter-mcp の `export_sql` ツール実装）以降で MCP 経由の E2E テストとして実施する想定。本タスクでは以下を手動確認:
