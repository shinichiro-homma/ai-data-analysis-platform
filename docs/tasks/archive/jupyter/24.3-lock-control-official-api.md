# タスク詳細: 24.3 ロック制御の公式 API 化

## 概要

`CommandRegistry.execute` のモンキーパッチと capture-phase keydown ハンドラの 2 つのブロック機構を、`commands.isEnabled` のガードに一元化する。`commands.execute` の差し替えコードが除去され、キーボードショートカット・メニュー・ツールバーの全経路でロック制御が一貫する。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyterlab-ai-sync.md` の「F3: ノートブックロック機能」セクション（F3.1, F3.2, F3.3, AC3, AC6）
- 不変条件: `docs/design/invariants.md` の I2（排他制御はサーバー側で強制）

## 調査したファイル

- `jupyterlab-ai-sync/src/lock-manager.ts`: モンキーパッチ（L203-233 `installCommandBlocker`）と keydown ハンドラ（L255-274 `createExecutionBlockHandler`）が並存。`BLOCKED_COMMAND_IDS`（29 コマンド）と `LOCK_EXEMPT_COMMAND_IDS`（2 コマンド）のセット定義。`LockState` に `keydownHandler` を保持（L67-73）
- `jupyterlab-ai-sync/src/plugin.ts`: `LockManager` のインスタンス化（L27-28）と `unlockAll` 呼び出し（L40）
- `jupyterlab-ai-sync/src/notebook-updater.ts`: `lockNotebook`/`unlockNotebook` の呼び出し元（L317, L330）。公開 API のシグネチャ変更なし
- `jupyterlab-ai-sync/tests/unit/notebook-finder.test.ts`: `INotebookTracker` スタブのパターン（L8-23 `createTrackerStub`）。`as unknown as` キャストによる最小スタブ
- `node_modules/@lumino/commands`: `CommandRegistry.isEnabled`（型定義 L203）は keybinding 経由の実行前にチェックされる（`_executeKeyBinding` 内）。`isEnabled` が false ならキーバインド発火をスキップ。メニュー・ツールバーも `isEnabled` を参照して UI 状態を更新

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | `commands.isEnabled` ガード | 1 つの機構で全経路（キーボード・メニュー・ツールバー）をカバー。Lumino の UI が `isEnabled` に連動するため、メニュー項目のグレーアウト・ツールバーボタン無効化が自動。keydown ハンドラ不要 | `isEnabled` のオーバーライドは技術的にはプロパティ差し替えだが、`execute` 差し替えと異なり Lumino の UI 連携に沿った手法 |
| B | `commands.addKeyBinding` でブロック対象ショートカットを上書き + CSS でメニュー・ツールバーの視覚的無効化 | モンキーパッチ完全排除（100% 公式 API）。`IDisposable` によるライフサイクル管理 | メニュー・ツールバーのクリックは実際にはブロックされず、AC6（Kernel メニューからの再起動ブロック）を満たせない。2 つのサブ機構（keybinding + CSS）が必要 |

採用理由: AC6 が Kernel メニュー経由の再起動ブロックを明示的に要求しており、案 B では達成できない。案 A は `isEnabled` を通じて Lumino の UI システムと自然に連携し、メニュー・ツールバー・キーバインドの全経路を 1 つの機構でカバーする。`commands.execute` の差し替えは完全に除去される。

ADR 要否: 不要。`isEnabled` ガードはコンポーネント内の実装詳細であり、コンポーネント間契約や状態の所有権に影響しない。

## 異常系・不変条件

- 該当する異常系: ロック中にメニュー・ツールバーからブロック対象コマンドを実行しようとした場合 → `isEnabled` が false を返し、メニュー項目がグレーアウト・ツールバーボタンが無効化される。万一 `commands.execute()` が直接呼ばれても、サーバー側ロック（I2）が書き込みを拒否する
- 関係する不変条件:
  - I2（排他制御はサーバー側で強制）: UI 層の `isEnabled` ガードは UX 改善。サーバー側の 423 拒否が真の保証。本タスクは UI 層の改善のみ

### 技術的な考慮事項

- `createIsEnabledGuard` を純粋関数として export することで、JupyterLab のスタブなしにガードロジックを単体テストできる
- `notifyCommandChanged()` はロック/アンロック時にのみ呼ばれる低頻度イベントのため、全コマンド通知でもパフォーマンス影響なし
- `isEnabled` ガードは `commands.execute()` の直接呼び出しを防がないが、I2（サーバー側ロック強制）が保証を担い、UI 層は UX 改善に位置づけられる
- Lumino の `_executeKeyBinding` は実行前に `isEnabled` をチェックするため、`isEnabled` ガードだけでキーボードショートカットの全ブロックが達成される（capture-phase keydown ハンドラは不要になる）

## リスクと検知方法

- ロック中にキーボードショートカットでブロック対象コマンドが実行される: `isEnabled` ガードが Lumino の `_executeKeyBinding` で参照されない場合。手動テスト（ロック中に Shift+Enter、0 0 等を押下して実行されないことを確認）で検知
- メニュー・ツールバーが `isEnabled` の変更を反映しない: `notifyCommandChanged` が正しく呼ばれない場合。手動テスト（ロック中にメニューのブロック対象項目がグレーアウトすることを確認）で検知
- 既存テスト（path-utils, notebook-finder）への影響: `lockNotebook`/`unlockNotebook`/`isLocked` の公開 API シグネチャは変更しないため影響なし。`bash scripts/test.sh --quiet jupyterlab-ai-sync` で回帰検知
