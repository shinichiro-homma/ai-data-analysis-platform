# タスク詳細: 21.4 再接続時の再同期

## 概要

WebSocket 切断中の変更を再接続後に回復する（不変条件 I5）。jupyter-server に同期状態照会 API（現在の seq とロック一覧）を新設し、ブラウザは再接続時に照会して、seq が自分の既知値と異なる開いているノートブックを revert し、ロック状態を再適用する。WS 送信に失敗したクライアントは接続リストから除去して close し、ブラウザ側の再接続 → 再同期経路に載せる（現行は失敗を握りつぶしてゾンビ接続が残る）。

あわせて監査レポート（`tmp/audit-21.2-21.3-report.md`）の指摘 1・2・6 を織り込む:

- **指摘 1（revert ガードの競合脆弱性）**: `notebook-updater.ts` の `dirty && !isLocked` ガードを廃止し、revert 要否判定を **seq ベース（自分が既知の seq か）** に置き換える。dirty（ユーザーの未保存変更あり）のときは ADR-0002 の帰結どおり「スキップ + 競合の warn」に倒す（isLocked を緩和条件に使わない）
- **指摘 2（自己エコー revert）**: ブラウザ自身の保存完了時に照会 API で最新 seq を取得して lastSeq に記録し、「自分の保存で進んだ seq は既知」として revert をスキップする（指摘 1 と同一機構）
- **指摘 6（seq ストアのリネーム時リセット）**: seq を比較に使い始めるため、リネーム・サーバー再起動による seq リセットで誤 revert / revert 漏れが起きないことを比較ロジック側（`!==` 比較 + resync での lastSeq 上書き）で吸収する。ストアの残置エントリ掃除自体はスコープ外

### 前提・依存

- **Issue #89**（`docs/issues/89-ai-event-boundary-validation.md`: イベント境界の入力検証）と **Issue #90**（`docs/issues/90-lock-path-normalization.md`: ロックキー正規化の共有）は別修正であり、**本タスクより先に修正される想定**。本タスクは WS イベント種別を追加しない（照会は REST GET）ため #89 の type allowlist と競合しない。#90 の正規化共有後は、照会 API が返すロックキーも正規化済みパスになる前提で、ブラウザ側の比較は既存の `normalizeNotebookPath` を通す
- ブラウザ実機での revert 動作確認（切断 → 変更 → 再接続 → 表示一致、自己エコー抑制）はタスク 21.5 で実施

## 検討した代替案

### 再同期方式（旧計画から維持、有効性を再確認済み）

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | ブラウザが lastSeq を記録し、再接続時に照会 API と突き合わせて差分のあるノートブックだけ revert | 無駄な revert をしない。ロック状態も同時に回復。**lastSeq が指摘 1・2 の根本対策（自己識別）を兼ねる** | ブラウザ側に lastSeq の Map を持つ |
| B | 再接続時に開いている全ノートブックを無条件 revert | 実装最小 | 切断が頻発する環境で不要な revert が走る。ロック回復には結局照会 API が必要。**指摘 1・2 は未解決のまま残る** |
| C | サーバー側にイベント履歴バッファを持ち、再接続時に欠落分を再送 | 差分粒度の回復 | ADR-0002 で不採用の複雑化（履歴・再送機構）。revert がフォールバックとして既にあるため不要 |

採用理由: A は照会 API 1 本で seq とロックの両方を回復でき、lastSeq がそのまま監査指摘 1（revert 要否の seq 判定）・2（自己エコー抑制）の共通対策になる。

### 自己エコー抑制の方式（指摘 2）

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | 自分の保存完了（`context.saveState` = 'completed'）時に照会 API で最新 seq を取得し lastSeq に記録 | 実際の seq 値を記録するため確実。resync と同じクライアント関数を再利用 | 保存ごとに HTTP GET 1 回。エコー到達が fetch より先の race がある（→ debounce タイマー発火時の再チェックで吸収） |
| B | 保存完了時刻を記録し、一定時間窓内の `notebook_changed` を自己エコーとみなす | HTTP 不要 | 時間窓のチューニングが脆弱。seq を記録しないため lastSeq が進まず、resync との整合が崩れる |

採用理由: A は「lastSeq = 自分が既知の状態」という単一の意味論に収束し、resync・イベント判定と同じ比較ロジックを共有できる。race は revert が 300ms debounce であるため、タイマー発火時に `seq <= lastSeq` を再チェックすれば実用上閉じる。

ADR 要否: 不要（ADR-0002 の設計要素 3 で決定済み。本タスクはその実装 + 監査指摘の吸収で、状態の所有権・コンポーネント間契約の新規決定はない）。

## 異常系・不変条件

- 切断中の変更（本タスクの主題）: 統合テスト「切断中 notebook_add_cell → 再接続 → seq 進行 + ディスク反映」で検証（完了条件 5）
- 照会 API 自体の失敗: resync は warn ログを出してスキップし、次回再接続時に再試行（ロックはサーバー強制があるため表示ずれのみで安全側）
- 照会 API への認証なしアクセス: 403（統合テストで検証、完了条件 4）
- 再接続直後に通知が届く race: 照会 → revert の間に `notebook_changed` が来ても seq 比較で判定するため、最悪でも冪等な revert が 1 回増えるだけ（debounce が吸収）
- ユーザー未保存変更との競合（指摘 1）: dirty かつ未知 seq → revert せず console.warn（ADR-0002 の帰結「競合通知 + 手動再読込」）。lastSeq を進めないため、ユーザーが保存/破棄した後の resync で回復できる
- 自己保存エコー（指摘 2）: `seq <= lastSeq` → スキップ。fetch が間に合わない race は debounce タイマー発火時の再チェックで吸収
- seq リセット（指摘 6）: リネーム後の新パスは lastSeq 未知（0）vs serverSeq 1 → 不一致 → 安全側の revert 1 回。サーバー再起動は WS 切断を伴うため、再接続時の resync が lastSeq を serverSeq で上書きし、イベント側の `seq <= lastSeq` スキップによる revert 漏れ窓を閉じる（→ 技術的考慮事項）
- 不変条件: I5 充足（本タスクの目的）。I2: ロック強制はサーバー側のまま（表示の再適用のみ追加）。I3: 照会ハンドラーはメモリ読み取りのみ。I6: seq/ロックストアの読み取りは Tornado 単一イベントループ上で await を挟まないスナップショット読み

### 技術的な考慮事項

- **seq 比較の方向（指摘 6 の吸収）**: resync の判定は `serverSeq !== lastSeq`（大小比較ではない）。これにより (a) リネーム後の新パス（serverSeq=1、lastSeq=0）は安全側の revert 1 回、(b) サーバー再起動で serverSeq が 0/低値に戻った場合も revert → lastSeq を serverSeq で上書きするため、以後のイベント側 `seq <= lastSeq` スキップで revert 漏れが起きない。サーバー再起動は必ず WS 切断 → 再接続 → resync を経由するため、lastSeq が stale なままイベントを取りこぼす窓は resync 完了までに限られる。`_seq_store` の残置エントリ（削除・リネームで残る）は monotonic 性を壊さないため掃除しない（本タスクのスコープ外、比較ロジックで吸収）
- **dirty の意味の純化**: `handleCellExecuteStart/End` はモデルを直接変更して dirty を立ててしまうため、変更前の dirty を退避し変更後に復元する。これで「dirty = ユーザーの未保存編集あり」が成立し、dirty → スキップ + 競合 warn（isLocked 不使用）が指摘 1 の (a)（ロック成立前のユーザー編集の revert 破棄 — dirty なら revert しない）と (b)（lock_released 先着による dirty スキップでの AI 変更取りこぼし — dirty でなければ seq 未知として revert される）の両方を塞ぐ
- **lastSeq の更新タイミング**: イベント受信時ではなく **revert 成功時**に更新する（revert 失敗時に lastSeq だけ進むと resync でも回復できなくなるため）。dirty スキップ時も据え置く（ユーザーが保存/破棄した後の resync で回復可能にする）
- **自己保存の race**: 保存完了 → fetch 完了より先にエコーイベントが届くと未知 seq として revert がスケジュールされるが、300ms debounce のタイマー発火時に `seq <= lastSeq` を再チェックするため、fetch（通常数十 ms）が間に合えばキャンセルされる。間に合わなくても同一内容の revert 1 回（表示変化なし）に留まる
- **`unlockAll()`（切断時の全ロック解除表示）は維持**しつつ、再接続時の resync でロック表示を復元する（「サーバーに強制があるので表示は安全側に倒す」という 21.2 の方針と整合）。`lockNotebook` は既ロックで早期 return する冪等実装のため再適用は安全
- **resync は冪等**（何度呼んでも同じ最終状態）。初回接続時にも発火するが、開いた直後のノートブックはディスクと一致しており revert は表示に影響しない（ディスクが真実）
- **handlers.py へ module-level import を追加しない**: `SyncStateHandler` を handlers.py 内に定義し sync_state を get() 内で lazy import することで、`conftest.py` の `custom_api.ai_events` / `custom_api.handlers` モック（60-79行）や既存テストの handlers ロード（test_cell_execute_batch.py）を壊さない。**前回実装試行で計画外の handlers.py・conftest.py・test_kernel_crash_recovery.py に変更が波及した根本原因（import 追加によるモック不足の連鎖）をこの設計で回避する**
- **ルート追加位置**は `get_handlers()` の AI 同期セクション（`/api/ai/locks` の隣）。contents 系ルートの相対順序を変えない（`test_cell_execute_batch.py` の route 順序テスト `test_execute_batch_route_before_cells_route` に影響させない）
- **ロックキーの正規化基準の差**: ブラウザの `normalizeNotebookPath`（`path-utils.ts:8-10`）は先頭スラッシュ削除のみで、Issue #90 がサーバー側で正規化する `.` セグメント・連続スラッシュは正規化しない。resync のロック突き合わせ（サーバー返却パス vs `lockedNotebooks` キー）は「サーバーが正規化済みキーを返し、ブラウザ側キーも同一イベント由来のパスで構築される」ことで一致する前提を置く。表記揺れパスは MCP 正規経路では発生しないため実害は限定的だが、実装時にこの前提をコメントで明記する
- I3: SyncStateHandler はメモリ読み取りのみで I/O なし。I6: get_all / get_locks は await を挟まない単一イベントループ上のスナップショット読みで並行安全
