# タスク詳細: 18.1 カーネルクラッシュ検出と自動復旧

## 概要

カーネルがクラッシュ（dead 状態）した際に自動的に検出し、新しいカーネルを起動してセッションを復旧する。クラッシュ前のワークスペース情報（sandbox、cwd）を引き継ぎ、MCP 経由の操作を中断なく継続できるようにする。

## 背景

- 要件定義 NF3 に「カーネルクラッシュ時、自動的に新しいカーネルを起動可能（Phase未着手）」と記載されている
- 現在の `KernelRestartHandler`（`POST /api/kernels/{id}/restart`）は `kernel_manager.restart_kernel()` を呼ぶだけで、ワークスペース sandbox の再注入を行っていない
- カーネルクラッシュ後のリカバリには、dead 状態の検出、新カーネル起動、sandbox 再注入の3ステップが必要

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-server.md` の「NF3: 可用性」セクション
- API仕様: `docs/design/api-contracts.md` の「POST /api/kernels/{kernel_id}/restart」セクション

### 実装手順

1. **`jupyter_server_config.py` に自動再起動設定を追加**
   - `c.MappingKernelManager.restart_dead_kernels = True` を設定
   - Jupyter Server 標準機能でカーネルが dead 状態になった際に自動的に再起動する

2. **`__init__.py` に `restart_kernel` のラッパーを追加**
   - `shutdown_kernel` と同様に `restart_kernel` もラップする
   - 再起動後に workspace sandbox を再注入するロジックを追加
   - `_kernel_workspace_map` から workspace_id を取得し、`generate_sandbox_code()` で sandbox を再注入
   - workspace 情報がない場合（ワークスペース外のカーネル）はスキップ

3. **`KernelRestartHandler` に sandbox 再注入を追加**
   - `POST /api/kernels/{id}/restart` の明示的な再起動時にも sandbox を再注入
   - `session_handlers.get_kernel_workspace()` で workspace_id を取得
   - workspace_id がある場合、`KernelExecutor` で sandbox コードを実行
   - sandbox 注入前にカーネルの準備完了を待機（`asyncio.sleep(2)`、セッション作成時と同様）

4. **ユニットテストを作成**
   - `test_kernel_crash_recovery.py` を作成

5. **要件定義ドキュメントを更新**
   - NF3 セクションの「Phase未着手」を実装済みの内容に更新

### 技術的な考慮事項

- **`restart_dead_kernels` の動作**: Jupyter Server の `MappingKernelManager` は、culler ループ内で dead 状態のカーネルを検出し `restart_kernel()` を呼ぶ。これはインターバル（`cull_interval`）ごとにチェックされるため、検出までに最大 `cull_interval` 秒（デフォルト: `max(60, KERNEL_TIMEOUT // 5)`）の遅延がある
- **sandbox 再注入のタイミング**: `restart_kernel()` は内部で既存カーネルプロセスを停止→新プロセス起動を行う。ラッパーでは `restart_kernel()` 完了後に sandbox を再注入する。IOPub チャンネル準備のため `asyncio.sleep(2)` が必要（`CustomSessionsHandler.post` と同じパターン）
- **`_kernel_workspace_map` の保持**: `restart_kernel()` は kernel_id を変更しないため、既存のマッピングはそのまま有効。`unregister_kernel` は呼ばない
- **sandbox 再注入失敗時**: sandbox の再注入に失敗した場合、カーネルは起動しているがセキュリティ制限が効いていない状態になる。この場合はログに警告を出力し、次回の操作時にエラーを返すか、カーネルをシャットダウンする
- **変数の喪失**: カーネルの再起動（手動・自動とも）では実行状態（変数、import）は失われる。これは Jupyter の標準動作であり、本タスクのスコープ外

## テスト計画

### ユニットテスト (`jupyter-server/tests/test_kernel_crash_recovery.py`)

1. **`restart_kernel` ラッパーのテスト**
   - workspace_id がある場合に sandbox 再注入が呼ばれることを確認（mock）
   - workspace_id がない場合にスキップされることを確認
   - sandbox 再注入が失敗した場合のエラーハンドリングを確認

2. **`KernelRestartHandler` のテスト**
   - 明示的な再起動後に sandbox が再注入されることを確認
   - 存在しないカーネルの再起動が 404 を返すことを確認

### 手動テスト

1. `scripts/test.sh --rebuild jupyter-server` でリビルド＆テスト
2. Docker 環境でワークスペース + カーネルを起動
3. カーネル内で `import os; os._exit(1)` を実行してクラッシュさせる
4. カーネル状態が dead → starting → idle に遷移することを確認
5. 復旧後のカーネルで他ワークスペースへのアクセスが PermissionError で拒否されることを確認
6. `POST /api/kernels/{id}/restart` で明示的に再起動し、sandbox が有効であることを確認
