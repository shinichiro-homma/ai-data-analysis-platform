# タスク詳細: 23.5 sandbox の os ホワイトリスト統一

## 概要

`code_validator.py`（AST 静的検査・主防御）と `workspace_sandbox.py`（ランタイム monkey-patch・二重防御）の os 関数制御方式を統一する。現在 code_validator は import 時にホワイトリスト（`ALLOWED_OS_ATTRIBUTES`）、呼び出し時にブロックリスト（`BLOCKED_OS_FUNCTIONS`）の二重基準で運用されており、`os.rename` / `os.replace` がブロックリストから漏れている。workspace_sandbox も `os.rename` を一切ガードしていない。code_validator の属性アクセス検査をホワイトリスト方式に統一し、workspace_sandbox に `os.rename` / `os.replace` のランタイムガードを追加する。

## 調査したファイル

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | code_validator の `_check_attribute` をホワイトリスト化。sandbox に `os.rename`/`os.replace` のワークスペース境界チェックを追加 | 将来の os 関数追加に対して安全（未知の関数は自動でブロック）。import 時と属性アクセス時で同一の定数を使用し一貫性が高い | `_is_blocked_os_attr()` の廃止に伴い既存テストの前提が変わる |
| B | code_validator / sandbox 両方のブロックリストに `os.rename`/`os.replace` を追加するだけ | 変更量が最小。既存テストへの影響なし | ブロックリストとホワイトリストの二重基準が残る。将来の漏れリスクが解消されない |

採用理由: 案 B は即時の漏れを塞ぐだけで、根本原因（ブロックリストのデフォルト許可）が残る。案 A は `ALLOWED_OS_ATTRIBUTES` に明示的に追加しない限り新しい os 関数もブロックされるため、防御の方向が正しい（deny by default）

ADR 要否: 不要。os 関数の許可判定方式の変更であり、状態の所有権やコンポーネント間契約の変更を伴わない

### 技術的な考慮事項

- **os.rename の引数**: `os.rename(src, dst)` は 2 引数。ワークスペース境界チェックは src / dst 両方に適用する必要がある（`_sandbox_chdir` は 1 引数のため、ラッパーの構造が異なる）
- **os.replace と os.rename の違い**: `os.replace` は dst が存在する場合に上書きする点のみ異なる。sandbox での扱いは同一（パスチェック + 元関数へ委譲）
- **ALLOWED_OS_ATTRIBUTES の拡張不要**: 現在のホワイトリスト（`path`, `sep`, `linesep`, `getcwd`, `listdir`, `stat`, `fspath`, `PathLike`, `environ`）はすべて読み取り専用/安全な関数。`rename`/`replace`/`makedirs` 等のファイル操作関数を追加する必要はない
- **pathlib.Path.rename の扱い**: pathlib の rename はこのタスクのスコープ外。code_validator は pathlib をモジュールレベルで許可しており、sandbox も Path.rename をラップしていない。必要であれば将来タスクで対応

## リスクと検知方法

- **既存テストの破損**: code_validator のホワイトリスト化により、これまでブロックリストに依存していたテストが失敗する可能性 → テスト自体は「この os 関数がブロックされる」ことを検証しているだけなので、判定方式が変わっても結果は同じ。ステップ 1 のスコープテストで検知
- **意図しない関数のブロック**: ホワイトリスト化により、ブロックリストに入っていなかった os 関数もブロックされる。これは意図的な動作（deny-by-default）であり、代替手段が存在する。主な影響と代替:
  - `os.getenv()` → `os.environ.get()`（`environ` はホワイトリスト内）
  - `os.makedirs()` / `os.mkdir()` → `pathlib.Path.mkdir()`
  - `os.walk()` / `os.scandir()` → `pathlib.Path.rglob()` / `pathlib.Path.iterdir()`
  - `os.remove()` / `os.unlink()` / `os.rmdir()` → 変更なし（既にブロックリストでブロック済み）
  - 検知不要（意図的ブロック）。プロダクションコード・テストコードに `os.getenv` / `os.makedirs` の使用がないことを `grep` で確認済み
