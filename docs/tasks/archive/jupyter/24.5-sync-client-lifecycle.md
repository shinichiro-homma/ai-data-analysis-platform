# タスク詳細: 24.5 同期クライアントのライフサイクルと表示不整合の解消

## 概要

jupyterlab-ai-sync プラグインのリソースリーク（WebSocket 未切断）、revert タイマーのクローズ済みパネル参照、ephemeral イベントと revert の順序ちらつきを解消する。`tmp/refactor-notes.md` §2-4・§2-8 と `tmp/audit-21.2-21.3-report.md` 指摘 5・7 への対応。

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | IDisposable 的ライフサイクル + panel 再解決 + ephemeral 時 revert 取消 | 3 つの問題を根本から解消。JupyterLab の IDisposable 慣習に沿う。テスト可能なメソッドを export | 変更ファイル 3 + テスト 2 |
| B | 最小修正（disconnect 呼び出し追加のみ + try/catch 強化） | 変更量が最小 | revert/ephemeral の順序問題が未解消。timer リークが残る |

採用理由: 案 B は §2-8・監査指摘 7（ephemeral/revert ちらつき）を未解消のまま残す。案 A は 5 ファイルで 3 問題を根本解消し、スコープ上限内に収まる。

ADR 要否: 不要。状態の所有権やコンポーネント間契約の変更なし。既存の WebSocketClient/NotebookUpdater の内部改善のみ。

## 異常系・不変条件

- 該当する異常系: **切断**（disconnect 未呼び出しによる WebSocket リーク）、**並行**（revert debounce 中のノートブック閉じ）、**順序**（ephemeral イベントと revert の到着順によるちらつき）。完了条件の 2・3・5 で検証
- 関係する不変条件: **I5**（失敗しうる通信には回復パス）— revert の取消は `notebook_changed` の再送で回復するため、回復パスは維持される。ephemeral 取消後もサーバーは execution 完了時に新たな `notebook_changed` を送信し、最終的な revert は正しく発火する

### 技術的な考慮事項

- `app.shell.disposed` は `Widget.disposed` シグナル（Lumino）。通常のブラウザ操作（タブ閉じ）では発火しないが、開発時のホットリロードやプラグインの再活性化時に WebSocket の無限再接続ループを防ぐ
- `cancelPendingRevert` で ephemeral イベント時に revert を取り消しても、サーバーは execution 完了時に新たな `notebook_changed` を送信するため、最終状態は必ず revert される（I5 維持）
- `panel.disposed.connect` でのクリーンアップでは、`panel.context.path` を `widgetAdded` 時点で取得する。ノートブックのリネーム後は旧パスのタイマーがクリアされ、新パスは新たなイベントで管理される

## リスクと検知方法

- **ephemeral 取消が revert を遅延させないか**: `cancelPendingRevert` は pending revert のみ取り消す。次の `notebook_changed` で新しい revert がスケジュールされるため、最終的なディスク同期は保証される。テストで確認
- **dispose 後の再接続防止が正しく動くか**: `_disposed` フラグと `connect()` / `scheduleReconnect()` のガードで防止。テストで確認
- **既存テスト（event-validation, lock-manager, path-utils, notebook-finder, file-browser-customizer）への影響**: 変更は内部実装のみで export インターフェースは追加のみ（既存 export は変更なし）。フルゲートで確認
