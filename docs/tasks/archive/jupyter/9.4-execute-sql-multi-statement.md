# タスク詳細: 9.4 execute_sql 複数SQL命令句対応

## 概要

`execute_sql` の SQL バリデーションをブラックリスト方式で拡張する。現在は DELETE のみ拒否しているが、危険な操作（スキーマ変更、権限操作等）も明示的にブロック対象に追加する。併せて、jupyter-server と jupyter-mcp の両方にユニットテストを追加する。

### 現状

現在の `_classify_sql` 関数は以下のロジック：
- SELECT / WITH → `is_select=True`
- DELETE → エラー（拒否）
- **それ以外すべて → `is_select=False`（許可）**

DDL/DML/トランザクション系の実行自体は 13.1/13.2 で対応済み。ただし、ブラックリストが DELETE のみのため、`ALTER TABLE`, `GRANT`, `REVOKE`, `CREATE TABLE`（非TEMP）, `CREATE INDEX` 等の危険な操作も通ってしまう。

### このタスクで実現すること

1. ブラックリスト拡張（jupyter-server）— 危険な SQL コマンドを追加ブロック
2. `CREATE`/`DROP` の後続トークンを `sqlparse` で解析し、安全な形式（TEMP TABLE, FUNCTION）のみ許可
3. 要件定義をブラックリスト方式に更新
4. jupyter-server のユニットテスト追加（`_classify_sql` 等の純粋関数）
5. jupyter-mcp のユニットテスト追加（DDL/DML/トランザクション系の各シナリオ）

### 実装手順

#### ステップ 0: 要件定義の更新（前提作業）

要件定義の F7.1 / F9.1 を、現在のホワイトリスト記述（「以下のSQL命令句を実行可能」）からブラックリスト記述に変更する。

**変更前（ホワイトリスト方式）:**
> 以下のSQL命令句を実行可能:
> - SELECT / WITH, DDL系: CREATE TEMP TABLE, DROP TABLE, ..., DML系: INSERT INTO, UPDATE, トランザクション系: BEGIN, COMMIT, ROLLBACK
> - DELETE文は禁止

**変更後（ブラックリスト方式）:**
> 以下のSQL命令句を**拒否**する:
> - DELETE（データ削除）
> - ALTER TABLE / ALTER COLUMN（スキーマ変更）
> - GRANT / REVOKE（権限操作）
> - CREATE TABLE（非TEMP。永続テーブル作成）
> - CREATE INDEX / DROP INDEX（インデックス操作）
> - VACUUM / ANALYZE（メンテナンス操作）
>
> 上記以外のSQL命令は実行可能。ただし CREATE / DROP は後続トークンで安全性を判定する:
> - CREATE: TEMP TABLE / TEMPORARY TABLE / OR REPLACE FUNCTION のみ許可
> - DROP: TABLE / FUNCTION のみ許可

※ この要件変更は `/custom-change-requirement` → `/custom-apply-change` ワークフローで実施する。

#### ステップ 1: jupyter-server `_classify_sql` のブラックリスト拡張

`sql_handlers.py` の `_classify_sql` 関数を以下のロジックに変更する：

```python
# 明示的ブラックリスト
BLOCKED_COMMANDS = {"DELETE", "ALTER", "GRANT", "REVOKE", "VACUUM", "ANALYZE"}

# SELECT系
if first_keyword in ("SELECT", "WITH"):
    return SqlClassification(is_select=True, error=None)

# ブラックリスト
if first_keyword in BLOCKED_COMMANDS:
    return SqlClassification(is_select=False, error=f"{first_keyword} statements are not allowed.")

# CREATE の後続判定（sqlparse トークン解析）
if first_keyword == "CREATE":
    return _classify_create(stmt)

# DROP の後続判定（sqlparse トークン解析）
if first_keyword == "DROP":
    return _classify_drop(stmt)

# その他は非SELECT として許可
return SqlClassification(is_select=False, error=None)
```

**`_classify_create` 関数（新規）:**
`sqlparse` のトークン列を走査し、以下のパターンのみ許可：
- `CREATE TEMP TABLE ...` / `CREATE TEMPORARY TABLE ...`
- `CREATE OR REPLACE FUNCTION ...`

それ以外（`CREATE TABLE`, `CREATE INDEX`, `CREATE VIEW` 等）は拒否。

**`_classify_drop` 関数（新規）:**
`sqlparse` のトークン列を走査し、以下のパターンのみ許可：
- `DROP TABLE ...`
- `DROP FUNCTION ...`

それ以外（`DROP INDEX`, `DROP DATABASE`, `DROP VIEW` 等）は拒否。

### 技術的な考慮事項

- **CREATE / DROP の後続判定は `sqlparse` で行う**: `sqlparse` のトークン列を走査し、`token.ttype` と `token.normalized` で判定する。文字列の前方一致ではなく、トークンレベルの解析を行うことで、コメントや余分な空白が挟まっても正しく判定できる
- **大文字小文字**: `sqlparse` の `token.normalized` は大文字化されているため、比較はすべて大文字で行う
- **エラーメッセージ**: 既存の DELETE 拒否メッセージ `"DELETE statements are not allowed."` と統一感のある形式にする（例: `"CREATE TABLE statements are not allowed. Use CREATE TEMP TABLE instead."` ）
- **後方互換性**: 13.1/13.2 で実装済みの DDL/DML/トランザクション系の動作（CREATE TEMP TABLE, DROP TABLE, INSERT INTO, UPDATE, BEGIN, COMMIT, ROLLBACK）は変更しない。新たにブロックされるのはブラックリスト追加分のみ
- **`_classify_sql` のテスト方法**: 既存の `test_base.py` と同様に、純粋関数を直接テストする方式（HTTP モック不要）
- **要件変更ワークフロー**: ステップ 0 の要件変更は `/custom-change-requirement` → `/custom-apply-change` で実施する
