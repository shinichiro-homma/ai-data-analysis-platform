# タスク詳細: 23.1 カーネル単位の実行直列化

## 概要

同一カーネルへの並行 execute リクエストで出力が混線する問題（`tmp/refactor-notes.md` §4-1）を解消する。

現状の `KernelExecutor.execute()` は実行ごとに新規 client を生成して同じ IOPub チャンネル（カーネル単位の broadcast）を購読するが、`parent_header.msg_id` によるメッセージのフィルタリングを行っていない。このため同一カーネルに 2 つの実行が並行すると、リクエスト A のレスポンスにリクエスト B の `stream` / `execute_result` が混入し、さらに B 由来の `status: idle` で A の収集ループが早期終了しうる。

対策は 2 層:

1. **カーネル単位の asyncio.Lock による直列化**（不変条件 I6 の充足）: 同一カーネルでの実行を同時に 1 つに制限する
2. **`parent_header.msg_id` によるメッセージフィルタ**: タイムアウトでロックを解放した後もカーネル側では実行が継続するため、直列化だけでは「前リクエストの遅延メッセージが次リクエストに混入する」余地が残る。自リクエスト由来のメッセージのみを収集することで防御する

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | カーネル単位 asyncio.Lock で `execute()` を直列化 + `parent_header.msg_id` で自リクエストのメッセージのみ収集 | I6 を「直列化」で素直に充足。タイムアウト後の遅延メッセージ混入（ロックだけでは残る穴）もフィルタで防御。変更が kernel_executor.py に閉じる | ロック待機中はリクエストが滞留する（カーネルはシングルスレッドなのでスループット低下は実質なし） |
| B | msg_id フィルタのみ（ロックなし、並行実行を許容） | 待機なし | カーネル自体が逐次実行のため並行の利点がない。後着リクエストのタイムアウトが先行実行の所要時間を含んでしまい、タイムアウト超過後もカーネル側でコードが実行される事象が増える。I6 の「並行しても安全」の根拠がメッセージ層のみで、execution_count の取り違え等の検証負担が大きい |
| C | ロックのみ（フィルタなし） | 変更最小 | タイムアウトでロック解放後、カーネル側で継続中の前リクエストの遅延 IOPub メッセージが次リクエストの収集ループに混入する残存バグ（調査で確認済みのシナリオ）。混線の根本原因（無フィルタ購読）が残る |

採用理由: A はロックで「並行実行」を、フィルタで「タイムアウト残存メッセージ」をそれぞれ塞ぎ、§4-1 の混線シナリオを両方向から閉じる。B 単独は実行時間の予測不能化という新しい問題を生み、C 単独は異常系（タイムアウト）で混線が再発する。

ロックの設置場所はハンドラ層ではなく `KernelExecutor.execute()` 内とする。呼び出し元 8 箇所（`handlers.py` の 6 箇所 = execute API・カーネル状態取得・変数一覧・変数単体・セル実行・バッチ、`session_handlers.py:123-125` の sandbox 注入、`__init__.py:135-136` の restart/autorestart 再注入）がすべて自動的に直列化の対象になり、登録漏れが構造的に起きないため。

ADR 要否: 不要（コンポーネント内部の実装改善であり、状態の所有権・コンポーネント間契約・API 外形を変えない。I6 充足の根拠は本計画に記載）

## 異常系・不変条件

- 該当する異常系:
  - **並行**: 同一カーネルへの並行 execute → ロックで直列化される（新規テストで検証）
  - **タイムアウト**: 実行タイムアウト時も finally でロックが解放され、次のリクエストが実行できる。前リクエストの遅延メッセージは msg_id フィルタで無視される（新規テストで検証）
  - **例外**: IOPub 受信中の予期しない例外でもロックが解放される（新規テストで検証）
  - **再起動（autorestart）と再注入の順序**: autorestart 由来の sandbox 再注入（`__init__.py:135-136`）もロックの取得対象になる。クラッシュ時に先行 execute がロックを保持していた場合、再注入はその finally 解放（最悪で先行 timeout まで）を待つ。この間「再起動済みだが sandbox 未注入」の窓が延びうるが、**この窓自体はロック導入前から存在する既存ギャップ**（再注入は `asyncio.ensure_future` の独立タスクで、ユーザー execute との順序保証がもともとない）。asyncio.Lock の待機は FIFO のため、再注入より後に到着したユーザー execute は必ず再注入の後に実行されるようになり、順序はむしろ改善する（悪化しない根拠）。窓を完全に閉じる（再注入完了までカーネルへの実行を拒否する）のは既存ギャップの解消であり本タスクのスコープ外（必要なら別タスクで扱う）
- 関係する不変条件:
  - I6（並行アクセスの直列化）: 本タスクで既知違反を解消。完了後に `docs/design/invariants.md` の I6 に充足済みの注記を追記する
  - I3（ブロッキング I/O 禁止）: asyncio.Lock は非ブロッキング（await）であり抵触しない

### 技術的な考慮事項

- **ロック待機に上限を設けない**: リクエストの `timeout` は「実行時間」の上限（`base.py` の `validate_timeout` の思想）であり、待機時間は先行実行の timeout（最大 300 秒）で実質的に上限が決まる。待機上限が必要になったら別タスクで扱う
- **restart / autorestart 時にロックを強制解放しない**: `asyncio.Lock` の非所有タスクからの release は相互排他を壊す。実行中の execute は finally で必ず解放するため、再起動後の新リクエスト・sandbox 再注入は最悪でも先行実行の timeout まで待つだけで固着しない（kernel_id は再起動で変わらないことを調査で確認済み）
- **restart / autorestart 再注入もロック対象に含める（除外しない）**: 除外すると再注入の IOPub 購読が並行実行と重なり、直列化の例外パスが生まれる。混線自体は msg_id フィルタで防げるが、「全 execute が一律にロックを通る」単純さを優先する。再注入待機の影響と順序の根拠は「異常系・不変条件」の再起動の項を参照
- **execute-batch はセル単位でロックを取得・解放する**: バッチ全体の排他は行わない（現状もバッチ中に他リクエストが割り込める仕様であり、本タスクの目的は出力混線の防止。バッチ全体の排他が必要なら別タスク）
- **`get_execution_count()` / `get_variables()` / `get_variable()` は `execute()` 経由のため自動的に直列化される**（個別のロック処理は追加しない）
- ロック導入により、これまで「たまたま並行で通っていた」呼び出し（例: 実行中の変数取得）は先行実行の完了まで待つようになる。応答時間は伸びるが、混線した誤データを返すより正しい
- 混線の残存リスク: タイムアウト後にカーネル側で実行が継続している間の `execution_count` はカーネル内部で進むため、次リクエストの `execute_input` が示す count は正しい（カーネルが採番する）。フィルタ導入後に問題は残らない
