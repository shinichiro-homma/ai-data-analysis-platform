# タスク詳細: 24.1 フロントエンドテスト基盤と純粋関数のユニットテスト

## 概要

jupyterlab-ai-sync に vitest によるユニットテスト基盤を新設し、純粋関数モジュール（`path-utils.ts` / `notebook-finder.ts`）の仕様化テストを整備する。`scripts/test.sh` と CI（`jupyterlab-ai-sync-build` ジョブ）にテスト実行を組み込み、Phase 24 後続タスク（24.2〜24.5 のリファクタリング）の回帰防止基盤とする。

対象コンポーネント: jupyterlab-ai-sync（＋ scripts/test.sh・ci.yml のテスト実行組み込み）
タスク種別: test

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyterlab-ai-sync.md` の F4（対象ノートブックの特定）。本タスクは機能追加なし（既存挙動の仕様化テスト）
- テスト方針: `.claude/rules/testing.md`（ユニットテストで主要ロジックをカバー）、`.claude/rules/tdd.md`

## 調査したファイル

- `jupyterlab-ai-sync/src/path-utils.ts:8-10`（全 10 行）: `normalizeNotebookPath` — 先頭スラッシュ 1 つのみ除去する純粋関数（依存ゼロ）
- `jupyterlab-ai-sync/src/notebook-finder.ts:14-38`（全 38 行）: `findNotebookByPath` — 完全一致（currentWidget → find）→ サフィックス一致（`'/' + path` で境界確認）の順で探索。`INotebookTracker` は `currentWidget` と `find()` のみ使用（最小スタブでテスト可能）
- `jupyterlab-ai-sync/package.json`: `"type": "module"`、`scripts` に `test` なし、devDependencies は `typescript` / `@jupyterlab/builder` のみ。npm workspaces 非参加（node_modules 個別管理）
- `jupyterlab-ai-sync/tsconfig.json`: `"types": []`・`"composite": true`・`"rootDir": "src"`・`include: ["src/**/*"]` — 本体ビルド設定は変更しない。`rootDir: "src"` を継承したまま tests/ を include すると TS6059 になるため、テスト用 tsconfig では `rootDir: "."` に上書きする（計画レビューの実測指摘）
- `scripts/test.sh:312-341`: jupyterlab-ai-sync 分岐。現状は typecheck（`tsc --noEmit`）と build のみで `npm test` を実行しない。`:98-103` で `-- FILE...` 絞り込みの対象外
- `.github/workflows/ci.yml:178-215`: `jupyterlab-ai-sync-build` ジョブ。`npm ci` + `uv run --project .. npm run build` のみ。ルートの `npm ci` は実行しない（→ ルート node_modules に依存する設定は CI で壊れる）
- `.github/workflows/ci.yml:346-347`: `npm --prefix jupyterlab-ai-sync audit --audit-level=high`（devDep 追加は audit 対象になる）
- `jupyter-mcp/vitest.config.ts` / `vitest.shared.ts`: 既存 MCP コンポーネントの vitest 設定。shared 設定はトップレベルで `dotenv` を import する
- `jupyter-mcp/tests/unit/utils/path-validator.test.ts:1-33`: 純粋関数テストの代表例（日本語テスト名 `'入力 => 期待'` 形式、`vitest` からの明示 import）
- 調査エージェント結果: フロントエンドテストは皆無（テストファイル 0 件・テストランナー devDep なし）。`path-utils` / `notebook-finder` が最も依存が薄くテスト導入の起点に適する

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | vitest を standalone 設定で導入（`vitest.shared.ts` を import しない） | プロジェクト標準のテストランナーと一致。ESM（`"type": "module"`）ネイティブ対応。CI の `jupyterlab-ai-sync-build` ジョブ（ルート npm ci なし）でもそのまま動く | 共有設定 `vitest.shared.ts` と設定値の二重管理（globals / environment の 2 項目のみ） |
| B | jest を導入 | JupyterLab 公式テンプレートの実績 | ESM 対応に transform 設定が必要。プロジェクト内に前例がなく規約・チートシートも vitest 前提 |
| C | Playwright（galata）でブラウザ統合テストを先行整備 | AC3/AC5/AC6 を実ブラウザで検証できる | JupyterLab 起動・CI へのブラウザ導入コストが大きい。プロジェクトには playwright-cli による対話的動作確認の運用が既にあり（`.claude/rules/testing.md`）、後続タスクの UI 検証はそちらで担保できる |
| D | `vitest.shared.ts` の dotenv import を `loadEnv` 内の遅延取得に変えて `sharedTestConfig` を共有 | I8/DRY を完全に満たす | `loadEnv` は jupyter-mcp / document-mcp の `vitest.config.ts` から同期呼び出しされており、遅延化は共有ファイルの契約変更として 3 コンポーネントへ波及する。重複回避できる値は `globals` / `environment` の 2 項目のみで割に合わない |

採用理由: 既存 2 コンポーネント（jupyter-mcp / document-mcp）と同じ vitest に揃えるのが学習・規約コスト最小。shared 設定を import しないのは、`vitest.shared.ts` がトップレベルで `dotenv`（ルート node_modules）を import しており、CI の `jupyterlab-ai-sync-build` ジョブはルートの `npm ci` を実行しないため解決できないという構造的理由による（`.claude/rules/dry.md` の「共通ベースを extends」からの意図的逸脱。値は globals / environment の 2 項目のみで乖離リスクは小さい）。

ADR 要否: 不要（コンポーネント内のテスト基盤導入であり、状態の所有権・コンポーネント間契約・通信方式に触れない）。

### 技術的な考慮事項

- 本体 `tsconfig.json`（`composite: true` / `types: []` / `rootDir: "src"` / labextension ビルドの入力）は変更しない。tests の型チェックは `tsconfig.test.json` に分離し、`rootDir: "."` に上書きする（継承値 `src` のままでは `tests/` が TS6059 `is not under 'rootDir'` で失敗する — レビュー時に最小再現で実測済み）
- テストの実行は `scripts/test.sh` 経由を正とする（`.claude/rules/testing.md`）。npm 直接実行が許されるのは手順 1 の依存追加のみ
- テストは `vitest` から `describe` / `test` / `expect` を明示 import する（`path-validator.test.ts` と同形式。`types: []` 継承下でも型が解決される）
- `INotebookTracker` のスタブは `{ currentWidget, find }` のみ持つ最小オブジェクトを `as unknown as INotebookTracker` でキャストする（テストコード限定の許容。振る舞いレベルのモック — `.claude/rules/testing.md`）
- prettier の lint 対象（`jupyterlab-ai-sync/src/**/*.ts`）は変更しない。tests/ を lint 対象外とするのは他コンポーネント（jupyter-mcp 等も src のみ）と同じ扱い
- `scripts/test.sh:98-103` の `-- FILE...` 絞り込み対象外は維持する（テストファイル 2 件のため全件実行で十分。ファイル数が増えた時点で対応を検討）
- vitest 追加は CI の `npm audit --audit-level=high`（ci.yml:346-347）の対象になる。high 以上の脆弱性が出た場合はバージョン選定で回避する

## リスクと検知方法

- `scripts/test.sh` の分岐変更で既存フロー（typecheck / build）を壊す: 手順 6・8 のフルゲート実行で検知
- CI ジョブへの `npm test` 追加が docs-only スキップ条件（`needs.changes.outputs.code_changed`）と干渉する: 既存ステップと同じ `if` 条件のステップ内に追記することで回避。PR の CI 実行で検知
- `normalizeNotebookPath` の現仕様（先頭スラッシュ 1 つのみ除去、空文字はそのまま）を「バグ」と誤解してテストで別仕様を期待する: 本タスクは仕様化テスト（挙動変更なし）と手順 6 に明記。挙動変更が必要なら別タスクで行う
