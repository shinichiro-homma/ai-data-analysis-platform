# タスク詳細: 21.2 ノートブックロックのサーバー側強制

## 概要

ノートブックロックを jupyter-server 側の状態にし、書き込み系 API で強制する（不変条件 I2）。jupyter-mcp は編集ツール実行の前後でロック取得/解放 API を呼び、ブラウザ（jupyterlab-ai-sync）は `lock_acquired` / `lock_released` 通知に追従して readOnly 表示する（UX に格下げ）。`ai_edit_start` / `ai_edit_end` イベントは廃止。ロック解除がイベント配信の成否に依存する現行の固着バグ（`ai-edit-helpers.ts:72-80` が失敗を握りつぶす）を TTL で根絶する。

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | ロックストアを独立モジュール `notebook_locks.py` に置き、強制は `contents_manager.save` のラップ（単一チョークポイント）で行う。正当な書き込みは ContextVar 経由のロックトークンで識別 | ブラウザの標準 `/api/contents` 保存・カスタム API・今後増える書き込み経路すべてを 1 箇所で強制（I2 の「迂回できない層」） | ContextVar の伝播を理解する必要がある |
| B | 各カスタムハンドラー（cells PATCH / execute / PUT 等）の冒頭で個別にロック検査 | 実装が直感的 | ブラウザの標準 `/api/contents` PUT を強制できない（カスタム API しか通らない）。ハンドラー追加のたびに検査の書き忘れが可能 = 手動 allowlist と同じ構造問題の再生産 |
| C | 独自 `ContentsManager` サブクラスを `contents_manager_class` に設定 | Jupyter の公式拡張点 | jupyter_config の変更が必要で、既存の `__init__.py` メソッドラップ方式と二重の拡張機構になる。テストも重くなる |

採用理由: B はブラウザ保存を強制できず I2 を満たさない。A は既存の `_wrap_shutdown_kernel` と同型のラップで実現でき、書き込み経路の追加に対しても閉じている。

ADR 要否: 不要（ADR-0002 で決定済み。強制点の選定は本計画の「調査したファイル」に基づく実装詳細）。

## 参考にする既存実装

- コピー元: `jupyter-server/extensions/custom_api/session_handlers.py` の `_kernel_workspace_map` + アクセサ関数（同種のグローバルストア実装は 2 個目）
- コピー元: `jupyter-server/extensions/custom_api/__init__.py` の `_wrap_shutdown_kernel`（メソッドラップは 2 個目）

## 異常系・不変条件

- 切断・プロセス死: MCP がロック解放前に死んでも TTL で自動失効し、失効時に `lock_released` が配信される（完了条件の異常系で検証）
- 並行: 同一ノートブックへの二重 acquire は 423 を返す（先勝ち）。ロックストアの操作は Tornado のシングルイベントループ上で同期実行されるため race しない（await を挟まない）ことを実装の前提として明記する
- 不変条件: I2 を充足（本タスクの目的）。I6: ロックストアへの並行アクセスは上記の根拠で安全。I3: ロックストア操作はメモリのみでブロッキング I/O なし

### 実装手順

1. `notebook_locks.py` を TDD で実装する（acquire 成功/競合、release の所有者検証、TTL 失効、renew、`sweep_expired` が失効エントリを返す）。検証: `scripts/test.sh jupyter-server` で新規テストが成功する
2. `lock_handlers.py` と `get_handlers()` 登録を実装する。acquire は `{lock_token, expires_at}` を返し、競合時は 423 `NOTEBOOK_LOCKED`。検証: `scripts/test.sh jupyter-server` のハンドラーテスト（モックパターン踏襲）が成功する
3. `__init__.py` に `contents_manager.save` ラップを追加する: 対象 path がロック中かつ `lock_token_ctx.get()` が不一致なら `tornado.web.HTTPError(423)`。カスタム書き込みハンドラーの冒頭で `X-Lock-Token` ヘッダーを ContextVar に設定する。検証: ハンドラーテストで「ロック中 + トークンなし save → 423」「ロック中 + 正トークン → 成功」の両方が通る
4. ロック取得/解放/失効時に `_websocket_clients` へ `lock_acquired` / `lock_released` `{notebook_path}` を配信する（失効は 5 秒間隔のスイーパーから配信。実装方式は上記「作成するファイル」の注記参照）。検証: `scripts/test.sh jupyter-server` のイベント配信テストが成功する
5. jupyter-mcp: `client.ts` にロック API クライアントを追加し、`lock-helpers.ts` のミドルウェアヘルパー（acquire → 20 秒間隔で renew タイマー → finally で release + タイマー解除。release 失敗は warn ログのみ = TTL に委ねる）を実装。`tools/index.ts` の `handleToolCall` を差し替え、acquire が 423 の場合はツールを実行せず `NOTEBOOK_LOCKED` エラーレスポンスを返す。`ai-edit-helpers.ts` の emit 関数と `ai_edit_start/end` 型を削除する。検証: `scripts/test.sh jupyter-mcp` で新規・既存ユニットテストが成功する
6. jupyterlab-ai-sync: `notebook-updater.ts` の `ai_edit_start/end` case を `lock_acquired/lock_released` に差し替える（`AiEditStartEvent` 等の型名も変更）。検証: `scripts/test.sh jupyterlab-ai-sync --typecheck` とビルドが成功する
7. 要件定義（jupyter-server F4.2 / jupyter-mcp F6.1・AC8 / ai-sync F3・AC3）と `docs/design/api-contracts.md`（ロック API 3 メソッド・423・`X-Lock-Token`）を改訂する。検証: `uv run python scripts/check-docs-consistency.py` が成功する

### 技術的な考慮事項

- TTL デフォルトは 60 秒とし、acquire リクエストで上書き可能（上限 600 秒）。長時間実行（execute_code の timeout 最大 300 秒、execute_batch は無制限に近い）は MCP 側の renew タイマー（20 秒間隔）でカバーする
- `interrupt` はロック貫通（既存要件、`api-contracts.md` 設計方針）: interrupt はカーネル API でありノートブック書き込みを伴わないため、本設計では自然に貫通する（検査対象にしない）
- ブラウザ保存が 423 で拒否された場合、JupyterLab は標準のエラーダイアログを表示する（本タスクではカスタム通知は作らない。ロック中は readOnly 表示のため通常発生しない）
- `unlockAll()`（WS 切断時の全ロック解除表示）は維持する。表示が実状態とずれても、強制はサーバー側にあるため安全側（21.4 の再同期で復元）

## リスクと検知方法

- `contents_manager.save` ラップの副作用（ノートブック以外のファイル保存への影響）: 検査対象を `.ipynb` パスに限定し、既存の Contents 系テスト（`test_cell_*` 等）の全件成功で検知
- ContextVar が async ハンドラー内で伝播しないケース: 手順 3 の「正トークンで成功」テストで検知
- MCP の renew タイマー漏れ（clearInterval 忘れ）: `lock-helpers.test.ts` でタイマーのモック検証（`vi.useFakeTimers`）
- ai_edit_start/end 廃止によるブラウザ互換: 同一 PR 内で 3 コンポーネントを同時に更新するため中間状態はデプロイされない
