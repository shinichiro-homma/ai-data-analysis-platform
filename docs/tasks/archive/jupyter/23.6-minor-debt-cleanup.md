# タスク詳細: 23.6 軽微な負債の解消

## 概要

`tmp/refactor-notes.md` §4-6/7 で指摘された jupyter-server の軽微な技術的負債4件を解消する。挙動を変えない純リファクタ（Contents POST 重複・タイムアウトエラー3重複）と、エラーステータスの統一（DATABASE_URL）、状態管理の改善（_seq_store 掃除）を含む。

対象の負債:
1. **except 握りつぶし（log.debug のみ）** — `cell_handlers.py` のワークスペース解決フォールバックで `Exception` を `log.debug` でしか記録しない
2. **Contents POST の重複実装** — `ContentsListHandler.post` と `ContentsHandler.post` がほぼ同一コード
3. **タイムアウトエラー組み立て3重複** — コード実行系ハンドラ3箇所でタイムアウトレスポンスのdict組み立てがコピペ
4. **`_seq_store` 残置エントリの掃除** — ノートブック削除時に `sync_state._seq_store` のエントリが残り続ける
5. **DATABASE_URL 未設定時のエラーステータス不一致** — execute系は400、export系は500を返す

- 不変条件: `docs/design/invariants.md` の I8（rule of three — タイムアウトエラー3重複）

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | 各負債を局所ヘルパー抽出+フック追加で個別に解消 | 変更が局所的で影響範囲が小さい。既存テストで回帰検知可能。スコープ上限内（変更ファイル7、新規テスト7） | タイムアウトエラーの共通化が `base.py` と `cell_handlers.py` に分散する |
| B | Contents POST の重複を `ContentsHandler.post` 側に統合し、`ContentsListHandler.post` を削除（ルートを `ContentsHandler` にリダイレクト） | 重複を完全に排除 | ルート構成の変更が API 契約に影響。MCP 側の呼び出し元も確認が必要。リファクタタスクとしてはスコープ超過 |

採用理由: 案Aは各負債を独立して修正でき、既存のクラス構造やルーティングを変更しない。案Bは Contents API のルート変更を伴い、MCP 側への影響確認が必要になるためスコープ超過。

### `_seq_store` 掃除の方式比較

| 方式 | 概要 | 利点 | 欠点 |
|------|------|------|------|
| X（採用） | `__init__.py` で `contents_manager.delete` をラップ（`_wrap_contents_save` と同パターン） | カスタム API・標準 Jupyter API 両方の削除パスをカバーする単一チョークポイント。`_wrap_contents_save` と一貫したアーキテクチャ | `__init__.py` に変更が増える（変更ファイル+1） |
| Y | `contents_handlers.py` の `ContentsHandler.delete` にフック追加 | 変更が局所的 | 標準 `/api/contents/{path}` の DELETE ルート経由（JupyterLab UI からの削除等）でエントリが残置される |

採用理由: 方式Yでは JupyterLab 標準 API 経由の削除が漏れる。`_wrap_contents_save` と同じパターンで `_wrap_contents_delete` を実装する方式Xが、全削除パスをカバーする正しいアプローチ。

ADR 要否: 不要。局所的なヘルパー抽出とログレベル変更であり、コンポーネント間契約・方式選定を伴わない。

3. **`cell_handlers.py` のタイムアウトエラー組み立てを置換**

### 技術的な考慮事項

- `ContentsHandler.post` → `ContentsListHandler.post` への委譲は、Tornado ハンドラの `self` コンテキストが異なるため、直接のメソッド呼び出しではなく共通ヘルパー関数 `_handle_create_content(handler, body, path_default)` を抽出する
- `_seq_store` の rename 対応（`cm.rename` のラップ）は本タスクのスコープ外。`refactor-notes.md` §4-7 に記載のとおり、21.4 再計画で `!==` 比較 + resync 上書きにより機能影響はない。rename 後の新パスは seq=1 から始まるため、残置エントリの影響はメモリリークのみ（ノートブック数は通常少数のため実害なし）。将来的に rename API をカスタム API として追加する際に対応する
- タイムアウトエラーヘルパーは `base.py` に配置する（`cell_handlers.py` と `handlers.py` の両方から参照するため）
- `_wrap_contents_delete` は `_wrap_contents_save` と異なり、ロックチェックは不要（削除にロック保護は要件外）。`.ipynb` 判定と `remove_path` 呼び出しのみ
- `cell_handlers.py` のフォールバックログ: `resolve_workspace_for_kernel` の第3段フォールバック（L75-88）では、`Path.relative_to()` の `ValueError` はワークスペース外カーネルの正常ケースで発生する。これを `log.warning` にするとノイズになるため、例外種別で `log.info`（expected）と `log.warning`（unexpected）に分岐する
- バッチ実行のタイムアウトヘルパー利用: `_build_timeout_error_result` は `execution_time_ms` を引数に取るが、バッチ実行ではセル単位の経過時間は計測していない。バッチ実行では `result["error"]` のみを取り出し（`execution_time_ms` は最終レスポンスに含めない — 現在の実装と同じ）、`cells[i]["outputs"]` の nbformat エラーは別構造のため個別に組み立てる

## リスクと検知方法

- Contents POST の委譲変更でレスポンス形式が変わるリスク: 新規テスト `TestContentsPostDelegation` と MCP 側の統合テストで検知
