# タスク詳細: 23.2 同期 I/O のイベントループ外オフロード

## 概要

jupyter-server の `handlers.py`（ContentsPreviewHandler）と `workspace_handlers.py`（4 ハンドラー）で、async ハンドラー内の同期 I/O がイベントループをブロックしている。不変条件 I3（async コンテキストでブロッキング I/O をしない）の既知違反を解消し、`run_in_executor` でスレッドプールにオフロードする。

最も影響が大きいのは ContentsPreviewHandler の CSV 行数カウント（`sum(1 for _ in f) - 1`）で、大きな CSV では全行走査によりイベントループが数秒ブロックされる。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-server.md` の「F5: ファイル管理」「F6: ワークスペースディレクトリ管理」セクション
- 不変条件: `docs/design/invariants.md` の「I3: async コンテキストでブロッキング I/O をしない」
- 既存パターン: `extensions/custom_api/sql_handlers.py` の `run_in_executor` 実装

## 調査したファイル

- `jupyter-server/extensions/custom_api/handlers.py:960-1077`: ContentsPreviewHandler — `def get`（同期メソッド）内で stat, pd.read_csv, open+行数カウント, pq.ParquetFile を直接呼び出し。Tornado では非コルーチンハンドラーは IOLoop スレッド上で同期実行されるため全 I/O がブロッキング
- `jupyter-server/extensions/custom_api/workspace_handlers.py:1-288`: 全 4 ハンドラー（post/get/put/post）が `async def` だが、内部で mkdir, json.load/dump, iterdir, read_text を await なしで直接呼び出し
- `jupyter-server/extensions/custom_api/sql_handlers.py:470-507,638-686`: `_execute_sql_sync` + `loop.run_in_executor(None, func, ...)` パターン。`asyncio.get_running_loop()` を使用
- `jupyter-server/tests/test_kernel_executor_serialization.py:28-72`: importlib による単体モジュールロードと外部依存モックのパターン
- `docs/design/invariants.md`: I3 の定義確認

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | sync 関数抽出 + `run_in_executor` | 既存パターン（sql_handlers.py）と一致。依存追加なし。per-call タイムアウト可能 | ハンドラーごとにボイラープレート（`loop = asyncio.get_running_loop()` + `await loop.run_in_executor(...)`） |
| B | `aiofiles` + `aiopath` ライブラリ導入 | よりイディオマティックな async I/O | pandas/pyarrow に async 版がなく preview は結局 run_in_executor が必要。依存追加。既存パターンと不一致 |

採用理由: 案 A は sql_handlers.py で実績があるパターンをそのまま踏襲でき、新規依存の追加も不要。案 B は preview の主要ボトルネック（pd.read_csv, row count）を解決できず、部分的にしか適用できない。

ADR 要否: 不要。既存パターン（sql_handlers.py）の横展開であり、新しい設計判断を含まない。

## 参考にする既存実装

- コピー元: `jupyter-server/extensions/custom_api/sql_handlers.py` の `_execute_sql_sync` + `run_in_executor` パターン（L470-507, L638-646）。同種の実装は sql_handlers.py（1 箇所目）→ 今回の handlers.py + workspace_handlers.py（2, 3 箇所目）で 3 回目に達するが、各ファイルのボイラープレートは 3 行（`loop = ...` / `result = await ...` / `run_in_executor(None, func, ...)`) のみで、共通化の実益がないため I8 の例外とする

## 異常系・不変条件

- 該当する異常系（並行）: preview 処理中に別の API リクエストが到達した場合、イベントループがブロックされずに応答できること。完了条件 1 で検証
- 該当する異常系（エラー）: sync 関数内の例外（ファイル不在、パース失敗等）が `run_in_executor` 経由で正しく呼び出し元に伝播し、既存のエラーレスポンス形式が維持されること。完了条件 3 で検証
- 関係する不変条件: I3（async コンテキストでブロッキング I/O をしない）— 本タスクで充足する

### 技術的な考慮事項

- **Tornado の同期ハンドラー**: `ContentsPreviewHandler.get` は現在 `def get`（非 async）。Tornado では非コルーチンハンドラーは IOLoop スレッド上で同期実行されるため、`async def` への変更が必須。Tornado は `async def` のハンドラーメソッドを自動的にコルーチンとして扱う
- **`asyncio.get_running_loop()` vs `asyncio.get_event_loop()`**: 既存コードベース（sql_handlers.py）は `get_running_loop()` を使用。タスク記述の `get_event_loop()` ではなく、既存パターンに合わせる
- **`wait_for` の必要性**: sql_handlers.py では `asyncio.wait_for(..., timeout=timeout + 5)` でスレッドのハング対策をしている。preview にはユーザー指定のタイムアウトがないため `wait_for` は不要（スレッドプールのデフォルト挙動に任せる）。workspace 操作も同様（小さなファイル I/O で実用上ハングしない）
- **executor=None**: デフォルトの `ThreadPoolExecutor` を使用。カスタム executor は不要（sql_handlers.py と同じ判断）
- **軽量 stat/mkdir のオフロード対象外**: `Path.exists()`（内部的に `os.stat()`）と `Path.mkdir(exist_ok=True)` は async ハンドラーに残留する。理由: (1) これらはカーネル I/O ではなく OS メタデータ操作で、通常マイクロ秒オーダー (2) 404 判定のための exists チェックを sync 関数に含めると、エラーハンドリングの責務が分散し可読性が下がる (3) `_ensure_workspace_root` は全 workspace ハンドラーから呼ばれる冪等関数で、ディレクトリが既に存在する場合（通常ケース）は即 return。イベントループへの影響は preview の CSV 全行走査（秒単位）と比較して無視できる

## リスクと検知方法

- **リグレッション（preview のレスポンス形式変更）**: 既存テストの維持 + 新規 sync 関数のユニットテストで検知。API レスポンスの dict 構造は `_preview_file_sync` の戻り値として保持
- **workspace の read-modify-write 競合**: `_update_metadata_sync` は json.load → modify → json.dump のパターンで、既存と同じ。run_in_executor への移行で新たな競合は生まれない（ハンドラーレベルの並行性は変わらない）。将来の I6 対応が必要であれば別タスク
- **import 順序の変更**: `import asyncio` の追加で isort の整合が崩れる可能性 → lint で検知
