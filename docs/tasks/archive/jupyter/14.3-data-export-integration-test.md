# タスク詳細: 14.3 データエクスポートの結合テスト

## 概要

export_sql MCPツールの統合テストを実装する。カタログ参照 → SQLクエリによるデータエクスポート → execute_code での Parquet/CSV 読み込み → 分析という一連のフローが正しく動作することを検証する。また、大量行データでのストリーミング処理によるメモリ効率化も確認する。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-mcp.md` の「F11: SQLデータエクスポート」「AC12: SQLデータエクスポート」セクション
- 関連タスク: 14.1（jupyter-server SQL エクスポート API）, 14.2（jupyter-mcp export_sql ツール）

| `jupyter-mcp/tests/integration/export-sql.test.ts` | export_sql ツールの統合テスト |

### 実装手順

#### 1. テストファイルの作成

`jupyter-mcp/tests/integration/export-sql.test.ts` を新規作成する。既存の統合テストパターン（`query-save.test.ts`、`external-data-e2e.test.ts`）を踏襲する。

#### 2. テスト環境セットアップ

既存パターンに従い以下を準備:

- `beforeAll`: `checkJupyterConnection()` で Jupyter サーバー接続確認
- `afterEach`: セッション・ワークスペースのクリーンアップ
- `createTestEnvironment()` ヘルパー: ワークスペース + notebook_path 付きセッション作成（`execute_sql`/`export_sql` には notebook_path 付きセッションが必要）
- document-server 接続確認ヘルパー（カタログ参照テストで使用）

#### 3. テストケースの実装

以下の 5 つの describe ブロックに分けて実装する。

##### A. 基本エクスポート機能テスト

| テストケース | 内容 |
|-------------|------|
| Parquet エクスポート（デフォルト形式） | `export_sql` で SELECT を実行し、Parquet ファイルが `data/` に保存される。レスポンスに `file_path`, `row_count`, `file_size_bytes`, `format: "parquet"`, `execution_time_ms` が含まれる |
| CSV エクスポート | `format: "csv"` 指定で CSV ファイルが保存される |
| Parquet を execute_code で読み込み | エクスポートした Parquet を `pd.read_parquet('data/filename.parquet')` で読み込み、行数・カラムを検証 |
| CSV を execute_code で読み込み | エクスポートした CSV を `pd.read_csv('data/filename.csv')` で読み込み、行数・カラムを検証 |

##### B. バリデーション・エラーテスト

| テストケース | 内容 |
|-------------|------|
| 非SELECT文の拒否 | INSERT 文を指定するとバリデーションエラーが返る |
| タイムアウト設定 | `timeout` パラメータが機能する（短いタイムアウトで重いクエリを実行し、エラーを確認） |

##### C. 大量データのメモリ効率テスト

| テストケース | 内容 |
|-------------|------|
| 大量行データのエクスポート | `generate_series` 等で 10 万行以上のデータを生成し、Parquet にエクスポート。行数が一致すること、ファイルサイズが 0 より大きいことを検証 |
| エクスポート後のデータ整合性 | 大量行エクスポート後に `pd.read_parquet` で読み込み、行数・先頭行・末尾行の値を検証し、チャンク処理でデータが欠落していないことを確認 |

##### D. E2E: カタログ参照 → export_sql → execute_code 分析フロー

| テストケース | 内容 |
|-------------|------|
| カタログ参照→エクスポート→分析の一連フロー | (1) document-server からテーブル定義を取得 (2) `export_sql` で DB テーブルを Parquet にエクスポート (3) `execute_code` で Parquet を読み込み集計分析 (4) 分析結果を検証 |

##### E. execute_sql との使い分けテスト

| テストケース | 内容 |
|-------------|------|
| execute_sql（集計確認）→ export_sql（データセット作成）→ execute_code（分析） | (1) `execute_sql` で件数確認（集計用途） (2) `export_sql` で全データを Parquet にエクスポート（データセット作成用途） (3) `execute_code` でエクスポートデータを読み込み分析 |

### 技術的な考慮事項

- **notebook_path 付きセッションが必要:** `export_sql` は `session_id` からワークスペースIDを特定するため、`session_create` 時に `notebook_path` を指定する必要がある。既存の `query-save.test.ts` と同じパターンで `createTestEnvironment` ヘルパーを実装する。
- **大量データの生成:** PostgreSQL の `generate_series()` を使って SQL 内でテストデータを動的に生成する。テスト用テーブルの事前準備は不要。例: `SELECT gs AS id, 'item_' || gs AS name, random() * 1000 AS value FROM generate_series(1, 100000) AS gs`
- **document-server 依存テスト:** カタログ参照を含む E2E テストは `documentServerAvailable` フラグで制御し、document-server が起動していない環境ではスキップする（`external-data-e2e.test.ts` と同じパターン）。
- **テストタイムアウト:** 大量データのエクスポートテストはデフォルトの 5 秒では足りないため、`test('...', async () => {...}, 60000)` でタイムアウトを延長する。
- **Parquet 読み込みの前提:** jupyter-server の Docker イメージには `pyarrow` が含まれている（タスク 14.1 で追加済み）ため、`pd.read_parquet` が使用可能。
