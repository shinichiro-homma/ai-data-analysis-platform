# タスク詳細: 23.3 SQL エンジンのプール化とタイムアウト後の接続解放

## 概要

リクエストごとに `create_engine` + `dispose` している SQL 実行を、アプリケーション起動時に作成した共有エンジン（コネクションプール）に変更する。加えて `asyncio.wait_for` タイムアウト時にバックグラウンドスレッドが接続を保持し続ける問題を解消し、プール枯渇を防止する。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-server.md` の「F7.1 SQLクエリ実行」「F7.2 SQL実行制御」「F7.3 SQLデータエクスポート」
- API仕様: `docs/design/api-contracts.md` の「POST /api/sql/execute」「POST /api/sql/export」
- 不変条件: `docs/design/invariants.md` の I3（async でブロッキング I/O をしない）、I6（並行アクセスの直列化）

## 調査したファイル

- `jupyter-server/extensions/custom_api/sql_handlers.py`: SQL 実行の全ロジック。`_create_sql_engine`（L460-467）が `pool_size=1, max_overflow=0` で毎回新規エンジンを作成。3 つの sync 関数（`_export_sql_sync` L426-457、`_execute_sql_sync` L470-506、`_execute_non_select_sync` L509-534）が各自 `try/finally: engine.dispose()` で即破棄。ハンドラ側は `asyncio.wait_for(loop.run_in_executor(...), timeout=timeout+5)` でラップ
- `jupyter-server/extensions/custom_api/__init__.py`: `_load_jupyter_server_extension`（L239-269）で拡張ロード。`web_app.settings` へのリソース登録パターンが `kernel_manager`/`contents_manager` で確立済み。シャットダウン時のクリーンアップフック（`_wrap_shutdown_kernel` 等）の前例あり
- `jupyter-server/extensions/custom_api/base.py`: `BaseCustomHandler` に `kernel_manager`/`contents_manager` プロパティ（L142-150）。`self.settings["..."]` で共有オブジェクトにアクセスするパターン
- `jupyter-server/tests/test_sql_handlers.py`: importlib による単体モジュールロード + 重い依存のモック。純粋関数（`_classify_sql` 等）のテスト
- `jupyter-server/tests/test_kernel_executor_serialization.py`: `_ensure_mock_module` / `_load_module` ヘルパー（L36-55）。`FakeKernelClient` による非同期テストパターン
- `docs/tasks/archive/jupyter/23.2-sync-io-offload.md`: `run_in_executor` 導入パターン、sync 関数抽出パターンの前例

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | モジュールレベル共有エンジン + `cancel_after` ラッパー | 依存追加なし。3 関数の `create_engine`/`dispose` を除去でき簡潔。タイムアウト時は接続を強制クローズして返却。`atexit` + 拡張 unload でグレースフル dispose | エンジンのライフサイクル管理（初期化・破棄）がモジュールに分散する |
| B | `web_app.settings["sql_engine"]` に登録し `BaseCustomHandler` にプロパティ追加 | `kernel_manager` と同じアクセスパターン。`__init__.py` でライフサイクルを一元管理 | `DATABASE_URL` が環境変数なので `__init__.py` ロード時に未設定の可能性がある。sync 関数が `self` を受け取らないモジュールレベル関数なのでハンドラプロパティ経由のエンジン受け渡しが煩雑。テストでモック差し替えが困難 |

採用理由: 案 A は既存の sync 関数シグネチャ（`database_url: str` 引数）を `engine` 引数に差し替えるだけで済み、変更が局所的。`DATABASE_URL` 未設定時はリクエスト時に 500 を返す現在の挙動を維持できる。案 B は `__init__.py` での `DATABASE_URL` 読み取りタイミング問題と、sync 関数への受け渡し経路の変更が広範になる。

ADR 要否: 不要（既存の SQLAlchemy プール機構をそのまま使う標準的なパターンであり、新しいアーキテクチャ判断を含まない）

## 参考にする既存実装

- コピー元: `sql_handlers.py` の `_execute_sql_sync` / `_export_sql_sync` / `_execute_non_select_sync`（同種の engine 生成・破棄パターンが 3 回繰り返されている。本タスクで共有エンジンに統一するため、I8 rule of three に該当する共通化を実施する）

## 異常系・不変条件

- 該当する異常系:
  - **タイムアウト**: `asyncio.wait_for` タイムアウト時、バックグラウンドスレッドが DB 接続を保持し続ける → `cancel_after` ラッパーでタイムアウト発生時に `connection.connection.cancel()` で PostgreSQL クエリをキャンセルし、接続をプールに返却する
  - **並行アクセス**: 複数リクエストが同時に SQL 実行しても接続プールが適切に管理する → SQLAlchemy のプール機構（QueuePool）が保証
  - **DB 再起動**: DB が再起動した場合、stale connection を検出して再接続する → `pool_pre_ping=True` で接続取得時に liveness check
- 関係する不変条件:
  - I3: sync 関数内の DB アクセスは既に `run_in_executor` でオフロード済み（23.2 で対応済み）。本タスクでは変更なし
  - I6: SQL 実行の並行アクセスは SQLAlchemy の QueuePool が接続の排他管理を行う。同一コネクションを複数スレッドが共有することはない

### 実装手順

1. **共有エンジンの生成関数を実装**: `_create_sql_engine` を `_get_engine(database_url)` に変更。同じ `database_url` に対してはキャッシュされたエンジンを返す。`pool_size=5, max_overflow=2, pool_pre_ping=True, pool_recycle=1800` を設定。検証: `grep -n "_get_engine\|_create_sql_engine" sql_handlers.py` で `_create_sql_engine` が消え `_get_engine` に置き換わっていること

2. **3 つの sync 関数のシグネチャ変更**: `database_url: str` 引数を `engine` 引数に変更し、関数内の `engine = _create_sql_engine(database_url)` と `finally: engine.dispose()` を除去。`engine.connect()` はそのまま維持（プールから接続を取得・返却）。同時に、3 関数内の `SET default_transaction_read_only = ON` と `SET statement_timeout = :timeout_ms` を `SET LOCAL default_transaction_read_only = ON` と `SET LOCAL statement_timeout = :timeout_ms` に変更する（プール化により接続が再利用されるため、セッションレベル設定は他リクエストに漏洩する。`SET LOCAL` はトランザクションスコープなので返却時に自動リセットされる）。検証: `grep -n "engine.dispose\|_create_sql_engine" sql_handlers.py` がヒットしないこと。`grep -n "SET LOCAL" sql_handlers.py` が 5 箇所ヒットすること（`read_only` 2 箇所 + `statement_timeout` 3 箇所）

3. **ハンドラ側の呼び出し変更**: `_handle_select`・`_handle_non_select`・`SqlExportHandler.post` で `database_url` を直接 sync 関数に渡す代わりに、`_get_engine(database_url)` で取得した `engine` を渡す。検証: `grep -n "_get_engine" sql_handlers.py` が 4 箇所以上ヒットすること（定義 1 + 呼び出し 3）

4. **タイムアウト時の接続キャンセル処理を追加**: `asyncio.wait_for` タイムアウト時にバックグラウンドスレッドの DB 接続をキャンセルする仕組みを実装。sync 関数内で `engine.connect()` した raw connection（`conn.connection.dbapi_connection`）への参照をスレッドセーフな変数（リスト等）に格納し、`asyncio.TimeoutError` 発生時に `dbapi_connection.cancel()` を呼び出して PostgreSQL クエリを中断させる。これにより sync 関数内で `OperationalError("canceling statement")` が発生し、`with engine.connect()` の context manager が接続をプールに正常に返却する。検証: テストで `wait_for` タイムアウト後に後続クエリが成功すること

5. **エンジンの shutdown 処理を追加**: `sql_handlers.py` にモジュールレベルの `shutdown_engines()` 関数を追加し、キャッシュされた全エンジンの `dispose()` を呼ぶ。`__init__.py` の `_load_jupyter_server_extension` で `atexit.register(shutdown_engines)` を登録。検証: `grep -n "atexit\|shutdown_engines" sql_handlers.py __init__.py` がヒットすること

6. **既存テストの確認**: `scripts/test.sh --quiet --test --no-lint jupyter-server -- tests/test_sql_handlers.py` が PASS すること

7. **新規テストの作成と実行**: `test_sql_engine_pool.py` を作成し、プール共有・タイムアウト接続解放のテストを記述。`scripts/test.sh --quiet --test --no-lint jupyter-server -- tests/test_sql_engine_pool.py` が PASS すること

### 技術的な考慮事項

- **`SET LOCAL` への変更が必須**: 現在の `SET statement_timeout` と `SET default_transaction_read_only = ON` はセッションレベル設定であり、`ROLLBACK` でリセットされない。プール化後は接続が再利用されるため、SELECT 系で設定された `read_only = ON` が非 SELECT 系に漏洩して書き込み操作が失敗する致命的バグを引き起こす。`SET LOCAL` に変更することでトランザクションスコープに限定され、接続返却時に自動リセットされる
- **`SET LOCAL default_transaction_read_only`**: SELECT 系の `_execute_sql_sync` と `_export_sql_sync` では `SET LOCAL` で read-only 設定を行い、`_execute_non_select_sync` では行わない。`SET LOCAL` はトランザクション終了時にリセットされるため、同一プールの接続間で設定が漏洩しない
- **`pool_pre_ping=True`**: DB 再起動後の stale connection を検出するために有効化。接続取得時に `SELECT 1` を発行するオーバーヘッドがあるが、SQL 実行のレイテンシに対して無視できる
- **`dbapi_connection.cancel()`**: psycopg2 の `connection.cancel()` はスレッドセーフで、別スレッドから呼び出し可能。キャンセル後、実行中のクエリは `OperationalError` で終了し、`with engine.connect()` が接続をプールに返却する

## リスクと検知方法

- **既存の SQL テストが壊れる**: エンジン作成パターンの変更により、モジュールロード時の挙動が変わる可能性 → `scripts/test.sh --quiet jupyter-server -- tests/test_sql_handlers.py` で検知
- **接続リーク**: プール化後に接続が返却されないケースがある可能性 → テストで `engine.pool.checkedout()` が 0 に戻ることを検証
- **`cancel()` の副作用**: psycopg2 の `cancel()` が接続を使用不能にする可能性 → テストでキャンセル後に同一プールからの後続クエリが成功することを検証
