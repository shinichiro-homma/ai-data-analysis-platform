# タスク詳細: 11.3 ファイルサイズ予算の CI 検知

## 概要

1 ファイルあたりの行数に予算（500 行）を定め、**ラチェット方式**（現状をベースライン化し、悪化のみをブロック）で CI 検知する。新規スクリプト `scripts/check-file-size.py`（標準ライブラリのみ）とベースライン `scripts/file-size-baseline.json` を追加し、`.github/workflows/ci.yml` に `fitness-functions` ジョブを新設する。

ラチェットの契約は以下の 3 つ:

1. **ベースライン未登録のファイルが予算を超えたら FAIL**（新規の肥大化をブロック）
2. **ベースライン登録済みのファイルが記録行数を 1 行でも超えたら FAIL**（既存の肥大化をブロック）
3. **スクリプトのどのモードも、既存ベースラインがある状態で緩和方向にファイルを書き換えない。** 緩和したい場合は該当エントリを手編集するしかなく、その差分が PR に現れてレビューに乗る（`rm` してから `--init` すれば作り直せるが、それは意図的な操作であり全行書き換えとして差分に出る。「リスクと検知方法」参照）

スクリプトのモードは 4 つ。**ベースラインへの書き込みは必ずスクリプト自身が行い、シェルのリダイレクトでは書かない**（`cmd > baseline.json` はプロセス起動前にシェルがファイルを 0 バイトに truncate するため、スクリプトが「既存ベースライン」を読む時点で必ず空になり、下記のガードが常に素通りしてしまう。計画時に実測確認済み）:

| モード | 用途 | ガード |
|--------|------|--------|
| 引数なし | 検査（CI が実行する） | — |
| `--update` | ベースラインの縮小・陳腐エントリ削除を反映して**ファイルを書く** | 拡大が必要なエントリが 1 つでもあれば書き込まず exit 1。予算超過の未登録ファイルは追加しない |
| `--init` | 初期ベースラインを生成して**ファイルを書く** | `scripts/file-size-baseline.json` が存在し非空なら、書き込まず exit 1（初回限定。運用中の全面再生成を塞ぐ） |
| `--print-baseline` | 現状の予算超過ファイルを JSON で stdout に出す（点検専用。ファイルは書かない） | `evaluate()` が errors を返す状態（＝ゲートが赤）なら何も出力せず exit 1 |

実測ベースライン（本タスクのブランチ時点、dev = `0df398f`）は **17 ファイル**（対象 313 ファイル中）。詳細は「背景: ベースラインの実測」参照。

## 検討した代替案

### 主論点: ゲートの実現方式

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | 自前の Python スクリプト（標準ライブラリのみ）+ JSON ベースライン + 専用 CI ジョブ | 言語横断（`.py` / `.ts` / `.sh` を 1 つのルールで扱える）。ラチェットの意味論を自分で決められる。新規依存ゼロ。`check-docs-consistency.py` と同じ構造で `uv sync` なしに CI で動く | 自前実装のため約 150 行のコードとそのテストを保守する必要がある |
| B | ESLint の `max-lines` ルール + Python 側は別手段 | TypeScript 側は既製ルールで済む | **Python にファイル行数を検査する ruff ルールが存在しない**（`select` に該当ルールがない）ため、結局 Python 用の自前実装が必要になり、ゲートが 2 系統に分裂する。さらに ESLint は本リポジトリに導入されていない（TS の lint は prettier のみ、`scripts/lint.sh:40-48`）ため、ESLint 導入自体が別タスク規模になる |
| C | 既製の品質ゲート（SonarQube / danger-js 等）を導入する | 重複検出・複雑度など他の指標も同時に得られる | 外部サービス連携またはトークン管理が必要で、CI 実行時間と運用コストが跳ね上がる。11.4（jscpd）とも役割が重複する。「コストがほぼゼロなゲートから入れる」という Phase 11 の方針に反する |
| D | ラチェットなしの固定予算（超過 17 ファイルを本タスクで分割する） | ベースラインファイルという中間状態を持たずに済む | 17 ファイル（最大 890 行）の分割は本タスクのスコープ上限（実装ファイル 8 個）を大幅に超える。`docs/plan/04-infrastructure.md:17` が明示的に「ラチェット方式」を指定している |
| E | 差分ベース（ベースラインファイルを持たず、`git diff origin/{base}...HEAD` の変更ファイルのみを base 側の行数と比較する） | ベースライン JSON が不要になり、マージコンフリクト・陳腐化・初期生成の 3 問題が構造的に消える。既存 `ci.yml:32` に `git diff --name-only origin/${{ github.base_ref }}...HEAD` の前例がある | **常時実行にできない。** base ref との比較には `fetch-depth: 0` と base ブランチの存在が必要で、ローカル実行（`uv run python scripts/check-file-size.py` を手元で叩く）や main へのプロモーション経路では基準が定まらない。また「現状どのファイルが予算超過か」が**どこにも記録されない**ため、負債の可視化（Phase 11 の目的）に寄与しない。ベースライン JSON はゲートの副産物であると同時に、分割候補リストとしての価値がある |

採用理由: A は言語横断で 1 つの意味論に統一でき、既存の `check-docs-consistency.py`（標準ライブラリのみ・`uv sync` 不要・`errors` 配列に集約して `main() -> int`）とまったく同じ構造で書けるため、実装・レビュー・CI 配線のすべてが既存パターンの反復になる。B は Python 側に穴が空く時点で目的（言語横断の構造ゲート）を満たさない。

E は運用コスト（JSON の保守）だけを見れば A より優れているが、**`.claude/` 配下のみの変更では `changes` ジョブが `code_changed=false` を返す**（`ci.yml:37`）ため base 依存のジョブは実質スキップされ、`.claude/hooks/*.sh`（22 ファイル）がゲートの外に落ちる。A はベースラインという静的なスナップショットを持つことで base ref に依存せず、`doc-consistency` と同じ常時実行にできる。加えて、17 件のベースラインそのものが「次に分割すべきファイル」の優先度付きリストになる点を積極的に評価して A を採る。

### 副論点 1: ラチェットの意味論（ベースライン登録済みファイルが縮小したときの扱い）

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A2（採用） | 増加は FAIL、減少は「縮小できます」のヒントを出して exit 0。`--update` は**縮小・削除のみ**反映し、拡大が必要な場合は exit 1 で拒否する | ラチェットの本質（増加させない）を保ちつつ、無関係な PR を赤くしない。緩和は JSON の手編集が必要になるため、必ず PR 差分に現れてレビューに乗る | ベースラインが縮小に追従しない期間が生じ、一度縮んだファイルが記録値まで再拡大しうる（毎回ヒントが出るので気付ける） |
| B2 | 減少も FAIL とし、`--update` + コミットを強制する | ベースラインが常に最新。ラチェットが緩まない | 3 行削っただけの無関係な PR が赤くなる。「赤いのが普通」の状態はフィットネス関数の信頼を壊し、`--update` を反射的に叩く運用に堕落する |
| C2 | 新規に予算超過したファイルのみ FAIL（登録済みファイルには上限を課さない） | 実装が最も単純 | `sql_handlers.py` が 890 → 1500 行になっても素通りする。既存の最悪ファイルこそ止めたい対象なので、ゲートの意味がほぼ失われる |

採用理由: A2。B2 の「常に最新」は魅力的だが、フィットネス関数が失敗する最大の要因は**無関係な赤による信頼喪失**である。A2 は「増加は機械が止め、緩和は人間の手編集をレビューが見る」という非対称性を持つ。

この非対称性は、**ベースラインを書けるモードすべてにガードを置いて**初めて成立する（`--update` は拡大を拒否、`--init` はベースラインが非空なら拒否、`--print-baseline` はゲートが赤なら何も出さない）。どれか 1 つでも全面再生成を許すと、1 フラグの差で契約 3 が迂回でき、しかも再生成は意図した 1 件だけでなく他のエントリの増加も同時に無言で取り込んでしまう。したがって「既存ベースラインがある状態での緩和 = 該当エントリの手編集」を唯一の経路とする。

### 副論点 2: 不変条件 I9 の新設

`docs/design/invariants.md` に**ファイルサイズ／ファイル分割に対応する不変条件は存在しない**（I1〜I8 を全文確認済み）。11.2 は I3、11.4 は I8 に対応するが、11.3 だけが対応する不変条件を持たない。

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A3（採用） | `docs/design/invariants.md` に I9「1 ファイルは予算行数に収める」を追記する | ゲートの目的が invariants.md に明文化され、`.claude/rules/task-design.md` のチェックリスト（「`docs/design/invariants.md` に抵触しないか」）から自動的に参照される。11.2 / 11.4 と対称になる | invariants.md が「守るべき性質」から「機械検知のカタログ」に寄る懸念 |
| B3 | invariants.md は変更せず、`.claude/rules/lint.md` にのみ方針を書く | 変更が 1 ファイルで済む | 計画レビュー時の不変条件チェックにファイルサイズが乗らず、「どの不変条件を守っているのか」が説明できないゲートになる |

### 副論点 3: 予算値と対象範囲

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A4（採用） | 全対象ファイルに単一の予算 500 行（テストも含む） | 説明が 1 文で済む。テストファイルの肥大化（最大 837 行）も止まる。ラチェットにより既存 17 件は即座には修正不要 | ベースラインが 17 件と多め。既存の大きなテストファイルにケースを追加する PR は分割を強いられる |

### 実装手順

1. **`scripts/check-file-size.py` を新規作成する（判定ロジック）。** `scripts/check-docs-consistency.py:1-41,218-241` の構造に揃える。以下のモジュールレベル定数と純粋関数に分離すること（テストから直接呼ぶため）:

   ```python
   BUDGET = 500
   TARGET_SUFFIXES = (".py", ".ts", ".sh")
   # 生成物は検査対象外（scripts/lib/generate_init.py が生成し、production 環境では
   # テーブル数に比例して肥大するため、人が分割できる対象ではない）
   EXCLUDE_GLOBS = ("postgres/init/*/load-data.py",)
   BASELINE_PATH = ROOT / "scripts" / "file-size-baseline.json"

   def iter_source_files(root: Path) -> list[str]: ...      # git ls-files -z + 拡張子 + 除外
   def count_lines(path: Path) -> int: ...                  # 物理行数
   def evaluate(counts: dict[str, int], baseline: dict[str, int]) -> tuple[list[str], list[str]]: ...
   def plan_update(counts: dict[str, int], baseline: dict[str, int]) -> tuple[dict[str, int], list[str]]: ...
   def plan_baseline(counts: dict[str, int]) -> dict[str, int]: ...   # 予算超過ファイルのみを抽出（純粋関数）
   # 各モードのガードも純粋関数に切り出す（テストから辞書リテラルで直接呼ぶため。
   # 第 1 要素が None なら「出力・書き込みをしない」、第 2 要素が理由メッセージ）
   def plan_print_baseline(counts, baseline) -> tuple[dict[str, int] | None, list[str]]: ...
   def plan_init(existing_text: str | None, counts) -> tuple[dict[str, int] | None, list[str]]: ...
   def serialize_baseline(data: dict[str, int]) -> str: ...           # json.dumps(...) + "\n"（唯一のシリアライズ経路）
   def write_baseline(path: Path, data: dict[str, int]) -> None: ...  # serialize_baseline() の結果を書く
   def main(argv: list[str] | None = None) -> int: ...
   ```

   **ガードを `main()` の中に直書きしないこと。** `BASELINE_PATH` はモジュール定数で `main()` に root / baseline パスを注入する引数がないため、ガードが `main()` にしかないとテストは実リポジトリの `scripts/file-size-baseline.json` に対して `--init` を走らせるしかなくなり、**テスト実行のたびにコミット済みベースラインを上書きする**（`scripts/test.sh` は CI の `Test scripts` ステップからも走る）。`plan_init` が受け取るのは `Path` ではなく**既存ファイルの中身（`str | None`）**である点に注意する — ファイル読み取りは `main()` の責務とし、判定を I/O から切り離す。

   `iter_source_files` は **`subprocess.run(["git", "ls-files", "-z"], cwd=root, check=True, ...)` を使い、`stdout.split("\0")` で分割する**（`-z` は必須。理由は「技術的な考慮事項」の非 ASCII パスの項）。node_modules 等の除外は git に委ねる。`evaluate` は `(errors, hints)` を返す純粋関数とし、ファイル I/O を含めない。

   検証: `uv run ruff check scripts/check-file-size.py` と `uv run ruff format --check scripts/check-file-size.py` がともに exit 0。

2. **`evaluate()` に 3 つの判定を実装する。**

   | 条件 | 結果 |
   |------|------|
   | `path in baseline` かつ `counts[path] > baseline[path]` | errors に追加（`{path}: {n} 行（ベースライン {b} 行を超過）`） |
   | `path in baseline` かつ `counts[path] < baseline[path]` | hints に追加（`{path}: {n} 行（ベースライン {b} 行より縮小。--update で反映できます）`） |
   | `path not in baseline` かつ `counts[path] > BUDGET` | errors に追加（`{path}: {n} 行（予算 {BUDGET} 行を超過）`） |
   | `path in baseline` だが `path not in counts` | errors に追加（`{path}: ベースラインに登録されているがファイルが存在しない`） |

   `main()` は errors があれば一覧を出力して `return 1`、なければ hints を出力して `return 0`。

   検証: 手順 6 で作成するユニットテスト 1〜6 が pass する（TDD でテストを先に作る場合は、この手順で Red → Green に変わることを確認する）。

3. **`--update` / `--init` / `--print-baseline` の 3 モードを実装する。** `argparse` の相互排他グループで受ける（`check-docs-consistency.py` は argparse を使っていないが、本スクリプトは 4 モードあるため導入する）。

   `--update` の挙動（`plan_update()`）:
   - 記録値より小さくなったエントリは新しい値に更新する
   - 予算以下になったエントリはベースラインから削除する
   - **`counts` に存在しないエントリ（削除・リネーム・分割されたファイル）は削除する。** これがないと、ベースライン登録済みファイルを分割した PR で `evaluate()` が「陳腐エントリ」で赤になったまま、スクリプトでは直せない状態になる。**ファイル分割は本ゲートが最も奨励する変更**であり、`--update` はその正規の解消手段である

     ただし解消できるのは**分割の結果すべてのファイルが予算内に収まった場合**に限る。予算超過のまま単に `git mv` でリネームした場合は、旧キーが削除される一方で新パスは「予算超過の未登録ファイル」として errors に入る（次項により `--update` は追加しない）ため、**`--update` を実行してもゲートは赤のままになる**。この場合の正規の手順は「`scripts/file-size-baseline.json` の該当キー名だけを手で書き換える（値は据え置き）」であり、差分は旧キー削除＋新キー追加の 2 行に収まる。この制約を手順 9 で `.claude/rules/lint.md` に明記すること
   - **記録値より大きくなったエントリが 1 つでもあれば、JSON を書かずに exit 1** し、「緩和は `scripts/file-size-baseline.json` の該当エントリを手編集し、理由を PR に書くこと」と案内する
   - 予算超過の未登録ファイルは新規エントリとして追加**しない**（追加してしまうと「超過したら update すれば通る」になり、ゲートが無意味になる）
   - 書き出しは `json.dumps(..., indent=2, ensure_ascii=False, sort_keys=True)` + 末尾改行（差分を安定させるため）

   `--init` の挙動（`plan_init()`）: `plan_baseline(counts)`（予算超過ファイルのみを抽出する純粋関数）の結果を `write_baseline()` で `scripts/file-size-baseline.json` に**スクリプト自身が書く**。**既存ファイルの中身が非空なら、何も書かずに exit 1** とし「初期生成は 1 回限り。既存ベースラインの更新は `--update`、緩和は該当エントリの手編集」と案内する。これが運用中の無意識な全面再生成を塞ぐガードであるため、シェルのリダイレクトに書き込みを任せてはならない（truncate により自分自身のガードを無効化するため。「概要」のモード表参照）

   `--print-baseline` の挙動（`plan_print_baseline()`）: `plan_baseline(counts)` の結果を **stdout に出すだけ**でファイルは書かない。**`evaluate()` が errors を返す状態（ゲートが赤）なら何も出力せず exit 1** とする。拒否条件を「既存エントリの拡大」ではなく「errors 全般」にすることで、拡大・**予算超過の未登録ファイル**・陳腐エントリのすべてを一様に塞ぐ。この一本化がないと、900 行の新規ファイルを含む状態で出力した JSON をベースラインに書けば契約 1 が 1 コマンドで無効化される。用途は「コミット済みベースラインが実測と一致するかの点検」（完了条件「ベースライン生成の再現性」）に限定する。

   **出力は `print()` ではなく `sys.stdout.write(serialize_baseline(...))` を使う。** `write_baseline()` も同じ `serialize_baseline()` を通す唯一の経路とすること。`serialize_baseline()` が末尾に改行を付ける一方で `print(json.dumps(...))` を使うと改行が 1 個多くなり、完了条件「ベースライン生成の再現性」の `diff` がこの 1 バイトだけで落ちる（原因がベースラインの中身に見えるため誤診しやすい）。

   検証: 手順 6 で作成するユニットテスト 7〜11 が pass する。

4. **`scripts/file-size-baseline.json` を生成する。** `scripts/check-file-size.py --init` にファイルを書かせる（リダイレクトを使わない理由は「概要」のモード表）。

   ```bash
   uv run python scripts/check-file-size.py --init
   ```

### 技術的な考慮事項

- **`git ls-files` への依存**: CI の `actions/checkout` は `.git` を含むチェックアウトを行うため `git ls-files` は動作する（`fetch-depth` の指定は不要 — インデックスを読むだけで履歴を必要としない）。`iter_source_files` は `subprocess.run(..., check=True)` とし、git が使えない環境では例外で明示的に落とす（無言で 0 ファイルを返して「全部グリーン」になるのが最悪の失敗モードのため）
- **非 ASCII パスのクォート（`-z` が必須な理由）**: `git ls-files` は `-z` も `-c core.quotePath=false` も付けないと、非 ASCII を含むパスを C クォート形式（`"document-server/data/sample/glossary/terms/\345\272\227\350\210\227.yaml"` のような二重引用符つきエスケープ列）で出力する。この文字列は `.py` ではなく `.py"` で終わるため**拡張子判定をすり抜け、対象から無言で落ちる**。本リポジトリには実際に日本語ファイル名が 4 件存在する（`git ls-files "*.yaml"` で確認済み。いずれも `.yaml` のため現時点の実測 313 / 17 件には影響しないが、日本語名の `.py` / `.ts` が 1 つ追加されるだけで恒久的な検査回避経路になる）。`-z` + `split("\0")` にすればクォートは行われない。ユニットテスト 13 でこの性質を固定する
- **インデックスにあるが作業ツリーに無いファイル**: `git ls-files` はインデックス上のパスを返すため、`git rm` していない削除済みファイルも列挙される。`count_lines` を呼ぶ前に `path.is_file()` で弾き、**存在しないパスは `counts` に入れない**（結果として `evaluate()` の「陳腐エントリ」判定に落ち、`--update` で解消できる）。`FileNotFoundError` で異常終了させない
- **対象拡張子**: `.py` / `.ts` / `.sh` の 3 種。`.tsx` / `.js` / `.jsx` / `.mjs` の追跡ファイルは現時点で **0 件**（`git ls-files "*.tsx" "*.js" "*.mjs"` が空を返すことを計画時に確認）。将来これらが増えたら `TARGET_SUFFIXES` に追加する
- **行数の数え方**: 物理行数（改行の数）。空行・コメントを含める。「実効行数」にすると数え方の定義が増え、ローカルと CI でずれる余地が生まれるため採らない。末尾に改行がないファイルの扱いは `sum(1 for _ in f)` に統一する（`wc -l` とは 1 ずれうるが、ベースラインも同じ関数で採るため整合する）
- **`postgres/init/*/load-data.py` の除外**: `scripts/lib/generate_init.py:129,271` が生成する成果物であり、production 環境ではテーブル数に比例して肥大する（`docs/tasks/archive/infrastructure/7.6-production-large-data-load.md`）。人が分割できる対象ではないため除外する。`postgres/init/production/load-data.py` は現在 git 管理外（`.gitkeep` のみ）だが、将来コミットされる可能性に備えて glob で指定する
- **`.claude/` 配下の 22 個の `.sh`（hooks 等）は対象に含める**。すべて 400 行未満で予算内であり、除外する理由がない。ただし `.claude/*` のみの変更では `changes` ジョブが `code_changed=false` を返すため（`ci.yml:37`）、`fitness-functions` を**常時実行**（`changes` 非依存）にしておく必要がある。`doc-consistency` と同じ扱いにする理由がここにある
- **JSON の書式安定化**: `sort_keys=True` + `indent=2` + 末尾改行で固定する。ソート順が実行環境で揺れるとベースラインの差分がノイズになる
- **`prettier` の対象外**: `scripts/file-size-baseline.json` は `prettier_targets()`（`scripts/lint.sh:40-48`）に含まれない（対象は `*/src/**/*.ts` のみ）ため、フォーマット競合は起きない
- **ベースラインの自己言及**: `scripts/check-file-size.py` と `scripts/tests/test_check_file_size.py` はどちらも検査対象（手順 7 で `scripts/tests/*.py` を ruff 対象に足すのとは別に、ファイルサイズゲートは `git ls-files` ベースなので最初から対象）。**新規ファイルの予算超過は `--update` では解消できず分割するしかない**ため、両方とも 500 行を超えないよう注意する。特に 14 ケースを持つテストファイルは接近しやすい（模倣元の `check-docs-consistency.py` は 241 行、`test_workspace_cwd_resolution.py` は 274 行）

## リスクと検知方法

- **新ジョブがブランチ保護の必須チェックに入っていないため、赤くてもマージできてしまう**: 現在の必須チェックは 4 件のみで、`Doc consistency check` も必須になっていない（`gh api repos/shinichiro-homma/ai-data-analysis-platform/branches/dev/protection` で確認済み）。**`Fitness functions` を必須にするかはユーザーの判断事項**であり、Claude はブランチ保護を変更しない。完了条件「ブランチ保護の案内」でユーザーに提示する。必須にしない場合も「PR 画面で赤が見える」ところまでは本タスクで担保される
- **ベースライン JSON のマージコンフリクト**: 複数ブランチが同時にベースラインを更新すると衝突する。`sort_keys=True` で行順が安定しているため、衝突しても手で解決可能。頻度が問題になったら 11.4 完了後に再検討する
- **既存の大きなテストファイルにケースを追加する PR が止まる**: 11 個のテストファイルがベースラインに載るため、それらへのケース追加は必ず FAIL する。これは設計上の意図（分割を促す）だが、緊急時の逃げ道として「`scripts/file-size-baseline.json` の該当エントリを手編集して緩和し、その理由を PR に書く」経路を `.claude/rules/lint.md` に明記する
- **`git ls-files` が使えない環境での無言グリーン**: `check=True` で例外にする（上記「技術的な考慮事項」）。ユニットテスト 14（実リポジトリで 200 ファイル以上を収集できること）で「0 ファイルしか見ていない」状態を検知する
- **非 ASCII ファイル名による検査回避**: `-z` を落とすと無言で対象から漏れる。ユニットテスト 13（`iter_source_files` の結果に `"` で始まるパスが 1 件もないこと）で固定する
- **ベースラインの全面再生成によるラチェットの空洞化**: ベースラインを書けるモードは `--update`（縮小・陳腐エントリ削除のみ）と `--init`（ベースラインが空のときのみ）の 2 つに限られ、`--print-baseline` はゲートが赤なら何も出さない（ユニットテスト 8・10・11 で固定）。したがって既存ベースラインがある状態で緩和する手段は「該当エントリの手編集」だけになり、差分が 1 行に閉じてレビューで意図が読める。**全面再生成を許すと、意図した 1 件だけでなく他エントリの増加も同時に無言で取り込まれる**点が、この制約の主たる理由である。方針は `.claude/rules/lint.md` に明記する（手順 9）
- **シェルのリダイレクトによるガードの無効化**: `cmd > scripts/file-size-baseline.json` はプロセス起動前にファイルを 0 バイトへ truncate するため、スクリプトが「既存ベースライン」を読む時点で必ず空になり、`--init` の初回限定ガードが常に素通りする。**ベースラインへの書き込みは必ずスクリプト自身に行わせる**（手順 4）。計画時に実測で確認した挙動
- **`--init` のガードは事故防止であって、意図的な全面再生成は防げない**: `rm scripts/file-size-baseline.json` してから `--init` を実行すれば作り直せる（大規模なリファクタ後など、正当な用途もある）。これは穴ではなく**逃げ道の設計**である — ガードが防ぐのは「`--update` が拒否されたので何となく再生成する」類の無意識な緩和であり、`rm` を伴う再生成は JSON の全行書き換えとして PR 差分に現れ、レビュアーが必ず気付く。したがって「機械が止めるのは無意識の緩和、意図的な緩和はレビューが見る」という本ゲート全体の方針と一貫している
- **`scripts` を `scripts/test.sh` の `COMPONENTS` に足したことによる副作用**: (1) `scripts/test.sh`（引数なし）が新たに `cd scripts && pytest` を実行するようになる — `scripts/tests/` 以外に pytest が拾うファイルがないことを手順 5・6 の検証と完了条件「scripts テスト」で確認する。(2) `scripts/test.sh:174` の `${#TARGETS[@]} -eq ${#COMPONENTS[@]}` 分岐が `scripts` を `LINT_TARGETS` へ二重登録する — 手順 5 で 175 行目から `"scripts"` を外し、173 行目のコメントも直して塞ぐ。(3) `usage()` のヘルプとコードの乖離 — 手順 5 で同時に更新する

## テスト計画

### 既存テストの被覆状況

`scripts/test-map.sh:40` の `ALL_COMPONENTS` は `jupyter-mcp document-mcp jupyter-server document-server e2e` であり、**`scripts` はテストマップの対象外**である。`scripts/` 配下には `tests/` ディレクトリが存在せず（Glob で確認）、`scripts/pyproject.toml` にも pytest 設定がない。

したがって **`scripts/` 配下のスクリプトを対象とした既存テストは 1 つも存在せず、流用できる回帰検知手段はない**。本タスクで新設するテストが唯一の網になる。

以下はいずれも「参考のみ」で、回帰検知には使えない:

- `jupyter-server/tests/test_workspace_cwd_resolution.py`: **参考のみ**（importlib ロードと subprocess によるゲート回帰の模倣元）。対象は `cell_handlers.py` であり `scripts/` とは無関係
- `.claude/hooks/tests/*.test.sh`: **参考のみ**。シェル製で対象は `.claude/hooks/` 配下。`ci.yml:56-62` の `hooks-test` ジョブが実行するが、`scripts/` は対象外

### 新規テスト

`scripts/tests/test_check_file_size.py` に 14 ケース（対応する完了条件があるものは併記。ケース 1・3・5 は正常系・境界値であり、対応する個別の完了条件は持たない）。

**ケース 1〜11 はすべて純粋関数テスト**（`evaluate()` / `plan_update()` / `plan_baseline()` / `plan_print_baseline()` / `plan_init()` を辞書リテラルと文字列で直接呼ぶ）。一時 git リポジトリもファイル I/O も不要である。**テストから `main()` を実リポジトリに対して走らせてはならない** — `--init` / `--update` は `scripts/file-size-baseline.json` を書き換えるモードであり、`scripts/test.sh` は CI の `Test scripts` ステップからも走るため、コミット済みベースラインを破壊する。ガードを純粋関数に切り出してあるのはこのためである（手順 1 参照）。

`.claude/rules/testing.md` の命名規約に従い `Test{名前}` クラス + `test_{振る舞い}` メソッドで書く。

**`TestEvaluate`**

1. `test_passes_when_all_files_within_budget` — 全ファイルが予算内・ベースライン空 → errors・hints ともに空（正常系）
2. `test_fails_for_unlisted_file_over_budget` — 未登録ファイルが 501 行 → errors 1 件、メッセージにパスと行数を含む（**異常系**・完了条件「異常系: ゲート回帰」の単体側）
3. `test_passes_when_baselined_file_unchanged` — 登録済みファイルが記録値ちょうど → errors 空（境界値）
4. `test_fails_when_baselined_file_grows_by_one_line` — 登録済み 890 行が 891 行 → errors 1 件（**異常系**・完了条件「異常系: ラチェット」。境界値でもある）
5. `test_hints_when_baselined_file_shrinks` — 登録済み 890 行が 800 行 → errors 空・hints 1 件（副論点 1 の A2 の意味論を固定する）
6. `test_fails_for_stale_baseline_entry` — ベースラインにあるパスが counts に存在しない → errors 1 件（**異常系**・完了条件「異常系: 陳腐エントリ」）

**`TestPlanUpdate`**

7. `test_update_shrinks_and_drops_entries` — 登録済み 890→800 は 800 に更新、登録済み 520→480（予算以下）はエントリごと削除、**`counts` に存在しないエントリ（リネーム・分割されたファイル）は削除**、予算超過の未登録ファイルは**追加されない**（完了条件「陳腐エントリの解消」）
8. `test_update_refuses_to_grow` — 登録済み 890→891 が 1 件でもあれば errors を返し、更新後の dict を書き出させない（**異常系**・完了条件「異常系: update の拡大拒否」）
**`TestPlanBaseline`**

9. `test_plan_baseline_lists_only_over_budget` — `plan_baseline(counts)` が予算超過ファイルのみを `{パス: 行数}` で返し、予算内のファイルを含めないこと（純粋関数）
10. `test_print_baseline_refuses_when_gate_is_red` — `plan_print_baseline(counts, baseline)` が、`evaluate()` が errors を返す 3 パターン（拡大／予算超過の未登録ファイル／陳腐エントリ）のいずれでも第 1 要素に `None` を返すこと。緑の状態でのみ `plan_baseline()` と同じ dict を返すこと（**異常系**・完了条件「異常系: print-baseline の赤時拒否」）

**`TestIterSourceFiles`**（実リポジトリに対して実行する）

12. `test_excludes_generated_load_data` — `iter_source_files(REPO_ROOT)` の結果に `postgres/init/sample/load-data.py` が**含まれない**こと、かつ `scripts/check-docs-consistency.py` が**含まれる**こと（完了条件「除外」）。**存在確認の対象に `scripts/check-file-size.py` を使ってはならない** — 実装中の同ファイルは `git add` されるまで未追跡であり、`git ls-files` に列挙されないためテストが必ず落ちる（理由は「テスト参照ポインタ」の注意点）
13. `test_returns_unquoted_paths` — 結果のどのパスも `"` で始まらないこと（`git ls-files` の C クォートが解除されていることの確認）。あわせて `.py` / `.ts` / `.sh` 以外の拡張子が 1 件も含まれないことを assert する（**異常系**・完了条件「非 ASCII パス」・リスク「非 ASCII ファイル名による検査回避」）

**`TestGateAgainstRealRepo`**

14. `test_real_repository_is_green` — `subprocess.run(["uv", "run", "python", "scripts/check-file-size.py"], cwd=REPO_ROOT)` の returncode が 0。あわせて `iter_source_files` の件数が 200 以上であること（`git ls-files` が失敗して 0 件になる無言グリーンの検知）。**skip 条件は `FileNotFoundError`（uv 未インストール）に限定し、returncode が 0 以外なら skip せず fail させる**（完了条件「グリーン」・リスク「無言グリーン」）
