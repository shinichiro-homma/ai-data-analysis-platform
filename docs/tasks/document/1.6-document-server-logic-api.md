# タスク詳細: 1.6 document-server ロジックAPI実装

## 概要

document-server に既存ロジック（定型SQL/Python）のAPI群を実装する。テーブルAPI・用語集APIに続く第3のコンテキスト情報提供機能であり、AIが分析コード生成時に既存の業務ロジック（洗い替え処理、集計処理など）を参照できるようにする。

3つのエンドポイントを提供する:
- `GET /logic/index` — ロジック一覧（インデックス）
- `POST /logic/meta` — ロジックメタ情報の一括取得
- `GET /logic/code/{logic_name}` — ロジックのコードファイル内容取得

### 実装手順

#### ステップ1: サンプルYAMLデータ作成

要件定義のYAML形式に従い、`data/logic/` ディレクトリにサンプルデータを作成する。

- `index.yaml`: `logic_index` キーで2件（member_id_remapping, sales_basic_aggregation）
- `meta/member_id_remapping.yaml`: language=sql, usage_type=template
- `meta/sales_basic_aggregation.yaml`: language=python, usage_type=reference
- `code/sql/member_id_remapping.sql`: SQLサンプル
- `code/python/sales_basic_aggregation.py`: Pythonサンプル

#### ステップ2: Pydanticモデル追加

`models.py` に以下のモデルを追加する（既存の `TermIndex`/`TermDetail` パターンに準拠）。

- `LogicIndex`: `logic_name`, `summary`, `category`
- `LogicMeta`: `logic_name`, `description`, `file_path`, `language`, `usage_type`, `input_tables`, `output_description`, `usage_context`(任意), `related_logic`(任意), `notes`(任意)
- `LogicMetaRequest`: `logic_names: list[str]` (min_length=1, max_length=100)

#### ステップ3: CatalogStore にロジック読み込み・取得メソッド追加

`catalog_loader.py` に以下を追加する。

- `_parse_logic_index()`, `_parse_logic_meta()` パーサー関数
- `load_logic(data_dir)`: `_load_resource()` 共通メソッドを使い `logic/` からインデックスとメタを読み込む
  - index_key: `"logic_index"`, id_field: `"logic_name"`, detail_dir: `"meta"`
- `get_all_logic_indexes()`: 全インデックス返却
- `get_logic_metas(logic_names)`: `_lookup_many()` で一括取得
- `get_logic_code(logic_name)`: メタ情報の `file_path` からコードファイルを読み込んで返却（新パターン）
- `logic_count` プロパティ: `return 0` を実データに更新

コードファイル取得のために `data_dir` を保持する必要がある。既存の `load_tables()` / `load_terms()` が `data_dir` を引数で受け取るパターンと同様に、`load_logic()` で `data_dir` をインスタンス変数に保存する。

#### ステップ4: ロジックAPIルーター作成

`src/routers/logic.py` を新規作成する（`terms.py` をベースに）。

- `GET /logic/index`: `store.get_all_logic_indexes()` → `index_response("logic", ...)`
- `POST /logic/meta`: `store.get_logic_metas(request.logic_names)` → `detail_response("logic", ...)`
- `GET /logic/code/{logic_name}`: `store.get_logic_code(logic_name)` → コード情報を返却
  - ロジックが見つからない場合: `error_response(404, "LOGIC_NOT_FOUND", ...)`
  - コードファイルが見つからない場合: `error_response(404, "LOGIC_CODE_NOT_FOUND", ...)`

#### ステップ5: main.py / admin.py の更新

- `main.py`: lifespan に `store.load_logic(DATA_DIR)` 追加、`app.include_router(logic_router)` 追加
- `admin.py`: reload ハンドラに `store.load_logic(data_dir)` 呼び出し追加（現在は logic_count=0 固定で返しているため、ロード処理を追加するだけで正常動作する）

### 技術的な考慮事項

#### コードファイル取得（新しいパターン）

テーブルAPI・用語集APIにはない機能として `GET /logic/code/{logic_name}` がある。これはメタ情報の `file_path` を元にファイルシステムからコードを読み込むため、以下を考慮する。

- **パストラバーサル防止**: `file_path` が `../` 等で `data/` ディレクトリ外を参照しないよう、`Path.resolve()` で正規化してベースパスの配下にあることを検証する
- **file_path の解決**: メタ情報の `file_path` は `data/` ディレクトリからの相対パスとして解決する（例: `logic/sql/member_id_remapping.sql` → `data/logic/sql/member_id_remapping.sql` ではなく `data/logic/code/sql/member_id_remapping.sql`）。要件定義のファイル構成をよく確認して正しくマッピングする
- **エラーの2段階分離**: ロジック自体が見つからない（`LOGIC_NOT_FOUND`）とコードファイルが見つからない（`LOGIC_CODE_NOT_FOUND`）を区別する

#### data_dir の保持

`get_logic_code()` でコードファイルを読むため、`CatalogStore` にデータディレクトリのパスを保持する必要がある。`load_logic()` 呼び出し時に `self._data_dir = data_dir` として保存する。

#### _load_resource の再利用

ロジックのインデックス＋メタ読み込みは既存の `_load_resource()` パターンで対応可能。`sub_dir="logic"`, `detail_dir="meta"`, `index_key="logic_index"`, `id_field="logic_name"` で呼び出す。
