# タスク詳細: 21.4 再接続時の再同期

## 概要

WebSocket 切断中の変更を再接続後に回復する（不変条件 I5）。jupyter-server に同期状態照会 API（現在の seq とロック一覧）を新設し、ブラウザは再接続時に照会して、seq が進んでいる（または未知の）開いているノートブックを revert し、ロック状態を再適用する。WS 送信に失敗したクライアントは切断し、ブラウザ側の再接続 → 再同期経路に載せる（現行は失敗を握りつぶしてゾンビ接続が残る）。

## 関連ドキュメント

- ADR: `docs/adr/0002-ai-sync-notify-reload.md` の「設計要素 3. シーケンス番号と再同期」
- 要件定義: `docs/requirements/jupyterlab-ai-sync.md` F1.1・AC4（再接続の要件に再同期を追加）、`docs/requirements/jupyter-server.md` F4（状態照会 API を追加）
- API 契約: `docs/design/api-contracts.md`（状態照会 API の追加）
- 不変条件: `docs/design/invariants.md` I5（本タスクで違反を解消）

## 調査したファイル

- `jupyterlab-ai-sync/src/websocket-client.ts`: 再接続は固定 5 秒間隔の再 connect のみ。再接続後の状態回復処理なし（76-103行）。`onopen` コールバックが再同期のフック地点
- `jupyterlab-ai-sync/src/plugin.ts`: `wsClient` 生成と `onDisconnect`（`unlockAll`）の配線。再同期コールバックの追加先
- `jupyter-server/extensions/custom_api/ai_events.py`: broadcast ループが `write_message` 失敗を log のみで継続（101-107行）。切断処理の追加先
- `jupyter-server/extensions/custom_api/sync_state.py`（21.3 で新設）: `get_all()` が照会 API のデータ源
- `jupyter-server/extensions/custom_api/notebook_locks.py`（21.2 で新設）: `get_locks()` が照会 API のデータ源
- `jupyterlab-ai-sync/src/lock-manager.ts`: `lockNotebook` / `unlockNotebook` / `unlockAll`（再適用で流用）
- `jupyterlab-ai-sync/src/notebook-updater.ts`（21.3 で改修済み前提): revert 実装の流用元

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | ブラウザが seq を記録し、再接続時に照会 API と突き合わせて差分のあるノートブックだけ revert | 無駄な revert をしない。ロック状態も同時に回復 | ブラウザ側に lastSeq の Map を持つ |
| B | 再接続時に開いている全ノートブックを無条件 revert | 実装最小 | 切断が頻発する環境で不要な revert が走り、ユーザーのスクロール位置等が失われる。ロック回復には結局照会 API が必要 |
| C | サーバー側にイベント履歴バッファを持ち、再接続時に欠落分を再送 | 差分粒度の回復 | ADR-0002 で不採用の複雑化（履歴・再送機構）。revert がフォールバックとして既にあるため不要 |

採用理由: A は照会 API 1 本で seq とロックの両方を回復でき、B の欠点（無差別 revert）を seq 比較だけで回避できる。

ADR 要否: 不要（ADR-0002 で決定済み）。

## 参考にする既存実装

- コピー元: `jupyter-server/extensions/custom_api/handlers.py` の `HealthHandler`（読み取り専用 GET ハンドラーの最小例）

## 異常系・不変条件

- 切断中の変更（本タスクの主題）: E2E テスト欄のシナリオで検証（下記完了条件）
- 照会 API 自体の失敗: 再同期をスキップして次回再接続時に再試行（ロックは安全側 = サーバー強制があるため表示ずれのみ）。warn ログを出す
- 再接続直後に通知が届く race: 照会 → revert の間に `notebook_changed` が来ても、seq は単調増加のため二重 revert になるだけで整合性は壊れない（debounce が吸収）
- 不変条件: I5 充足（本タスクの目的）。I3: 照会ハンドラーはメモリ読み取りのみ

### 実装手順

1. 照会 API `GET /api/ai/sync-state` を TDD で実装する（seq 0 件・ロック 0 件の空応答、変更後の seq 反映、ロック中の一覧反映）。検証: `scripts/test.sh jupyter-server` が成功する
2. `ai_events.py` の broadcast で送信失敗クライアントを除去 + close する。検証: ハンドラーテストで「失敗クライアントが 2 回目の broadcast の対象にならない」ことをモック検証
3. ブラウザ側: `sync-state-client.ts` と `notebook-updater.ts` の `lastSeq` 記録・`resync()` を実装する。resync のロジック: 照会結果の各ロックを `lockNotebook`、ロックにないパスを `unlockNotebook`、開いているノートブックのうち `lastSeq` と照会 seq が異なる（または lastSeq 未知で照会 seq > 0 の）ものを revert。検証: `scripts/test.sh jupyterlab-ai-sync --typecheck` とビルドが成功する
4. `websocket-client.ts` に `onReconnect` を追加し `plugin.ts` で配線する。検証: 同上
5. 統合テスト: WS 接続 → 切断 → `notebook_add_cell` 実行 → 再接続 → 照会 API の seq が記録値より進んでいることを検証する（`tests/helpers/ws-event-client.ts` を利用）。検証: `scripts/test.sh jupyter-mcp --integration` が成功する
6. 要件定義（ai-sync F1.1/AC4 に再同期、jupyter-server F4 に照会 API）と `docs/design/api-contracts.md` を改訂する。検証: `uv run python scripts/check-docs-consistency.py` が成功する

### 技術的な考慮事項

- `unlockAll()`（切断時の全ロック解除表示）は維持しつつ、再接続時の resync でロック表示を復元する（切断中は「サーバーに強制があるので表示は安全側に倒す」という 21.2 の方針と整合）
- resync は冪等（何度呼んでも同じ最終状態）に実装する。初回接続時にも発火するが、lastSeq が空でも「seq > 0 の開いているノートブックを revert」は安全（ディスクが真実）
- ブラウザ実機での revert 動作確認（切断 → 変更 → 再接続 → 表示一致）は 21.5 で実施

## リスクと検知方法

- lastSeq の記録漏れ（イベント種別の追加時）: `notebook_changed` 受信処理の単一箇所で記録するため構造的に漏れない（レビュー観点として明記）
- 照会 API とロックストア/seq ストアの不整合: 両ストアとも同一プロセスのメモリで、照会はスナップショット読み取りのみ。テストで検証
- ゾンビ接続除去の副作用（正常クライアントの誤切断）: `write_message` の例外時のみ除去。統合テストの正常配信ケースで回帰検知
