# タスク詳細: 21.1 ノートブック編集ツール宣言の型化

## 概要

手動管理の allowlist `NOTEBOOK_EDIT_TOOLS`（`jupyter-mcp/src/tools/index.ts:807`）を廃止し、ツール登録型に必須フィールド `mutatesNotebook: boolean` を導入する。新規ツール追加時の宣言漏れをコンパイルエラーで検知できるようにし、21.2 のミドルウェア変更（ロック取得/解放）の対象集合をレジストリから導出可能にする。

## 関連ドキュメント

- ADR: `docs/adr/0002-ai-sync-notify-reload.md` の「設計要素 4. 編集ツール allowlist の型化」
- 要件定義: `docs/requirements/jupyter-mcp.md` の「F6.1: AI編集モードの自動制御」（NOTEBOOK_EDIT_TOOLS Set 前提の記述を改訂する）
- 不変条件: `docs/design/invariants.md`（本タスクは I1/I2/I5 の前提整備）

## 調査したファイル

- `packages/mcp-shared/src/tool-router.ts`: `ToolEntry<TResult>` は `definition` + `execute` の2フィールド。`registerTools` / `handleToolCall` を jupyter-mcp と document-mcp が共用
- `packages/mcp-shared/src/index.ts`: `ToolEntry` / `registerTools` / `handleToolCall` をエクスポート
- `jupyter-mcp/src/tools/index.ts`: `toolRegistry: ToolEntry<McpToolResult>[]`（23 ツール）、`NOTEBOOK_EDIT_TOOLS` Set（12 ツール、807-820行）、ミドルウェア `handleToolCall`（833-844行）
- `jupyter-mcp/tests/unit/tools/notebook-edit-cell.test.ts`: Vitest + `vi.mock` で jupyterClient を丸ごとモックするパターン

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | jupyter-mcp 内に `JupyterToolEntry extends ToolEntry` を定義し、必須フィールド `mutatesNotebook: boolean` を追加。`toolRegistry` の型を差し替え | 宣言漏れがコンパイルエラー。mcp-shared / document-mcp に影響なし | jupyter-mcp ローカル型が1つ増える |
| B | mcp-shared の `ToolEntry` にフィールドを追加 | 全 MCP で統一 | 必須にすると document-mcp の全ツールに無意味な宣言を強制、オプションにすると強制力がなく目的を達しない |
| C | Set を維持しレジストリ走査テストのみ追加 | 変更最小 | 検知がテスト実行時まで遅延。「型で強制」という ADR の決定に反する |

採用理由: `mutatesNotebook` は Jupyter 固有の概念であり、共有型を汚さずに必須化（コンパイル強制）できる A が ADR-0002 の意図に合致する。

ADR 要否: 不要（ADR-0002 で決定済みの設計要素の実装）。

## 参考にする既存実装

- コピー元: `packages/mcp-shared/src/tool-router.ts` の `ToolEntry`（拡張インターフェースの定義元。同種の実装は初）

## 異常系・不変条件

- 該当する異常系（不正入力）: `mutatesNotebook` 未宣言のツール登録 → `scripts/test.sh jupyter-mcp --typecheck` がコンパイルエラーで失敗することを完了条件で検証
- 関係する不変条件: I2/I5 の前提整備（配信・ロック対象の宣言漏れという構造的な穴を塞ぐ）。抵触なし

## 実装計画

### 作成するファイル

| ファイル | 内容 |
|----------|------|
| `jupyter-mcp/src/tools/index.ts`（変更） | `JupyterToolEntry` 型定義、`toolRegistry` の型差し替え、全23エントリへの `mutatesNotebook` 宣言、`NOTEBOOK_EDIT_TOOLS` Set をレジストリからの導出に置換 |
| `jupyter-mcp/tests/unit/tools/tool-registry.test.ts`（新規） | レジストリ走査テスト |

### 実装手順

1. `jupyter-mcp/src/tools/index.ts` に `interface JupyterToolEntry extends ToolEntry<McpToolResult> { mutatesNotebook: boolean }` を定義し、`toolRegistry: JupyterToolEntry[]` に変更する。検証: `scripts/test.sh jupyter-mcp --typecheck` が「mutatesNotebook がない」旨のエラーで失敗する（Red）
2. 全 23 エントリに `mutatesNotebook` を宣言する（true: 現行 `NOTEBOOK_EDIT_TOOLS` の 12 ツール / false: それ以外 11 ツール。`kernel_restart` はセル内容を変更しないため false を維持）。検証: `scripts/test.sh jupyter-mcp --typecheck` が成功する
3. `NOTEBOOK_EDIT_TOOLS` の Set リテラルを削除し、`const NOTEBOOK_EDIT_TOOLS = new Set(toolRegistry.filter(e => e.mutatesNotebook).map(e => e.definition.name))` の導出に置換する（ミドルウェアのロジックは本タスクでは変更しない）。検証: `scripts/test.sh jupyter-mcp` で既存ユニットテストが全件成功する
4. `tool-registry.test.ts` を新規作成: (a) `mutatesNotebook: true` のツール名集合が既知の 12 ツールと完全一致する（意味的な宣言ミスの検知）、(b) `registerTools()` の全ツール名がレジストリと1対1対応する。検証: `scripts/test.sh jupyter-mcp` で新規テストが成功する
5. `docs/requirements/jupyter-mcp.md` F6.1 の「`NOTEBOOK_EDIT_TOOLS` Set で管理し、Set に追加するだけで自動対応」の記述を「ツール登録時に必須フィールド `mutatesNotebook` で宣言する（宣言漏れは型チェックで検知）」に改訂する。検証: `uv run python scripts/check-docs-consistency.py` が成功する

### 技術的な考慮事項

- `sharedHandleToolCall` / `sharedRegisterTools` は `ToolEntry<TResult>[]` を受け取るため、構造的部分型により `JupyterToolEntry[]` をそのまま渡せる（mcp-shared の変更は不要）
- `definition`（MCP SDK の `Tool` 型）の中ではなく `JupyterToolEntry` 直下にフィールドを置く（`Tool` 型は SDK 定義のため拡張しない）

## リスクと検知方法

- ツールの true/false 分類ミス（編集ツールをロック対象から漏らす）: 手順 4(a) の既知 12 ツールとの完全一致テストで検知
- document-mcp への意図しない影響: mcp-shared を変更しないため構造的に影響なし。`scripts/test.sh document-mcp` の成功で確認
