# タスク詳細: 9.3 カタログ参照→SQL実行→分析の結合テスト

## 概要

document-mcp でデータカタログを参照し、テーブル構造を把握した上で SQL クエリを生成、execute_sql API でデータを取得し、execute_code で分析する一連の E2E フローを検証する結合テストを実装する。

Phase 9.1（SQL実行API）と 9.2（execute_sql ツール）で実装した機能が、既存のカタログ参照機能・コード実行機能と正しく連携して動作することを保証するために必要。

### 既存テスト（Phase 12.2）との違い

Phase 12.2 の e2e-workflow.test.ts では `pd.read_sql_query()` で直接 PostgreSQL に接続して SQL を実行していた。本タスクでは **`POST /api/sql/execute` API を経由した SQL 実行→CSV 保存→CSV 読み込み** というフローを検証する。これは execute_sql MCP ツールのバックエンドであり、以下の特徴がある:

- SELECT 文のみ許可（INSERT/UPDATE/DELETE は拒否）
- 結果をワークスペースの `data/` ディレクトリに CSV として保存
- メタデータ（行数、カラム一覧、ファイルサイズ）を返却

### 実装手順

#### ステップ 1: api-client.ts に SQL 実行ヘルパーを追加

`tests/e2e/helpers/api-client.ts` に以下を追加:

1. `SqlExecuteResult` 型定義

```typescript
export interface SqlExecuteResult {
  success: boolean;
  file_path: string;
  row_count: number;
  columns: string[];
  file_size_bytes: number;
  execution_time_ms: number;
  truncated: boolean;
}

export interface SqlExecuteError {
  success: false;
  error: { code: string; message: string };
}
```

2. `executeSql` 関数

```typescript
export async function executeSql(
  workspaceId: string,
  sql: string,
  filename: string,
  options?: { timeout?: number; max_rows?: number },
): Promise<SqlExecuteResult> {
  return jupyterFetch<SqlExecuteResult>("/api/sql/execute", {
    method: "POST",
    body: JSON.stringify({
      workspace_id: workspaceId,
      sql,
      filename,
      ...options,
    }),
  });
}
```

3. `jupyterPost` の re-export（エラー系テスト用、既存）

#### ステップ 2: sql-analysis-flow.test.ts を作成

以下のシナリオでテストケースを実装:

**シナリオ 1: カタログ参照→SQL実行→CSV読み込み→分析**
- `getTableIndex()` → `getTableDetail()` でカラム情報を取得
- `executeSql()` で SELECT クエリを実行、CSV が data/ に保存される
- `executeCode()` で `pd.read_csv('data/xxx.csv')` を実行
- DataFrame のカラムがカタログ定義と一致することを検証

**シナリオ 2: 複数テーブルの JOIN クエリ→分析**
- `getTableDetail()` で 2 テーブル（id_pos_transactions, customer_master）のカラム情報と key_type/domain を取得
- `executeSql()` で JOIN クエリを実行
- `executeCode()` で CSV を読み込み、結合結果を検証

**シナリオ 3: SQL 実行のエラーハンドリング**
- SELECT 以外のクエリ（INSERT）が拒否される
- 存在しないテーブルへのクエリでエラーが返る
- 構文エラーの SQL でエラーが返る

**シナリオ 4: 完全フロー（カタログ→用語→SQL→分析）**
- 用語解決（`getTermDetail`）→テーブル特定（`getTableDetail`）→SQL 実行（`executeSql`）→CSV 読み込み・分析（`executeCode`）の一連フロー

### 技術的な考慮事項

- **テスト配置**: 既存の `tests/e2e/` ディレクトリに追加。Phase 12.2 と同じ基盤（vitest, api-client.ts）を再利用
- **サービス依存**: document-server、jupyter-server、PostgreSQL が起動している必要がある。`checkServices()` で起動確認し、未起動時はスキップ
- **クリーンアップ**: 各テスト後にセッション・ワークスペースを削除。CSV ファイルはワークスペース削除で自動消去
- **タイムアウト**: カーネル初回起動を考慮し、統合フローテストは 120 秒に設定
- **SQL 実行 API の認証**: jupyter-server のトークン認証を経由（既存の JUPYTER_HEADERS を使用）
- **`POST /api/sql/execute` のレスポンス形式**: jupyter-server のレスポンスは `{ data: { ... } }` でラップされている可能性がある。実際のレスポンス形式に合わせて api-client.ts の型定義を調整する

### 実行方法

```bash
# 前提: 全サービス起動
docker-compose up -d

# テスト実行
cd tests/e2e && npx vitest run sql-analysis-flow.test.ts

# 全 E2E テスト実行
cd tests/e2e && npx vitest run
```

### 前提条件

- `docker-compose up -d` で全サービスが起動していること
- PostgreSQL に初期データがロードされていること
- 環境変数:
  - `DOCUMENT_SERVER_URL` (デフォルト: `http://localhost:3002`)
  - `JUPYTER_SERVER_URL` (デフォルト: `http://localhost:8888`)
  - `JUPYTER_TOKEN`
