# タスク詳細: 12.1 execute_sql クエリ保存実装

## 概要

execute_sql ツールでSQLクエリを実行した際、そのクエリをワークスペースの `data/queries/` ディレクトリに `.sql` ファイルとして保存する機能を追加する。ファイルにはメタデータ（実行日時、結果ファイル名、行数、実行時間）をSQLコメントとしてヘッダーに記載する。レスポンスに `query_file_path` を追加し、AIが実行したクエリを後から確認・検証できるようにする。

### 実装手順

#### 1. execute-sql.ts にクエリ保存ロジックを追加

`executeExecuteSql` 関数内で、SQL実行成功後（`jupyterClient.executeSql()` 成功後）にクエリ保存処理を追加する。

**処理フロー:**

1. `data/queries/` ディレクトリの存在確認・作成（Jupyter Contents API 経由）
2. 既存のクエリファイル数を取得して連番を決定（`file_list` で `data/queries/` を参照）
3. ファイル名を生成: `{連番(3桁ゼロ埋め)}_{filename(拡張子なし)}.sql`
   - 例: `001_transactions.sql`
   - `filename` は execute_sql の引数の filename パラメータ（CSVファイル名）から拡張子を除去
4. メタデータ付きのクエリファイル内容を生成
5. Jupyter Contents API 経由でファイルを書き込み
6. レスポンスに `query_file_path` を追加

**クエリファイルの形式:**

```sql
-- executed_at: 2024-01-15T10:05:00Z
-- result_file: transactions.csv
-- row_count: 1500
-- execution_time_ms: 250
SELECT transaction_id, customer_id, amount, transaction_date, status
FROM purchase_history
WHERE transaction_date >= '2024-01-01'
```

**連番の決定方法:**

Jupyter Contents API の `GET /api/contents/{workspace_path}/data/queries` でディレクトリ内容を取得し、既存ファイル数をカウントして `count + 1` を連番とする。ディレクトリが存在しない場合は連番 1 から開始。

**ファイル書き込み方法:**

Jupyter Contents API の `PUT /api/contents/{path}` を使用（`upload-external-data.ts` と同じパターン）。
- `type: "file"`
- `format: "text"`
- `content: クエリファイル内容（テキスト）`

execute_sql ツールの description にクエリ保存機能の説明を追記する（入出力スキーマの変更は不要、query_file_path はレスポンスの一部として自然に含まれる）。

### 技術的な考慮事項

- **ファイル書き込みは Jupyter Contents API 経由**: MCP サーバーからホスト側のファイルシステムに直接書き込むのではなく、Jupyter サーバー経由でワークスペース内に書き込む（既存パターンに準拠）
- **クエリ保存は実行成功時のみ**: バリデーションエラーやSQL実行エラー時にはクエリファイルを保存しない（要件 F9.3）
- **クエリ保存失敗時の挙動**: クエリ保存に失敗した場合は1回リトライを試みる。リトライも失敗した場合はエラーとして扱い、エラーレスポンスを返す（エラーを握りつぶさない）。SQL実行自体は成功しているが、クエリの保存・追跡が目的の機能であるため、保存失敗は看過しない
- **連番のユニーク性**: ディレクトリ内の既存ファイル数に基づく連番なので、ファイルが削除された場合に番号が飛ぶ可能性があるが、シンプルさを優先
- **Jupyter Contents API のディレクトリ自動作成**: `data/queries/` ディレクトリが存在しない場合、最初のクエリ保存時にディレクトリを作成する必要がある

## テスト計画

### 追加するテストケース（execute-sql.test.ts）

| カテゴリ | テストケース | 期待結果 |
|---------|------------|---------|
| 正常系 | SQL実行成功時にクエリファイルが保存される | Contents API の PUT が呼ばれ、正しいパスとメタデータ付き内容が渡される |
| 正常系 | レスポンスに query_file_path が含まれる | `data/queries/001_transactions.sql` 形式のパスが返る |
| 正常系 | 連番が正しくインクリメントされる | 既存ファイルが2つある場合、003 から始まる |
| 正常系 | filename の拡張子が除去される | `transactions.csv` → `001_transactions.sql` |
| 正常系 | メタデータが正しいフォーマットで含まれる | `-- executed_at:`, `-- result_file:`, `-- row_count:`, `-- execution_time_ms:` のSQLコメント |
| 正常系 | data/queries/ ディレクトリが未作成の場合に作成される | Contents API でディレクトリ作成が呼ばれる |
| 異常系 | バリデーションエラー時にクエリ保存されない | Contents API の PUT が呼ばれない |
| 異常系 | SQL実行エラー時にクエリ保存されない | Contents API の PUT が呼ばれない |
| 異常系 | クエリ保存失敗時に1回リトライされる | Contents API の PUT が2回呼ばれる |
| 異常系 | クエリ保存がリトライ後も失敗した場合エラーが返る | success: false のエラーレスポンスが返る（QUERY_SAVE_ERROR） |
