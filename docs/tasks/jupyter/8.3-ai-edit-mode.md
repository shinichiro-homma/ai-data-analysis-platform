# タスク詳細: 8.3 AI編集モード（ロック制御）

## 概要

AIがノートブックを編集する際に、`ai_edit_start` でノートブックをロック（read-only化）し、AI操作が完了したら `ai_edit_end` でロック解除する機能を実装する。

ロック中はユーザーのキーボード入力・セル編集・セル実行を無効化し、「AI が編集中です」というバナーを表示する。ロック中もセル追加・実行結果のリアルタイム反映（8.1, 8.2で実装済み）は引き続き動作する。

### なぜこのタスクが必要か

9.1（セル追加同期）と9.2（セル実行同期）ではAI操作のリアルタイム反映を実装したが、AI操作中にユーザーが同時にノートブックを編集するとセルインデックスがずれるなどの不整合が発生する。ロック制御により、AI操作中はユーザー操作を安全に無効化し、操作完了後に編集権を返す。

### 実装手順

#### ステップ1: 型定義の追加（jupyter-mcp）

`jupyter-mcp/src/jupyter-client/types.ts` に `AiEditStartEvent` と `AiEditEndEvent` 型を追加し、`AiEvent` 型のユニオンに含める。

```typescript
export interface AiEditStartEvent extends AiEventBase {
  type: 'ai_edit_start';
  notebook_path: string;
}

export interface AiEditEndEvent extends AiEventBase {
  type: 'ai_edit_end';
  notebook_path: string;
}

export type AiEvent = CellAddedEvent | CellExecuteStartEvent | CellOutputEvent | CellExecuteEndEvent | AiEditStartEvent | AiEditEndEvent;
```

#### ステップ2: MCPツール実装（jupyter-mcp）

**ai-edit-start.ts:**
- `session_id` を引数に受け取る
- セッションからノートブックパスを取得する（既存の `jupyterClient.getSessions()` を使用）
- `jupyterClient.postAiEvent({ type: 'ai_edit_start', notebook_path })` でイベントを配信
- 戻り値: `{ locked: true, notebook_path }`

**ai-edit-end.ts:**
- `session_id` を引数に受け取る
- セッションからノートブックパスを取得する
- `jupyterClient.postAiEvent({ type: 'ai_edit_end', notebook_path })` でイベントを配信
- 戻り値: `{ locked: false, notebook_path }`

**index.ts:**
- ツール定義（name, description, inputSchema）を追加
- `handleToolCall` に `ai_edit_start`, `ai_edit_end` のルーティングを追加

#### ステップ3: LockManager 実装（jupyterlab-ai-sync）

**lock-manager.ts:**
- `lockNotebook(notebookPath)`: 対象ノートブックをロックする
  - `NotebookPanel` を取得し、セルエディタを read-only 化
  - キーボードショートカット（実行系）を無効化
  - ロックインジケータを表示
- `unlockNotebook(notebookPath)`: ロックを解除する
  - read-only を解除
  - ショートカットを再有効化
  - インジケータを非表示
- ロック状態の管理（どのノートブックがロック中か追跡）

**ロック方法の技術詳細:**
JupyterLab 4.x の API を使用:
1. **セル編集の無効化**: `notebook.widgets` を走査し、各セルの `editor.setOption('readOnly', true)` で read-only 化。新規追加セルにも適用するため、`model.sharedModel.changed` シグナルを監視する。
2. **セル実行の無効化**: `NotebookActions.run` 等のコマンドをブロックするため、ノートブック操作のコマンド（`notebook:run-cell`等）にガードを追加。具体的には `app.commands` の `commandExecuted` シグナルを監視するか、より簡易にセルの `readOnly` 状態で実行をブロックする。
3. **ツールバーボタンの無効化**: ロック中は実行ボタン等を disabled にする。

### 技術的な考慮事項

#### ロック方法の選択

JupyterLab にはノートブック全体を read-only にする単一のフラグは存在しない。以下のアプローチを組み合わせる:

1. **エディタの readOnly プロパティ**: 各セルの CodeMirror エディタに `readOnly: true` を設定。これにより文字入力が無効になる。
2. **セル追加後の自動ロック**: AI がセルを追加した場合、そのセルも自動的に readOnly になるよう、`sharedModel.changed` シグナルを監視する。
3. **コマンドパレット経由の操作防止**: `notebook:run-cell`, `notebook:delete-cell` 等のコマンドにガードを設ける。

#### エッジケースの考慮

- **AI操作中に接続が切れた場合**: WebSocket 切断時にロック状態のノートブックがあれば自動アンロックする（安全側に倒す）
- **ai_edit_end が呼ばれなかった場合**: タイムアウト（例: 5分）でも自動アンロックを検討。ただし、Phase 8.3 では基本フローの実装に注力し、タイムアウトは統合テスト（8.4）の結果を見て検討する。
- **ロック中にブラウザをリロードした場合**: リロード後はロック状態がリセットされるため問題なし（AI操作はサーバー側で継続し、次の `ai_edit_start` でロック再開）。

#### 既存ツールとの連携

`ai_edit_start` / `ai_edit_end` はイベント配信のみを行い、既存の `notebook_add_cell` や `execute_code` には変更を加えない。これらのツールは 9.1, 9.2 で既にイベント配信を実装済みであり、ロックはフロントエンド側のみの関心事である。
