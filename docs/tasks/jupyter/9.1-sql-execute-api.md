# タスク詳細: 9.1 jupyter-server: SQL実行API実装

## 概要

`POST /api/sql/execute` エンドポイントを jupyter-server に実装する。当初は SELECT 専用で実装済みだが、DELETE 以外の全 SQL 命令に対応するよう拡張する。

**初期実装（完了済み）:**
- SELECT/WITH(CTE) クエリの実行
- 結果 CSV のワークスペース `data/` への保存
- `_validate_select_only()` による SELECT 以外の拒否
- `SET default_transaction_read_only = ON` による多層防御

**今回の拡張（対象）:**
- DELETE 以外の全 SQL 命令を許可（DDL/DML/トランザクション系含む）
- DELETE のみ明示的に拒否
- 非 SELECT 命令は CSV 保存なしで `affected_rows` を返却

## 13.2（MCP 側）との整合

13.2 の実装が先行しているため、サーバー側はこれに合わせる。

**MCP 側の前提:**
- `SqlExecuteResponse` 型に `affected_rows?: number` が追加済み（`types.ts` L375）
- MCP は常に `workspace_id`/`filename` をサーバーに送信する（セッションから解決）
- クエリ保存で `result.row_count ?? result.affected_rows ?? 0` を使用済み
- 非 SELECT テスト（INSERT INTO → affected_rows 返却）が存在

**サーバー側の対応方針:**
- `workspace_id`/`filename` は常にリクエストに含まれるため、パラメータとしては受け取る
- 非 SELECT 時はワークスペース検証・CSV 保存をスキップする
- レスポンス形式は MCP のテスト期待値と一致させる

|----------|----------|

### 実装手順

#### 1. SQL 分類関数の新設 — `_classify_sql()`

`_validate_select_only()` を置き換える新しい関数を作成する。SQL 文を「SELECT」か「非 SELECT」かに分類し、DELETE のみ拒否する。

```python
@dataclass
class SqlClassification:
    is_select: bool        # True: SELECT系, False: 非SELECT系
    error: str | None      # 拒否の場合のエラーメッセージ（許可時は None）

def _classify_sql(sql: str) -> SqlClassification:
    """
    SQL を分類し、許可/拒否を判定する。

    - SELECT / WITH → is_select=True（結果セットあり、CSV保存対象）
    - DELETE → error（拒否）
    - その他全て → is_select=False（結果セットなし、affected_rows返却）
    """
```

**分類ロジック:**

1. 正規化（空白除去、セミコロン除去）
2. 空文字チェック
3. `sqlparse.parse()` で単一文であることを確認（複文拒否）
4. 先頭キーワードを抽出し、以下のルールで分類:

| 先頭キーワード | 結果 |
|---------------|------|
| `SELECT`, `WITH` | `is_select=True` |
| `DELETE` | `error="DELETE statements are not allowed."` |
| その他すべて | `is_select=False` |

**ポイント:**
- DELETE 以外は全て許可する（CREATE TABLE, ALTER, CREATE INDEX 等もすべて OK）
- 複文（セミコロンで連結した複数SQL）は引き続き拒否
- sqlparse の先頭トークン解析は既存実装（`_validate_select_only`）のパターンを踏襲

#### 2. 非 SELECT 用実行関数の新設 — `_execute_non_select_sync()`

SELECT 用の `_execute_sql_sync()` はそのまま維持し、非 SELECT 用の新しい関数を追加する。

```python
def _execute_non_select_sync(database_url: str, sql: str, timeout: int) -> dict:
    """
    非 SELECT SQL を同期的に実行する。

    Returns:
        dict: {"affected_rows": int}
    """
    engine = sqlalchemy.create_engine(
        database_url,
        connect_args={"connect_timeout": 5},
        pool_size=1,
        max_overflow=0,
    )
    try:
        with engine.connect() as conn:
            # ※ read_only は設定しない（書き込み操作を許可）
            timeout_ms = timeout * 1000
            conn.execute(
                sqlalchemy.text("SET statement_timeout = :timeout_ms"),
                {"timeout_ms": timeout_ms},
            )
            result = conn.execute(sqlalchemy.text(sql))
            conn.commit()  # 明示的にコミット
            affected_rows = result.rowcount if result.rowcount >= 0 else 0
            return {"affected_rows": affected_rows}
    finally:
        engine.dispose()
```

**`_execute_sql_sync()`（SELECT 用）との違い:**
- `SET default_transaction_read_only = ON` を**設定しない**
- `conn.commit()` を明示的に呼ぶ
- `fetchmany()` せず `result.rowcount` を取得
- DataFrame を返さない

#### 3. ハンドラーの条件分岐 — `SqlExecuteHandler.post()`

ハンドラーの処理フローを SQL 分類に応じて分岐させる。

```
リクエストパース（sql, workspace_id, filename, timeout, max_rows）
  ↓
sql バリデーション（必須）
  ↓
_classify_sql() で分類 ──→ error あり → SQL_NOT_ALLOWED 返却
  ↓
DATABASE_URL 確認
  ↓
timeout バリデーション
  ↓
┌─ is_select=True ────────────────────────┐
│ workspace_id バリデーション（必須）       │
│ filename バリデーション（必須）           │
│ max_rows バリデーション                   │
│ ワークスペース存在確認                    │
│ _execute_sql_sync() で実行               │
│ CSV 保存                                  │
│ SELECT 用レスポンス返却                   │
└─────────────────────────────────────────┘
┌─ is_select=False ───────────────────────┐
│ _execute_non_select_sync() で実行        │
│ 非 SELECT 用レスポンス返却               │
│  { success: true, affected_rows: N,     │
│    execution_time_ms: N }                │
└─────────────────────────────────────────┘
```

**非 SELECT 時のパラメータ扱い:**
- `workspace_id`: リクエストに含まれるが検証・使用しない（MCP が常に送るため）
- `filename`: リクエストに含まれるが検証・使用しない（MCP が常に送るため）
- `max_rows`: 無視
- `timeout`: 有効（デフォルト 30 秒、最大 300 秒）

**エラーハンドリング:**
- SELECT / 非 SELECT とも、DB 接続エラー・タイムアウト・SQL 実行エラーのハンドリングは共通
- 既存の try/except ブロックをそのまま活用する

### 技術的な考慮事項

#### `_validate_select_only()` の扱い

- 旧関数 `_validate_select_only()` は削除し、`_classify_sql()` で完全に置き換える
- 後方互換性の考慮は不要（内部関数のため）

#### SELECT 判定の簡素化

- 既存実装の sqlparse トークン解析パターンをベースに、判定を簡素化する
- SELECT/WITH → is_select=True、DELETE → 拒否、それ以外 → is_select=False
- キーワード別の細かい allowlist は不要（DELETE 以外は全て許可）

#### トランザクション系の `affected_rows`

- `BEGIN`, `COMMIT`, `ROLLBACK` の `result.rowcount` は -1 を返す
- この場合 `affected_rows: 0` として返却する（`max(result.rowcount, 0)` で処理）

#### 既存テストへの影響

- `jupyter-server/tests/test_base.py` は `_validate_select_only()` を直接テストしていない（base.py のユーティリティのみ）
- 関数名変更による既存テスト破損はない

## テスト計画

jupyter-server はコンテナ起動後の統合テスト方式のため、単体テストファイルは作成しない。
タスク 9.4（jupyter-mcp テスト追加 + jupyter-server 結合テスト）で以下を検証する:

**SELECT 系（既存テストで検証済み）:**
- 正常系: SELECT クエリ実行 → CSV 保存 → メタデータ返却
- 正常系: WITH...SELECT (CTE) → CSV 保存
- 異常系: タイムアウト → SQL_TIMEOUT エラー

**DDL 系（新規）:**
- 正常系: CREATE TEMP TABLE → affected_rows: 0, CSV 保存なし
- 正常系: DROP TABLE IF EXISTS → affected_rows: 0, CSV 保存なし
- 正常系: CREATE TABLE → affected_rows: 0（DELETE 以外は全て許可）
- 正常系: TRUNCATE → affected_rows: 0, CSV 保存なし

**DML 系（新規）:**
- 正常系: INSERT INTO → affected_rows が正の整数
- 正常系: UPDATE → affected_rows が正の整数
- 異常系: DELETE → SQL_NOT_ALLOWED エラー

**トランザクション系（新規）:**
- 正常系: BEGIN → affected_rows: 0
- 正常系: COMMIT → affected_rows: 0
- 正常系: ROLLBACK → affected_rows: 0

**複文拒否（既存の動作維持）:**
- 異常系: `SELECT 1; DROP TABLE x` → エラー
