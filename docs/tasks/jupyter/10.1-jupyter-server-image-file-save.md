# タスク詳細: 10.1 jupyter-server 画像ファイル保存対応

## 概要

`execute_code` で matplotlib 等のグラフ描画コードを実行した際に、画像を base64 文字列としてレスポンスに含めるのではなく、ワークスペースの `output/` ディレクトリに PNG ファイルとして保存し、レスポンスにはファイルパスのみを返すようにする。

**目的:** AI のコンテキストウィンドウを画像の base64 データで圧迫しないようにする。画像データは数十KB〜数百KBになるが、ファイルパス文字列なら数十バイトで済む。

## 関連ドキュメント

- 要件定義: `docs/requirements/jupyter-server.md` の「F2.1: コード実行」セクション（画像出力）
- 要件定義: `docs/requirements/jupyter-server.md` の「F6.1: ワークスペースディレクトリ作成」セクション（output/ ディレクトリ）
- API仕様: `docs/design/api-contracts.md` の「POST /api/kernels/{kernel_id}/execute」セクション（images レスポンス形式）

### 実装手順

#### ステップ 1: kernel_executor.py の `execute()` メソッドにファイル保存ロジックを追加

現在の実装（96〜104行目）:

```python

    if "image/png" in data:
        img_data = data["image/png"]

            "id": f"img-{len(images) + 1:03d}",
```

変更後:

```python
elif msg_type == "display_data":
    data = content.get("data", {})
    if "image/png" in data:
        img_data = data["image/png"]
        img_id = f"img-{len(images) + 1:03d}"
        filename = f"{img_id}.png"

        if output_dir:
            # base64デコードしてファイル保存
            img_bytes = base64.b64decode(img_data)
            file_path = output_dir / filename
            file_path.write_bytes(img_bytes)
            images.append({
                "file_path": f"{workspace_rel_path}/output/{filename}",
                "mime_type": "image/png",
                "description": f"matplotlib output [{len(images) + 1}]",
            })
        else:
            # output_dir が未指定の場合（後方互換）
            images.append({
                "file_path": None,
                "mime_type": "image/png",
                "description": f"matplotlib output [{len(images) + 1}]",
            })
```

- `execute()` メソッドのシグネチャに `output_dir: Path | None = None` と `workspace_rel_path: str | None = None` を追加
- `base64` モジュールは既にインポート済み（8行目）
- `pathlib.Path` を新規インポート

#### ステップ 2: handlers.py の `KernelExecuteHandler.post()` で workspace_id を解決

現在の `KernelExecuteHandler.post()` は `executor.execute(code, timeout)` を呼んでいる。これを以下のように変更:

1. kernel_id からセッション情報を取得し、workspace_id を特定
2. `resolve_workspace_dir(workspace_id)` で workspace ディレクトリを解決
3. `output_dir = workspace_dir / "output"` を算出
4. `workspace_rel_path = f"workspaces/{workspace_id}"` を算出
5. `executor.execute(code, timeout, output_dir=output_dir, workspace_rel_path=workspace_rel_path)` を呼び出す

workspace_id の特定方法: `kernel_manager` の sessions API を使用してセッション一覧から kernel_id に対応するセッションを見つけ、そのパスから workspace_id を逆引きする。

### 技術的な考慮事項

- **workspace_id の逆引き**: kernel_id → session → notebook path → workspace_id の導出が必要。`handlers.py` の `KernelExecuteHandler` で sessions API を使い、kernel_id に紐づくセッション情報からワークスペースパスを解決する。
- **output_dir が存在しない場合**: ワークスペース作成時に `output/` は自動生成されるが、念のため `output_dir.mkdir(parents=True, exist_ok=True)` で確保する。
- **ファイル名の衝突**: `img-001.png`, `img-002.png` は execute 呼び出しごとにリセットされるため、同一ワークスペースで複数回実行すると上書きされる。衝突を避けるため、ファイル名にタイムスタンプまたは execution_count を含める（例: `exec-{count}-img-001.png`）。
- **base64 データの除外**: レスポンスの images 配列に `data` フィールドを含めない。`file_path`, `mime_type`, `description` のみ。
- **エラー時の挙動**: ファイル保存に失敗した場合でも実行結果自体は返す。images にはエラー情報を含める代わりに、file_path を None にしてログ出力する。
- **sql_handlers.py のパターンとの一貫性**: ファイル保存→パス返却のパターンは sql_handlers.py（CSV保存）と同じ。`resolve_workspace_dir()` + `Path` 操作を使う。
