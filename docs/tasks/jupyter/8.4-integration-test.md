# タスク詳細: 8.4 統合テスト

## 概要

Phase 8（AIリアルタイム同期）で実装した全機能の統合テストを作成する。AI編集モード（ロック→セル追加→コード実行→アンロック）の一連フローを、MCPツール経由で実行し、jupyter-server の AI同期WebSocket エンドポイントにイベントが正しく配信されることを自動テストで検証する。

### なぜこのタスクが必要か

8.1〜8.3 では各機能の単体テスト（モック使用）と手動でのブラウザ確認のみ行った。統合テストでは、モックを使わず実際の jupyter-server に対して MCPツールを実行し、WebSocket 経由でイベントが配信される一連のフローを自動的に検証する。これにより：

1. **コンポーネント間の結合**: jupyter-mcp → jupyter-server → WebSocket の経路が正しく機能するか
2. **イベントの正確性**: 各イベントのペイロード（type, notebook_path, cell_index 等）が正しいか
3. **フロー全体の整合性**: ロック→操作→アンロックの順序・状態遷移が正しいか
4. **リグレッション防止**: 今後の変更でフローが壊れないことを保証

## 実装計画

### テスト範囲

統合テストは **jupyter-mcp ↔ jupyter-server** の間のイベント配信を検証する。JupyterLab拡張（jupyterlab-ai-sync）のブラウザ上の動作は自動テストの対象外（手動確認で補完）。

テスト戦略:
1. テスト用 WebSocket クライアントを `/api/ai/events` に接続
2. MCP ツールを実行（`handleToolCall` 経由）
3. WebSocket で受信したイベントを検証

| ファイル | 内容 |
|----------|------|
| `jupyter-mcp/tests/integration/ai-sync-flow.test.ts` | AI同期フローの統合テスト（メインテストファイル） |

### 実装手順

#### ステップ1: WebSocket イベント受信クライアントの作成

`tests/helpers/ws-event-client.ts` にテスト用の WebSocket クライアントを実装する。

**機能:**
- `ws://localhost:8888/api/ai/events?token={token}` に接続
- 受信したイベントを配列に蓄積
- 特定のイベントタイプを待機する `waitForEvent(type, timeout)` メソッド
- 複数イベントを順序付きで待機する `waitForEvents(types[], timeout)` メソッド
- 接続・切断のライフサイクル管理

```typescript
export class WsEventClient {
  private ws: WebSocket;
  private events: AiEvent[] = [];

  constructor(serverUrl: string, token: string);
  connect(): Promise<void>;
  disconnect(): void;
  getEvents(): AiEvent[];
  clearEvents(): void;
  waitForEvent(type: string, timeoutMs?: number): Promise<AiEvent>;
  waitForEvents(types: string[], timeoutMs?: number): Promise<AiEvent[]>;
}
```

**使用ライブラリ:** `ws`（Node.js WebSocket クライアント）。既に jupyter-mcp の依存関係に含まれている可能性があるが、なければ devDependencies に追加。

#### ステップ2: 統合テストの実装

`tests/integration/ai-sync-flow.test.ts` に以下のテストケースを実装する。

**テストの前提条件:**
- jupyter-server が起動していること（docker-compose up -d）
- 環境変数 JUPYTER_SERVER_URL, JUPYTER_TOKEN が設定されていること

**テスト構成:**

```
describe('AI同期フローの統合テスト')
├── beforeAll: Jupyter接続確認 + WebSocketクライアント接続
├── afterAll: WebSocketクライアント切断
├── afterEach: セッション・ノートブック・イベントバッファクリーンアップ
│
├── describe('セル追加のリアルタイム同期')
│   ├── test: notebook_add_cell → cell_added イベントが配信される
│   └── test: cell_added イベントのペイロードが正しい
│
├── describe('セル実行のリアルタイム同期')
│   ├── test: execute_code → cell_execute_start, cell_output, cell_execute_end イベントが配信される
│   ├── test: stdout 出力が cell_output イベントで配信される
│   ├── test: エラー出力が cell_output イベントで配信される
│   └── test: 画像出力が cell_output イベントで配信される
│
├── describe('AI編集モード（ロック制御）')
│   ├── test: ai_edit_start → ai_edit_start イベントが配信される
│   ├── test: ai_edit_end → ai_edit_end イベントが配信される
│   └── test: イベントの notebook_path が正しい
│
└── describe('E2Eフロー: ロック→セル追加→実行→アンロック')
    ├── test: 完全フローで全イベントが正しい順序で配信される
    └── test: 複数セル追加・実行のフロー
```

#### ステップ3: テストケースの詳細

**テスト1: セル追加イベントの検証**
```
1. session_create(notebook_path="test-sync.ipynb") でセッション作成
2. notebook_add_cell(session_id, cell_type="code", source="x = 1") でセル追加
3. WebSocket で cell_added イベントを待機
4. イベントの notebook_path, cell.cell_type, cell.source, index を検証
```

**テスト2: セル実行イベントの検証**
```
1. session_create + notebook_add_cell でセル付きノートブック作成
2. execute_code(session_id, code='print("hello")') を実行
3. WebSocket で以下のイベントを順序付きで待機:
   - cell_execute_start (cell_index を検証)
   - cell_output (output_type="stream", name="stdout", text="hello\n")
   - cell_execute_end (execution_count, success=true)
```

**テスト3: AI編集モードイベントの検証**
```
1. session_create(notebook_path="test-lock.ipynb") でセッション作成
2. ai_edit_start(session_id) を呼び出し
3. WebSocket で ai_edit_start イベントを待機
4. notebook_path が "test-lock.ipynb" であることを検証
5. ai_edit_end(session_id) を呼び出し
6. WebSocket で ai_edit_end イベントを待機
```

**テスト4: 完全E2Eフロー**
```
1. session_create(notebook_path="test-e2e.ipynb") でセッション作成
2. ai_edit_start(session_id) → ai_edit_start イベント
3. notebook_add_cell(code, "import pandas as pd") → cell_added イベント
4. notebook_add_cell(code, "print('hello')") → cell_added イベント
5. execute_code("print('hello')") → cell_execute_start + cell_output + cell_execute_end
6. ai_edit_end(session_id) → ai_edit_end イベント
7. 全イベントが正しい順序で配信されたことを検証
```

### 技術的な考慮事項

#### WebSocket イベントの非同期性

MCPツール呼び出しとWebSocketイベント配信は非同期。ツール呼び出しが完了してからイベントが到着するまでに若干のラグがある。`waitForEvent` にはタイムアウト（5秒）を設定し、イベント未到着時はテスト失敗とする。

#### イベントの順序保証

jupyter-server は `POST /api/ai/events/broadcast` を受信した順にWebSocketクライアントに配信するため、MCPツール内でのイベント送信順序がそのまま受信順序になる。ただし、execute_code 内では複数イベントを `await` 付きで順番にPOSTしているため、順序は保証される。

#### テスト間の独立性

- 各テストで固有のノートブック名を使用（`generateTestNotebookName()` を使用）
- `afterEach` でセッション・ノートブックをクリーンアップし、イベントバッファもクリア
- WebSocket 接続は `beforeAll` / `afterAll` で管理（テストごとの接続/切断はオーバーヘッドが大きい）

#### テスト用 WebSocket ライブラリの選定

Node.js 環境でWebSocketクライアントを使うために `ws` パッケージを使用する。ブラウザの `WebSocket` APIとほぼ互換で、テスト環境で安定して動作する。

#### セル実行イベントの cell_index

execute_code はセルインデックスをノートブックファイルのセル数から推定して配信する。テストでは notebook_add_cell でセルを追加した後に execute_code を呼ぶため、セルインデックスが正しいことを検証する。

#### 画像出力テストの考慮

matplotlib の画像出力テストでは、`cell_output` イベントの `output.output_type` が `display_data` で、`output.data` に `image/png` キーが含まれることを検証する。base64データの内容自体は検証しない（既存の画像テストでカバー済み）。
