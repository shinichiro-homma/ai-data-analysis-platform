# タスク詳細: 23.4 handlers.py の分割

## 概要

`jupyter-server/extensions/custom_api/handlers.py`（1,584行）を `cell_handlers.py` / `contents_handlers.py` / `preview_handlers.py` に分割する。挙動を変えない純リファクタ。カーネル管理・ヘルスチェック・同期状態のハンドラと `get_handlers()` は `handlers.py` に残す。

- 計画: `docs/plan/01-jupyter.md` Phase 23 — 23.4 の記述

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | 3 ファイル分割 + 共有ヘルパーを base.py に移動 | タスク記述どおりの分割。各ファイルが単一責務。循環 import なし | 変更ファイル数が 10（実装 5 + テスト 5）でスコープ上限 8 を超過。ただしテスト変更は import パスの機械的更新のみ |
| B | 2 ファイル分割（cell_handlers + preview_handlers）。contents は handlers.py に残す | 変更ファイル数 8 でスコープ内 | handlers.py が依然 ~700 行。タスク記述の「contents」分割が未達 |

採用理由: タスク記述が明示的に 3 分割を指定している。テスト変更は import パスの更新のみ（新規テストロジックなし）で、スコープ上限超過の実質的影響は小さい

ADR 要否: 不要。ファイル分割は構造整理であり、コンポーネント間契約や方式選定を伴わない

### 技術的な考慮事項

- **循環 import の回避**: `validate_path` と `_apply_lock_token` を `base.py` に移動することで、handlers.py → 新モジュール → base.py の一方向依存を維持する。`_resolve_workspace_for_kernel` は cell_handlers.py に移動し、handlers.py の `KernelExecuteHandler` が cell_handlers から import する形にする（handlers.py → cell_handlers の方向のみ）
- **テストの importlib ロードパターン**: テストは `importlib.util.spec_from_file_location` で handlers.py を直接ロードする。分割後は各テストが正しい新ファイルをロードするよう変更する。新ファイルは handlers.py より依存が少ないため、モックのセットアップが簡略化される
- **`__init__.py` の変更不要**: `__init__.py` は `from .handlers import get_handlers` のみを使用。`get_handlers()` が handlers.py に残るため変更不要
- **`check-docs-consistency.py` への影響**: CI で実行されるこのスクリプトは `handlers.py` の `get_handlers()` を正規表現でパースする（L142-153）。`get_handlers()` 自体は handlers.py に残留するため分割後も動作するが、フルゲート時に明示的に確認する
