# 横断不変条件（Invariants）

機能単位のタスクでは誰の担当にもならない「システム全体で常に守るべき性質」を明文化する。
新機能の設計・計画レビュー・コードレビューでは、変更がこれらに抵触しないかを確認すること（`.claude/rules/task-design.md` のチェックリスト、`.claude/rules/subagent-defaults.md` のレビュー観点から参照される）。

条件を破る必要がある場合は ADR（`docs/adr/`）で判断を記録し、この文書を更新する。

> 初版（2026-07-10）は横断レビューで見つかった負債から逆算して定義した。I1/I2/I5 の既知違反は Phase 21（ADR-0002）で解消済み。残りの不変条件は引き続き「目標」として機能する。

## I1: 状態の真実の情報源は1箇所

同じ状態（ノートブック内容、ロック状態、カタログ等）を複数の経路から書き込まない。書き込み経路を増やす設計は ADR 必須。

ノートブック内容はタスク 21.3（ADR-0002）で本不変条件を充足済み: ディスク上の `.ipynb` を唯一の真実とし、差分イベント（12種）を廃止して `notebook_changed` 通知 + ブラウザ側 `context.revert()` による再読込に統一した。

## I2: 排他制御・アクセス制限はサーバー側で強制する

UI 層の制御（ボタン無効化・readOnly 等）は体験改善であって保証ではない。ロック・権限・バリデーションは、迂回できない層（サーバー側 API）で必ず強制する。

ノートブックロックはタスク 21.2 で本不変条件を充足済み: jupyter-server が状態を保持し、`contents_manager.save` のラップ（標準 `/api/contents`・カスタム API を含む単一チョークポイント）でトークン不一致の書き込みを 423 で拒否する。ブラウザの readOnly 表示は UX への追従に格下げされた。

## I3: async コンテキストでブロッキング I/O をしない

async ハンドラ・イベントループ内で同期のファイル読み書き・DB アクセス・重い計算を直接呼ばない。`run_in_executor` 等へオフロードする。

## I4: プロセス境界を越えるデータは境界でランタイム検証する

他プロセス（REST/WS/MCP クライアント）から受け取るデータは、TypeScript の型キャストや「相手を信頼する」実装ではなく、zod / Pydantic 等で受信時に検証する。検証失敗は「形式不正」と分かるエラーで返す。

## I5: 失敗しうる通信には回復パスを定義する

WebSocket・HTTP・プロセス間通信を使う機能は、「切断中に起きた変更」「再接続後」「相手プロセスの再起動後」に状態がどう回復するかを設計に含める。回復パスのない通知は「失われてよい情報」に限る。

AI 同期 WebSocket はタスク 21.4 で本不変条件を充足済み: 再接続時に `GET /api/ai/sync-state` で seq ギャップを検出し、ギャップがあればブラウザが `context.revert()` でディスクから再読込する。ロック状態も再適用される。

## I6: 同一リソースへの並行アクセスは直列化するか、安全である根拠を示す

同一カーネル・同一ファイル・同一ストアへ複数リクエストが並行到達するケースを設計時に列挙する。ロック/キューで直列化するか、「並行しても安全」の根拠（アトミック性等）を計画に書く。

カーネル実行はタスク 23.1 で本不変条件を充足済み: `KernelExecutor.execute()` をカーネル単位の `asyncio.Lock` で直列化し、`parent_header.msg_id` フィルタで遅延メッセージの混入を防止する。

## I7: ビルドの入力はバージョン固定する

Docker ベースイメージ（digest）、言語ランタイム、依存パッケージ（lock ファイル）を固定し、「ビルドした日によって結果が変わる」要素を持ち込まない。更新は意図的な PR で行う。

## I8: 同種の実装の3回目のコピーは共通化する（rule of three）

既存実装をコピーして新機能を作るのは2回目までは許容。3回目が現れた時点で共通化を先行または同時に行う。計画時に「何のコピーか・何回目か」を明記する（`.claude/skills/task-plan-creation/SKILL.md`）。

## I9: 1 ファイルは予算行数（500 行）に収める

ファイルの肥大化を防ぎ、分割を促すための目標値。ラチェット方式で機械検知しており、既知の超過ファイルはベースラインに登録済みである（これは絶対条件ではなく目標値であり、ベースライン登録 = 既知の違反として許容されている）。予算値・対象拡張子・除外パターンは `scripts/check-file-size.py` が正。
