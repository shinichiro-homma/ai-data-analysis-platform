# 0002: AI 同期は「変更通知 + ブラウザ側再読込」の完全同期にする（差分同期を廃止）

- Status: 採用
- 日付: 2026-07-10
- 関連: ADR-0001（supersedes）、`tmp/refactor-notes.md` §1、`docs/design/invariants.md` I1/I2/I5

## 文脈（何を決める必要があったか）

ADR-0001 のイベントブロードキャスト方式は、「MCP がイベント配信」「MCP が REST でファイル書き込み」「ブラウザが ydoc へ差分反映」の3経路に状態を分散させ、不変条件 I1（真実の情報源は1箇所）・I2（排他制御はサーバー側で強制）・I5（通信の回復パス）に違反している。実害として「WS 接続クライアントが1以上だが対象ノートブックを開いていない場合、実行結果がどこにも永続化されない」バグが既知（Issue #76）。

再設計の選択肢は2つ:

- **(a) 書き込みを ydoc に一本化** — jupyter-collaboration（RTC）を導入し、サーバー側 YRoom を真実の情報源にする。MCP も Y プロトコルで YRoom に書き込む
- **(b) 差分同期を廃止し「変更通知 + ブラウザ側再読込」の完全同期** — ディスク上の .ipynb を真実の情報源とし、書き込みは jupyter-server の REST API に一本化。ブラウザは変更通知を受けたら Contents API から再読込する

## 決定

**案 (b) を採用する。** ノートブックの真実の情報源をディスク上のファイルとし、すべての書き込みを jupyter-server の API 層（MCP: cell-ops API / ブラウザ: Contents API 保存）で直列化する。ブラウザの ydoc は表示用キャッシュに格下げし、`notebook_changed` 通知を受けたら公式 API（`IDocumentManager` 経由の `context.revert()`）でディスクから再読込する。

## 比較（実装コスト / JupyterLab 依存度 / 不変条件）

| 観点 | (a) ydoc 一本化 | (b) 通知 + 再読込 |
|------|----------------|------------------|
| 実装コスト | **大**。jupyter-collaboration（サーバー拡張 + labextension）の導入、MCP（Node）用 Y プロトコルクライアントの自作（公式 TS クライアントなし、プロトコルは準内部仕様）、編集系ツール 12+ の書き込み経路の全面書き換え | **中**。書き込み経路は既存の cell-ops API を昇格して流用。ブラウザ側は差分反映ロジック（notebook-updater.ts の大半、約300行）を削除し revert() 呼び出しに置換。新規はロックストア + seq 管理（jupyter-server に1モジュール） |
| JupyterLab 依存度 | **高**。jupyter-collaboration は JupyterLab マイナーバージョンと密結合で、rolling タグ問題（refactor-notes §6）と複合してビルド脆弱性が上がる。ロック強制には YRoom 内部での更新元選別という非公式改造が必要 | **低**。使用するのは公式公開 API のみ（Contents API、IDocumentManager/context.revert、INotebookTracker）。ydoc 深層 API への依存はむしろ現状より減る |
| I1（真実の情報源1箇所） | ○ YRoom が単一ストア（純粋な充足） | ○ ファイルが単一ストア。書き手は MCP とブラウザの2者だが、全書き込みが jupyter-server API 層を通り、ロックで時間的に排他される |
| I2（サーバー側強制） | **×〜△** CRDT は全参加者の更新をマージする前提で、「AI 編集中は他クライアントの書き込みを拒否」を実現するには jupyter-collaboration 内部の改造が必要 | ○ 書き込み系 API（cell-ops / Contents PUT）でロック保有者以外を 423 Locked で拒否。UI の readOnly は体験改善に格下げ |
| I5（回復パス） | ○ CRDT 同期プロトコルが差分回復を内包 | ○ seq ギャップ検出 → フル再読込。**履歴バッファ・再送機構が不要**（再読込自体がフォールバック）で、回復パスが単純 |

## 設計要素

### 1. 真実の情報源とイベントの縮約

- ノートブックへの書き込みは jupyter-server の REST API のみ。execute 出力は**接続クライアント数に関わらず常にディスクへ書く**（現行の分岐を廃止 = Issue #76 の根本修正）
- イベントは2分類に縮約する:
  - **状態変更通知**（`notebook_changed {path, seq}`、`lock_acquired` / `lock_released`）— 回復パスあり（I5）
  - **進行表示**（`cell_execute_start` 等の実行中スピナー）— ephemeral。失われてよい情報に限定（I5 の但し書きに該当）
- 出力の逐次ストリーミング表示は廃止し、実行完了時に一括反映（帰結参照）

### 2. ロックのサーバー側強制（I2）

- jupyter-server にロックストアを新設（in-memory、notebook path キー、owner トークン + TTL + ハートビート延長）
- MCP は編集ツール実行前に lock acquire API を呼び、`finally` で release。**解除はイベント配信の成否と独立**し、release 失敗時も TTL で自動失効（固着バグの根絶）
- 書き込み系 API はロック保有者以外の書き込みを 423 Locked で拒否（複数タブ・直接 API 呼び出しにも有効）
- ロック状態は WS 通知に加え GET（状態照会 API）で取得可能にし、再接続時に再適用する

### 3. シーケンス番号と再同期（I5）

- jupyter-server がノートブックごとの単調増加 seq を維持し、全状態変更通知に付与
- ブラウザは最終受信 seq を記録。再接続時に状態照会 API で現在の seq とロック一覧を取得し、差があれば開いているノートブックを revert + ロック状態を再適用
- WS 送信に失敗したクライアントは切断してブラウザ側の再接続 → 再同期経路に載せる（現行は握りつぶし）

### 4. 編集ツール allowlist の型化

- 手動管理の `NOTEBOOK_EDIT_TOOLS` Set を廃止し、ツール登録型（ToolRegistration）に**必須フィールド** `mutatesNotebook: boolean` を追加。新規ツールの宣言漏れはコンパイルエラーになる
- ミドルウェア（ロック取得/解放・通知配信）はレジストリから対象を導出。全ツールがフィールドを持つことのレジストリ走査テストを併設

## 検討した代替案と不採用理由

| 案 | 不採用理由 |
|----|-----------|
| (a) ydoc 一本化（jupyter-collaboration 導入） | I2 のサーバー側ロック強制が CRDT のマージ前提と根本的に相性が悪く、非公式内部への改造依存になる。JupyterLab バージョン密結合の依存を増やし、MCP 用 Y プロトコルクライアント自作を含め実装コスト最大。得られる I1/I5 は (b) でも充足できる |
| 現行方式の部分修繕（seq とサーバーロックだけ追加） | 差分反映経路が残る限り「ブラウザ ydoc とファイルの2つの真実」が解消されず I1 違反が継続。差分適用のインデックスずれ（デフォルト空セル判定等）も温存される |

## 帰結（この決定が生む制約・受け入れたトレードオフ）

- **出力の逐次表示の喪失**: 長時間実行の途中経過はブラウザに流れない（実行完了時に一括反映、実行中は ephemeral なスピナー表示のみ）。必要になったら「N 秒ごとの定期フラッシュ + 通知」で拡張可能な設計とする
- **再読込の粒度はノートブック全体**: 大きいノートブックでは通知の throttle/debounce が必要。1操作 = 1 revert を保証しない（連続編集は間引かれてよい）
- **ブラウザ未保存変更との競合**: ロック取得後のブラウザ保存は 423 で拒否され、ユーザーに通知して解除後の再保存を促す。ai_edit_start 時点の未保存変更の保護（dirty なら revert を保留する等）の詳細は Phase 計画で定める
- ブラウザの readOnly・ロック UI は保証ではなく体験改善であることを前提にテストを設計する
- 採用時に ADR-0001 を「廃止（→ 0002）」に更新し、`docs/adr/README.md` の一覧と `docs/design/invariants.md` の既知違反の記述を更新する
