# 0001: AI 同期は jupyter-mcp からのイベントブロードキャストで実現する

- Status: 廃止（→ [0002](0002-ai-sync-notify-reload.md)）
- 日付: 2026-07-10（タスク 8.2 実装時 2026-03 頃の判断を後追いで文書化）
- 関連: 旧タスク Jupyter Phase 8（`docs/plan/archive/01-jupyter.md`）

## 文脈

AI（MCP クライアント）がノートブックを編集している様子をブラウザの JupyterLab にリアルタイム表示する必要があった。jupyter-server 側でファイル変更を検知して配信する案（Option B）と、変更を発生させた jupyter-mcp 自身がイベントを配信する案（Option A）があった。

## 決定

Option A を採用。jupyter-mcp がツール実行時に `POST /api/ai/events/broadcast` でイベントを送信し、jupyter-server が WebSocket `/api/ai/events` で接続中クライアントへ中継、jupyterlab-ai-sync がブラウザ側ノートブックモデル（ydoc）へ増分反映する。

## 検討した代替案と不採用理由

| 案 | 不採用理由 |
|----|-----------|
| B: jupyter-server 側でファイル変更を検知して配信 | 変更の意味（どのセルをどう操作したか）がファイル差分から復元しづらい |

## 帰結（後追い文書化のため、判明済みの問題を含む）

この決定は「イベント生成者（MCP）」と「ファイル書き込み」「ブラウザ側モデル」の3経路に状態を分散させた。2026-07 の横断レビューで以下が判明している（不変条件 I1・I2・I5 に抵触）:

- イベントにシーケンス番号・履歴がなく、切断中の変更を再接続後に回復できない
- ロックがブラウザ UI 層のみで、サーバー側の強制がない
- ロック解除がイベント配信の成否に依存し、配信失敗でロックが固着する
- 配信対象ツールの allowlist（`NOTEBOOK_EDIT_TOOLS`）が手動管理で、登録漏れを検知できない

再設計の主要な選択肢は「(a) 書き込みを ydoc に一本化する」「(b) 差分同期をやめ、変更通知＋ブラウザ側の再読込による完全同期に倒す」の2つ。決定時に後継 ADR を作成し、本 ADR を廃止すること。
