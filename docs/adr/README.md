# ADR（Architecture Decision Records）

コンポーネントをまたぐ設計判断を記録する。テンプレートは [_template.md](_template.md)。

## なぜ必要か

機能タスクの中で暗黙に下された設計判断（例: 「同期イベントは MCP 側から配信する」）は、そのタスクの粒度でしかレビューされず、影響範囲がタスクを超える場合に検討漏れが起きる。ADR に切り出すことで、判断そのものを独立してレビュー・再検討できるようにする。

## 書く契機（いずれかに該当したら書く）

- **状態の所有権を決めるとき** — どのコンポーネントが真実の情報源を持つか
- **コンポーネント間の契約・プロトコルを新設・変更するとき** — イベント形式、認証方式、エラー契約など
- **技術選定・方式選定で、後から変更するコストが大きいとき** — 通信方式、永続化方式、ビルド構成
- 迷ったら書く（10〜30行の軽量文書。書くコストより、暗黙判断が負債化するコストの方が大きい）

機能タスクの詳細計画（`docs/tasks/`）の「検討した代替案」で足りるのは、影響がそのタスク内に閉じる場合のみ。

## 運用

- ファイル名: `{連番4桁}-{短い英語名}.md`（例: `0001-ai-sync-broadcast-architecture.md`）
- Status: `採用` / `再検討中` / `廃止（→ 後継 ADR へのリンク）`。**ADR は書き換えず、判断が変わったら新しい ADR で置き換える**（`supersedes` を明記）
- ADR の追加・Status 変更は通常の PR レビューに含める。タスク計画レビュー時に「ADR を書くべき判断が含まれていないか」を確認する（`.claude/rules/task-design.md`）
