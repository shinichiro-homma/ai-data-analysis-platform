# document-server 要件定義

> **API 実装はコードが正**: エンドポイントの入出力スキーマ・パラメータ・デフォルト値・上限値・エラーは `document-server/src/routers/` と `src/models.py`（Pydantic）を参照。エンドポイント一覧は [API仕様](../design/api-contracts.md) に一元化。カラム定義・statistics・用語詳細・ロジックメタ等の YAML フィールド構成もコード（Pydantic モデル）が正であり、本書には設計判断（Why）のみを残す。

## 概要

事前に作成されたデータカタログ、用語集、既存ロジックを読み込み、APIを提供するサーバー。生成AIが適切なデータソースを特定し、業務用語を理解し、既存の分析ロジックを活用できるようにする。

## 前提条件

- データカタログ・用語集はYAMLファイルとして事前作成済み。ロジックはメタ情報（YAML）とコード本体（.sql/.py）を分離
- PoCフェーズではPostgreSQLにCSVデータを初期ロードして使用（data_sourceはpostgresql/csv両対応）
- サンプルデータと本番データを環境変数 `DATA_ENV` で切り替え可能（デフォルト: `sample`）。データファイルは環境別ディレクトリ（`data/sample/`, `data/production/`）で管理し、本番データは `.gitignore` で管理外として手動配置する
- 外部テーブル定義（`catalog/external/*.yaml`）は `index.yaml` を経由せず、ディレクトリ配下のYAMLファイルを直接パースして読み込む
- カタログ・用語集・ロジックの動的な登録・更新機能は不要

## 用語定義

| 用語 | 説明 |
|------|------|
| テーブル | データの単位。既存DBのテーブルやビュー、または外部データの定義 |
| カテゴリ | テーブルの分類（マスタ系 / トランザクション系 / アプリ系 / 施設利用系 / 外部マスタ系 等。外部データは「外部マスタ系」で管理） |
| 外部データ | DBにテーブルが存在しないが、カタログにスキーマ定義を保持するデータ。テナントマスタやカレンダーマスタなど、フォーマットが固定で都度チャットから提供されるデータ |
| key_type / key_types | カラムの結合キー種別。用語集の業務用語と整合させる識別子。`key_type` は単一、`key_types` は別カラムの値によってキー種別が異なる条件付き定義。両者は排他 |
| domain | カラムの取りうる値の定義（マスタ参照型 or 直接列挙型） |
| ロジック | 組織内で標準化された分析ロジック（SQL/Pythonスクリプト） |
| usage_type | ロジックの利用方法（template: パラメータ変更で再利用 / reference: 参考にして新規作成） |

## 機能要件

### F1: カタログ・用語集・ロジックの読み込み

#### F1.1: 起動時読み込み
- **Why**: 分析に必要なメタ情報を起動時に一括ロードし、API応答を高速化する
- 指定ディレクトリからカタログ・用語集・ロジックの各YAMLファイル（複数可）を読み込む

#### F1.2: リロード
- **Why**: ファイル変更のたびにサーバー再起動を要求しないことで運用負荷を下げる
- API経由でカタログ・用語集・ロジックを再読み込みできる

### F2: テーブル情報取得

#### F2.1: テーブルインデックス
- **Why**: 生成AIが全テーブルを俯瞰し、分析に使うテーブルを特定できるようにする
- 登録済みテーブルの一覧（table_name, display_name, summary, category）を返す
- 外部データ定義（`catalog/external/` 配下を直接パース）も含まれる

#### F2.2: テーブル詳細（一括対応）
- **Why**: カラムの結合キー・注意点・統計量を提供し、生成AIが正しい分析コードを書けるようにする。複数テーブルの一括取得で往復回数を削減する
- 指定テーブルの詳細情報を取得（複数指定可）
- 5セクション構成: 基本情報、データソース、カラム定義、基本統計量（テーブル固有の拡張統計項目を含む）、テーブルレベル注意点
- **受け入れ条件**: 条件付き key_types を持つカラム、拡張統計項目（additional）を持つ／持たないテーブル、external 型のテーブルがいずれも正しく返却される。存在しないテーブルを含む場合は見つかったもの／見つからなかったもの両方を返却

### F3: 用語情報取得

#### F3.1: 用語インデックス
- **Why**: 業務用語を横断検索し、生成AIが組織固有の語彙を理解できるようにする
- 登録済み用語の一覧（name, summary）を返す
- オプションの query パラメータで用語名（name）・別名（aliases）・関連用語（related_terms）を部分一致検索できる。省略時は全件返却、ヒットなしは空配列
- 起動時に全用語詳細から aliases・related_terms を読み込み、インメモリの検索インデックスを構築する

#### F3.2: 用語詳細（一括対応）
- **Why**: 用語の定義・別名・関連語・値体系を提供し、生成AIの用語解釈を支援する
- 指定用語の詳細情報を取得（複数指定可）

### F4: ロジック情報取得

#### F4.1: ロジックインデックス
- **Why**: 既存の標準ロジックを俯瞰し、再利用候補を特定できるようにする
- 登録済みロジックの一覧（logic_name, summary, category）を返す

#### F4.2: ロジックメタ（一括対応）
- **Why**: ロジックの目的・入出力・利用方法を提供し、生成AIが再利用可否を判断できるようにする
- 指定ロジックのメタ情報を取得（複数指定可）

#### F4.3: ロジックコード
- **Why**: 標準ロジックのコード本体を提供し、template/reference として活用できるようにする
- 指定ロジックのコードファイルの中身を取得（logic_name のバリデーションはコードのパスパラメータ定義が正）

### F5: 管理機能

#### F5.1: リロード
- カタログ・用語集・ロジックを再読み込み（F1.2 参照）

#### F5.2: ヘルスチェック
- サーバーの稼働状態を確認

## カタログ YAML の設計思想

> YAML フィールドの網羅的な属性一覧（必須/任意・型）はコードの Pydantic モデルが正。ここではコードから読み取れない設計判断のみ記載する。

### 格納形式に YAML を選ぶ理由

- 人間が読み書きしやすく、分析チームがテキストエディタで直接編集・レビュー可能
- Git管理との相性が良い（差分が見やすい）
- document-serverのAPI層で抽象化するため、将来的にDB移行が必要になってもMCP側の変更は不要

### 2層構造（index / 詳細）を採る理由

テーブル・用語・ロジックはいずれも「一覧（index.yaml）」と「詳細（個別ファイル）」の2層で管理する。生成AIはまず軽量な index で全体を俯瞰して対象を絞り込み、必要なものだけ詳細を一括取得する。これにより初回の探索コストと1回あたりのレスポンスサイズを抑える。外部テーブルのみ index.yaml を経由せず `catalog/external/` を直接パースする（DBに実体がなく、都度提供されるデータのため）。

### key_type の2パターンを持つ理由

結合キーは通常は単一（`key_type`）だが、`member_type` のように別カラムの値で会員コード体系が変わるケースがある。そのため条件付き定義（`key_types`: 各要素に `value` 必須・`condition` オプション）を用意し、生成AIが結合時の分岐を理解できるようにする。両者は排他。

### domain の2パターンを持つ理由

コード値の意味を別マスタで管理する場合（マスタ参照型: `master_table`/`master_column`/`label_column`）と、少数で固定的な値の場合（直接列挙型: `values`）を区別する。前者はラベル解決の結合先を、後者は取りうる値そのものを生成AIに伝える。

### data_source の3パターンを持つ理由

生成AIが読み込みコードを出し分けられるようにデータの格納先を型で表現する。`postgresql` なら `pd.read_sql()`、`csv` なら `pd.read_csv()`、`external` はDBに実体がなくチャットから都度提供されるデータをワークスペースに配置してから読み込む。

### statistics の拡張統計項目（additional）

`row_count` / `date_range` / `update_frequency` は共通の既知フィールドとして扱い、それ以外のキー（`avg_basket_size`, `top_categories` 等）はテーブル固有の拡張統計項目として `additional` にまとめて返す。テーブルごとに意味のある統計が異なるため、スキーマを固定せず任意キーを許容する設計とする。

### ロジックのメタ・コード分離

ロジックはメタ情報（YAML: 目的・入出力・usage_type 等）とコード本体（.sql/.py）を分離する。生成AIはまずメタで再利用可否を判断し、必要な場合のみコードを取得する。`usage_type` で template（パラメータ変更で再利用）／reference（参考にして新規作成）を区別する。

### ファイル構成

> `document-server/data/` 配下のディレクトリ構成は実際のファイルシステムを参照。sample/ はgit管理、production/ はgit管理外（手動配置）。各データセットは glossary/、catalog/、logic/ の3カテゴリで構成される。

## 非機能要件

### NF1: パフォーマンス

| 項目 | 要件 |
|------|------|
| API応答時間 | 200ms以内 |
| 起動時間 | 5秒以内（100テーブル規模） |

### NF2: セキュリティ

- DB接続情報はJupyter環境の環境変数で管理（document-serverは関与しない）
- **認証**: Bearer トークン認証を実装済み。`DOCUMENT_SERVER_TOKEN` 環境変数でトークンを設定する。`/health` エンドポイントのみ認証除外

### NF3: 運用性

- カタログ・用語集・ロジックファイルの変更はAPI経由で再読み込み
- YAMLの構文エラーは起動時に検出・報告

## 受け入れ条件

### AC1: データ読み込み
- [ ] 起動時に `DATA_ENV` で指定された環境のディレクトリ（デフォルト: `sample`）から catalog/tables、catalog/external（無ければスキップ）、glossary、logic を読み込む
- [ ] 指定された環境ディレクトリが存在しない場合はエラーで起動失敗
- [ ] 複数ファイルを読み込める。YAML構文エラーがあれば起動時にエラー表示
- [ ] statistics に既知3フィールド以外のカスタム統計項目を含むYAMLを正しく読み込める

### AC2: テーブル情報
- [ ] テーブルインデックスを取得できる（外部データ定義も含む）
- [ ] 指定テーブルの詳細を取得できる（一括対応）。基本情報・データソース・カラム定義（key_type/key_types, domain含む）・基本統計量（additional含む）・注意点が含まれる
- [ ] additional が定義されている／未定義（固定フィールドのみ）いずれでも正常に返却される
- [ ] 条件付き key_types を持つカラム、`data_source.type` が external のテーブルが正しく返却される
- [ ] 存在しないテーブルを含む場合、見つかったもの／見つからなかったもの両方を返却
- [ ] 一括取得の上限を超えた場合にバリデーションエラーが返る

### AC3: 用語情報
- [ ] 用語インデックスを取得できる（query なしで全件、name/aliases/related_terms への部分一致で絞り込み、ヒットなしは空配列）
- [ ] query が上限を超えた場合にバリデーションエラーが返る
- [ ] 指定用語の詳細を取得できる（一括対応、上限超過でバリデーションエラー）

### AC4: ロジック情報
- [ ] ロジックインデックス・メタ情報（一括対応）・コードファイルの中身を取得できる
- [ ] 一括取得の上限を超えた場合、および logic_name に不正な文字が含まれる場合にバリデーションエラーが返る

### AC5: 再読み込み
- [ ] `/admin/reload` でカタログ・用語集・ロジックを再読み込みできる
