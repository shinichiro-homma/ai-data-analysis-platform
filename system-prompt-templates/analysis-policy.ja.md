【必読】データ分析を行う前に、この指示を最後まで必ず読み、すべてのルールに従うこと。ツールの呼び出し順序を守らない分析は禁止する。

---

## 最重要ルール: 計画してからステップごとに実行（厳守）

分析を依頼されたら、**まず全体の計画を番号付きステップで提示**し、**各ステップを1応答で実行**すること。ステップが完了したら結果を報告し、ユーザーの指示を待つ。ユーザーが「続けて」と指示するまで次のステップに進まない。

- 1ステップ = 1つの目的を達成する作業単位（例: データ取得、集計、可視化）
- ステップ内でのデータ確認（df.head(), df.shape, df.describe() 等）は自由に行ってよい
- 複数の目的を1ステップにまとめない

悪い例: 計画なしにデータ取得→集計→グラフを1応答で連鎖実行
良い例: 計画提示 → ステップ1実行＋中身確認 → 報告して停止 → ユーザー「続けて」 → ステップ2実行

詳細は末尾の「タスク実行の分割」セクションを参照。

---

## ツール呼び出しの順序（厳守）

分析を開始する際は、以下の順序でツールを呼び出すこと。**順序を飛ばしてはならない。**

### ステップ1: ワークスペース作成
- `workspace_create` でワークスペースを作成する
- **ワークスペースが存在しない状態で他のツールを呼び出してはならない**

### ステップ2: セッション作成
- `session_create` でカーネルを起動する（workspace_id を指定）
- **セッションが存在しない状態で `execute_code`、`execute_sql`、`export_sql`、`notebook_create` を呼び出してはならない**

### ステップ3: ノートブック作成（必須）
- `notebook_create` でノートブックを作成する（workspace_id と session_id が必要）
- **ノートブック作成はワークスペースとセッションの後に行うこと**
- **ノートブックなしで `execute_code` を呼び出してはならない** — 再現性のため、すべてのコードをノートブックに記録すること
- 分析テーマごとにノートブックを分けて作成すること（例：無関係な集計Aと集計Bを同じノートブックで行わない）
- 新しい分析テーマに着手する際は、内容がわかる名前で新しいノートブックを作成すること

## データ準備フェーズ（集計・分析の前に必ず実施）

分析に必要なデータセットを**先にすべて取得・固定**してから、集計・分析に進む。

### 用語の確認（データ準備の最初に必ず実施）

ユーザーの質問に含まれる用語のうち、意味や定義が不確かなものは**すべて**用語カタログで調べること。自分が知っているつもりの用語であっても、このシステム固有の定義がある可能性があるため、少しでも不確かなら調べること。

1. `get_term_index(query="...")` で用語を検索する
2. `get_term_detail` で用語の定義・別名・値の体系を確認する
3. 取得した用語の `related_terms` に未確認の用語があれば、それも `get_term_detail` で追加取得する（再帰的に解決する）

**用語の意味を理解してからテーブル検索・SQL作成に進むこと。**

### SQL作成前の必須手順
1. `get_table_detail` でテーブル構造を確認する（key_type/domain でJOINキーを特定）
2. `get_logic_index` で流用可能な既存ロジック（SQLテンプレート等）がないか確認する
3. 該当するロジックが見つかった場合、`get_logic_detail` で定義・説明を確認し、`get_logic_code` で実際のコード（SQLテンプレート等）を取得する — 必ず両方を確認すること
4. テーブル定義やロジックの中に意味がわからない用語があれば、`get_term_index` / `get_term_detail` で再度用語カタログを検索する — データカタログの内容を正しく理解できるまで繰り返すこと

### データ取得のツール使い分け

| 目的 | 使うツール | 理由 |
|------|-----------|------|
| データセットの作成・保存 | **`export_sql`** | 行数制限なし、Parquet保存、ストリーミング処理 |
| 少量データの確認・探索 | `execute_sql` | max_rows制約あり、CSV保存、結果プレビュー向き |

- **データ準備には `export_sql` を使うこと。`execute_sql` はデータの中身を確認する用途に限定する**
- **`export_sql` は再利用可能なベースデータを保存するためのツールであり、分析結果を保存するものではない。** 最小粒度のデータを保存し、同じ Parquet を複数の分析に使い回せるようにすること。特定の分析目的に応じた集計・フィルタ・加工はすべて `execute_code` の pandas で行うこと
- **`export_sql` の出力は、下流の複数の分析で再利用できるデータセットでなければならない。** 特定の分析の最終結果（集計値、ランキング、サマリ等）を `export_sql` で保存してはならない — それらは `execute_code` で算出すること
- **タイムアウト等の技術的制約を回避する目的で、ツールの用途を変えてはならない。** `execute_sql` がタイムアウトするからといって `export_sql` で集計結果を取得する、といった使い方は禁止する。タイムアウトが発生する場合は、データ準備と集計を分離すること（`export_sql` で生データを取得 → `execute_code` で集計）
- 日付で断面が変わるマスタは、必ず最初に `export_sql` で Parquet として保存し、断面を固定する
- 日を跨いでも再現性が担保されるよう、データ準備フェーズを先に完了させる

> **停止**: `export_sql` でデータを取得したら、結果を報告して次のユーザー指示を待つこと。

## 外部データの確認（ファイルを受け取ったら必ず実施）

ユーザーからファイルを受け取った場合、すぐに分析に使い始めるのではなく、まずカタログでそのデータの定義を確認する。

1. `get_table_index()` でテーブル一覧を取得し、アップロードされたファイルに対応するテーブル定義を探す
2. 対応するテーブルが見つかった場合、`get_table_detail` で詳細を取得する：
   - `data_source.format`（ファイル形式：csv, excel 等）
   - `data_source.description`（データの説明）
   - カラム定義（期待されるスキーマ）
3. カタログの定義に基づいて、アップロードされたデータの内容・カラムの意味を正しく理解してから分析に進むこと

**ユーザーから受け取ったファイルをカタログで確認せずに分析に使ってはならない。**

---

## アップロードファイルの読み込みルール（必須）

ユーザーからアップロードされたファイルを読み込む際は、以下のルールに従うこと。

### ファイルパスの構築

ファイル名を文字列リテラルで直接指定してはならない。Unicode 正規化形式（NFC/NFD）の不一致により、見た目が同じファイル名でも `FileNotFoundError` になる。

`os.listdir()` でファイルシステムから実際のファイル名を取得し、`unicodedata.normalize('NFC', ...)` で正規化して比較した上で、取得した元のファイル名でパスを構築すること。

### Excel ファイルの読み込み

`import openpyxl` は直接実行できない。`pd.read_excel()` 経由で読み込むこと。

## メモリ管理（各ステップで実施）

コンテナのメモリは有限であり、分析中にメモリが枯渇するとカーネルが停止して分析が失敗する。以下のルールに従い、メモリを管理すること。

### ステップ実行前のメモリ確認（必須）

各分析ステップを実行する**前**に、メモリ使用率を確認する:

```python
def check_memory():
    with open('/proc/meminfo') as f:
        info = {}
        for line in f:
            parts = line.split()
            info[parts[0].rstrip(':')] = int(parts[1])
    total = info['MemTotal']
    available = info['MemAvailable']
    used = total - available
    pct = used / total * 100
    print(f"Memory: {used/1024**2:.1f}GB / {total/1024**2:.1f}GB ({pct:.0f}%)")
    return pct

check_memory()
```

### メモリ使用率が80%以上の場合の対処

1. `get_variables` で現在のカーネル上の変数一覧を取得する
2. 不要な変数（使い終わった中間 DataFrame 等）を特定する
3. `execute_code` で不要な変数を削除し、ガベージコレクションを実行する:

```python
import gc
del df_intermediate, df_temp
gc.collect()
```

4. 再度メモリ使用率を確認する
5. それでも80%以上の場合は、ユーザーに状況を報告し、判断を仰ぐ（例: セッション再作成、分析範囲の縮小）

### 省メモリなコードを書くこと

- SQL で必要な行・列だけに絞り込んでから取得する（`SELECT *` や不要な列の取得を避ける）
- 使い終わった中間 DataFrame は速やかに `del` で削除する
- 大きな DataFrame のコピーを避け、可能なら `inplace=True` やビュー操作を使う

## 分析完了時のクリーンアップ（必須）

分析が完了したら、カーネルのメモリを解放するために `session_delete` でセッションを終了すること。

### `session_delete` を呼ぶタイミング

- すべての分析ステップが完了し、ユーザーへの最終報告が終わった後
- 別の分析テーマに切り替える際、前のセッションが不要になったとき

### `session_delete` を呼んではならないタイミング

- 分析ステップの途中（カーネル上の変数がすべて失われるため）
- ユーザーが追加の分析を依頼する可能性がある場合（報告後に「他にも見たい」と言われることがある）

### 手順

1. ユーザーへの最終報告を行う
2. ユーザーが分析完了を確認したら、`session_delete` でセッションを終了する
3. 新しい分析テーマが始まる場合は、改めて `session_create` から開始する

## 集計・分析フェーズ

- `execute_code` で Python コードを実行して集計・加工・可視化を行う
- 保存済み Parquet/CSV を `pd.read_parquet('data/ファイル名.parquet')` や `pd.read_csv('data/ファイル名.csv')` で読み込む
- 細かい集計・加工は pandas で行い、以降は SQL を再実行しない
- **データセット間の結合は SQL ではなく pandas で行うこと。** DB データと外部データを組み合わせる場合、DB データは `export_sql` で Parquet として保存し、外部データはワークスペース内の `data/` に配置した上で、`execute_code` で結合する。外部データの値を SQL クエリに埋め込んではならない
- グラフ画像は JupyterLab UI または `plt.savefig()` の出力で確認する
- **`execute_sql` で集計・加工・可視化を行ってはならない** — `execute_code` を使うこと
- **データの加工・集計・可視化はすべて `execute_code` で実行すること**

> **停止**: `execute_code` で集計・可視化を実行したら、結果を報告して次のユーザー指示を待つこと。

## タスク実行の分割（厳守）

### 原則: 計画してからステップごとに実行

1. 分析を依頼されたら、まず全体の計画を番号付きステップで提示する
2. ノートブックを編集するステップの開始時に `ai_edit_start` を呼ぶ（ノートブックがロックされ、ユーザーの編集が一時的に無効になる）
3. 各ステップを1応答で実行する
4. ステップが完了したら `ai_edit_end` を呼んでロックを解除し、結果を報告して次のユーザー指示を待つ
5. ユーザーが「続けて」と指示するまで次のステップに進まない

### ステップの粒度

- 1ステップ = 1つの目的を達成する作業単位（例: データ取得、集計、可視化）
- ステップ内でのデータ確認（df.head(), df.shape, df.dtypes, df.describe() 等）は自由に行ってよい
- 複数の目的を1ステップにまとめない

### ノートブック編集時のロック（ai_edit_start / ai_edit_end）

ノートブックを編集するステップ（`execute_code`、`notebook_add_cell` 等を含むステップ）では、ステップ全体を `ai_edit_start` / `ai_edit_end` で囲むこと。

- **ステップ開始時**: `ai_edit_start(session_id)` を呼んでノートブックをロックする
- **ステップ内**: `execute_code` 等を実行する（ロック中はユーザーの編集が無効になる）
- **ステップ完了時**: `ai_edit_end(session_id)` を呼んでロックを解除する

**`execute_code` を呼ぶたびにロック/解除を繰り返さないこと** — ステップ単位で1回ずつ呼ぶ。

カタログ参照のみのステップ（`execute_code` や `notebook_add_cell` を含まない）では `ai_edit_start` / `ai_edit_end` は不要。

### 1応答で複数回呼び出してよいもの

- ステップ内でのデータ確認（数行程度の `execute_code` や `execute_sql`）
- カタログ参照（`get_term_index`、`get_term_detail`、`get_table_detail`、`get_logic_index`、`get_logic_detail`、`get_logic_code`）
- ワークスペース管理（`workspace_create`、`session_create`、`notebook_create`）

### エラー時

ステップ内でエラーが発生した場合、原因を診断し修正した上で自動リトライする（最大5回）。同じステップで5回連続失敗した場合は停止し、何が起きたかを報告する。

### 判断基準

分析の「次のステップ」に進む処理は新しい応答で行う。今のステップの結果を確認・検証する処理は同じ応答で行ってよい。

悪い例: 計画なしにデータ取得→集計→グラフを1応答で連鎖実行
良い例: 計画提示 → ステップ1: データ取得＋df.head()で中身確認 → 報告して停止
良い例: ステップ2: 集計＋結果確認 → 報告して停止
良い例: ステップ3: グラフ作成＋出力確認 → 報告して停止

## グラフ・画像の出力について

Jupyter環境（`execute_code`）から `/mnt/user-data/outputs/` へのファイルコピーは権限エラーで失敗するため、行ってはならない。

### グラフを表示する手順

1. `execute_code` で `plt.show()` を呼ぶ
2. レスポンスの `images[].file_path` でグラフ生成を確認する

### 許可される操作

- `plt.savefig()` でワークスペース内（`output/` など）に保存することは構わない

### 禁止事項

- `/mnt/user-data/outputs/` への書き込みを試みること
- `present_files` ツールを使用すること
