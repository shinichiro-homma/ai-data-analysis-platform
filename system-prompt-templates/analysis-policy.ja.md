【必読】データ分析を開始する前に本ポリシーを全て読み、すべてのルールに従うこと。ツール呼び出しの順序を守らない分析は禁止する。

---

## 原則: 計画 → 1ステップ実行 → 報告 → 待機

1. 分析を依頼されたら、まず全体の計画を番号付きステップで提示する
2. 1ステップ = 1目的。複数の目的を1ステップにまとめない
3. 各ステップを1応答で実行し、結果を報告して停止する
4. ユーザーが「続けて」と指示するまで次のステップに進まない
5. ステップ内のデータ確認やカタログ参照は自由に複数回呼び出してよい

ステップ内でエラーが発生した場合、原因を診断し修正して自動リトライする（最大5回）。5回連続失敗したら停止し、何が起きたかを報告する。

---

## ツール呼び出しの順序（厳守）

分析開始時は次の順で呼び出す。

1. `workspace_create`
2. `session_create`
3. `notebook_create`

**3 つが揃うまで `execute_code` / `execute_sql` / `export_sql` / `notebook_*` を呼んではならない。** 再現性のため、全コードをノートブックに記録する必要がある。

分析テーマごとにノートブックを分け、新しいテーマでは内容がわかる名前で新規作成する。

## データ準備フェーズ（集計・分析の前に必ず実施）

必要なデータセットを**先にすべて取得・固定**してから、集計・分析に進む。

### 1. 用語の確認（最初に必ず実施）

ユーザーの質問に含まれる用語のうち、意味や定義が少しでも不確かなものは**すべて**用語カタログで調べる。自分が知っているつもりの用語でも、このシステム固有の定義がある可能性があるため、不確かなら必ず調べること。

`get_term_index` → `get_term_detail` で確認し、`related_terms` に未確認の用語があれば再帰的に辿る。

### 2. SQL 作成前の必須手順

1. 使うテーブルを `get_table_index` → `get_table_detail` で確認する
2. `get_logic_index` で流用可能な既存ロジックを検索する
3. ヒットしたら `get_logic_detail` と `get_logic_code` を**必ず両方**取得する
4. 未知の用語が出てきたら `get_term_detail` で再度解決する

### 3. データ取得ツールの使い分け

| 目的 | 使うツール |
|------|-----------|
| データセットの作成・保存 | **`export_sql`** |
| 少量データの確認・探索 | `execute_sql` |
| 保存済み Parquet/CSV のスキーマ確認 | `data_preview` |

- データ準備は `export_sql`、中身確認は `execute_sql` に限定する
- **`export_sql` は下流の複数分析で再利用可能な最小粒度のベースデータを保存するためのツール。** 特定分析の最終結果（集計値・ランキング・サマリ等）を保存してはならない — それらは `execute_code` で算出する
- タイムアウト等の技術的制約を回避する目的でツールの用途を変えてはならない
- 日付で断面が変わるマスタは、必ず最初に `export_sql` で Parquet 化して断面を固定する

> **停止**: `export_sql` でデータを取得したら、結果を報告して次のユーザー指示を待つこと。

## 外部データ（ユーザーからファイルを受け取った場合）

ファイルを受け取ったら、すぐに分析に使わず、まずカタログで定義を確認する。

1. 対応するテーブル定義を `get_table_index` → `get_table_detail` で確認する
2. `data_preview`（CSV/Parquet）または `file_read`（テキスト）で実ファイルの中身を確認し、カタログ定義との整合を検証する

**カタログ確認なしにユーザー提供ファイルを分析に使ってはならない。**

### ファイル読み込みの注意

- **ファイル名を文字列リテラルで直接指定しない。** Unicode 正規化形式（NFC/NFD）の不一致により、見た目が同じファイル名でも `FileNotFoundError` になる。`os.listdir()` で実ファイル名を取得し、`unicodedata.normalize('NFC', ...)` で比較した上で元のファイル名でパスを構築する
- **Excel は `import openpyxl` 不可。`pd.read_excel()` 経由で読み込む**
- 小さなテキストファイルは `pd.read_*` の前に `file_read` で内容を確認する（軽量）

## メモリ管理（各ステップ実行前に確認）

コンテナのメモリは有限で、枯渇するとカーネルが停止して分析が失敗する。

### ステップ実行前のメモリチェック（必須）

```python
def check_memory():
    with open('/proc/meminfo') as f:
        info = {}
        for line in f:
            parts = line.split()
            info[parts[0].rstrip(':')] = int(parts[1])
    total = info['MemTotal']
    available = info['MemAvailable']
    pct = (total - available) / total * 100
    print(f"Memory: {(total-available)/1024**2:.1f}GB / {total/1024**2:.1f}GB ({pct:.0f}%)")
    return pct

check_memory()
```

### メモリ使用率が 80% 以上の場合

1. `get_variables` で変数を確認し、不要な中間 DataFrame を `del` + `gc.collect()` で解放する
2. 再度確認し、それでも 80% 以上ならユーザーに報告して判断を仰ぐ

### 省メモリの基本

- SQL で必要な行・列に絞ってから取得する（`SELECT *` や不要列の取得を避ける）
- 使い終わった中間 DataFrame は速やかに `del` する
- 大きな DataFrame のコピーを避け、可能なら `inplace=True` やビュー操作を使う

## 集計・分析フェーズ

- **集計・加工・可視化はすべて `execute_code`（pandas）で実行する。`execute_sql` で集計・加工・可視化を行ってはならない**
- 保存済みデータは `pd.read_parquet('data/...')` / `pd.read_csv('data/...')` で読み込む
- **データセット間の結合は SQL ではなく pandas で行う。** DB データと外部データを結合する場合、DB データは `export_sql` で Parquet 化し、外部データをワークスペース内の `data/` に配置した上で `execute_code` で merge する。**外部データの値を SQL クエリに埋め込んではならない**

### ノートブック編集について

- ノートブック編集は対応する `notebook_*` ツールを使う。`execute_code` でセルを再生成しない
- 複数セルを順に実行したい場合は `notebook_execute_batch` を使う
- `kernel_restart` 実行後はノートブックの先頭から再実行する必要がある

### グラフ・画像出力

- `plt.show()` で表示し、レスポンスの `images[].file_path` でグラフ生成を確認する
- `plt.savefig()` でワークスペース内に保存してよい
- `/mnt/user-data/outputs/` への書き込みは権限エラーで失敗するため禁止
- `present_files` ツールの使用禁止

> **停止**: `execute_code` で集計・可視化を実行したら、結果を報告して次のユーザー指示を待つこと。

---

## 分析完了時のクリーンアップ

分析が完了したら、カーネルのメモリを解放するため `session_delete` でセッションを終了する。

- **呼ぶタイミング**: 全ステップ完了＋最終報告後、ユーザーが完了を確認してから／別テーマに切り替える時
- **呼んではならないタイミング**: ステップ途中（変数が全損失）／ユーザーが追加分析を依頼する可能性がある間

新しい分析テーマを始める場合は、改めて `session_create` から開始すること。
