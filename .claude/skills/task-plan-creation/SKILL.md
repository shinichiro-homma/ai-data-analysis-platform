# Task Plan Creation Skill

タスクの開発計画を作成するための共通スキル。
調査手順・計画ファイルテンプレート・レビューステータスの定義を提供する。

計画作成の原則:

- **推測で計画を書かない**。変更対象・影響ファイルは調査（または自分の Read）で実在を確認してから書き、「調査したファイル」に列挙する
- **実装アプローチを 2 案以上検討**し、トレードオフを比較してから 1 案を選定する（自明な作業でも「最小変更案」と「構造改善案」の比較は可能）
- **各手順と完了条件には検証手段を書く**。第三者が実行して成否を判定できる形（実行コマンドと期待結果）で書き、「動作を確認する」のような曖昧な記述は不可
- **計画は実装フェーズの唯一の入力（コンテキストパック）として完結させる**。実装・テスト準備エージェントが計画外の探索なしで作業できるよう、変更対象と参照ファイルをすべて列挙する

## スコープ上限

以下のいずれかを超える計画は 1 タスクに詰め込みすぎである。計画を確定せず、**タスクの分割案を提示して停止する**（計画レビューでも超過は REJECT 対象）:

| 指標 | 上限 | 数え方 |
|------|------|--------|
| 新規・変更する実装ファイル数 | 8 | テストファイルを含む。docs・計画ファイルは除く |
| 新規テストケース数 | 15 | `test()` / `def test_` の単位 |
| 実装手順のステップ数 | 10 | テンプレートの「実装手順」の番号数 |
| 実装がまたがるコンポーネント数 | 2 | 契約変更に伴うテスト追従のみのコンポーネントは数えない |

根拠: 本リポジトリの通常タスクは 1〜8 ファイルで完結している（dev の直近履歴より）。これを超える計画は実装フェーズ 1 エージェントのコンテキストが肥大し、精度が落ちる。

## 1. タスクの特定

`docs/plan/README.md`（インデックス）から対象カテゴリファイルを特定し、対象タスクを見つけて以下の情報を特定する。カテゴリファイルには進行中・未着手のタスクのみがあり、完了済みの Phase は `docs/plan/archive/` にある。Phase 番号は archive を含む通し番号のため、新 Phase を採番する場合は archive 側も含めた最大番号 + 1 とする（`docs/plan/README.md` の「番号体系」参照）。

- **タスク番号**
- **タスク内容**: PLAN.md に記載された説明
- **対象コンポーネント**: 以下のいずれか（複数可）
  - `jupyter-server` / `jupyter-mcp` / `jupyterlab-ai-sync` / `document-server` / `document-mcp`
- **タスク種別**: 以下のいずれか
  - `mcp` — MCPツール実装（jupyter-mcp, document-mcp）
  - `api` — REST API 実装（jupyter-server, document-server）
  - `extension` — JupyterLab 拡張実装（jupyterlab-ai-sync）
  - `infra` — Docker/インフラ関連
  - `test` — テスト実装
  - `other` — その他

## 2. 調査手順

ステップ1で特定した **コンポーネント** と **タスク種別** に基づき、以下の起動判定表に従って調査を実行する。

**必要なものだけを選び、1つのメッセージで並列に起動すること。**

### 起動判定表

| Agent | 起動条件 | subagent_type | model |
|-------|----------|---------------|-------|
| A: 要件定義 | **常に起動** | `requirements-researcher` | `haiku` |
| B: API 仕様 | `api` または `mcp` タスクのみ | `requirements-researcher` | `haiku` |
| C: コードパターン | **常に起動** | `codebase-explorer` | `sonnet` |
| D: 類似タスク | `docs/tasks/**/*.md` に同一 Phase のファイルがあるとき | `requirements-researcher` | `haiku` |
| E: Skill | `mcp` タスクのみ | `requirements-researcher` | `haiku` |

テンプレートは `.claude/skills/parallel-investigation/SKILL.md` を参照。

### Agent A — 要件定義の収集

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `docs/requirements/{コンポーネント名}.md`
- 目的: タスクに関連する要件定義セクションの抜き出し
- 出力: 関連する機能要件（F番号と内容）、非機能要件、ツール/API 定義（入出力スキーマ）

※コンポーネントが複数ある場合は、コンポーネントごとに Agent A を分けて起動する。

### Agent B — API 仕様の収集

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `docs/design/api-contracts.md`
- 目的: タスクに関連する API 仕様セクションの抜き出し
- 出力: 関連するエンドポイント/ツール定義、リクエスト/レスポンス形式、エラーコード

### Agent C — 既存コードパターンの調査

**テンプレート B**（コード調査）を使用:
- コンポーネント: `{コンポーネント名}`
- 目的: 既存実装パターンの調査（タスクに最も近い実装を特定）
- 調査対象: src/ のディレクトリ構成、最も近い既存実装1つの詳細、共通型定義（types.ts等）、テストの書き方パターン
- 出力: ディレクトリ構成、実装パターン（コード付き具体例）、共通型定義一覧、テストパターン要約、参考ファイル一覧

※コンポーネントが複数ある場合は、コンポーネントごとに Agent C を分けて起動する。

### Agent D — 類似タスク計画の参照

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `{類似タスク計画ファイルのパス}`（Glob で特定）
- 目的: 類似タスクの実装パターンと構成の把握
- 出力: 参考タスクのファイル名、実装手順の要約、テスト計画の要約

### Agent E — Skill の確認

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `.claude/skills/mcp-typescript-server/SKILL.md`
- 目的: MCP サーバー実装に必要な要点の把握
- 出力: MCP サーバー実装の必須パターン、ツール定義の書き方、テストの書き方

### 調査結果の統合

すべてのエージェントの結果が返ってきたら、統合して計画作成に使用する。
個別にドキュメントやソースコードを読み直す必要はない。

## 3. 計画ファイルテンプレート

`docs/tasks/_template.md` をベースに、以下のファイルを作成する。

**ファイル名:** `docs/tasks/{category}/{タスク番号}-{タスク名（英語、ハイフン区切り）}.md`

例: `docs/tasks/jupyter/1.1.1-dockerfile.md`

配置先の `docs/tasks/{category}/` ディレクトリが存在しない場合は作成する。現役タスクの詳細計画はここに置き、タスク完了後は `docs/plan/README.md` の「アーカイブ規約」に従って `docs/tasks/archive/{category}/` へ移動される（完了済みの計画を探す場合のみ archive を見る）。

```markdown
# タスク詳細: {タスク番号} {タスク名}

## 概要

（このタスクで何を実現するか）

## 関連ドキュメント

- 要件定義: `docs/requirements/XXX.md` の「YYY」セクション
- API仕様: `docs/design/api-contracts.md` の「ZZZ」セクション

## 調査したファイル

- `path/to/file.ts`: （把握した要点を一言。調査エージェントの結果または自分の Read に基づく）

## 検討した代替案

| 案 | 概要 | 利点 | 欠点 |
|----|------|------|------|
| A（採用） | （概要） | （利点） | （欠点） |
| B | （概要） | （利点） | （欠点） |

採用理由: （A を選んだ決め手）

ADR 要否: （状態の所有権・コンポーネント間契約・方式選定を決める場合は `docs/adr/` に起票。不要ならその理由を1行）

## 参考にする既存実装

- コピー元: `path/to/existing.ts`（同種の実装は現在 N 個目。3個目以降なら共通化の手順を実装計画に含める — `docs/design/invariants.md` I8）

## 異常系・不変条件

- 該当する異常系（切断・再起動・並行・タイムアウト・不正入力）: （このタスクでの挙動と、受け入れ条件のどれで検証するか）
- 関係する不変条件（`docs/design/invariants.md` の番号）: （例: I3, I5 — 抵触しないことをどう担保するか。抵触が必要なら ADR 参照）

## 実装計画

### 作成・変更するファイル

| ファイル | 内容 |
|----------|------|
| `path/to/file.ts` | （説明） |

### 参照ファイル（実装時に Read するファイル）

| ファイル | 参照理由・注目箇所 |
|----------|-------------------|
| `path/to/existing.ts` | （例: 同種実装のパターン。L40-80 のハンドラ構成） |

※実装・テスト準備フェーズはこの表と「作成・変更するファイル」の範囲でのみ作業する（範囲外の Glob/Grep 探索は禁止）。情報が不足していたら探索せず、不足内容を報告して終了する。

### 実装手順

1. （手順1 — 末尾に「検証: 実行コマンドと期待結果」を書く）
2. （手順2 — 同上）

### 技術的な考慮事項

- （考慮すべき点）

## リスクと検知方法

- （壊れうる箇所・影響を受ける既存機能）: （どう検知するか — テスト・grep・実行確認）

## 完了条件

- [ ] （条件1 — 実行コマンドと期待結果で書く）
- [ ] （条件2 — 同上）
- [ ] （異常系の条件を1つ以上含める — `.claude/rules/task-design.md`）

## テスト計画

- （テスト内容）

---

## レビューステータス

- [ ] 計画レビュー完了
- [ ] 実装完了
- [ ] テスト完了
```
