# Test Fix Loop Skill

実装エージェントのテスト失敗を、オーケストレーター主導の修正ループで解消する共通スキル。

実装エージェントは失敗ログを抱えて内部反復せず、スコープ実行 1 回で報告・終了する
（`.claude/rules/tdd.md` の「Green フェーズ」）。修正の反復はこのループが担う:
オーケストレーターが失敗を**失敗ダイジェスト**に要約し、毎回クリーンなコンテキストの
小さな修正エージェントに渡す。これにより 1 試行あたりのコンテキストが常に有界になる。

呼び出し側コマンドは「## 呼び出し側が定義するパラメータ」を埋めてこのループを実行する。

---

## 呼び出し側が定義するパラメータ

| パラメータ | 説明 | 例 |
|-----------|------|-----|
| タスクコンテキスト | タスク番号・内容（またはIssue番号）、対象コンポーネント | `21.4: 再接続時の再同期` |
| 完了条件 | タスク計画（またはイシュー詳細）の完了条件。**計画全文は渡さない** | 完了条件のリストのみ |
| スコープ情報 | 変更ファイル一覧（`git diff --name-only`）、テストファイル、参照ファイル、テスト参照ポインタ | — |
| テスト実行コマンド | スコープ実行コマンド（`--quiet` 必須） | `scripts/test.sh --quiet --test --no-lint {コンポーネント名} -- {テストファイル}` |
| 最大修正回数 | 修正エージェント起動の上限（**デフォルト 3 回**） | 3 / 4 |
| エスカレーション先 | 上限超過時の導線 | `custom-auto-dev.md` の 2g / ユーザー報告して停止 |

`.claude/rules/general.md` の「サブエージェントのモデル選択」に従い、起動時は `subagent_type` と `model` を必ず併記すること。

---

## 失敗ダイジェストのスキーマ

試行間の引き継ぎはこの形式に統一する（自由記述の要約で渡さない）:

```
## 失敗ダイジェスト
- 失敗テスト: {テストファイルパス::クラス/describe::テスト名（全件）}
- エラー種別: {アサーション失敗 / 例外 / タイムアウト / インポート・構文エラー}
- 期待と実際: {失敗テストごとに expected / actual の要点を 1-2 行}
- 実装側の該当箇所: {スタックトレース中のテストファイル以外の ファイル:行}
- 試行済み仮説: {過去の試行の「仮説→修正→結果」を 1 行ずつ蓄積。初回は「なし」}
```

## ステップ 1: 失敗ダイジェストの抽出（オーケストレーターが実行）

1. 直近のテスト実行ログ（`--quiet` が保存した `tmp/test-logs/{ログファイル}`。パスはテスト実行時のコンソール出力に表示される）を **Grep で絞って**上記スキーマを埋める（全文 Read はしない。`FAILED` / `AssertionError` / `✗` / `Error` 等で当たりを付け、該当行の前後を `-C` で読む）
2. 直前のエージェント報告の「仮説・修正内容・結果」を「試行済み仮説」に追記する（初回は実装エージェントの報告から）

## ステップ 2: 修正エージェントの起動

**設定:**
- subagent_type: `general-purpose`
- model: `sonnet`。ただし**同一の失敗テストが 2 回連続で解消しない場合、次の修正エージェントは `opus` に引き上げる**

**プロンプト:**

```
{タスクコンテキスト} のテスト失敗を修正してください。
対象コンポーネント: {コンポーネント名}

## 必読
- `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『実装（Green）・バグ修正』のルールを Read すること

## 完了条件（計画より抜粋）
{完了条件のリスト}

{失敗ダイジェスト（スキーマのまま貼る）}

## スコープ
- 変更済みファイル: {git diff --name-only の一覧}
- テストファイル: {パス}
- 参照してよい範囲: {計画の「参照ファイル」「テスト参照ポインタ」}
- テスト実行コマンド: {スコープ実行コマンド}

## 手順
1. 失敗ダイジェストから原因仮説を 1 つ立てる（「試行済み仮説」と同じ修正を繰り返さない）
2. 実装コードを修正する（テストコードは変更しない）
3. テスト実行コマンドを 1 回だけ実行し、PASS / FAIL に関わらず結果を報告して終了する（`.claude/rules/tdd.md` の「Green フェーズ」）

## 制約
- 「スコープ」の範囲でのみ作業すること。範囲外の Glob/Grep 探索は禁止
- `.claude/rules/tdd.md` の「テスト実行コマンドの規律」「テストコードの読み方の規律」、lint 失敗時は `.claude/rules/lint.md` に従うこと

## 報告
- 仮説: {何が原因と判断したか（1-2 行）}
- 修正内容: {変更ファイルと要点}
- テスト結果: {PASS / FAIL（失敗テスト名）}
```

## ステップ 3: 結果の確認（オーケストレーターが実行）

- 報告が **PASS** → 報告を鵜呑みにせず、**メインで**テスト実行コマンドを再実行して PASS を確認する。確認できたらループを終了し、呼び出し側の後続処理（フルゲート等）へ進む
- 報告が **FAIL**（またはメインの再実行で FAIL）→ 修正回数をカウントし、最大修正回数以内ならステップ 1 へ戻る
- **テストコード自体のバグが疑われる報告**があった場合はループを中断し、エスカレーション先へ（実装を通すためにテストを緩める判断はこのループでは行わない — `.claude/rules/tdd.md` の原則）

## ステップ 4: エスカレーション

最大修正回数を超えても FAIL の場合、ループを**停止**して呼び出し側のエスカレーション先に従う。
報告には最終の失敗ダイジェスト（試行済み仮説の全履歴を含む）を添える。
