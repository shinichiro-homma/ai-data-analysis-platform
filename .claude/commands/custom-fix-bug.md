Issue #$ARGUMENTS のバグ修正を開始します。

以下の手順で作業してください：

## 0. ブランチの確認・作成

`.claude/rules/branch-workflow.md` の「ブランチ確認」に従い、現在のブランチを確認してください。

新しいブランチを作成する場合は「ブランチ作成」に従い、ブランチ名は「ブランチ命名規則」の「バグ修正」に従ってください（`fix/{issue番号}-{短い英語名}`）。
Issue タイトルから英語名を生成してください。

## 1. イシュー情報の確認（メインで直接実行）

### GitHub Issue の確認

```bash
gh issue view $ARGUMENTS
```

Issue の内容を確認してください。

### イシュー詳細ファイルの確認

`docs/issues/` ディレクトリから、Issue #$ARGUMENTS に対応するファイルを探して読んでください。

ファイルが存在しない場合は、GitHub Issue の内容をもとに `docs/issues/_template.md` をベースとして作成してください。

### 影響コンポーネントの特定

Issue の内容から、以下を特定してください：

- **影響コンポーネント**: jupyter-server / jupyter-mcp / jupyterlab-ai-sync / document-server / document-mcp
- **バグの種別**:
  - `api` — REST API の不具合
  - `mcp` — MCP ツールの不具合
  - `ui` — UI 表示/操作の不具合
  - `logic` — ロジック/データ処理の不具合
  - `other` — その他

## 2. 並列原因調査（必要なサブエージェントのみ起動）

ステップ1で特定した**コンポーネント**と**バグ種別**に基づき、以下の起動判定表に従ってサブエージェントを選択してください。

**必要なものだけを選び、1 つのメッセージで並列に起動すること。**

### 起動判定表

| Agent | 起動条件 | subagent_type | model |
|-------|----------|---------------|-------|
| A: ソースコード調査 | **常に起動** | `codebase-explorer` | `sonnet` |
| B: 要件定義の確認 | **常に起動** | `requirements-researcher` | `haiku` |
| C: API 仕様の確認 | `api` または `mcp` バグのみ | `requirements-researcher` | `haiku` |

まず `.claude/skills/parallel-investigation/SKILL.md` を読み、テンプレートを確認してください。
全 Agent 共通で「`.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『調査』のルールを Read すること」をプロンプトに含めてください。

### Agent A — ソースコード調査

**テンプレート B**（コード調査）を使用:
- コンポーネント: `{コンポーネント名}`
- subagent_type: `codebase-explorer`, model: `sonnet`
- 目的: Issue #$ARGUMENTS のバグ原因調査
- コンテキスト: バグの概要、症状、エラーメッセージやスタックトレース
- 調査対象の追加指示: エラーメッセージに含まれるファイル名・関数名での検索、正常系の処理フロー、バグ発生条件の特定
- 出力: 原因の候補（ファイルパス・行番号を含む）、処理フローの要約、関連するテストファイル一覧

※コンポーネントが複数にまたがる場合は、コンポーネントごとに Agent A を分けて起動してください。

### Agent B — 要件定義の確認

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `docs/requirements/{コンポーネント名}.md`
- subagent_type: `requirements-researcher`, model: `haiku`
- 目的: Issue #$ARGUMENTS に関連する要件定義の確認（仕様通りの動作とバグ症状の照合）
- コンテキスト: バグの概要、対象コンポーネント
- 出力: 関連する要件定義セクション（要約）、仕様と実際の動作のギャップ、仕様自体に問題がある可能性（あり/なし）

### Agent C — API 仕様の確認

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `docs/design/api-contracts.md`
- subagent_type: `requirements-researcher`, model: `haiku`
- 目的: Issue #$ARGUMENTS に関連する API 仕様の確認（仕様とバグ症状の照合）
- コンテキスト: バグの概要、対象コンポーネント
- 出力: 関連する API 仕様セクション（要約）、仕様と実際の動作のギャップ

### 調査結果の統合

各エージェントの結果を統合して、バグの原因を特定してください。
エージェントの結果だけでは原因が特定できない場合は、追加の調査を自分で行ってください。

## 3. イシュー詳細ファイルに記入

調査結果をイシュー詳細ファイルに記入してください：

### 原因

- 根本原因を簡潔に記述
- 関連するファイルと行番号

### 修正方針

- 修正のアプローチ
- 修正方法に複数の選択肢がある場合は比較

### 影響範囲

- 修正が影響するファイル・コンポーネント
- 要件定義・API仕様の変更が必要か

### 修正ファイル

| ファイル | 変更内容 |
|----------|----------|
| `path/to/file` | （変更内容） |

### テスト計画

- どのようにテストするか
- 回帰テストの必要性

## 4. ステータス更新

イシュー詳細ファイルのステータスを更新してください：

```markdown
- [x] 起票
- [x] 原因特定        ← チェックを入れる
- [ ] 修正方針レビュー完了
- [ ] 修正完了
```

## 5. 承認確認

修正方針を報告し、**必ず `AskUserQuestion` ツールを使って**以下の選択式で確認を取ってください：

**質問:** "この修正方針を承認しますか？"
**選択肢:**
1. **OK** - この方針で修正を進める
2. **Modify** - 方針の修正が必要（修正内容を入力）

### OK が選択された場合

1. イシュー詳細ファイルのステータスを更新する：
   ```markdown
   - [x] 修正方針レビュー完了   ← チェックを入れる
   ```
2. イシュー詳細ファイルをコミットする：
   ```
   docs: Issue #$ARGUMENTS の修正設計を完了
   ```
3. 以下の形式で報告して**終了する**：
   ```
   ## 修正設計完了

   - Issue: #$ARGUMENTS
   - 設計ファイル: docs/issues/{番号}-{名前}.md
   - ステータス: 修正方針レビュー完了

   修正を実装するには、コンテキストをクリアしてから以下を実行してください：
   /custom-start-fix $ARGUMENTS
   ```

**注意:** このコマンドでは修正の実装を行わない。設計完了後はコンテキストをクリアし、`/custom-start-fix` で実装を開始する。

### Modify が選択された場合

1. ユーザーが入力した修正内容を確認する
2. イシュー詳細ファイルの修正方針を更新する
3. 再度承認確認を行う

**注意:** 承認（OK）を得るまで、設計は完了としないでください。
