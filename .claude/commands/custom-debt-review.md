技術的負債の横断レビューを実施します。対象: $ARGUMENTS

機能単位の開発では検出されない「どの機能にも属さない負債」（並行性・障害回復・構造侵食・整合性・ビルド再現性）を、複数レンズの並列レビューで洗い出します。

**実施契機**: リリースサイクル（`scripts/promote-to-main.sh`）の前、または大きな機能群（3 Phase 程度）の完了時。

## 1. 範囲の決定（メインで直接実行）

- `$ARGUMENTS` にコンポーネント名があればそのコンポーネントに限定、なければ全体
- `docs/plan/README.md` から進行中の作業を確認し、進行中ブランチと競合しない読み取り専用レビューであることを確認する

## 2. レンズ別レビューの並列起動

以下の4レンズを **1つのメッセージで並列に起動**する。全レンズ共通の指示:

- subagent_type: `code-reviewer`, model: `sonnet`
- `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『レビュー・検証』のルールを Read すること（`docs/design/invariants.md` を含む）
- 指摘は証拠スキーマ（場所 file:line / 問題 / 壊れ方のシナリオ / 修正案）に従うこと
- 出力: 総合判定（重大な構造問題 / 改善余地あり / 概ね健全）+ 重大度順の指摘リスト

| レンズ | 観点 |
|--------|------|
| A: 並行性・障害回復 | 並行アクセス時の競合（I6）、切断・再起動からの回復パス（I5）、ロック等の強制層（I2）、async 内のブロッキング I/O（I3）、タイムアウト後のリソース解放 |
| B: 構造侵食 | 肥大化したファイル（目安800行超）、同種実装のコピー数（I8）、単一関数への責務集中、デッドコード・deprecated 残置 |
| C: 整合性・非対称 | 同種の処理がコンポーネント間・ツール間で異なる実装になっていないか（エラーコード、バリデーション、ログ、境界検証 I4）、真実の情報源の分散（I1） |
| D: ビルド・環境再現性 | バージョン固定（I7: ベースイメージ・依存・ランタイム）、lock ファイルの整合、CI とローカルの乖離、非決定的なビルド手順 |

## 3. 統合と報告

全レンズの結果を統合し、以下の形式で報告する:

```
## 負債レビュー結果（対象: {範囲}）

| レンズ | 判定 | 重大 | 高 | 中 |
|--------|------|------|-----|-----|

### 重大・高の指摘（重大度順）
- {場所}: {問題}（壊れ方: {シナリオ}）

### 推奨対応
- 即時 Issue 化すべきもの（実害のあるバグ）
- タスク化すべきもの（Phase 提案。`.claude/rules/task-design.md` の横断的性質タスクとして）
- 不変条件（invariants.md）への追記候補
```

## 4. ユーザー確認と起票

報告後、ユーザーの指示に応じて:

- 実害バグ → `/custom-report-bug` フローで Issue 起票
- 構造的負債 → `docs/plan/` の該当カテゴリに Phase/タスクとして追加（`.claude/rules/task-design.md` 準拠。E2E テスト欄には異常系シナリオを書く）
- 新しい横断的性質 → `docs/design/invariants.md` に追記

**ユーザーの確認なしにファイル変更・Issue 起票を行わないこと。**
