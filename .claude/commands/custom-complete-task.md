現在進行中のタスクまたは Issue 修正を完了します。

以下の手順で作業してください：

## 0. ブランチ確認とフロー判定

現在 feature/fix ブランチ上にいることを確認してください。
dev ブランチ上にいる場合は、対象の feature/fix ブランチに切り替えてください（`.claude/rules/branch-workflow.md` の「ブランチ切り替え」参照）。

ブランチ名から以下のフローを判定してください：

| ブランチパターン | フロー |
|-----------------|--------|
| `feature/*` | **タスクフロー** |
| `fix/*` | **fix フロー** |

以降のステップで使用する**対象識別子**をフローに応じて記録してください（ステップ 4・6・8 で参照します）。

## 1. 対象の特定（メインで直接実行）

**サブエージェントは使わず、メインで直接読むこと。**

### タスクフローの場合

`docs/plan/README.md` を Read ツールで読み、対象カテゴリファイルを特定してから該当カテゴリファイルも Read し、ステータスが `[→]` のタスクを見つけてください。

以下を特定してください：

- **タスク番号**と**タスク内容**
- **対象コンポーネント**（jupyter-server / jupyter-mcp / jupyterlab-ai-sync / document-server / document-mcp）
- **タスク種別**（mcp / api / extension / infra / test / other）

**対象識別子**: `タスク {番号}: {タスク内容}`

`[→]` のタスクが存在しない場合は、ステップ2〜7をスキップして**ステップ8（次のタスクの提案）**に進んでください。

### fix フローの場合

ブランチ名 `fix/{Issue番号}-*` から Issue 番号を抽出し、`docs/issues/{Issue番号}-*.md` を Glob で検索して詳細ファイルを Read ツールで読んでください。

以下を特定してください：

- **Issue 番号**と**タイトル**
- **対象コンポーネント**
- **タスク種別**（api / mcp / ui / logic / other）

**対象識別子**: `Issue #{番号}: {タイトル} の修正`

## 2. 完了条件の確認（メインで直接実行）

### タスクフローの場合

`docs/tasks/**/{タスク番号}-*.md` を Glob で検索し、見つかった計画ファイルを Read ツールで読み、**完了条件**を確認してください。

### fix フローの場合

ステップ1で読んだイシュー詳細ファイルの「修正ファイル」「テスト計画」を完了条件として扱ってください。

## 3. テスト再実行（必須）

タスク完了前の最終確認として、フルゲートを実行してください。

`scripts/test.sh --quiet {対象コンポーネント名}`（lint + 型チェック + 全テスト）を実行してください。
ユニットテストにリビルドは不要（`.claude/rules/build-freshness.md` 参照）。タスクに統合テストや Docker 動作確認が含まれる場合のみ `--integration --rebuild` を使う。
lint 失敗時は `.claude/rules/lint.md` に従うこと。

## 4. 完了検証

以下の検証を **1 つのメッセージで並列に実行** してください。

まず `.claude/skills/parallel-investigation/SKILL.md` を読み、テンプレートを確認してください。

### 4a. 要件照合（条件に応じたサブエージェントを起動）

以下の起動判定表に従って Agent ツールでサブエージェントを起動してください。

#### 起動判定表

| Agent | 起動条件 | subagent_type | model |
|-------|----------|---------------|-------|
| A: 要件照合 | **常に起動** | `requirements-verifier` | `haiku` |
| B: API 仕様照合 | `api` または `mcp` タスクのみ | `requirements-verifier` | `haiku` |
| C: ドキュメント整合性 | `api` または `mcp` タスクのみ | `requirements-verifier` | `sonnet` |

全 Agent 共通の必読: `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『レビュー・検証』のルールを Read すること。
充足の根拠（実行したコマンドと結果、確認したファイルパス:行番号）を必ず添えること。「確認しました」だけの判定は不可。
できなかった確認は省略せず報告すること。

#### Agent A — 要件定義との照合

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `docs/requirements/{コンポーネント名}.md`
- subagent_type: `requirements-verifier`, model: `haiku`
- 目的: 「{対象識別子}」の実装が要件を満たしているか検証
- コンテキスト: 完了条件（ステップ2で読んだ内容をここに貼る）
- 調査対象の追加指示: 対象コンポーネントの src/ ディレクトリから実装ファイルも確認し、完了条件の各項目が実装されているか検証する
- 出力: 充足している要件一覧（根拠となるファイルパス:行番号付き）、未充足の要件一覧（あれば）、ブラウザ動作確認が必要か（はい/いいえ）

#### Agent B — API 仕様との照合

**テンプレート A**（単一ドキュメント読み取り）を使用:
- ファイル: `docs/design/api-contracts.md`
- subagent_type: `requirements-verifier`, model: `haiku`
- 目的: 「{対象識別子}」の実装が API 仕様に準拠しているか検証
- コンテキスト: 対象コンポーネント名
- 調査対象の追加指示: 対象コンポーネントの src/ から該当する実装を確認し、リクエスト/レスポンス形式が仕様と一致しているか検証する
- 出力: 準拠している仕様一覧（根拠となるファイルパス:行番号付き）、不一致の箇所一覧（あれば）

### 4b. ドキュメント整合性チェック（条件に応じたサブエージェントを起動）

要件照合と **同時に**、以下の起動判定に従って Agent ツールでサブエージェントを起動してください。

#### 起動判定

| Agent | 起動条件 | subagent_type | model |
|-------|----------|---------------|-------|
| C: ドキュメント整合性 | `api` または `mcp` タスクのみ | `requirements-verifier` | `sonnet` |

`infra` / `docs` / `test` タスクではスキップしてください。

#### Agent C — ドキュメント整合性チェック（コード → ドキュメント方向）

**テンプレート C**（ドキュメント整合性検証）を使用:
- subagent_type: `requirements-verifier`, model: `sonnet`
- 対象: `{対象識別子}`
- コンポーネント: `{コンポーネント名}`
- 追加の検証観点: `.claude/skills/doc-code-audit/SKILL.md` の「監査の3つのモード」（A. 欠落検出 / B. 陳腐化検出 / C. 冗長検出）に従うこと

### 検証結果の統合

要件照合結果・ドキュメント整合性チェック結果を統合して判断してください：

- **要件全充足 + ドキュメント整合**: ステップ 4c（メイン再検証）に進む
- **要件不充足**: 問題を修正してから再検証（最大 2 回。解消しなければユーザーに報告して停止）
- **ドキュメント不整合あり（欠落・陳腐化・冗長）**: 以下の「ドキュメント不整合検出時の自動修正」フローを実行してからステップ 4c に進む
- **ブラウザ動作確認が必要**: `.claude/rules/testing.md` に従い `@playwright/cli` で確認してからステップ 4c に進む

### 4c. メインでの機械的再検証（必須）

サブエージェントの「充足しました」報告を鵜呑みにせず、**メインで**以下を実行して主要な主張を裏取りする：

- ステップ3のテスト実行コマンドの結果（PASS）を確認する
- 計画ファイル（またはイシュー詳細ファイル）の完了条件チェックボックスを Read し、Agent A/B が「充足」と報告した項目について、根拠として示されたファイルパス:行番号を実際に Read して裏取りする
- 裏取りできない、または矛盾する場合 → 該当項目を未充足として扱い、修正してから再検証（最大 2 回。解消しなければユーザーに報告して停止）

すべて裏取りできた場合のみステップ 5 に進む。

#### ドキュメント不整合検出時の自動修正

不整合が見つかった場合、`.claude/commands/custom-auto-audit-docs.md` の手順に従い自動修正を実行する。

- 対象: {コンポーネント名}
- `.claude/rules/requirement-workflow.md` の「例外: コード追従によるドキュメント修正」に基づき、コードが正の方向での修正は直接行ってよい
- 修正完了後（全コンポーネントが "clean"）にステップ 5 に進む
- 3 ループ超過でエスカレーションになった場合はステップ 5 に進まず停止し、残存指摘を報告する

### ブラウザ動作確認（要件照合で必要と判定された場合のみ、ステップ 5 へ進む前に実施）

`.claude/rules/testing.md` のブラウザ確認手順に従うこと。

## 5. ステータス更新

### タスクフローの場合

該当タスクのステータスを `[→]` から `[x]` に更新してください（`docs/plan/` カテゴリファイル）。

### fix フローの場合

1. イシュー詳細ファイルのステータスを更新:

   ```markdown
   - [x] 修正完了
   ```

2. `tests/known-failures.json` に該当エントリがあれば削除する:

   ```bash
   scripts/manage-known-failures.sh list
   scripts/manage-known-failures.sh remove --id {kf-XXX}
   ```

### 5b. アーカイブへの退避（両フロー共通）

`docs/plan/README.md` の「アーカイブ規約」に従い、以下を実施してください（規約本文はここに転記しない）：

- Phase 内の全タスクが完了した場合、その Phase セクションを `docs/plan/archive/{同名ファイル}` へ移動する
- 該当タスクの詳細計画ファイルを `docs/tasks/{カテゴリ}/` から `docs/tasks/archive/{カテゴリ}/` へ移動する
- fix フローの場合、`docs/issues/` の該当ファイル（参照する添付画像を含む）を `docs/issues/archive/` へ移動する

## 6. コミット & 次のアクションの選択

### 6a. コミット

`.claude/skills/commit-and-push/SKILL.md` を読み、その手順に従って commit を行ってください。

パラメータ（フローに応じて設定）:

| パラメータ | タスクフロー | fix フロー |
|-----------|-------------|-----------|
| context | タスク {番号} {タスク名} 完了 | Issue #{番号} 修正完了（コミット本文に `Refs #{番号}` を含めること） |
| push | false | false |
| agent | none | none |

### 6b. ユーザーに次のアクションを確認

`AskUserQuestion` で以下の選択肢を提示してください：

1. **push & PR 作成する** — このタスクで PR を出す場合。push 後、`.claude/rules/branch-workflow.md` の「PR 作成」「PR 作成後の CI 待機と自動修正」に従う
2. **push のみ（PR は後で作成）** — リモートにバックアップしたいが PR はまだ出さない場合。`git push -u origin {ブランチ名}` のみ実行
3. **このブランチで開発を継続する** — push も PR もスキップし、そのまま次の作業に進む

## 7. 次のタスクの提案（タスクフローのみ）

**fix フローの場合はスキップしてステップ 8 に進んでください。**

同じフェーズ内で、次に着手すべきタスク（ステータスが `[ ]` のもの）を提案してください。
依存関係がある場合は考慮してください。

## 8. 完了報告

フローに応じて以下の形式で報告してください。

### タスクフローの場合

```
## タスク完了

- タスク: {番号} {タスク名}
- ブランチ: {ブランチ名}
- PR: {PR URL}（PR 作成した場合のみ）
- 次のタスク候補: {番号} {タスク名}
```

**次のタスクを案内する際は /custom-plan-task {番号} としてください。**

### fix フローの場合

```
## 修正完了

- Issue: #{番号}
- ブランチ: {ブランチ名}
- PR: {PR URL}（PR 作成した場合のみ）
- 設計ファイル: docs/issues/{番号}-{名前}.md
```
