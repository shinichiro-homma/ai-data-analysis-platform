タスク「$ARGUMENTS」を自律的に実装します。

このコマンドはオーケストレーターとして動作し、サブエージェントに計画・実装・レビューを委譲することで、
人間のレビューなしにタスクを順次完了していきます。

---

## 0. タスク範囲の解析

`$ARGUMENTS` からタスク番号のリストを作成してください。

**入力形式の例:**
- `29.1-29.5` → 29.1, 29.2, 29.3, 29.4, 29.5
- `29.1,29.3,29.5` → 29.1, 29.3, 29.5
- `29.1-29.3,29.7` → 29.1, 29.2, 29.3, 29.7

## 1. 事前準備（メインで直接実行）

以下を **並列に** 実行してください：

1. `git status` で未コミットの変更がないことを確認し、`.claude/rules/branch-workflow.md` の「ブランチ確認」に従って現在のブランチを確認する。新しいブランチを作成する場合は「ブランチ作成」に従い、ブランチ名は「ブランチ命名規則」の「複数タスク」に従う
2. `docs/plan/README.md` を Read ツールで読み、対象カテゴリファイルを特定してから該当カテゴリファイルも Read し、対象タスクの一覧と内容を把握する
3. 対象タスクの計画ファイルを Glob で検索: `docs/tasks/**/{タスク番号}*-*.md`（例: `docs/tasks/**/29.*-*.md`）

**中止条件:**
- 未コミットの変更がある → 先にコミットを案内して停止
- 対象タスクが `[x]`（完了済み）→ そのタスクをスキップ
- 対象タスクが見つからない → 停止

**開始報告:**

```
## 自律開発を開始します

- 対象タスク: {タスク一覧}
- 計画ファイル: {あり: N件 / なし: N件}
- タスク数: {N} 件
- モード: 計画作成 → テスト先行 → 実装 → レビュー → 修正ループ

各タスクはサブエージェントで実行し、タスク間でコンテキストをクリアします。
テスト失敗またはレビュー修正が上限を超えた場合は停止します。
```

---

## 2. タスクループ

対象タスクリストの各タスクについて、以下のステップ 2a〜2h を **順番に** 実行してください。

### タスク種別の判定

PLAN.md のタスク内容から種別を判定し、ワークフローを分岐してください：

- **style**（フォーマッター適用、lint 修正）: タスク内容に「prettier 適用」「ruff 適用」「フォーマット」「lint」を含む場合
- **feature/fix/refactor/test/other**: 上記以外

| 種別 | ワークフロー |
|------|-------------|
| style | 2a → 2b（計画作成のみ、レビューなし）→ 2d（実装）→ 2e（レビュー）→ 2f（コミット）→ 2h |
| その他 | 2a → 2b（計画作成 + レビュー）→ 2c → 2d → 2d-ref（リファクタリング）→ 2e → 2f → 2h（フルフロー） |

**style タスクでスキップされるステップ:**
- 2b-ii（計画レビュー）: フォーマッター適用の計画は単純なため不要
- 2c（テスト準備）: 新規テスト作成は不要。既存テストの通過は 2d の実装ステップで確認する
- 2d-ref（リファクタリング）: フォーマット変更のみのため不要

### ステップ間の原則

- `.claude/rules/tdd.md` の原則に従うこと。
- `.claude/rules/dry.md` と `.claude/rules/documentation.md` の原則に従うこと。ドキュメントを変更するサブエージェントには、`docs/STRUCTURE.md` の SSoT 表に従って正のファイルにのみ詳細を書くよう指示すること。
- 各ステップのサブエージェントには、必要な情報（タスク内容、対象ファイル、コンポーネント名）を明示的に渡すこと。

---

### 2a. PLAN.md ステータス更新

対象タスクのステータスを `[ ]` → `[→]` に更新してください（メインで直接実行）。

---

### 2b. 計画作成（計画ファイルがない場合のみ）

対象タスクの計画ファイル `docs/tasks/**/{タスク番号}-*.md` が **既に存在し、「計画レビュー完了」にチェックが入っている** 場合は、このステップをスキップしてください。

#### 2b-i. 計画作成（Agent: general-purpose, model: opus）

Agent ツールでサブエージェントを起動してください。

**設定:**
- subagent_type: `general-purpose`
- model: `opus`

**プロンプト:**

```
タスク「{タスク番号}: {タスク内容}」の開発計画を作成してください。
対象コンポーネント: {コンポーネント名}
タスク種別: {mcp / api / extension / infra / test / other}

## PLAN.md でのタスク記載内容
{PLAN.md から読み取ったタスクの行をここに貼る}

## 手順

`.claude/skills/task-plan-creation/SKILL.md` を読み、セクション2「調査手順」とセクション3「計画ファイルテンプレート」に従って、
調査と計画ファイルの作成を行ってください。

調査時は `.claude/skills/parallel-investigation/SKILL.md` のテンプレートも参照してください。

## 報告
以下の形式で報告してください：
- 計画ファイルパス: {作成したファイルのパス}
- 概要: {1-2行の要約}
- 作成するファイル数: {N}
- 完了条件数: {N}
```

#### 2b-ii. 計画レビュー（Agent: code-reviewer, model: opus）

Agent ツール（subagent_type: `code-reviewer`, model: `opus`）で計画をレビューしてください。

渡す情報:
- 計画ファイルパス
- タスク番号・内容・コンポーネント名

レビュー観点:
- **必須チェック（NG なら REJECT）:** 完了条件の明確さ、実装手順の妥当性、スコープの適切さ、要件との整合性
- **品質チェック（WARNING のみ）:** テスト計画、技術的考慮事項、ファイル構成

**結果を確認してください:**
- **APPROVE** → 計画ファイルのレビューステータスを更新（`- [x] 計画レビュー完了`）し、ステップ 2c に進む
- **REJECT** → ステップ 2b-iii（計画修正ループ）に進む

#### 2b-iii. 計画修正ループ（最大 5 回）

計画レビューが REJECT の場合、Agent ツール（subagent_type: `general-purpose`, model: `sonnet`）で修正を実行させてください。

渡す情報:
- 計画ファイルパス
- レビューの REJECT 理由と修正指示

修正後、再度ステップ 2b-ii（計画レビュー）を実行してください。

**5 回修正しても REJECT の場合 → ステップ 2g（エスカレーション）に進む。**
停止理由は「計画レビュー修正上限超過」としてください。

### 2c. テスト準備（Agent: general-purpose, model: opus）

Agent ツールでサブエージェントを起動してください。

**設定:**
- subagent_type: `general-purpose`
- model: `opus`

**プロンプト:**

```
タスク「{タスク番号}: {タスク内容}」のテスト準備を行ってください。
対象コンポーネント: {コンポーネント名}

## タスク計画
{計画ファイルの内容を貼る}

## 手順

`.claude/rules/tdd.md` を読み、「Red フェーズ」の手順に従ってテストを準備してください。
テスト実行コマンド: `scripts/test.sh --rebuild {コンポーネント名}`

## 報告
以下の形式で報告してください：
- テストファイル: {パスの一覧}
- テスト状態: {PASS / FAIL（Red フェーズ） / 既存テスト流用}
- 新規作成したテスト: {あれば一覧}
- テスト実行コマンド: {使用するコマンド}
```

**結果を確認し、テストファイルのパスとテスト実行コマンドを記録してください。**

### 2d. 実装（Agent: general-purpose, model: sonnet）

Agent ツールでサブエージェントを起動してください。

**設定:**
- subagent_type: `general-purpose`
- model: `sonnet`

**プロンプト:**

```
タスク「{タスク番号}: {タスク内容}」を実装してください。
対象コンポーネント: {コンポーネント名}

## タスク計画
{計画ファイルの内容を貼る}

- テスト実行コマンド: {ステップ 2c で記録したコマンド}

## 実装手順

`.claude/rules/tdd.md` を読み、「Green フェーズ」の手順に従って実装してください。
テストが通るまで最大 5 回繰り返すこと。

## 報告
以下の形式で報告してください：
- 変更ファイル: {パスの一覧}

- テスト修正の有無: {なし / あり（理由: ...）}

```

### 2d-ref. リファクタリング（Agent: code-reviewer × 2-3 並列 + general-purpose）

実装完了後、コード品質を改善するためのリファクタリングを行います。

#### 2d-ref-i. 並列レビュー

以下のレビューエージェントを **1つのメッセージで並列に** 起動してください。
変更ファイルにシェルスクリプト（`*.sh`）が含まれる場合のみ Agent C も追加してください。

| Agent | 観点 | subagent_type | model |
|-------|------|---------------|-------|
| A | コード品質（重複排除、命名、エラーハンドリング、責務分離） | `code-reviewer` | `sonnet` |
| B | セキュリティ・型安全性 | `code-reviewer` | `sonnet` |
| C | シェルスクリプト安全性（`*.sh` がある場合のみ） | `code-reviewer` | `sonnet` |

各 Agent には以下のコンテキストを渡してください：
- タスク番号・内容
- `git diff --name-only HEAD`（差分がなければ `HEAD~1`）で特定した変更ファイル一覧
- テストファイル・ドキュメント・設定ファイルは除外

各 Agent の出力: ファイルごとの「問題点」と「推奨する修正」一覧。問題ゼロなら「リファクタリング不要」。

#### 2d-ref-ii. リファクタリング判定

全レビューエージェントの結果を統合してください。

- **全エージェントが「リファクタリング不要」と報告** → ステップ 2e に進む（リファクタリングスキップ）
- **問題点あり** → ステップ 2d-ref-iii に進む

#### 2d-ref-iii. リファクタリング実施（Agent: general-purpose, model: sonnet）

Agent ツールでサブエージェントを起動し、レビュー指摘に基づくリファクタリングを実行させてください。

渡す情報:
- タスク番号・内容・コンポーネント名
- Agent A・B・C のレビュー結果（問題点を統合）
- テスト実行コマンド: `scripts/test.sh --rebuild {コンポーネント名}`

制約:
- `.claude/rules/tdd.md` の原則に従うこと
- 機能の追加・変更を行わない（リファクタリングのみ）
- テストが通るまで最大 3 回繰り返す

**結果を確認してください。テストが FAIL の場合はステップ 2g（エスカレーション）に進みます。**

---

### 2e. レビュー（Agent: code-reviewer, model: opus）

Agent ツール（subagent_type: `code-reviewer`, model: `opus`）でレビューを実行してください。

渡す情報:
- タスク番号・内容・コンポーネント名
- `git diff HEAD`（差分がなければ `HEAD~1`）で確認するよう指示

レビュー観点:
- **必須チェック（NG なら REJECT）:** 意味的変更の混入、テストコードの不正変更、セキュリティ脆弱性、未関連ファイルの変更
- **品質チェック（WARNING のみ）:** コードスタイル、不要なコード、型安全性（変更差分のスコープ内のみ）

出力形式: `APPROVE` または `REJECT`（REJECT の場合は修正指示を含む）

**結果を確認してください:**
- **APPROVE** → ステップ 2f（コミット）に進む
- **REJECT** → ステップ 2e-fix（修正ループ）に進む

---

### 2e-fix. レビュー修正ループ（最大 5 回）

レビューが REJECT の場合、Agent ツール（subagent_type: `general-purpose`, model: `sonnet`）で修正を実行させてください。

渡す情報:
- タスク番号・内容・コンポーネント名
- レビューの REJECT 理由と修正指示
- テスト実行コマンド: `scripts/test.sh --rebuild {コンポーネント名}`

制約: テストコードを変更しない、指摘箇所のみ修正

修正後、再度ステップ 2e（レビュー）を実行してください。

**5 回修正しても REJECT の場合 → ステップ 2g（エスカレーション）に進む。**

---

### 2g. エスカレーション（人間に委譲）

以下のいずれかの状況で、自律開発を **停止** してユーザーに報告してください：

- 計画レビュー修正が 5 回を超えても REJECT された
- テストが FAIL のまま実装サブエージェントが終了した
- コードレビュー修正ループが 5 回を超えて REJECT された
- テストコードにバグがある可能性がある（実装サブエージェントが報告した場合）

**報告形式:**

```
## 自律開発を停止しました

- 停止タスク: {タスク番号} {タスク内容}
- 停止理由: {計画レビュー修正上限超過 / テスト失敗 / コードレビュー修正上限超過 / テストコードのバグ疑い}
- 完了済みタスク: {完了したタスクの一覧}
- 詳細: {エラーメッセージやレビュー指摘の要約}

### 再開方法
問題を解決した後、以下で残りのタスクを再開できます：
`/custom-auto-dev {残りのタスク範囲}`
```

**この時点でコマンドを終了してください。停止時はステップ 3（PR 作成）に進んではなりません。また、停止タスクで未コミットの変更がある場合も `git push` や `gh pr create` を実行せず、ユーザーの判断を待つこと。**

タスクのステータスを `[→]` → `[x]` に更新してください。


## 3. PR 作成と CI 待機

すべてのタスクが完了したら、`.claude/rules/branch-workflow.md` の「PR 作成」および「PR 作成後の CI 待機と自動修正」セクションに従って、feature → dev の PR 作成から CI グリーン化までを実施してください。

## 4. 全タスク完了報告

以下の形式で報告してください：

```
## 自律開発完了

| タスク | 状態 | 修正回数 |
|--------|------|---------|
| {番号}: {内容} | 完了 | {N} 回 |
| ... | ... | ... |

- 総コミット数: {N}
- PR: {PR URL}
- 停止・スキップしたタスク: {あれば一覧}
```
