タスク「$ARGUMENTS」を自律的に実装します。

このコマンドはオーケストレーターとして動作し、サブエージェントに計画・実装・レビューを委譲することで、
人間のレビューなしにタスクを順次完了していきます。

メインはオーケストレーションと**検証**に徹します。サブエージェントの報告を鵜呑みにせず、
テスト結果・差分はメインで機械的に確認します（pytest/diff/Grep）。

---

## 0. タスク範囲の解析

`$ARGUMENTS` からタスク番号のリストを作成してください。

**入力形式の例:**
- `29.1-29.5` → 29.1, 29.2, 29.3, 29.4, 29.5
- `29.1,29.3,29.5` → 29.1, 29.3, 29.5
- `29.1-29.3,29.7` → 29.1, 29.2, 29.3, 29.7

## 1. 事前準備（メインで直接実行）

以下を **並列に** 実行してください：

1. `git status` で未コミットの変更がないことを確認し、`.claude/rules/branch-workflow.md` の「ブランチ確認」に従って現在のブランチを確認する。新しいブランチを作成する場合は「ブランチ作成」に従い、ブランチ名は「ブランチ命名規則」の「複数タスク」に従う
2. `docs/plan/README.md` を Read ツールで読み、対象カテゴリファイルを特定してから該当カテゴリファイルも Read し、対象タスクの一覧と内容を把握する
3. 対象タスクの計画ファイルを Glob で検索: `docs/tasks/**/{タスク番号}*-*.md`（例: `docs/tasks/**/29.*-*.md`）

**中止条件:**
- 未コミットの変更がある → 先にコミットを案内して停止
- 対象タスクが `[x]`（完了済み）→ そのタスクをスキップ
- 対象タスクが見つからない → 停止

**開始報告:**

```
## 自律開発を開始します

- 対象タスク: {タスク一覧}
- 計画ファイル: {あり: N件 / なし: N件}
- タスク数: {N} 件
- モード: 計画作成 → 計画レビュー → テスト先行（Red 確認）→ 実装 → リファクタ → レビュー → コミット

各タスクはサブエージェントで実行し、タスク間でコンテキストをクリアします。
テスト失敗またはレビュー修正が上限を超えた場合は停止します。
```

## 2. タスクループ

対象タスクリストの各タスクについて、以下のステップ 2a〜2h を **順番に** 実行してください。

### タスク種別の判定

PLAN.md のタスク内容から種別を判定し、ワークフローを分岐してください：

- **style**（フォーマッター適用、lint 修正）: タスク内容に「prettier 適用」「ruff 適用」「フォーマット」「lint」を含む場合
- **feature/fix/refactor/test/other**: 上記以外

| 種別 | ワークフロー |
|------|-------------|
| style | 2a → 2b-i（計画作成のみ、レビューなし）→ 2d（実装）→ 2e（レビュー）→ 2f（コミット）→ 2h |
| その他 | 2a → 2b → 2c → 2d → 2d-ref → 2e → 2f → 2h（フルフロー） |

### ステップ間の原則

- サブエージェント起動時は `subagent_type` と `model` を必ず併記する（`.claude/rules/general.md` の「サブエージェントのモデル選択」）
- 全サブエージェントのプロンプトに「`.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『{役割名}』のルールを Read すること」を含める（役割名は各ステップのプロンプトに記載。全ルールを読ませない）
- テスト準備・実装・修正系サブエージェントには**探索禁止**を指示する: タスク計画の「調査したファイル」「参照ファイル」「作成・変更するファイル」「テスト参照ポインタ」の範囲でのみ作業し、範囲外の Glob/Grep 探索を行わない。情報不足時は探索せず不足内容を報告して終了する
- `.claude/rules/tdd.md`、`.claude/rules/dry.md`、`.claude/rules/documentation.md` の原則に従う。ドキュメントを変更するサブエージェントには `docs/STRUCTURE.md` の SSoT 表に従うよう指示する
- 各ステップのサブエージェントには、必要な情報（タスク内容、対象ファイル、コンポーネント名）を明示的に渡す

#### 2b-ii. 計画レビューループ（review-loop/SKILL.md に従う）

`.claude/skills/review-loop/SKILL.md` のループに従い、計画をレビューしてください。

**パラメータ:**
- 対象: 計画ファイル（あわせてタスク番号・タスク内容・PLAN.md の記載内容を渡す）
- レビューエージェント: subagent_type `general-purpose`、model `opus`
- レビュー観点:
  - **必須チェック（NG なら REJECT）:**
    1. 実在性 — 計画が参照するファイル・関数が実際に存在するか（「調査したファイル」を自分でも Read して照合）
    2. 検証可能性 — 実装手順と完了条件が実行コマンドと期待結果の形で書かれているか
    3. 要件整合 — `docs/requirements/{コンポーネント}.md` と齟齬がないか
    4. スコープ — `.claude/skills/task-plan-creation/SKILL.md` の「スコープ上限」表を超えていないか（超過は REJECT し、タスク分割案の提示を求める）
    5. コンテキストパック完結性 — 「作成・変更するファイル」「参照ファイル」「テスト計画（既存テストの被覆状況・テスト参照ポインタ）」だけで実装・テスト準備エージェントが探索なしに作業できるか（テスト参照ポインタの `パス:行範囲` の実在も照合）
  - **品質チェック（WARNING のみ）:** 代替案比較の妥当性、テスト計画、ファイル構成
- 修正: subagent_type `general-purpose`、model `sonnet`、最大 5 回

**APPROVE** → 計画ファイルの `- [x] 計画レビュー完了` を更新し、ステップ 2c へ。
**5 回で APPROVE に至らない** → ステップ 2g（エスカレーション。停止理由「計画レビュー修正上限超過」）。

```

{計画ファイルの内容を貼る}

- テスト状態: {PASS / FAIL（Red フェーズ） / 既存テスト流用}
- 新規作成したテスト: {あれば一覧。それぞれが計画のどの完了条件に対応するか}
- テスト実行コマンド: {使用するコマンド}
```

#### 2c-ii. Red フェーズの確認（メインで実行）

新規テストが作成された場合、報告を鵜呑みにせず**メインで**テスト実行コマンドを実行し、
**新規テストが失敗（Red）であること**を確認してください。

- 新規テストが最初から通ってしまう場合、テストが実装を検証できていない可能性がある → テスト準備サブエージェントに差し戻す（最大 2 回。解消しなければ 2g へ）
- 既存テスト流用の場合はこの確認をスキップする

### 2d. 実装（Agent: general-purpose, model: opus）

**プロンプト:**

```
タスク「{タスク番号}: {タスク内容}」を実装してください。
対象コンポーネント: {コンポーネント名}

## 必読
- `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『実装（Green）・バグ修正』のルールを Read すること

## タスク計画

## テスト情報

- テスト実行コマンド: {ステップ 2c で記録したコマンド（スコープ実行・`--quiet` 付き）}

## 実装手順
`.claude/rules/tdd.md` の「Green フェーズ」の手順と「テスト実行コマンドの規律」「テストコードの読み方の規律」に従って実装してください。
lint 失敗時は `.claude/rules/lint.md` に従うこと。
テスト実行コマンドは**1 回だけ**実行し、PASS / FAIL に関わらず結果を報告して終了すること
（修正の反復はオーケストレーター側の修正ループが担う。失敗ログを抱えて粘らない）。

タスク計画の「調査したファイル」「参照ファイル」「作成・変更するファイル」「テスト参照ポインタ」の範囲でのみ作業すること。
範囲外の Glob/Grep 探索は禁止。情報が不足していたら探索せず、不足内容を報告して終了すること。

## 報告
- 変更ファイル: {パスの一覧}
- テスト結果: {PASS / FAIL と実行コマンド・出力の要約}
- テスト修正の有無: {なし / あり（理由: ...）}
- 失敗した場合: 仮説・修正内容・失敗テスト一覧（修正ループの「試行済み仮説」への引き継ぎ情報）
```

#### 2d-ii. Green フェーズの確認と修正ループ（メインで実行）

実装エージェントが FAIL を報告した場合は、`.claude/skills/test-fix-loop/SKILL.md` のループに従って修正してください。

**パラメータ:**
- タスクコンテキスト: タスク番号・タスク内容、対象コンポーネント
- 完了条件: 計画ファイルの「完了条件」（計画全文は渡さない）
- スコープ情報: `git diff --name-only` の変更ファイル、テストファイル、計画の「参照ファイル」「テスト参照ポインタ」
- テスト実行コマンド: ステップ 2c のスコープ実行コマンド
- 最大修正回数: 4
- エスカレーション先: ステップ 2g（停止理由「修正ループ上限超過」）

スコープテストが PASS になったら、**メインで**フルゲート `scripts/test.sh --quiet {コンポーネント名}`（lint + 型チェック + 全テスト）を実行し、全テスト PASS を確認してください。フルゲートで新たに FAIL したテストも同じ修正ループで扱う（修正回数は通算）。
あわせて `git diff --name-only` で変更ファイルが計画の範囲内か照合してください。

- テストが PASS だが「テスト修正あり」の報告に正当な理由がない場合 → ステップ 2g（エスカレーション）
- 計画範囲外の変更がある場合 → 実装サブエージェントに理由を確認し、不要な変更は差し戻す

### 2d-ref. リファクタリング（並列レビュー + 修正）

#### 2d-ref-i. 並列レビュー（3 観点）

以下のレビューエージェントを **1つのメッセージで並列に** 起動してください。

| Agent | 観点 | subagent_type | model |
|-------|------|---------------|-------|
| A | コード品質（重複排除、命名、エラーハンドリング、責務分離） | `code-reviewer` | `sonnet` |
| B | 正確性・堅牢性（バグ、境界値、セキュリティ、型安全性、テストの網羅性） | `code-reviewer` | `sonnet` |
| C | ファイル間整合性（呼び出し元との齟齬、import、副作用。`*.sh` があればシェル安全性も） | `code-reviewer` | `sonnet` |

**全 Agent 共通の指示:**
- 変更ファイル一覧（`git diff --name-only HEAD`、差分がなければ `HEAD~1`。ドキュメント・設定ファイルは除外）と「各ファイルを Read して確認すること」
- Agent B にはテストファイルも Read させ、「この入力で壊れないか」を具体的な値（空リスト、None、型不一致）で検証させる
- Agent C にはメインで `grep -rn` した呼び出し元ファイルのリストを渡す
- 指摘は `.claude/rules/subagent-defaults.md` の証拠スキーマに従うこと。問題ゼロなら「指摘なし」と判断根拠を報告

#### 2d-ref-ii. 統合と検証（メインで実行）

1. **重複統合**: 複数 Agent の同一箇所指摘は 1 件にまとめる
2. **指摘の検証**: バグ・整合性指摘は該当箇所を Read して失敗シナリオが実際に成立するか確認する。**成立が確認できない指摘は採用しない**
3. 全 Agent「指摘なし」→ ステップ 2e へ（リファクタリングスキップ）

#### 2d-ref-iii. 修正の実施

採用した指摘をバグ修正とリファクタリングに分類し、委譲する：

- **バグ修正**（テスト追加を含む）: subagent_type `general-purpose`、model `opus`。バグを再現するテストを追加してから修正させる（TDD）
- **純リファクタリング**: subagent_type `general-purpose`、model `sonnet`。機能追加・仕様変更を混ぜない。公開 API を変更する場合は呼び出し元も追従させる

いずれも渡す情報: 採用した指摘（証拠スキーマ形式）、対象ファイル、テスト実行コマンド `scripts/test.sh --quiet {コンポーネント名}`、subagent-defaults の必読指示（役割: バグ修正は『実装（Green）・バグ修正』、純リファクタは『リファクタ・レビュー指摘の修正』）。

修正後、**メインで**テスト実行コマンドを再実行して PASS を確認する（FAIL なら差し戻し最大 3 回 → 超過で 2g）。

### 2e. 最終レビューループ（review-loop/SKILL.md に従う）

`.claude/skills/review-loop/SKILL.md` のループに従い、実装をレビューしてください。

**パラメータ:**
- 対象: タスク番号・タスク内容と、`git diff HEAD`（差分がなければ `HEAD~1`）で確認するよう指示
- レビューエージェント: subagent_type `code-reviewer`、model `opus`
- レビュー観点:
  - **必須チェック（NG なら REJECT）:** 計画の完了条件を満たしているか、意味的変更の混入、テストコードの不正変更、セキュリティ脆弱性、未関連ファイルの変更
  - **品質チェック（WARNING のみ）:** コードスタイル、不要なコード、型安全性（変更差分のスコープ内のみ）
- 修正: subagent_type `general-purpose`、model `sonnet`、最大 5 回（制約: テストコードを変更しない、指摘箇所のみ修正、テスト実行コマンドで PASS 確認）

**APPROVE** → ステップ 2f へ。**5 回で APPROVE に至らない** → ステップ 2g へ。

### 2g. エスカレーション（人間に委譲）

以下のいずれかの状況で、自律開発を **停止** してユーザーに報告してください：

- 計画レビュー修正が 5 回を超えても REJECT された
- Red フェーズ確認の差し戻しが 2 回を超えた
- 修正ループ（`test-fix-loop`）が最大修正回数を超えてもテストが FAIL（2d-ii）
- リファクタ修正の差し戻しが 3 回を超えた
- コードレビュー修正ループが 5 回を超えて REJECT された
- テストコードにバグがある可能性がある（実装サブエージェントが報告した場合）

**報告形式:**

```
## 自律開発を停止しました

- 停止タスク: {タスク番号} {タスク内容}
- 停止理由: {上記のいずれか}
- 完了済みタスク: {完了したタスクの一覧}
- 詳細: {エラーメッセージやレビュー指摘の要約}

### 再開方法
問題を解決した後、以下で残りのタスクを再開できます：
`/custom-auto-dev {残りのタスク範囲}`
```

**この時点でコマンドを終了してください。停止時はステップ 3（PR 作成）に進んではなりません。また、停止タスクで未コミットの変更がある場合も `git push` や `gh pr create` を実行せず、ユーザーの判断を待つこと。**
