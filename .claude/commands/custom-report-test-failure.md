失敗したテストの GitHub Issue を起票し、既知障害として登録します。対象: $ARGUMENTS

**重要: コンテキスト節約のため、テスト実行・Issue 起票・再確認はすべてサブエージェントに委譲すること。メインコンテキストではユーザー対話と最終処理のみ行う。**

以下の手順で作業してください：

## 1. 対象コンポーネントの特定

引数 `$ARGUMENTS` からコンポーネント名を特定してください。

**引数の例:**
- `jupyter-mcp` → コンポーネント: jupyter-mcp
- `document-server` → コンポーネント: document-server
- 引数なし → 全コンポーネント

引数が空の場合は `AskUserQuestion` で対象コンポーネントを確認してください：

**質問:** "どのコンポーネントのテスト失敗を Issue 化しますか？"
**選択肢:**
1. **jupyter-mcp**
2. **document-server**
3. **document-mcp**
4. **全コンポーネント**

## 2. テスト実行＋解析（サブエージェントに委譲）

`Agent` ツール（`subagent_type: "general-purpose"`）を使い、テスト実行と結果解析をサブエージェントに委譲する。

**サブエージェントへの指示:**

```
以下の手順でテストを実行し、結果を解析してください。

### 手順1: テストを1回だけ実行し、出力をファイルに保存

scripts/test.sh --integration --rebuild --health --no-lint {コンポーネント名} 2>&1 | tee /tmp/test-output.log

（全コンポーネントの場合は引数なし: scripts/test.sh --integration --rebuild --health --no-lint 2>&1 | tee /tmp/test-output.log）

**重要: テストは1回しか実行しないこと。解析に必要な情報はすべて /tmp/test-output.log から Read ツールや Grep ツールで取得すること。**

### 手順2: 保存したログファイルから結果を解析

/tmp/test-output.log を Read ツールで読み込み、以下の情報を抽出してください。
テストを再実行してはいけません。

**以下のフォーマットのみ** を返してください（テストの生出力は返さない）：

## テスト結果サマリ

- コンポーネント: {名前}
- 総テスト数: {数}
- 成功: {数}
- 失敗: {数}
- 既知障害（登録済み）: {数}件

### 新規の失敗一覧

（新規失敗がない場合は「なし」と記載）

| # | テスト名 | ファイルパス | エラー要約 |
|---|---------|-------------|-----------|
| 1 | {describe > it のパス} | {ファイル} | {1行要約} |
| 2 | ... | ... | ... |
```

**注意:** サブエージェントの結果がテーブル形式で返ってくる。メインコンテキストにはこのサマリだけが入る。

### 新規の失敗がない場合

以下を報告して**終了**してください：

```
## テスト結果

- コンポーネント: {名前}
- 結果: 新規の失敗なし
- 既知障害: {件数}件（既に登録済み）

新たに Issue 化する失敗はありません。
```

### 新規の失敗がある場合

ステップ3に進んでください。

## 3. Issue 起票対象の確認

サブエージェントから受け取った新規失敗一覧をユーザーに提示し、`AskUserQuestion` で確認してください：

**質問:** "以下の失敗テストを Issue 化します。よろしいですか？"
**選択肢:**
1. **すべて Issue 化する**（推奨） - 全失敗を一括で Issue 化＆既知障害登録する
2. **個別に選択する** - 各失敗について1件ずつ確認する

一覧にはサブエージェントから受け取ったテーブルをそのまま含めてください。

### 「個別に選択する」が選択された場合

各失敗について `AskUserQuestion` で以下を確認してください：

**質問:** "「{テスト名}」を Issue 化しますか？"
**選択肢:**
1. **Issue 化する** - Issue を起票＆既知障害登録
2. **既知障害のみ登録** - Issue なしで既知障害として登録
3. **スキップ** - 何もしない

## 4. Issue 一括起票（サブエージェントに委譲）

確認された失敗テストのリストをサブエージェントに渡し、一括起票を委譲する。

`Agent` ツール（`subagent_type: "general-purpose"`）を使い、以下を指示：

```
以下のテスト失敗について、それぞれ Issue を起票してください。

### Issue 化する対象

| # | コンポーネント | テスト名 | ファイルパス | エラー要約 |
|---|--------------|---------|-------------|-----------|
| 1 | {comp} | {name} | {file} | {reason} |
| 2 | ... | ... | ... | ... |

### 各テストに対して実行するコマンド

scripts/create-test-issue.sh \
  --component {コンポーネント名} \
  --test-name "{テスト名}" \
  --file "{テストファイルパス}" \
  --reason "{エラー要約}" \
  --add-known

### 既知障害のみ登録する対象

（該当がある場合のみ）

| # | コンポーネント | テスト名 | ファイルパス | エラー要約 |
|---|--------------|---------|-------------|-----------|
| 1 | {comp} | {name} | {file} | {reason} |

各テストに対して実行するコマンド:

scripts/manage-known-failures.sh add \
  --component {コンポーネント名} \
  --test-name "{テスト名}" \
  --reason "{エラー要約}"

### 出力フォーマット

すべて完了したら、**以下のフォーマットのみ** を返してください：

## Issue 起票結果

| # | Issue番号 | テスト名 | URL |
|---|----------|---------|-----|
| 1 | #XX | {name} | {url} |
| 2 | #XX | {name} | {url} |

- 既知障害のみ登録: {件数}件
```

## 5. 再確認（サブエージェントに委譲）

`Agent` ツール（`subagent_type: "general-purpose"`）で再確認を委譲：

```
以下のコマンドを実行し、結果を報告してください（テスト再実行ではなく --health チェックのみ）：

scripts/test.sh --health {コンポーネント名}

**以下のフォーマットのみ** 返してください：

- exit code: {0 or 1}
- 未分類の失敗: {件数}
- 既知障害: {件数}

未分類の失敗がある場合は、そのテスト名のリストも含めてください。
```

すべての失敗が既知障害として分類され、exit 0 で正常終了することを確認する。

## 6. コミット

`tests/known-failures.json` の変更をコミットしてください（メッセージ: `test: テスト失敗の Issue 起票と既知障害登録`）：

```bash
git add tests/known-failures.json
# メッセージを Write で tmp/commit-msg.txt に書き出してから:
git commit -F tmp/commit-msg.txt
rm tmp/commit-msg.txt
```

## 7. 完了報告

サブエージェントから受け取った Issue 起票結果を使い、以下の形式で報告してください：

```
## テスト失敗 Issue 起票完了

- コンポーネント: {名前}
- 起票した Issue:
  - #{番号}: {テスト名}
  - #{番号}: {テスト名}
  ...
- 既知障害のみ登録: {件数}件
- スキップ: {件数}件

修正を進めるには、各 Issue に対して以下を順に実行してください：
1. `/custom-fix-bug {Issue番号}` で修正設計
2. コンテキストをクリア
3. `/custom-start-fix {Issue番号}` で修正実装
```
