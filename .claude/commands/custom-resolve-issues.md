Open Issue を根本原因別にグルーピングし、一括で修正・テスト・クローズします。対象: $ARGUMENTS

以下の手順で作業してください：

## Phase 1: 分析（読み取り専用）

### 1.1 Open Issue の取得

```bash
gh issue list --state open --limit 100 --json number,title,labels,body
```

引数 `$ARGUMENTS` が指定されている場合はフィルタしてください：

- コンポーネント名（例: `jupyter-mcp`）→ タイトルに含まれる Issue のみ
- `--label LABEL`（例: `--label test-failure`）→ `gh issue list --label LABEL`

### Open Issue がない場合

以下を報告して**終了**してください：

```
## 結果

Open Issue はありません。対応不要です。
```

### 1.2 既知障害との照合

```bash
scripts/manage-known-failures.sh list
```

`tests/known-failures.json` を読み、各 Issue と既知障害エントリの対応を確認してください（`issue_number` フィールドで照合）。

### 1.3 根本原因別グルーピング

各 Issue の内容（タイトル、本文、既知障害の `reason`）を分析し、根本原因が共通する Issue をグループ化してください。

**グルーピング基準:**

- 同じエラーメッセージ / 同じ失敗パターン
- 同じコード箇所（関数、モジュール）が原因
- 同じ設定・環境の問題

各グループに以下を設定してください：

- **グループ名**: 根本原因を簡潔に表す名前
- **分類**: `fixable`（修正可能）/ `config`（設定・環境の問題）/ `investigation`（原因不明、要調査）
- **含まれる Issue**: Issue 番号のリスト
- **既知障害 ID**: 対応する known-failures エントリの ID リスト

### 1.4 修正スコープの見積もり

`fixable` または `config` に分類されたグループについて、haiku サブエージェントを**並列に**起動し、修正スコープを見積もってください。

各グループに対して以下のサブエージェントを起動：

**subagent_type:** `codebase-explorer`
**model:** `haiku`

```
以下のテスト失敗グループの修正スコープを見積もってください。

## 必読
- `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『調査』のルールを Read すること

グループ名: {グループ名}
根本原因: {原因の説明}
関連 Issue: {Issue 番号リスト}
対象コンポーネント: {コンポーネント名}

調査対象:
1. {コンポーネント名}/src/ 内で原因に関連するコードを特定
2. {コンポーネント名}/__tests__/ 内で失敗しているテストを確認
3. 修正に必要な変更箇所（ファイルパスと概要）をリストアップ

**調査は {コンポーネント名}/ ディレクトリ内のみに限定してください。**

出力形式:
- 修正が必要なファイル一覧（パスと変更概要）
- 修正の難易度: easy / medium / hard
- 推奨する修正順序（他グループとの依存がある場合）
```

## Phase 2: 承認

### 2.1 グループ一覧の提示

分析結果を以下の形式で報告してください：

```
## Issue 分析結果

### グループ一覧

| # | グループ名 | 分類 | Issue | 既知障害 | 難易度 | 修正ファイル数 |
|---|-----------|------|-------|----------|--------|--------------|
| 1 | {名前} | fixable | #X, #Y | kf-001, kf-002 | easy | 2 |
| 2 | {名前} | config | #Z | kf-003 | medium | 1 |
| 3 | {名前} | investigation | #W | - | - | - |

### 各グループの詳細

#### グループ 1: {名前}
- 根本原因: {説明}
- 修正方針: {概要}
- 修正ファイル: {ファイル一覧}

（以下同様）
```

### 2.2 修正対象の選択

`AskUserQuestion` ツールを使って修正対象を確認してください：

**質問:** "どのグループを修正しますか？"
**選択肢:**
1. **すべて修正する**（推奨）— fixable + config グループをすべて修正
2. **fixable のみ** — fixable グループのみ修正
3. **個別に選択する** — グループごとに修正するか確認

`investigation` グループは修正対象外です。`/custom-fix-bug` での個別対応を案内してください。

### 「個別に選択する」が選択された場合

各グループについて `AskUserQuestion` で確認してください：

**質問:** "グループ「{名前}」（{Issue一覧}）を修正しますか？"
**選択肢:**
1. **修正する**
2. **スキップ**

## Phase 3: 実行（グループ順次処理）

選択されたグループを**順番に**処理してください。グループ内の処理順序は、Phase 1.4 で見積もった推奨順序に従ってください。

### 各グループの処理手順

#### 3.1 修正の実装（Agent: general-purpose, model: opus）

Agent ツールでサブエージェントを起動し、Phase 1.4 の見積もりに基づいて修正を実装させてください（メインでは実装しない）。

**設定:**
- subagent_type: `general-purpose`
- model: `opus`

**プロンプト:**

```
グループ「{グループ名}」のテスト失敗を修正してください。
対象コンポーネント: {コンポーネント名}

## 必読
- `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『実装（Green）・バグ修正』のルールを Read すること

## 修正スコープ（Phase 1.4 の見積もり）
{修正が必要なファイル一覧と変更概要}

## 関連 Issue
{Issue 番号と根本原因の要約}

## 実装時の注意
- 修正はグループ内の全 Issue を解決するように行う
- テストコードの修正が必要な場合、テストの意図を変えない
- 要件定義・API仕様の変更が必要な場合は、変更せずその旨を報告して停止する（メインが `/custom-change-requirement` での別途対応を案内し、グループをスキップする）
- テスト実行コマンド: scripts/test.sh --quiet --health {対象コンポーネント名}

## 報告
- 変更ファイル: {パスの一覧}
- テスト結果: {PASS / FAIL と実行コマンド・出力の要約}
- 対応できなかった Issue: {あれば理由}
```

#### 3.2 テスト実行（メインで実行）

サブエージェントの報告を鵜呑みにせず、**メインで**テストを再実行して PASS を確認してください。
lint 失敗時は `.claude/rules/lint.md` に従うこと。

```bash
scripts/test.sh --health {対象コンポーネント名}
```

#### テスト成功の場合

3.3 に進んでください。

#### テスト失敗の場合（最大3回再試行）

1. エラー内容を確認し、修正を調整する
2. 再度テストを実行する
3. 3回失敗した場合は、変更を元に戻して次のグループに進む：
   ```bash
   git checkout -- .
   ```
   このグループは `failed` としてマークし、Phase 4 の報告に含める。

#### 3.3 Issue クローズと既知障害削除

グループ内の各 Issue に対して：

1. **GitHub Issue をクローズ:**
   ```bash
   gh issue close {Issue番号} --comment "修正完了。根本原因: {グループの根本原因}"
   ```

2. **既知障害エントリを削除**（対応するエントリがある場合のみ）：
   ```bash
   scripts/manage-known-failures.sh remove --id {kf-XXX}
   ```

3. **イシューファイルをアーカイブへ退避**：`docs/plan/README.md` の「アーカイブ規約」に従い、`docs/issues/` に該当ファイル（参照する添付画像を含む）があれば `docs/issues/archive/` へ移動する（規約本文は転記しない）。

#### 3.4 コミット

グループごとにコミットしてください：

```
fix: {グループ名}を修正

{修正内容の要約}

Closes #{Issue番号1}, #{Issue番号2}, ...
```

## Phase 4: 報告

### 4.1 最終テスト

全コンポーネントの最終テストを実行してください。lint 失敗時は `.claude/rules/lint.md` に従うこと。

```bash
scripts/test.sh --health
```

### 4.2 統計レポート

以下の形式で報告してください：

```
## Issue 一括解決レポート

### 統計
- 対象 Issue: {総数}件
- 解決: {件数}件
- スキップ（investigation）: {件数}件
- 失敗（修正不可）: {件数}件

### 解決したグループ
| グループ名 | 解決した Issue | 削除した既知障害 | コミット |
|-----------|---------------|----------------|---------|
| {名前} | #X, #Y | kf-001, kf-002 | {hash} |

### 未解決の Issue
| Issue | 理由 | 推奨アクション |
|-------|------|--------------|
| #{番号} | investigation: 原因不明 | `/custom-fix-bug {番号}` で個別対応 |
| #{番号} | 修正失敗（3回再試行後） | `/custom-fix-bug {番号}` で個別対応 |

{scripts/test.sh --health の結果サマリ}
```
