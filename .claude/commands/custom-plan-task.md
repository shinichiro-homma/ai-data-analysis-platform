タスク「$ARGUMENTS」の開発計画を作成します。

メインはオーケストレーションに徹し、調査はサブエージェントに委譲します。
サブエージェント起動時は `.claude/rules/general.md` の「サブエージェントのモデル選択」に従い `model` を必ず明示してください。

## 0. ブランチの確認・作成

`.claude/rules/branch-workflow.md` の「ブランチ確認」に従い、現在のブランチを確認してください。

新しいブランチを作成する場合は「ブランチ作成」に従い、ブランチ名は「ブランチ命名規則」の「単一タスク」に従ってください。
既に対象タスクの feature ブランチが存在する場合は、「ブランチ切り替え」に従って切り替えてください。

## 1. タスクの特定（メインで直接実行）

`.claude/skills/task-plan-creation/SKILL.md` のセクション1「タスクの特定」に従い、
`docs/plan/README.md` を Read ツールで読み、対象カテゴリファイルを特定してから該当カテゴリファイルも Read し、タスク $ARGUMENTS を見つけてください。
**サブエージェントは使わず、メインで直接読むこと。**

## 2. 並列調査（必要なサブエージェントのみ起動）

`.claude/skills/task-plan-creation/SKILL.md` のセクション2「調査手順」に従い、
`.claude/skills/parallel-investigation/SKILL.md` のテンプレートを確認した上で、
必要なサブエージェントを並列に起動してください。

## 3. タスク詳細ファイルの作成

`.claude/skills/task-plan-creation/SKILL.md` の「計画作成の原則」（2 案以上の代替案比較・調査したファイルの列挙・検証可能な完了条件）とセクション3「計画ファイルテンプレート」に従い、計画ファイルを作成してください。

## 4. 敵対的レビュー（fresh-context サブエージェント）

計画作成に関与していない**別の**サブエージェントに計画のレビューを委譲してください：

- **subagent_type**: `general-purpose`
- **model**: `opus`

サブエージェントへの指示:

```
以下のタスク計画をレビューしてください。あなたは計画の作成者ではありません。批判的に検証してください。

## 対象
- `docs/tasks/{category}/{タスク番号}-*.md`

## 必読
- `.claude/rules/subagent-defaults.md` を Read し、指摘は証拠スキーマに従うこと

## レビュー観点
1. **実在性**: 計画が参照するファイル・関数・モジュールが実際に存在するか（「調査したファイル」を自分でも Read して照合する）
2. **検証可能性**: 実装手順と完了条件の検証手段が、実行コマンドと期待結果の形で書かれているか。曖昧な記述（「動作を確認」等）が残っていないか。「新規テスト（テストケース仕様）」の表が Given / When / Then と対応完了条件まで具体化され、完了条件を漏れなくカバーしているか
3. **要件整合**: `docs/requirements/{コンポーネント}.md` の関連要件と齟齬がないか
4. **影響範囲の漏れ**: 変更対象の呼び出し元で、計画に含まれていないファイルがないか（Grep で確認する）
5. **代替案比較**: 採用理由が妥当か。明らかに優れた第三案を見落としていないか

## 出力
- 判定: APPROVE / REJECT
- REJECT の場合: 証拠スキーマ形式の指摘一覧（観点番号つき）と修正指示
```

**REJECT の場合**: 指摘をメインで検証し（実在しない問題は棄却）、計画ファイルを修正して再レビューする（最大 3 回）。3 回で APPROVE に至らない場合は、指摘内容を要約してユーザーにエスカレーションする。

## 5. レビュー依頼

`.claude/skills/task-plan-creation/SKILL.md` のセクション4「計画作成の報告形式」で報告してください。
報告には**採用案と代替案の比較**・完了条件・リスクを含めてください。

## 6. 承認確認

報告後、**必ず `AskUserQuestion` ツールを使って**以下の選択式で確認を取ってください：

**質問:** "この開発計画を承認しますか？"
**選択肢:**
1. **OK** - この計画で進める（`/custom-start-task $ARGUMENTS` で実装開始可能）
2. **Modify** - 修正が必要（修正内容を入力）

### OK が選択された場合

タスク詳細ファイルのレビューステータスを更新してください：

`- [ ] 計画レビュー完了` を `- [x] 計画レビュー完了` に変更します。

### Modify が選択された場合

1. ユーザーが入力した修正内容を確認する
2. タスク詳細ファイルに修正を反映する
3. 修正後の計画を再度報告し、再び承認確認を行う

**注意:** 計画の承認（OK）を得るまで、実装は開始しないでください。
