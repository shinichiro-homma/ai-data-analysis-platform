バグ「$ARGUMENTS」を報告し、Issue を起票します。

以下の手順で作業してください：

## 1. バグの分類

報告内容「$ARGUMENTS」をもとに、以下の基準でバグを分類してください。

`.claude/rules/bug-fix-workflow.md` の分類基準（軽微 / 重要）に従って分類してください。

## 2. 分類結果の確認

**必ず `AskUserQuestion` ツールを使って**以下の選択式で確認を取ってください：

**質問:** "このバグの分類は「{軽微 or 重要}」で合っていますか？"
**選択肢:**
1. **軽微** - そのまま修正し `fix:` コミットする（Issue管理不要）
2. **重要** - Issue を起票して管理する

### 「軽微」が選択された場合

以下を報告して**終了**してください：

```
## バグ報告（軽微）

- 内容: $ARGUMENTS
- 分類: 軽微

軽微なバグのため、Issue管理は不要です。
そのまま修正し `fix: ...` でコミットしてください。
```

**注意:** 軽微の場合、ステップ3以降は実行しない。

### 「重要」が選択された場合

ステップ3に進んでください。

## 3. 関連コードの簡易調査

バグの報告内容をもとに、関連するソースコードを簡単に確認してください。

確認すること：
- バグが発生していると思われるファイル・モジュール
- 関連するタスク番号（`docs/plan/` のカテゴリファイルから特定）

**注意:** この段階では原因の深掘りは行わない。報告に必要な最低限の情報のみ確認する。

## 4. バグの再現確認

報告内容をもとに、実際にバグを再現して確認してください。

### 再現方法の選択

バグの種類に応じて、適切な方法で再現確認を行ってください：

#### ブラウザ操作が必要な場合（UI バグ、表示崩れ、画面遷移の問題等）

`.claude/rules/testing.md` の「ブラウザ動作確認」および [`docs/guides/browser-automation.md`](../../docs/guides/browser-automation.md) に従い、`@playwright/cli` でバグを再現してください。

エビデンス用スクリーンショットは `playwright-cli screenshot` で取得し、`docs/issues/evidence-{バグ概要}.png` に保存してください。コンソールエラーは `playwright-cli console` で確認します。

#### API・バックエンドのバグの場合

`curl` や適切なコマンドを使ってリクエストを送信し、レスポンスを確認してください。

#### ロジック・データ処理のバグの場合

関連するテストを実行するか、最小限のスクリプトで再現してください。

### 再現結果の記録

再現確認の結果を以下の形式で記録してください（後続のステップで Issue とイシュー詳細に反映します）：

- **再現できた場合:** 具体的な再現手順と観測された症状を記録する
- **再現できなかった場合:** 試した手順と結果を記録し、ユーザーに報告して判断を仰ぐ

**注意:** 再現確認のために Docker コンテナが起動している必要がある場合は、`docker-compose ps` で状態を確認し、必要なら起動を促してください。

## 4.5. テスト失敗の場合のショートカット

報告内容がテスト失敗に関するものであれば、以下のスクリプトで Issue 起票と既知障害登録を一括で行えます：

```bash
scripts/create-test-issue.sh \
  --component {コンポーネント名} \
  --test-name "{テスト名}" \
  --reason "{失敗の理由}" \
  --add-known
```

このスクリプトを使用した場合、ステップ5の手動 Issue 起票はスキップしてステップ6に進んでください。

## 5. GitHub Issue を起票

以下のコマンドで Issue を起票してください：

Issue 本文は `tmp/issue-body.md` に書き出してから `gh issue create` に渡す（heredoc 禁止）。

1. Write ツールで `tmp/issue-body.md` を作成:

```markdown
## 症状

{バグの症状を記述}

## 再現手順

1. {手順}

## 再現確認結果

- 再現: {できた / できなかった}
- 確認方法: {Playwright / curl / テスト実行 等}
- エビデンス: {スクリーンショットのパス、コンソールエラー、レスポンス内容等}

## 期待する動作

{本来どうあるべきか}

## 関連タスク

- {PLAN.md のタスク番号。不明な場合は「不明」}
```

2. Issue を起票:

```bash
gh issue create --title "bug: {バグの概要}" --body-file tmp/issue-body.md
```

`tmp/issue-body.md` は起票後に削除する。

起票された Issue 番号を控えてください。

## 6. イシュー詳細ファイルの作成

`docs/issues/_template.md` をベースに、以下のファイルを作成してください：

**ファイル名:** `docs/issues/{Issue番号}-{名前}.md`

例: `docs/issues/42-websocket-reconnect-failure.md`

**記入する項目:**
- 関連タスク（PLAN.md のタスク番号。不明な場合は「不明」）
- ステータス: 「起票」にチェック
- 症状
- 再現手順
- 再現確認結果（確認方法、エビデンスへのリンク）
- 期待する動作

**空欄にする項目（`/custom-fix-bug` で記入する）:**
- 原因
- 修正方針（影響範囲、修正ファイル、テスト計画）

## 7. コミット

`.claude/skills/commit-and-push/SKILL.md` の手順に従い、イシュー詳細ファイル（`docs/issues/{Issue番号}-{名前}.md`）のみをステージしてコミットする。パラメータ: context `docs: Issue #{Issue番号} のバグ報告を作成`、push `false`、agent `none`。

## 8. 完了報告

以下の形式で報告してください：

```
## バグ報告完了

- Issue: #{Issue番号}
- タイトル: {タイトル}
- 分類: 重要
- 詳細ファイル: docs/issues/{Issue番号}-{名前}.md
- 関連タスク: {タスク番号 or 不明}

修正を進めるには、以下を順に実行してください：
1. `/custom-fix-bug {Issue番号}` で修正設計
2. コンテキストをクリア
3. `/custom-start-fix {Issue番号}` で修正実装
```
