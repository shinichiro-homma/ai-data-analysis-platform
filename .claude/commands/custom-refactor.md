直近で実装したコードをリファクタリングします。

引数にタスク番号を指定した場合は、そのタスクで実装したコードを対象とします。

以下の手順で作業してください：

## 1. 対象ファイルの特定

### タスク番号が指定された場合（`$ARGUMENTS` が空でない）

以下の2つの情報源からリファクタ対象ファイルを特定してください：

#### 1.1 計画ファイルから特定

`docs/tasks/` ディレクトリから、タスク $ARGUMENTS の計画ファイルを探してください。

**ファイル名パターン:** `docs/tasks/**/$ARGUMENTS-*.md`

計画ファイルの「作成するファイル」セクションに記載されたファイル一覧を確認してください。

**計画ファイルが見つからない場合:**
タスク番号に対応するイシュー詳細ファイル（`docs/issues/*`）を確認してください。イシュー詳細の「修正ファイル」一覧を対象としてください。

#### 1.2 コミット履歴から特定

タスク番号を含むコミットで変更されたファイルを確認してください：

```bash
git log --oneline --all | grep -i "$ARGUMENTS"
```

該当するコミットが見つかったら、そのコミットで変更されたファイルを確認してください：

```bash
git diff --name-only {コミットハッシュ}~1 {コミットハッシュ}
```

#### 1.3 対象ファイルの確定

計画ファイルとコミット履歴の両方から得たファイル一覧を統合し、以下のファイルを除外してください：

- ドキュメントファイル（`docs/`、`*.md`）
- 設定ファイル（`package.json`、`tsconfig.json`、`Dockerfile` 等）
- テストファイル（`*.test.ts`、`*.spec.ts`）

残ったソースファイル（シェルスクリプト `*.sh` を含む）がリファクタリング対象です。

### タスク番号が指定されない場合

直近のタスクで作成・変更したファイルを確認してください。

```bash
git diff --name-only HEAD~1
```

または、現在作業中のコンポーネントのソースファイルを対象としてください。

## 2. 並列コードレビュー（subagent）

対象ファイルの一覧が確定したら、以下のレビューエージェントを **1つのメッセージで並列に** 起動してください。
対象ファイルにシェルスクリプト（`*.sh`）が含まれる場合のみ Agent C も追加してください。

| Agent | 観点 | subagent_type | model |
|-------|------|---------------|-------|
| A | コード品質（重複排除、命名、エラーハンドリング、責務分離） | `code-reviewer` | `sonnet` |
| B | セキュリティ・型安全性・依存関係 | `code-reviewer` | `sonnet` |
| C | シェルスクリプト安全性・可読性（`*.sh` がある場合のみ） | `code-reviewer` | `sonnet` |

各 Agent には対象ファイル一覧を渡してください。
各 Agent の出力: ファイルごとの「問題点」と「推奨する修正」一覧。問題ゼロなら「リファクタリング不要」。

### レビュー結果の統合

全エージェントの結果を統合し、以下の優先順で修正方針を決定してください：

1. **セキュリティ** — 脆弱性の修正（最優先）
2. **シェルスクリプトの安全性** — クォート漏れ、インジェクションリスク
3. **コードの重複排除** — 共通関数の抽出
4. **エラーハンドリングの統一** — パターンの適用
5. **責務の分離** — ファイル/関数の分割
6. **命名の改善** — 変数名・関数名の変更
7. **型定義の整理** — 型の追加・整理（TypeScript のみ）
8. **シェルスクリプトの可読性** — 関数分割、命名規則

## 3. リファクタリングの実施

問題を見つけたら、ステップ2の優先順リストの順序で修正してください。

**注意:** 各修正は小さく行い、動作確認しながら進めてください。

## 4. 動作確認（必須）

リファクタリング後、以下のテストを**すべて実行**してください。テストが全てパスするまで次のステップに進まないでください。

### 4.1 対象コンポーネントの特定

リファクタリングしたファイルのパスから対象コンポーネントを判定：

| パス | コンポーネント |
|------|---------------|
| `jupyter-mcp/` | jupyter-mcp |
| `document-mcp/` | document-mcp |
| `document-server/` | document-server |
| `jupyter-server/` | jupyter-server |
| `scripts/` | （コンポーネントテストなし。構文チェックのみ実施） |

### 4.2 リビルド＋テスト実行

`scripts/test.sh --rebuild {対象コンポーネント名}` を実行してください。
`.claude/rules/rebuild-before-test.md` に従うこと。
lint 失敗時は `.claude/rules/lint.md` に従うこと。

### 4.3.1 シェルスクリプトの動作確認（対象に `*.sh` が含まれる場合）

シェルスクリプトを修正した場合は、以下を確認してください：

1. **構文チェック:** `bash -n {スクリプトパス}` でパースエラーがないことを確認
2. **ヘルプ表示:** `{スクリプトパス} --help` または `{スクリプトパス} -h` が正常に動作することを確認
3. **影響範囲:** 修正したスクリプトが他のスクリプトから `source` されている場合、呼び出し元も動作確認

**注意:** 失敗した場合は修正して再実行してください。

### 4.4 ブラウザ動作確認

対象がブラウザ動作確認に該当するかの判定と手順は `.claude/rules/testing.md` に従うこと。リファクタリング前と同等の動作をしていることを確認する。

### 4.5 テスト失敗時の対応

テストが失敗した場合：
1. エラー内容を確認する
2. リファクタリングによって導入された問題を修正する
3. 再度テストを実行する
4. **全てのテストがパスするまで繰り返す**

テストが全てパスしたことを確認してから、次のステップに進んでください。

## 5. 完了報告

以下の形式で報告してください：

```
## リファクタリング完了

### 対象タスク
- タスク番号: {タスク番号 or "指定なし（直近の変更）"}
- 参照した計画: {計画ファイルパス or "なし"}

### 対象ファイル
- path/to/file1.ts
- path/to/file2.ts

### 実施した改善

#### セキュリティ
- ユーザー入力の検証を追加
- SQLクエリをパラメータ化

#### コードの重複排除
- `fetchData` 関数を `utils/api.ts` に抽出

#### 命名の改善
- `data` → `userSessions`（意図を明確化）
- `proc` → `processExecutionResult`（省略を解消）

#### エラーハンドリングの統一
- API呼び出しに統一的な try-catch パターンを適用

#### 責務の分離
- `session.ts`（300行）を `session-manager.ts` と `session-utils.ts` に分割

#### 型定義の整理
- `any` を `ExecutionResult` 型に置き換え

#### シェルスクリプト改善
- 変数のクォート漏れを修正
- 共通処理を関数に抽出
- エラーメッセージを stderr に統一

### 動作確認
- typecheck: パス
- test: パス
```
