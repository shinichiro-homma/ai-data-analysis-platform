直近で実装したコードをリファクタリングします。

引数にタスク番号を指定した場合は、そのタスクで実装したコードを対象とします。

以下の手順で作業してください：

## 1. 対象ファイルの特定

### タスク番号が指定された場合（`$ARGUMENTS` が空でない）

以下の2つの情報源からリファクタ対象ファイルを特定してください：

#### 1.1 計画ファイルから特定

`docs/tasks/` ディレクトリから、タスク $ARGUMENTS の計画ファイルを探してください。

**ファイル名パターン:** `docs/tasks/**/$ARGUMENTS-*.md`

計画ファイルの「作成するファイル」セクションに記載されたファイル一覧を確認してください。

**計画ファイルが見つからない場合:**
タスク番号に対応するイシュー詳細ファイル（`docs/issues/*`）を確認してください。イシュー詳細の「修正ファイル」一覧を対象としてください。

#### 1.2 コミット履歴から特定

タスク番号を含むコミットで変更されたファイルを確認してください：

```bash
git log --oneline --all | grep -i "$ARGUMENTS"
```

該当するコミットが見つかったら、そのコミットで変更されたファイルを確認してください：

```bash
git diff --name-only {コミットハッシュ}~1 {コミットハッシュ}
```

#### 1.3 対象ファイルの確定

計画ファイルとコミット履歴の両方から得たファイル一覧を統合し、以下のファイルを除外してください：

- ドキュメントファイル（`docs/`、`*.md`）
- 設定ファイル（`package.json`、`tsconfig.json`、`Dockerfile` 等）
- テストファイル（`*.test.ts`、`*.spec.ts`）

残ったソースファイル（シェルスクリプト `*.sh` を含む）がリファクタリング対象です。

### タスク番号が指定されない場合

直近のタスクで作成・変更したファイルを確認してください。

```bash
git diff --name-only HEAD~1
```

または、現在作業中のコンポーネントのソースファイルを対象としてください。

## 2. 並列コードレビュー（3 観点）

### 2.0 レビュー入力の準備（メインで実行）

レビューエージェント（`code-reviewer`）は git を実行できないため、メインで入力を用意してください：

1. 対象ファイルの差分をパッチに保存する:
   `git diff HEAD -- {対象ファイル...} > tmp/refactor-diff.patch`
   （対象が直近コミットに含まれる場合は `git diff {コミットハッシュ}~1 -- {対象ファイル...} > tmp/refactor-diff.patch`）
2. 対象コンポーネントのテストマップを保存する（Agent B 用）:
   `scripts/test-map.sh {対象コンポーネント} > tmp/test-map.txt`

（この 2 ファイルはステップ 6 のコミット前に削除する）

### 2.1 レビューエージェントの起動

以下のレビューエージェントを **1つのメッセージで並列に** 起動してください。

| Agent | 観点 | subagent_type | model |
|-------|------|---------------|-------|
| A | コード品質（重複排除、命名、エラーハンドリング、責務分離） | `code-reviewer` | `sonnet` |
| B | 正確性・堅牢性・テスト網羅（バグ、境界値、セキュリティ、型安全性、テストの網羅性） | `code-reviewer` | `sonnet` |
| C | ファイル間整合性・呼び出し元副作用（import、副作用。`*.sh` があればシェル安全性も） | `code-reviewer` | `sonnet` |

**全 Agent 共通の指示:**
- `.claude/rules/subagent-defaults.md` を Read し、必読ルール表の役割『レビュー・検証』のルールを Read すること
- **一次入力は `tmp/refactor-diff.patch`**。まずパッチを Read し、指摘の裏取りに必要な場合のみ、hunk の行番号を使って該当ファイルの行範囲を Read（offset/limit 指定）する。**対象ファイルの全文 Read は禁止**（変更していない箇所の指摘はスコープ外）
- Agent B は「この入力で壊れないか」を具体的な値（空リスト、None、型不一致）で検証する。テストの網羅性は `tmp/test-map.txt`（テスト名一覧）とパッチ内の新規・変更テストで判断し、既存テストファイルの全文 Read はしない
- Agent C にはメインで `grep -rn` した呼び出し元ファイルのリストを渡す（呼び出し元も該当行範囲のみ Read）
- 指摘は `.claude/rules/subagent-defaults.md` の証拠スキーマ（場所・問題・根拠・修正案）に従うこと。問題ゼロなら「指摘なし」と判断根拠を報告

### 2a. 統合と検証（メインで実行）

1. **重複統合**: 複数 Agent の同一箇所指摘は 1 件にまとめる
2. **指摘の検証**: バグ・整合性指摘は該当箇所を Read して失敗シナリオが実際に成立するか確認する。**成立が確認できない指摘は採用しない**
3. 採用した指摘を以下の優先順で並べ、修正方針を決定する：

1. **セキュリティ** — 脆弱性の修正（最優先）
2. **シェルスクリプトの安全性** — クォート漏れ、インジェクションリスク
3. **コードの重複排除** — 共通関数の抽出
4. **エラーハンドリングの統一** — パターンの適用
5. **責務の分離** — ファイル/関数の分割
6. **命名の改善** — 変数名・関数名の変更
7. **型定義の整理** — 型の追加・整理（TypeScript のみ）
8. **シェルスクリプトの可読性** — 関数分割、命名規則

全 Agent「指摘なし」の場合はステップ 3・4 をスキップし、ステップ 5（完了報告）へ進む。

## 3. リファクタリングの実施

採用した指摘をバグ修正とリファクタリングに分類し、委譲する：

- **バグ修正**（テスト追加を含む）: subagent_type `general-purpose`、model `opus`。バグを再現するテストを追加してから修正させる（TDD）
- **純リファクタリング**: subagent_type `general-purpose`、model `sonnet`。機能追加・仕様変更を混ぜない。公開 API を変更する場合は呼び出し元も追従させる

いずれのサブエージェントにも「`.claude/rules/subagent-defaults.md` を Read し、必読ルール表の該当役割（バグ修正は『実装（Green）・バグ修正』、純リファクタは『リファクタ・レビュー指摘の修正』）のルールを Read すること」を含める。

**注意:** 各修正は小さく行い、動作確認しながら進めてください。

## 4. 動作確認（必須）

リファクタリング後、以下のテストを**すべて実行**してください。テストが全てパスするまで次のステップに進まないでください。

### 4.1 対象コンポーネントの特定

リファクタリングしたファイルのパスから対象コンポーネントを判定：

| パス | コンポーネント |
|------|---------------|
| `jupyter-mcp/` | jupyter-mcp |
| `document-mcp/` | document-mcp |
| `document-server/` | document-server |
| `jupyter-server/` | jupyter-server |
| `scripts/` | （コンポーネントテストなし。構文チェックのみ実施） |

### 4.2 テスト実行（フルゲート）

`scripts/test.sh --quiet {対象コンポーネント名}`（lint + 型チェック + 全テスト）を実行してください。
ユニットテストにリビルドは不要（`.claude/rules/build-freshness.md` 参照）。
統合テストの実行要否は `.claude/rules/testing.md` の「フルゲート実行時の統合テスト検出」に従って判定すること。
lint 失敗時は `.claude/rules/lint.md` に従うこと。

### 4.3.1 シェルスクリプトの動作確認（対象に `*.sh` が含まれる場合）

シェルスクリプトを修正した場合は、以下を確認してください：

1. **構文チェック:** `bash -n {スクリプトパス}` でパースエラーがないことを確認
2. **ヘルプ表示:** `{スクリプトパス} --help` または `{スクリプトパス} -h` が正常に動作することを確認
3. **影響範囲:** 修正したスクリプトが他のスクリプトから `source` されている場合、呼び出し元も動作確認

**注意:** 失敗した場合は修正して再実行してください。

### 4.4 ブラウザ動作確認

対象がブラウザ動作確認に該当するかの判定と手順は `.claude/rules/testing.md` に従うこと。リファクタリング前と同等の動作をしていることを確認する。

### 4.5 テスト失敗時の対応

テストが失敗した場合、`.claude/skills/test-fix-loop/SKILL.md` のループに従って修正してください。

**パラメータ:**
- タスクコンテキスト: リファクタ対象ファイルと採用した指摘、対象コンポーネント
- 完了条件: 採用した指摘の解消 + リファクタ前後で挙動が変わらないこと（全テスト PASS）
- スコープ情報: 対象ファイル一覧、`git diff --name-only` の変更ファイル
- テスト実行コマンド: 4.2 のフルゲート `scripts/test.sh --quiet {対象コンポーネント名}`
- 最大修正回数: 3
- エスカレーション先: ユーザーに報告して停止

テストが全てパスしたことを確認してから、次のステップに進んでください。

## 5. 完了報告

以下の形式で報告してください：

```
## リファクタリング完了

### 対象タスク
- タスク番号: {タスク番号 or "指定なし（直近の変更）"}
- 参照した計画: {計画ファイルパス or "なし"}

### 対象ファイル
- path/to/file1.ts
- path/to/file2.ts

### 実施した改善

#### セキュリティ
- ユーザー入力の検証を追加
- SQLクエリをパラメータ化

#### コードの重複排除
- `fetchData` 関数を `utils/api.ts` に抽出

#### 命名の改善
- `data` → `userSessions`（意図を明確化）
- `proc` → `processExecutionResult`（省略を解消）

#### エラーハンドリングの統一
- API呼び出しに統一的な try-catch パターンを適用

#### 責務の分離
- `session.ts`（300行）を `session-manager.ts` と `session-utils.ts` に分割

#### 型定義の整理
- `any` を `ExecutionResult` 型に置き換え

#### シェルスクリプト改善
- 変数のクォート漏れを修正
- 共通処理を関数に抽出
- エラーメッセージを stderr に統一

### 動作確認
- typecheck: パス
- test: パス
```

## 6. コミット

`tmp/refactor-diff.patch` と `tmp/test-map.txt` を削除してから、
`.claude/skills/commit-and-push/SKILL.md` を読み、その手順に従ってコミットしてください。

パラメータ:
- context: refactor: {対象コンポーネント}のコード改善
- push: false
- agent: none
