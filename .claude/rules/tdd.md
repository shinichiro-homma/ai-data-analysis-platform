# テスト駆動開発（TDD）ルール

実装タスクでは、**テストを先に作成してから実装する**こと。

## 原則

**テストコードは要件の具体化であり、実装を通すために書き換えてはならない。** 実装が通らなければ実装側を直す。例外はテストコード自体のバグ（構文エラー、明らかな typo）のみで、その場合は修正理由を明示すること。

## 要件変更時の既存テスト更新

**テスト書き換えの可否は「なぜ書き換えるか」で決まる。**

| ケース | 可否 | 理由 |
|-------|------|-----|
| 現タスクの実装を通すために、現タスクのテストを緩める | ❌ 禁止 | 要件を満たしたことにならない |
| 要件変更により、他所の既存テストが新要件と齟齬を起こす | ✅ 必須 | 新要件への追従。放置すると CI が壊れる |
| 依存先の API 契約が変わり、呼び出し側テストが実態と乖離 | ✅ 必須 | 呼び出し側が新契約に従うのは実装もテストも同じ |

**要件変更を伴うタスクでは、影響を受ける既存テストの更新もタスクのスコープ内。** 計画時点で影響範囲調査により特定し、実装と同時に更新、理由を commit メッセージで明示する（例: 「auth 必須化に伴う呼び出し側テストの追従」）。CI で齟齬が検出された場合は `.claude/rules/branch-workflow.md` の「自タスク起因」として現 feature ブランチで即修正する。

## テスト実行コマンドの規律

コンテキスト肥大（ビルドログ・テスト出力の蓄積）と実行負荷を抑えるため、テスト実行は以下に従う:

- **サブエージェントは常に `--quiet` を付けて実行する**: フル出力は `tmp/test-logs/` に保存され、コンソールにはサマリと失敗抜粋（末尾 120 行）のみ返る。抜粋で足りない場合はログファイルを Grep で絞って参照する（全文 Read はしない）
- **反復中はスコープ実行**: Red / Green / 修正ループの反復では、タスクのテストファイルに絞って実行する:
  `scripts/test.sh --quiet --test --no-lint {コンポーネント名} -- {テストファイル...}`
  （lint / 型チェックはフルゲートで担保する。保存時の自動整形は format-on-save hook が行う）
- **フルゲートは各フェーズの締めで 1 回**: メインでの Green 確認や complete-task の最終確認では
  `scripts/test.sh --quiet {コンポーネント名}`（lint + 型チェック + 全テスト）を実行する
- **ユニットテストに `--rebuild` を付けない**: ユニットテスト（vitest / pytest）はソースを直接実行するため、リビルドは結果に影響しない。`--rebuild` が必要なのは統合テスト（`--integration`）と Docker 環境での動作確認のみ（`.claude/rules/build-freshness.md` 参照）

## テストコードの読み方の規律

既存テストの乱読はコンテキストを浪費する。テストコードを参照する際は以下に従う:

- **テストファイルの全文 Read 禁止**: 先に当たりを付けてから、該当する describe ブロック / テストクラスの行範囲のみを Read（offset/limit 指定）する
- **所在確認はテストマップで行う**: 既存テストの有無・場所は `scripts/test-map.sh {コンポーネント名}`（テストファイル → テスト名・行番号の一覧）で確認する。`tests/` 配下をファイルを開いて回らない
- **参照範囲は計画が正**: タスク計画・イシュー詳細に「テスト参照ポインタ」がある場合はその範囲のみ Read する。ポインタがない場合（旧形式の計画等）のみテストマップで絞り込む
- **規約はチートシートで学ぶ**: テストの書き方・fixture・モックの作法は、既存テストのサンプル収集ではなく `.claude/skills/testing-strategies/SKILL.md` から該当リファレンスを選んで読む

## 手順

### Red フェーズ（テスト準備）

1. 計画の「テスト計画」（既存テストの被覆状況・テスト参照ポインタ）を確認。既存テストで十分ならパスを記録して新規作成不要
2. 不足していれば計画の「完了条件」「テスト計画」に基づき作成。既存コードの参照は「テストコードの読み方の規律」に従う
3. `scripts/test.sh --quiet --test --no-lint {コンポーネント名} -- {対象テストファイル}` で失敗（Red）を確認

実装前にテストが失敗するのは正常。ただし構文・インポートエラーで実行自体が不可な場合は修正すること。

### Green フェーズ（実装）

テストが通るように**実装コードを書く**（テストコードは変更しない）。

サブエージェントとして実装・修正する場合は、スコープ実行を **1 回だけ**行い、PASS / FAIL に関わらず結果（仮説・修正内容・テスト結果）を報告して終了する。失敗ログでコンテキストが肥大した状態で粘るより、失敗ダイジェストを引き継いだクリーンな修正エージェントの方が精度が出るため。修正の反復はオーケストレーターの修正ループ（`.claude/skills/test-fix-loop/SKILL.md`）が担う。

メインコンテキストで直接実装する場合は、通るまで反復してよい。

### Refactor フェーズ

テストが通る状態を維持しつつコードを整理する。

## テスト不要なタスク

以下はテスト先行の対象外（ただし既存テストが通ることの確認は必須）:

- フォーマッター適用（prettier、ruff 等）
- ドキュメントのみの変更
- 設定ファイルのみの変更
