# テスト駆動開発（TDD）ルール

実装タスクでは、**テストを先に作成してから実装する**こと。

## 原則

- **テストコードは要件の具体化である。** テストが通るように実装を書くこと。
- **実装を通すためにテストを書き換えてはならない。** テストコード自体にバグがある場合（構文エラー、明らかな typo）のみ例外的に修正を許可するが、修正理由を明示すること。

## 要件変更時の既存テスト更新

**テスト書き換えの可否は「なぜ書き換えるか」で決まる。**

| ケース | 可否 | 理由 |
|-------|------|-----|
| 現タスクの実装を通すために、現タスクのテストを緩める | ❌ 禁止 | テストは要件の具体化。実装を通すために緩めたら要件を満たしたことにならない |
| 要件変更により、他所の既存テストが新要件と齟齬を起こす | ✅ 必須 | 新要件への追従は自然。放置すると CI が壊れる |
| 依存先の API 契約が変わり、呼び出し側テストが実態と乖離 | ✅ 必須 | 呼び出し側が新契約に従うのは実装もテストも同じ |

**要件変更を伴うタスクでは、影響を受ける既存テストの更新もタスクのスコープ内。**

- タスク計画時点で「影響を受ける既存テスト」を洗い出す（要件変更ワークフローの影響範囲調査で特定する）
- 実装と同時に影響テストも更新する
- 更新理由を commit メッセージで明示する（例: 「auth 必須化に伴う呼び出し側テストの追従」）

CI で齟齬が検出された場合は、`.claude/rules/branch-workflow.md` の「自タスク起因の場合」として扱い、現在の feature ブランチで即修正する。

## 手順

### Red フェーズ（テスト準備）

1. 対象コンポーネントの `tests/` ディレクトリを確認し、関連する既存テストを調べる
2. 既存テストで十分な場合はそのパスを記録し、新規作成は不要
3. テストが不足している場合は、計画の「完了条件」「テスト計画」に基づいてテストを作成する
4. テストを実行して現在の状態を確認する（`scripts/test.sh --rebuild {コンポーネント名}`）

実装前の時点でテストが失敗するのは正常（Red フェーズ）。
ただし、構文エラーやインポートエラーで実行自体ができない場合は修正すること。

### Green フェーズ（実装）

1. テストが通るように実装する
2. テストが失敗した場合は**実装コードを修正する**（テストコードは変更しない）
3. テストが通るまで繰り返す

### Refactor フェーズ

テストが通る状態を維持しつつコードを整理する。

## テスト不要なタスク

以下のタスクはテスト先行の対象外とする：

- フォーマッター適用（prettier、ruff 等）
- ドキュメントのみの変更
- 設定ファイルのみの変更

ただし、既存テストが通ることの確認は必須。
