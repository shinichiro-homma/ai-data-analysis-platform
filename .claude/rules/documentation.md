# ドキュメント更新ルール

ドキュメントファイルを編集する際のルール。

## 要件変更時の手順

`docs/STRUCTURE.md` の依存関係と更新順序に従うこと。各ファイルの役割も同ドキュメントの「各ファイルの更新ポイント」を参照する。

## ドキュメント記述方針: コードが正（Single Source of Truth）

コードを読めば 30 秒で分かる情報はドキュメントに書かない。ドキュメントには「コードからは読み取れない情報」のみを記載する。

### ドキュメントに書くべき情報

| 種別 | 例 |
|------|-----|
| Why（設計判断の理由） | 「なぜこのアーキテクチャを選んだか」 |
| 機能の分類と責務 | F番号と概要説明、受け入れ条件 |
| 機能とツール/APIの対応 | ツール/エンドポイントの**名前と1行の目的のみ**の一覧表（CI がコードと照合する。形式は `docs/STRUCTURE.md` の「CI による整合性検証」を参照） |
| 未実装の将来要件 | ステータスを明記すること |

### ドキュメントに書いてはいけない情報

| 種別 | 理由 | 確認方法 |
|------|------|---------|
| 入出力スキーマ（パラメータ名・型・必須/任意・レスポンス形式） | コードの zod / Pydantic 定義が正 | コードを参照 |
| ディレクトリ構成 | `ls`/`tree` で確認可能 | コードを参照 |
| パラメータのデフォルト値・上限値・許可リスト | コードの定数が正 | `grep` で確認可能 |
| ブロック対象の全量リスト | 変更頻度が高い | コードを参照 |
| ツールの description 文言 | コードの文字列が正 | コードを参照 |
| エラーメッセージの文言・エラーコードの全量リスト | コードの文字列が正 | コードを参照 |

### 判断基準

> 「この情報はコードを grep/read すれば 30 秒で分かるか？」 Yes → 書かない／No → 書く

## 記述スタイル

- 見出し: H1 はファイルに 1 つ。簡潔に
- 表: 比較・一覧は表形式、ヘッダー行必須
- コードブロック: 言語を明示（```typescript / ```python / ```bash）。長い場合は `...` で省略
- リンク: 相対パスを使用し、リンク切れに注意
