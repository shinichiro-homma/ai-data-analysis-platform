# ドキュメント更新ルール

ドキュメントファイルを編集する際に適用されるルール。

## 要件変更時の手順

要件定義を変更する場合は、以下の手順に従う。

`docs/STRUCTURE.md` に記載された依存関係と更新順序に従うこと。

## ドキュメント記述方針: コードが正（Single Source of Truth）

コードを読めば30秒で分かる情報はドキュメントに書かない。ドキュメントには「コードからは読み取れない情報」のみを記載する。

### ドキュメントに書くべき情報

| 種別 | 例 |
|------|-----|
| Why（設計判断の理由） | 「なぜこのアーキテクチャを選んだか」 |
| 機能の分類と責務 | F番号と概要説明 |
| 入出力の型構造 | パラメータ名・型・必須/任意 |
| コンポーネント間の契約 | APIパス・メソッド・ステータスコード |
| 未実装の将来要件 | ステータスを明記すること |

### ドキュメントに書いてはいけない情報

| 種別 | 理由 | 確認方法 |
|------|------|---------|
| ディレクトリ構成 | `ls`/`tree` で確認可能 | コードを参照 |
| パラメータのデフォルト値・上限値・許可リスト | コードの定数が正 | `grep` で確認可能 |
| ブロック対象の全量リスト | 変更頻度が高い | コードを参照 |
| ツールの description 文言 | コードの文字列が正 | コードを参照 |
| エラーメッセージの文言 | コードの文字列が正 | コードを参照 |

### 判断基準

> 「この情報はコードを grep/read すれば30秒で分かるか？」
> → Yes: ドキュメントに書かない
> → No: ドキュメントに書く

## 記述スタイル

### 見出し

- 見出しレベルは適切に（H1 はファイルに1つ）
- 見出しは簡潔に

### 表

- 比較、一覧は表形式を使用する
- ヘッダー行を必ず含める

### コードブロック

- 言語を明示する（```typescript, ```python, ```bash）
- 長すぎるコードは省略（`...`）を使用

### リンク

- 相対パスを使用する
- リンク切れに注意する

## 各ファイルの役割

`docs/STRUCTURE.md` の「各ファイルの更新ポイント」を参照すること。
