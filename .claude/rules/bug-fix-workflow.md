# バグ修正ワークフロー

テストや動作確認中にバグを発見した場合、以下のルールに従うこと。

## 1. バグの分類

発見したバグを以下の基準で分類する。

### 軽微

以下の**すべて**に該当する場合：

- 原因が明白である（typo、パラメータ間違い、off-by-one等）
- 修正が1〜2ファイルで完結する
- 要件定義・API仕様の変更を伴わない
- 修正方法が1通りしかない

### 重要

以下の**いずれか**に該当する場合：

- 原因が不明で調査が必要
- 修正が3ファイル以上にまたがる
- 要件定義やAPI仕様の変更を伴う
- 修正方法に複数の選択肢がある
- 他の機能への影響が懸念される

## 2. 対応フロー

### 軽微なバグ

そのまま修正し、`fix: ...` でコミットする。Issue管理は不要。

### 重要なバグ

以下の手順に従う。**Issue を起票せずに修正を始めてはならない。**

#### ステップ1: GitHub Issue を起票

```bash
gh issue create --title "bug: {バグの概要}" --body "..."
```

#### ステップ2: イシュー詳細ファイルを作成

`docs/issues/_template.md` をベースに、以下のファイルを作成する：

```
docs/issues/{Issue番号}-{名前}.md
```

例: `docs/issues/42-websocket-event-not-delivered.md`

「症状」「再現手順」「期待する動作」を記入する。
「原因」「修正方針」はこの時点では空欄でよい。

#### ステップ3: ユーザーに報告

以下の形式で報告する：

```
Issue #{番号} を起票しました: {タイトル}
詳細: docs/issues/{番号}-{名前}.md

修正を開始するには `/custom-fix-bug {番号}` を実行してください。
```

#### ステップ4: 修正設計は `/custom-fix-bug` コマンドで行う

ユーザーが `/custom-fix-bug {番号}` を実行するまで、修正設計に着手しないこと。

`/custom-fix-bug` は設計のみを行い、実装は行わない。

#### ステップ5: 修正実装は `/custom-start-fix` コマンドで行う

設計完了後、コンテキストをクリアしてから `/custom-start-fix {番号}` で実装を行う。

**設計と実装を同一セッションで行わないこと。** コンテキストをクリアすることで、実装に十分なコンテキストウィンドウを確保する。

## 3. 判断に迷った場合

迷った場合は **重要** として扱う。過剰に管理するコストより、調査不足で誤った修正をするコストの方が大きい。
