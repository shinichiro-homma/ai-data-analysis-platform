# バグ修正ワークフロー

テストや動作確認中にバグを発見した場合のルール。

## 1. バグの分類

### 軽微

以下の**すべて**を満たすもの：

- 原因が明白（typo、パラメータ間違い、off-by-one 等）
- 修正が 1〜2 ファイルで完結する
- 要件定義・API 仕様の変更を伴わない
- 修正方法が 1 通りしかない

### 重要

以下の**いずれか**に該当するもの：

- 原因が不明で調査が必要
- 修正が 3 ファイル以上にまたがる
- 要件定義や API 仕様の変更を伴う
- 修正方法に複数の選択肢がある
- 他の機能への影響が懸念される

迷った場合は **重要** として扱う。

## 2. 対応フロー

### 軽微なバグ

そのまま修正し、`fix: ...` でコミットする。Issue 管理は不要。

### 重要なバグ

**Issue を起票せずに修正を始めてはならない。** 以下の 5 ステップで対応する。

#### ステップ1: GitHub Issue を起票

```bash
gh issue create --title "bug: {バグの概要}" --body "..."
```

#### ステップ2: イシュー詳細ファイルを作成

`docs/issues/_template.md` をベースに `docs/issues/{Issue番号}-{名前}.md` を作成する（例: `docs/issues/42-websocket-event-not-delivered.md`）。「症状」「再現手順」「期待する動作」を記入し、「原因」「修正方針」はこの時点では空欄でよい。

#### ステップ3: ユーザーに報告

```
Issue #{番号} を起票しました: {タイトル}
詳細: docs/issues/{番号}-{名前}.md

修正を開始するには `/custom-fix-bug {番号}` を実行してください。
```

#### ステップ4: 修正設計は `/custom-fix-bug` で行う

ユーザーが `/custom-fix-bug {番号}` を実行するまで、修正設計に着手しない。`/custom-fix-bug` は設計のみを行い、実装はしない。

#### ステップ5: 修正実装は `/custom-start-fix` で行う

設計完了後、**コンテキストをクリアしてから** `/custom-start-fix {番号}` で実装する。設計と実装を同一セッションで行わないこと（実装に十分なコンテキストウィンドウを確保するため）。
